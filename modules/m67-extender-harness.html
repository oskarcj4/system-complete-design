Extender un harness

Un harness recién instalado sabe programar en general y no sabe nada de tu equipo. Este módulo recorre las seis formas de enseñarle, darle herramientas y ponerle reglas, con un criterio para cada una: qué ocupa en el contexto, quién decide que se use y qué código corre en tu máquina.

Plano
M67
Parte

Duración

Requisitos previos

Estado
Sin empezar

Al terminar podrás

  • Nombrar los seis puntos de extensión de un harness y decir qué pone cada uno en el contexto, y cuándo.
  • Conectar servidores MCP a Claude Code y a Codex en el alcance correcto, y medir lo que cuestan sus definiciones.
  • Escribir una skill que se cargue solo cuando hace falta, y un subagente que devuelva poco.
  • Usar hooks para lo que tiene que pasar siempre: formatear, probar, impedir que el agente termine con pruebas rotas.
  • Empaquetar todo en un plugin y repartirlo a un equipo.
  • Revisar una extensión antes de instalarla: qué código corre como tú y qué texto entra al contexto.

67.1Seis formas de extender un harness

En M64 desarmaste un harness: el bucle, el system prompt por capas, las herramientas, el contexto. Todo eso viene de fábrica. Lo que lo vuelve útil para tu equipo se agrega desde afuera, y hay seis lugares donde agregarlo. En M62.8 los nombraste; aquí se configura cada uno.

Analogía

Una persona nueva en el equipo. El primer día lee una hoja con lo indispensable (el archivo de memoria). Tiene en el escritorio carpetas con procedimientos que abre cuando le toca (skills). Le dan accesos a sistemas (servidores MCP). Hay cosas que pasan sí o sí, como el CI que corre al hacer push (hooks). A veces le pide a alguien que investigue algo y le traiga un resumen (subagentes). Y cuando entra otra persona, se le entrega el kit completo de una vez (un plugin).

  1. Archivo de memoriaLo que el agente tiene que saber en cada turno. M64.9
  2. SkillsProcedimientos y conocimiento que se cargan cuando la tarea los pide. 67.4
  3. SubagentesUn agente con su propio contexto y sus propias herramientas. 67.6
  4. Servidores MCPHerramientas nuevas con acceso a otros sistemas. 67.2
  5. Reglas por rutaInstrucciones que entran al tocar ciertos archivos. 67.1
  6. HooksProgramas que corren en momentos fijos, fuera del modelo. 67.5
  7. El bucleEl harness, que decide qué entra al contexto y qué se ejecuta. M64.1

Lo que cada una pone en el contexto

La pregunta que ordena este módulo es la de M64.8: la ventana es finita y todo lo que entra compite por la atención del modelo. Las extensiones se distinguen por cuándo entran. Lo que entra al empezar se paga en cada turno; lo que entra al usarse, solo cuando sirve; y hay cosas que no entran nunca.

Las reglas por ruta son un caso intermedio: archivos en .claude/rules/ con un paths: en el frontmatter, que Claude Code carga solo cuando el agente lee o edita un archivo que coincide Documentado. Sirven para "en db/migrations/, nunca un índice sin CONCURRENTLY" sin pagar esa línea en cada turno de una tarea de frontend.

67.2Servidores MCP dentro de un harness

Qué es MCP, sus roles, su mensaje y sus transportes están en M25.5; cómo se autoriza un servidor remoto con OAuth, en M25.5 también. Aquí, lo que cambia cuando el host es un harness de código: dónde se configura, a quién le llega y cuánto cuesta.

# Un servidor remoto por HTTP (pide OAuth la primera vez, desde /mcp)
claude mcp add --transport http sentry https://mcp.sentry.dev/mcp

# Un servidor local por stdio: todo lo que va después de -- es el comando
claude mcp add --env PGURL=postgres://lector@localhost/tienda postgres -- npx -y @tuempresa/mcp-postgres-lectura

# Compartido con el equipo: se guarda en .mcp.json, en la raíz del repositorio
claude mcp add --scope project --transport http linear https://mcp.linear.app/mcp

claude mcp list          # qué servidores hay y si conectan

Los tres alcances Documentado:

  • local (por defecto): solo para ti y solo en este proyecto; se guarda en ~/.claude.json.
  • project: en .mcp.json, versionado con el repositorio. Claude Code pide aprobación antes de usar los servidores de ese archivo en una sesión interactiva.
  • user: para ti en todos tus proyectos.
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@tuempresa/mcp-postgres-lectura@1.4.2"],
      "env": { "PGURL": "${PGURL_LECTURA}" }
    },
    "linear": { "type": "http", "url": "https://mcp.linear.app/mcp" }
  }
}

.mcp.json admite variables de entorno con ${VAR}, así la credencial no queda en el repositorio. Fija la versión del paquete (@1.4.2): npx -y paquete sin versión ejecuta lo último que se publicó, cada vez que arranca la sesión, que es exactamente el riesgo de cadena de suministro de M56.

# ~/.codex/config.toml
[mcp_servers.postgres]
command = "npx"
args = ["-y", "@tuempresa/mcp-postgres-lectura@1.4.2"]
env = { PGURL = "postgres://lector@localhost/tienda" }

Codex lee los servidores de config.toml, en tablas [mcp_servers.nombre] Documentado. Un servidor escrito para Claude Code funciona igual: el protocolo es el mismo.

{ "mcp": { "postgres": { "type": "local", "command": ["npx", "-y", "@tuempresa/mcp-postgres-lectura@1.4.2"] } } }

OpenCode los declara en opencode.json, con type local o remote Documentado.

Lo que devuelve un servidor también ocupa

Un tools/call que devuelve 4 000 filas de una tabla mete esas filas en el contexto. Claude Code avisa cuando una respuesta pasa de 10 000 tokens y la corta en 25 000 por defecto; el tope se cambia con MAX_MCP_OUTPUT_TOKENS Documentado. Subir el tope es la salida fácil; la buena es la de M25.4: herramientas que filtran, paginan y resumen del lado del servidor. Un servidor bien diseñado devuelve lo que el modelo necesita para decidir, no lo que tiene.

67.3Herramientas bajo demanda

Cada herramienta que el modelo puede llamar trae su definición: nombre, descripción y esquema de argumentos, como viste en M63.5. Cinco servidores con 16 herramientas cada uno son 80 definiciones; a unos 400 tokens cada una son 32 000 tokens que entran en cada turno, antes de que el agente lea un archivo. Ocupan ventana, distraen al modelo con herramientas que no van a servir y se pagan siempre.

La carga bajo demanda invierte el orden: al empezar entran solo los nombres, más una herramienta para buscar. Cuando el modelo necesita algo, busca, y entonces entra la definición completa de lo que encontró. Es lo que en M63.5 quedó pendiente.

En Claude Code la búsqueda de herramientas MCP está activa por defecto, y se controla con ENABLE_TOOL_SEARCH: true (siempre buscar), auto (cargar todo mientras las definiciones ocupen menos del 10 % de la ventana, y buscar si pasan), auto:N (otro porcentaje) o false (todo por adelantado) Documentado. La API de Anthropic ofrece lo mismo como herramienta de servidor, para quien arma su propio harness con el Agent SDK.

Trade-off

Buscar cuesta un turno y puede fallar: si la descripción de la herramienta no usa las palabras que el modelo busca, no la encuentra. Con pocas herramientas que se usan siempre, cargarlas por adelantado es mejor. Por eso existe auto: la búsqueda paga cuando la lista es larga.

Prueba los tres ejemplos. El de "plugins a granel" es el que aparece cuando cada persona del equipo instala lo que vio en un blog.

El caché del prefijo (M16) baja el costo de lo fijo a una décima, pero no la ventana ni la atención: 50 000 tokens de definiciones cacheadas siguen siendo 50 000 tokens que el modelo tiene que mirar. Cómo se ordena todo lo que entra, y por qué el orden cambia la factura, es M68.

67.4Skills: conocimiento que se carga al usarse

Una skill es una carpeta con un archivo SKILL.md: un frontmatter con nombre y descripción, y un cuerpo con instrucciones; al lado, si hace falta, referencias, plantillas y scripts. El harness pone solo el nombre y la descripción en el contexto; cuando la tarea coincide con la descripción, o la persona la invoca con /nombre, carga el cuerpo Documentado.

---
name: revisar-migracion
description: Revisa una migración SQL de PostgreSQL antes de mergearla. Úsala cuando el
  usuario pida revisar, aprobar o escribir una migración, o cuando cambie algo en db/migrations/.
allowed-tools: Read Grep Glob Bash(psql -c "EXPLAIN *")
---

# Revisar una migración

1. Lee la migración y la anterior en `db/migrations/`.
2. Busca operaciones que bloquean la tabla en producción:
   - `ALTER TABLE … ADD COLUMN … DEFAULT` con función volátil
   - `CREATE INDEX` sin `CONCURRENTLY`
   - `ALTER COLUMN … TYPE` sobre tablas de más de 1 millón de filas
3. Si hay alguna, propone la versión en varios pasos de [patrones.md](patrones.md).
4. Comprueba que existe la migración de vuelta (`down`).

Responde con una lista: bloqueante, riesgo o bien, y la línea.

Lo que importa del ejemplo:

  • La descripción es el disparador. El modelo decide usar la skill leyendo solo esa frase, así que dice qué hace y cuándo usarla, con las palabras que aparecerán en el pedido. Una descripción vaga es una skill que nunca se usa.
  • El cuerpo es corto y apunta a archivos. La documentación sugiere mantener SKILL.md por debajo de 500 líneas y mover lo largo a archivos que el cuerpo enlaza; esos solo entran si se leen Documentado.
  • allowed-tools aprueba, no restringe. Mientras la skill está activa, esas herramientas no piden permiso; las demás siguen las reglas normales de M66.2 Documentado. Para restringir, disallowed-tools o las reglas deny.

Otros campos útiles Documentado: disable-model-invocation: true hace que solo la persona pueda invocarla (para un deploy, que no tiene que dispararse porque el modelo lo creyó oportuno); context: fork la ejecuta en un subagente, con su propio contexto; paths la limita a ciertos archivos. Los comandos con barra que antes eran archivos aparte ahora son skills: un mismo mecanismo con dos formas de invocarlo.

Qué pasa con una skill al compactar

El cuerpo de una skill invocada queda en la conversación. Cuando el harness compacta (M64.8), Claude Code vuelve a adjuntar cada skill usada con sus primeros 5 000 tokens, dentro de un presupuesto de 25 000 para todas, y descarta primero las más viejas Documentado. La consecuencia práctica: lo más importante va arriba en SKILL.md.

En producción real

El formato de las skills es un estándar abierto (Agent Skills): name, description, license, compatibility, metadata y allowed-tools son los campos portables, y otros harnesses leen la misma carpeta Documentado. Lo que una skill sabe de tu equipo es lo menos atado a un proveedor de toda la configuración, el argumento de M65 para no quedar atrapado.

67.5Hooks: lo que pasa siempre

Un hook es un programa que el harness ejecuta en un momento fijo de la sesión, con un JSON por stdin que describe el evento. No le pide nada al modelo: corre siempre, igual. En M66.9 lo usaste para bloquear; aquí, el mecanismo completo.

Claude Code tiene más de 30 eventos; los que más se usan son los de la figura, más PermissionRequest (cuando aparece un diálogo de permiso), Notification, SubagentStop y PostCompact Documentado. Cada hook se configura con un matcher (el nombre de una herramienta, Edit|Write o una expresión regular como mcp__memoria__.*) y uno o más manejadores. El manejador más común es command, un programa; también hay http, que manda el JSON a una URL, prompt, que se lo pasa a un modelo para que decida, y mcp_tool Documentado.

{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [ { "type": "command", "command": "npx prettier --write \"$(jq -r '.tool_input.file_path')\"" } ] }
    ],
    "Stop": [
      { "hooks": [ { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/pruebas-verdes.sh" } ] }
    ]
  }
}

El primer hook formatea cada archivo que el agente edita. Podrías pedirlo en CLAUDE.md, y el modelo lo haría casi siempre; con un hook pasa siempre, y no gasta tokens. El segundo impide que el agente diga "listo" con las pruebas rotas:

#!/usr/bin/env bash
# .claude/hooks/pruebas-verdes.sh: el agente no termina con las pruebas rotas
entrada=$(cat)                                              # (1) el evento Stop, en JSON
if [ "$(echo "$entrada" | jq -r '.stop_hook_active')" = "true" ]; then
  exit 0                                                    # (2) ya se le pidió una vez: no lo encierres en un bucle
fi
if ! salida=$(npm test --silent 2>&1); then
  echo "Las pruebas fallan. Arréglalas antes de terminar:" >&2
  echo "$salida" | tail -n 30 >&2
  exit 2                                                    # (3) en Stop, 2 significa: sigue trabajando
fi
exit 0
  1. El evento Stop llega cuando el agente termina su turno.
  2. stop_hook_active dice que el agente ya está siguiendo por un hook anterior. Sin este corte, un error que no sabe arreglar lo deja en un bucle sin fin.
  3. En Stop, el código 2 no bloquea una herramienta: impide que el agente se detenga, y stderr le dice por qué Documentado.

La salida se lee igual que en M66: código 0 sigue (y si imprime JSON, se aplica), código 2 bloquea con stderr como razón, cualquier otro es un error que no bloquea. En lugar del código, un hook puede imprimir un JSON con decision, continue, systemMessage o, en PreToolUse, permissionDecision y updatedInput, que cambia los argumentos antes de ejecutar Documentado.

Qué pasa si falla

Un hook lento frena cada llamada: el timeout por defecto de un command es de 600 segundos Documentado, así que un npm test de 4 minutos en PostToolUse convierte cada edición en una espera de 4 minutos. Las pruebas van en Stop, una vez por turno; en PostToolUse, lo que tarda menos de un segundo.

67.6Definir subagentes

Qué es un subagente y por qué protege el contexto está en M64.10: un agente con contexto propio que trabaja y devuelve solo su resultado. Claude Code trae tres (Explore y Plan, de solo lectura, y uno de propósito general); los tuyos se definen en un Markdown Documentado.

---
name: auditor-sql
description: Audita consultas SQL y migraciones buscando bloqueos, índices faltantes y
  N+1. Úsalo de forma proactiva después de cambiar código que toca la base.
tools: Read, Grep, Glob
model: haiku
skills: revisar-migracion
---

Eres un auditor de SQL. Lee el código que te indiquen, busca los problemas de la lista
y devuelve como máximo 15 líneas: archivo:línea, problema, arreglo. No edites nada.

El archivo va en .claude/agents/ (del proyecto) o en ~/.claude/agents/ (tuyo). El frontmatter decide lo que lo hace útil Documentado:

  • description: igual que en una skill, es lo que el agente principal lee para decidir delegar. "Úsalo de forma proactiva" lo invita a hacerlo sin que se lo pidas.
  • tools: la lista de herramientas. Un auditor que no edita no tiene Edit, y eso sí restringe.
  • model: un modelo más chico y barato para trabajo de lectura.
  • skills, mcpServers, hooks y permissionMode: lo que se carga solo dentro del subagente. Un servidor MCP pesado que solo usa el auditor no ocupa el contexto principal.
  • isolation: worktree: corre en una copia del repositorio, para que dos subagentes que editan no se pisen.

Lo que devuelve es la pieza que más se descuida. El prompt del subagente dice cuánto y en qué forma: "como máximo 15 líneas". Anthropic sugiere resúmenes de 1 000 a 2 000 tokens Documentado; un subagente que devuelve todo lo que leyó no protegió nada.

67.7Plugins: empaquetar y repartir

Un plugin es una carpeta con un manifiesto que agrupa skills, subagentes, hooks y servidores MCP para instalarlos de una vez Documentado. No agrega un mecanismo nuevo: empaqueta los anteriores.

{
  "name": "revision-pagos",
  "version": "0.3.0",
  "description": "Skills, subagente y hooks para revisar cambios en el servicio de pagos",
  "author": { "name": "Equipo de Pagos" }
}
# Agregar el marketplace del equipo (un repositorio con .claude-plugin/marketplace.json)
/plugin marketplace add tuempresa/plugins-internos

# Instalar un plugin de ese marketplace, para todo el proyecto
/plugin install revision-pagos@plugins-internos --scope project

Tres detalles que cambian el uso Documentado. Las skills de un plugin se invocan con su espacio de nombres, /revision-pagos:revisar-migracion, para que dos plugins no choquen. Sus herramientas MCP llevan el prefijo mcp__plugin_<plugin>_<servidor>__. Y cada plugin activado pone los nombres y descripciones de lo que trae en el contexto de cada turno: diez plugins instalados "por si acaso" son la barra roja del widget de 67.3.

67.9Combinar: un equipo de pagos

Las extensiones se combinan. El equipo de pagos de la Parte III quiere que el agente revise cada cambio en las migraciones del ledger. Lo arman así Diseño de referencia:

  1. Una línea en CLAUDE.md"Las migraciones del ledger se revisan con la skill revisar-migracion antes de proponer un cambio." Diez palabras que se pagan siempre y apuntan a lo que se paga solo al usarse.
  2. La skill revisar-migracionEl procedimiento de 67.4, con patrones.md al lado, que solo se lee si hay un problema.
  3. Un servidor MCP de solo lecturaConectado a una réplica de staging con un rol que solo puede SELECT y EXPLAIN: el permiso lo impone la base, no el prompt (M35).
  4. El subagente auditor-sqlCon Haiku, sin Edit, con la skill precargada y el servidor MCP solo en su contexto. El agente principal nunca carga las definiciones de la base.
  5. Un hookPostToolUse sobre Write en db/migrations/ que corre squawk, un linter de migraciones, y devuelve los avisos al modelo.
  6. Un plugin del proyectoTodo lo anterior en revision-pagos, instalado con --scope project, versionado en el marketplace interno.

El resultado: una tarea que no toca la base paga una línea de memoria, un par de descripciones y nada más. Una que toca una migración carga la skill, delega en el auditor y recibe 15 líneas.

67.10Seguridad de las extensiones

Instalar una extensión es darle algo a un tercero. Conviene separar tres cosas, porque cada una se controla distinto.

  • Código que corre como tú. Un servidor MCP por stdio, un hook o el script de una skill se ejecutan en tu máquina con tus permisos, fuera del sandbox de comandos de M66.4 Documentado. Un plugin que trae los tres es un programa que instalaste. Se revisa como una dependencia: de dónde viene, quién lo mantiene, versión fijada (M56).
  • Texto que entra al contexto. La descripción de una herramienta MCP, lo que devuelve y el cuerpo de una skill entran al contexto como cualquier otro texto, y pueden traer instrucciones: es la injection indirecta de M25, con la diferencia de que la instalaste tú. La especificación de MCP dice que las descripciones y anotaciones de una herramienta se traten como no confiables salvo que el servidor lo sea Documentado. Una descripción que cambia entre versiones sin que cambie el código es una señal.
  • Datos que salen. Los argumentos de una llamada a un servidor remoto salen de tu máquina; si el modelo leyó un secreto, puede mandarlo como argumento. Es la tercera pata de la trifecta, y se corta con servidores de confianza y scopes OAuth mínimos.

En producción real

El .mcp.json y el .claude/settings.json de un repositorio que clonas pueden traer servidores y hooks. Claude Code pide aprobación antes de usarlos en una sesión interactiva; en modo headless (M69.1) no hay nadie a quien preguntar, y una automatización sobre repositorios ajenos corre con --bare, que no carga la configuración del proyecto. Las organizaciones restringen qué marketplaces y servidores se permiten desde managed settings.
