C.2Diseño: cobrar el uso de la API de IA

La API de la Parte II tiene la flota del M19 y el metering del M21. Hasta ahora solo facturaba a fin de mes a 3 000 empresas. Hace tres meses se abrió el autoservicio: cualquiera crea una cuenta, compra créditos con tarjeta y llama a la API en minutos. El autoservicio se armó rápido, con una columna balance en la tabla de organizaciones que se resta en cada request y un endpoint que cobra la tarjeta y suma. El mes pasado salió mal:

  • Hubo 180 contracargos sobre unas 31 000 compras (0.58 %): compras de unos 300 USD con tarjetas robadas, gastadas en menos de un día.
  • Una noche, un script probó 30 000 tarjetas en dos horas contra el formulario de compra.
  • Dos clientes recibieron dos cobros por la misma recarga automática.
  • Entre lo que dice Stripe y la suma de las columnas balance hay 3 400 USD de diferencia, y nadie sabe explicarla.
  • Un cliente con 2 USD de saldo lanzó 40 streams con prompts largos a la vez y terminó con −11 USD.

Te piden rediseñar el cobro completo, para las dos clases de clientes y en dos regiones.

La regla que ordena todo: el ledger es la verdad y el saldo caliente es una proyección rápida. El gateway nunca lee el ledger y nunca llama a Stripe. El ledger nunca está en el camino de una request. Si el saldo caliente y el ledger no coinciden, gana el ledger y el saldo caliente se corrige.

El ledger

El saldo de una organización deja de ser una columna que se resta y pasa a ser la suma de asientos de doble entrada, como en el M27. Los créditos que el cliente pagó y no usó son un ingreso diferido: servicio que la empresa le debe (M21). Cada compra o promoción es un lote con su vencimiento, y el uso consume primero el que vence antes.

Un asiento por organización y hora

El uso no se asienta request por request. El rating del M21 ya produce el costo de cada organización por hora, versionado; ese agregado es un asiento, con source_ref = uso:{org}:{hora}:v{versión}. Son 432 000 asientos por día, 5 por segundo. Uno por evento serían 260 por segundo, 520 en el pico, todos contra la misma cuenta de ingresos. Si una hora se reprocesa (M21), la versión nueva no reemplaza el asiento: se asienta la diferencia como v2.

La cuenta de ingresos se reparte en 32 subcuentas, ingresos:uso:{hash(org) % 32}, igual que la de comisiones del M27. A 5 asientos por segundo una sola fila aguantaría; las subcuentas quedan para el día en que se asiente por minuto, y al leer solo cuestan una suma.

El esquema

CREATE TABLE ledger_accounts (
  account_id  text PRIMARY KEY,                 -- 'creditos:org_7:lote_41', 'ingresos:uso:17'
  kind        text NOT NULL CHECK (kind IN ('activo', 'pasivo', 'ingreso', 'gasto')),
  org_id      text,                             -- NULL en las cuentas de la empresa
  currency    text NOT NULL DEFAULT 'usd'
);

CREATE TABLE ledger_transactions (
  tx_id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  source_ref   text NOT NULL UNIQUE,            -- 'pi_3Qa…:captura', 'uso:org_7:2026-10-04T14:v1'
  kind         text NOT NULL,                   -- compra, uso, promo, reembolso, disputa, factura, pago, payout
  effective_at timestamptz NOT NULL,            -- cuándo ocurrió
  recorded_at  timestamptz NOT NULL DEFAULT now(),   -- cuándo se supo
  metadata     jsonb NOT NULL DEFAULT '{}'
);

CREATE TABLE ledger_entries (
  tx_id       bigint NOT NULL REFERENCES ledger_transactions,
  account_id  text   NOT NULL REFERENCES ledger_accounts,
  amount_nano bigint NOT NULL CHECK (amount_nano <> 0),  -- débito +, crédito −, en nanodólares
  PRIMARY KEY (tx_id, account_id)
);
-- Más el trigger diferido suma_cero del M27: cada tx_id suma 0 al confirmar.

CREATE TABLE credit_lots (
  lot_id         text PRIMARY KEY,              -- 'lote_41'
  org_id         text NOT NULL,
  origin         text NOT NULL CHECK (origin IN ('compra', 'recarga', 'promo', 'sla')),
  granted_nano   bigint NOT NULL,
  expires_at     timestamptz NOT NULL,          -- compra: un año; promoción: 30 días
  state          text NOT NULL DEFAULT 'vigente'
                 CHECK (state IN ('vigente', 'congelado', 'agotado', 'vencido', 'reembolsado')),
  payment_intent text UNIQUE                    -- un lote por cobro, aunque el asiento se intente dos veces
);
CREATE INDEX lotes_por_vencer ON credit_lots (org_id, expires_at) WHERE state = 'vigente';

CREATE TABLE org_balances (                     -- saldo materializado, en la misma transacción que los asientos
  org_id         text PRIMARY KEY,
  available_nano bigint NOT NULL,
  ledger_seq     bigint NOT NULL                -- último tx_id aplicado: la versión del saldo
);

El dinero va en nanodólares en un bigint, la misma unidad que los precios del M21 (nanousd_per_unit): un double no representa 0.1 exacto y los errores se acumulan; los enteros suman exacto, y un bigint llega a 9.2 × 1018 nanodólares, unos 9 200 millones de USD por cuenta. La aplicación escribe con un rol que puede hacer INSERT en las tablas del ledger y no puede hacer UPDATE ni DELETE: nada se edita, todo se corrige con un asiento nuevo.

Postear una sola vez

from dataclasses import dataclass

NANO_POR_CENTAVO = 10_000_000          # 1 USD = 100 centavos = 10**9 nanodólares

@dataclass(frozen=True)
class Linea:
    cuenta: str
    nano: int                          # débito +, crédito −

def postear(db, source_ref: str, tipo: str, effective_at, lineas: list[Linea]) -> int | None:
    """Escribe un asiento una sola vez. Devuelve el tx_id, o None si ese source_ref ya existía."""
    assert sum(l.nano for l in lineas) == 0, "un asiento suma cero"
    with db.transaction():
        tx = db.fetchval("""
            INSERT INTO ledger_transactions (source_ref, kind, effective_at)
            VALUES ($1, $2, $3)
            ON CONFLICT (source_ref) DO NOTHING
            RETURNING tx_id""", source_ref, tipo, effective_at)
        if tx is None:
            return None                # un reintento o un webhook repetido: ya está asentado
        db.executemany("INSERT INTO ledger_entries (tx_id, account_id, amount_nano) VALUES ($1, $2, $3)",
                       [(tx, l.cuenta, l.nano) for l in lineas])
        for org, delta in efecto_en_creditos(lineas).items():      # suma de las cuentas creditos:{org}:*
            db.execute("""UPDATE org_balances
                          SET available_nano = available_nano - $2, ledger_seq = $3
                          WHERE org_id = $1""", org, delta, tx)
            if tipo != "uso":          # el uso ya lo descontó el gateway en caliente
                db.execute("INSERT INTO outbox (topic, key, payload) VALUES ('saldos', $1, $2)",
                           org, {"tx_id": tx, "delta_nano": -delta})
    return tx

El ON CONFLICT DO NOTHING sobre source_ref es la idempotencia del ledger, independiente de la de la API: el webhook, el camino síncrono y el barrido pueden intentar el mismo asiento, y solo uno lo escribe. El cambio de saldo sale por un outbox (M07) en la misma transacción, así que no hay asiento sin aviso ni aviso sin asiento. Las cuentas de créditos son pasivos, con saldo acreedor: una compra las mueve en negativo y el saldo disponible sube, de ahí el signo menos.

El saldo prepago en caliente

Una request prepaga tiene que saber si puede empezar, pero su costo se conoce al final. Es el problema del M18 con dinero en lugar de tokens, y el M21 comparó tres políticas: cobrar al terminar, reservar el máximo y reservar por tramos. Pruébalas en el simulador del M21 con el caso de este checkpoint: saldo bajo y muchos streams a la vez. El simulador usa tramos de 0.04 USD; este diseño elige 0.05, por la cuenta que sigue.

Decisión: tramos de 0.05 USD con un sobregiro de 5 USD. Un tramo paga 6.25 requests de costo medio, así que la mayoría de las requests reserva una sola vez; la más cara del M21, de 0.48 USD, pide 10 tramos a lo largo de su stream. El cliente de los 40 streams y 2 USD reserva 40 tramos, exactamente su saldo, y sus extensiones siguen hasta −5 USD: como mucho gasta 7 USD, no 13. El stream que no consigue el tramo siguiente se corta con un evento de error de SSE (M17) y se cobra lo usado hasta ahí. Los 5 USD de sobregiro se descuentan de la próxima compra.

A 400 requests por segundo, entre reservas, cierres y extensiones son unas 880 operaciones por segundo por región: nada para Valkey, que atiende decenas de miles por segundo en un nodo (M04). La reserva se pide cuando la request ya pasó el limitador de cuotas.

El cruce del umbral se detecta dentro del script. Solo la reserva que lleva el saldo de "arriba del umbral" a "debajo" lo ve: marca el cruce con su versión en el mismo hash, en la misma operación atómica que el descuento, y el gateway lo publica en el tópico cruces de Kafka. Si el gateway muere entre las dos cosas, un barrido que corre cada minuto sobre las organizaciones con recarga activa encuentra el campo cruce sin su recarga y lo publica. Publicar dos veces no hace daño, porque la recarga se identifica por la versión (más abajo). Así se arregla lo que causó los dos cobros del piloto: dos gateways leían el saldo, los dos veían el cruce y los dos cobraban con claves distintas.

Cómo entran las compras al saldo caliente. Un proyector consume el outbox del ledger y aplica cada cambio una sola vez, comparando el tx_id con el campo seq: si el asiento ya se aplicó, no hace nada. El uso no se aplica, porque el gateway ya lo descontó. Cada hora, la conciliación comprueba la cuenta:

saldo caliente = saldo del ledger − uso todavía sin asentar − reservas abiertas

La diferencia que pasa de 1 centavo por organización se corrige en el saldo caliente, porque el ledger gana, y se cuenta en una métrica: si crece, hay un bug en el gateway o en el proyector.

Si Valkey no responde

Valkey es la única pieza que el gateway necesita para atender a un cliente prepago, así que su caída tiene que tener un costo acotado. Cada gateway guarda en memoria, actualizada cada 30 s, una marca por organización: saldo holgado, que significa que el saldo alcanza para 20 minutos del gasto máximo que permiten las cuotas de su nivel.

Con Valkey caído, las organizaciones holgadas se atienden a ciegas hasta 10 minutos por región. Con las dos regiones a ciegas a la vez son 20 minutos del gasto máximo, que el saldo cubre: la exposición es cero. Las demás organizaciones prepago reciben un 503 con Retry-After, porque no hicieron nada mal y el problema es del proveedor; nunca un 402 ni un 429 (M18). Los clientes de pospago no dependen del saldo y siguen sin cambios. Al volver Valkey, el saldo de cada organización se reconstruye desde el ledger y el metering, y se descuentan por precaución los tramos que pudieran haber quedado en vuelo.

La compra desde la consola

  1. El navegador genera la claveAl abrir el formulario, la consola crea un UUID y lo manda como Idempotency-Key en cada intento de esa compra. Un doble clic o un reintento del navegador repiten la clave, y el servidor devuelve la misma compra.
  2. La API registra la compraComprueba los límites (mínimo de 10 USD y 100 USD en los primeros 7 días de la cuenta) y guarda la compra con la clave del navegador, en una transacción que bloquea la fila de la organización.
  3. La API crea el PaymentIntentCon su propia idempotency key, compra:{id}, pide 3D Secure en la primera compra de la cuenta y guarda la tarjeta para cobrarla después sin el cliente (setup_future_usage). Devuelve el client_secret.
  4. El navegador confirma con StripeLos datos de la tarjeta van del formulario de Stripe Elements directo a Stripe, y si el banco pide 3D Secure el desafío aparece ahí mismo. Los servidores de la empresa nunca ven un número de tarjeta.
  5. El ledger acreditaLlegan dos avisos: la consola llama a POST …/{id}/sync, que vuelve a leer el PaymentIntent, y el webhook payment_intent.succeeded llega segundos después. Los dos intentan el mismo asiento, con source_ref pi_…:captura, y solo uno lo escribe.

def crear_compra(db, org, clave_navegador: str, centavos: int) -> dict:
    if centavos < MINIMO:
        raise ErrorApi(400, "amount_too_small")
    with db.transaction():
        # Bloquear la organización serializa sus compras: dos pestañas no pueden pasar
        # juntas el tope de la cuenta nueva leyendo el mismo total (M05).
        db.execute("SELECT 1 FROM orgs WHERE id = $1 FOR UPDATE", org.id)
        compra = db.fetchrow("SELECT * FROM credit_purchases WHERE org_id = $1 AND idempotency_key = $2",
                             org.id, clave_navegador)
        if compra is None:
            if org.edad_dias < 7 and comprado_en_7_dias(db, org.id) + centavos > TOPE_CUENTA_NUEVA:
                raise ErrorApi(422, "new_account_purchase_limit")
            compra = db.fetchrow("""INSERT INTO credit_purchases (org_id, idempotency_key, amount_cents)
                                    VALUES ($1, $2, $3) RETURNING *""", org.id, clave_navegador, centavos)
        elif compra["amount_cents"] != centavos:
            raise ErrorApi(409, "idempotency_key_reused")
    if compra["payment_intent"]:
        # Stripe puede olvidar una clave después de 24 h: si ya hay PaymentIntent, se relee.
        pi = stripe.PaymentIntent.retrieve(compra["payment_intent"])
    else:
        pi = stripe.PaymentIntent.create(
            amount=centavos, currency="usd", customer=org.stripe_customer,
            setup_future_usage="off_session",               # la tarjeta queda para la recarga automática
            payment_method_options={"card": {
                "request_three_d_secure": "automatic" if org.tiene_compras_pagadas else "any"}},
            metadata={"org_id": org.id, "purchase_id": str(compra["id"])},
            idempotency_key=f"compra:{compra['id']}",       # el mismo PaymentIntent en cada reintento
        )
        db.execute("UPDATE credit_purchases SET payment_intent = $2 WHERE id = $1", compra["id"], pi.id)
    return {"id": f"cp_{compra['id']}", "status": pi.status, "amount_cents": centavos,
            "client_secret": pi.client_secret}

Hay dos claves y cada una protege un tramo distinto. La del navegador evita dos compras por un doble clic; la de Stripe, compra:{id}, evita dos PaymentIntents si el servidor se cae entre la llamada a Stripe y el UPDATE. La llamada a Stripe va fuera de la transacción: nunca se sostiene un bloqueo de la base mientras se espera a un tercero. El cliente configura un umbral y un monto: por ejemplo, recargar 50 USD cuando el saldo baja de 10. La recarga se cobra sin el cliente presente, con la tarjeta que guardó la primera compra.

def procesar_cruce(db, org_id: str, version: int):
    """Consume el tópico cruces. Llega al menos una vez: la clave hace el resto."""
    org = cargar_org(db, org_id)
    if not org.recarga.activa:
        return
    with db.transaction():
        if recargas_de_hoy(db, org_id) >= MAX_RECARGAS_DIA:
            pausar_recarga(db, org_id, motivo="tope_diario")      # un bug o un abuso no cobra sin fin
            notificar(org_id, "recharge.paused")
            return
        r = db.fetchrow("""INSERT INTO recharges (org_id, clave, amount_cents)
                           VALUES ($1, $2, $3)
                           ON CONFLICT DO NOTHING RETURNING *""",
                        org_id, f"{org_id}:recarga:saldo-v{version}", org.recarga.monto_centavos)
    if r is not None:          # None: este cruce ya tiene recarga, o hay otra abierta
        cobrar_recarga(db, r, org)

def cobrar_recarga(db, r, org):
    try:
        pi = stripe.PaymentIntent.create(
            amount=r["amount_cents"], currency="usd",
            customer=org.stripe_customer, payment_method=org.metodo_guardado,
            off_session=True, confirm=True,                       # sin el cliente presente
            metadata={"org_id": r["org_id"], "recharge": r["clave"]},
            expand=["latest_charge.balance_transaction"],         # la comisión real, para el asiento
            idempotency_key=f"{r['clave']}:intento-{r['attempt']}",
        )
    except stripe.CardError as e:
        estado = "requiere_accion" if e.error.code == "authentication_required" else "rechazada"
        db.execute("UPDATE recharges SET state = $2 WHERE id = $1", r["id"], estado)
        pausar_recarga(db, r["org_id"], motivo=estado)
        notificar(r["org_id"], "recharge.requires_action" if estado == "requiere_accion" else "recharge.failed")
        return
    # Un corte de red o un 5xx no se atrapan aquí: el worker reintenta y repite la misma clave.
    bt = pi.latest_charge.balance_transaction
    if bt is not None:                                            # si todavía no existe, asienta el webhook
        acreditar(db, pi, comision_centavos=bt.fee, origen="recarga")   # postear() con source_ref pi_…:captura
    db.execute("UPDATE recharges SET state = 'pagada', payment_intent = $2 WHERE id = $1", r["id"], pi.id)

Por qué la clave sale de la versión del saldo. Una clave aleatoria se genera en cada proceso: dos workers que procesan el mismo cruce generan dos claves y cobran dos veces, que es lo que pasó en el piloto. La versión es determinista, así que cualquier proceso que vea el cruce v4182 llega a la misma clave. Y es distinta para cada cruce legítimo: después de la recarga el saldo sube, la próxima vez que baje del umbral la versión será otra, y esa recarga sí tiene que cobrarse. El tope de tres recargas por día corta el caso que nada de esto ve: un bug que haga cruzar el umbral en bucle.

Stripe guarda el código y el cuerpo de la primera respuesta a una clave una vez que la request empezó a ejecutarse, incluso si fue un 500, y cualquier reintento con esa clave recibe la misma respuesta. No la guarda si los parámetros no pasaron la validación o si chocó con otra request concurrente con la misma clave, y puede olvidar la clave pasadas 24 horas. Si los parámetros de un reintento no coinciden con los del original, responde con un error. Documentado De ahí sale la tabla:

La regulación europea de autenticación reforzada (SCA, M27) permite que el banco pida autenticar incluso un cobro sin el cliente presente. Por eso el estado requiere_accion existe y la recarga se pausa en lugar de reintentar: reintentar sin el cliente daría el mismo error.

Los webhooks que entran

El receptor hace lo mínimo y responde rápido: verifica la firma sobre el cuerpo crudo, guarda el evento si es nuevo y deja el trabajo a un worker por un outbox. Los webhooks que salen

Los clientes también quieren enterarse sin consultar: balance.low, recharge.succeeded, recharge.failed, recharge.requires_action, spend_limit.reached e invoice.issued. El diseño copia lo que funciona en Stripe (M02):

  • Cada entrega lleva un id whe_… que se repite en las reentregas, para que el cliente deduplique.
  • La firma es un HMAC-SHA256 del timestamp y el cuerpo (M36). Firmar también el timestamp impide reenviar una entrega vieja capturada.
  • Cada endpoint de cliente tiene su propia cola: un cliente lento o caído no demora a los demás.
  • Reintentos con backoff exponencial y jitter (1 min, 5 min, 30 min, 2 h, 8 h…) durante tres días. Después se deshabilita el endpoint y se avisa por correo.
import hashlib, hmac, time

def firmar(secreto: bytes, cuerpo: bytes, ahora: int | None = None) -> str:
    t = ahora if ahora is not None else int(time.time())
    mac = hmac.new(secreto, f"{t}.".encode() + cuerpo, hashlib.sha256).hexdigest()
    return f"t={t},v1={mac}"                   # va en el header Webhook-Signature

def verificar(secreto: bytes, cuerpo: bytes, firma: str, tolerancia: int = 300) -> bool:
    """Lo que publicamos en la documentación para que el cliente compruebe la firma."""
    partes = dict(p.split("=", 1) for p in firma.split(","))
    t = int(partes["t"])
    if abs(time.time() - t) > tolerancia:
        return False                           # una entrega vieja reenviada
    esperado = hmac.new(secreto, f"{t}.".encode() + cuerpo, hashlib.sha256).hexdigest()
    return hmac.compare_digest(esperado, partes.get("v1", ""))

Fraude, card testing y disputas

El autoservicio con tarjeta es exactamente lo que buscan dos clases de atacantes. El que tiene tarjetas robadas compra créditos y los gasta antes de que el titular se entere: el servicio se entrega y nunca se cobra. El que hace card testing usa el formulario para averiguar cuáles de miles de números robados funcionan, con compras chicas (M27). Ninguna defensa sola alcanza, así que se apilan:

La pérdida máxima por tarjeta, con la cuenta de la tabla de estimaciones: antes se podían comprar 300 USD y gastarlos en un día, así que una disputa costaba 15 de tarifa, 9.00 de comisión y 300 × 0.35 = 105.49 de GPU, 129.49 USD en total. Con el tope de 100 USD, el peor caso es 15 + 3.20 + 35.16 = 53.36 USD. Y si el pago se autenticó con 3D Secure, la disputa por fraude todavía puede llegar, pero la responsabilidad pasó al emisor y Stripe adjunta la evidencia de la autenticación. Documentado Pedir 3D Secure en la primera compra de cada cuenta agrega fricción una sola vez.

Los 30 000 intentos en dos horas del piloto son 250 por minuto, unos 4 por segundo: nada para el borde, pero cada uno es una autorización real contra un banco, y las tarjetas que resulten válidas se usan después contra otros comercios. Contra eso, límites que el atacante no puede repartir: como mucho 3 tarjetas distintas por cuenta y por día, 5 intentos fallidos por sesión y por hora, y el alta con correo verificado y desafío. Para probar 30 000 tarjetas con 3 por cuenta, el atacante necesita 10 000 cuentas verificadas.

La alerta temprana: ¿reembolsar o esperar?

Los emisores de Visa, Mastercard y JCB reportan los pagos que sospechan fraudulentos, y Stripe los entrega como alertas tempranas (radar.early_fraud_warning.created). Según Stripe, si no se reembolsa, cerca del 40 % de esas alertas terminan en una disputa por fraude; reembolsar antes evita la disputa, aunque no borra el reporte de fraude. Documentado La cuenta con la compra de 50 USD de la que quedaban 25 sin usar:

OpciónCálculoPérdida esperada
Reembolsar todo25 de servicio entregado + 1.75 de comisión que no vuelve26.75 USD
Congelar el lote y esperar40 % × (25 de servicio + 1.75 + 15 de tarifa)16.70 USD

Esperar sale más barato en promedio, y coincide con lo que recomienda Stripe: reembolsar las alertas de pagos de más o menos el monto de la tarifa de disputa, y no las de pagos bastante mayores. Documentado La excepción es este piloto: con un 0.58 % de disputas, cada disputa más empuja la cuenta hacia los programas de monitoreo de las redes, que cuestan mucho más que 10 USD. Decisión: ante una alerta, siempre se congela la cuenta y se revocan sus claves, para que no se gaste nada más; y se reembolsa todo mientras la tasa de disputas esté por encima del 0.3 % o el pago sea de 20 USD o menos. Cuando la tasa baje, se espera.

La disputa. Stripe retira el monto disputado más la tarifa el día en que se abre, y el asiento se hace ese mismo día (M27). Responder con evidencia cuesta otra tarifa, que Stripe devuelve si se gana; la tarifa de la disputa recibida no vuelve. Documentado Por eso no se responden todas: una disputa por fraude sin 3D Secure casi nunca se gana, y responderla agrega 15 USD. Se responden las autenticadas con 3D Secure y las de más de 100 USD con evidencia fuerte de uso legítimo (las mismas IP y el mismo dispositivo de siempre, el uso de la API con la clave de la cuenta).

Dos regiones

Un saldo único y sincrónico para las dos regiones costaría un viaje de unos 80 ms a us-east-1 en cada request europea, y dejaría a eu-west-1 sin servicio prepago si el enlace se corta: el CAP del M06 aplicado al dinero. La solución es la del escrow del M18:

  • Cada organización tiene una región de origen, la de su alta, donde vive su saldo caliente.
  • La otra región pide prestados 10 tramos (0.50 USD) y reserva contra ese préstamo. Cuando le quedan menos de 3, pide más en segundo plano. El origen descuenta lo prestado de su saldo en el momento de prestarlo, así que el dinero nunca está disponible en los dos lados a la vez.
  • Si el enlace se corta, eu-west-1 gasta como mucho lo que tenía prestado, y no hay exceso posible. Después atiende a ciegas solo a las organizaciones con saldo holgado, hasta 10 minutos, y a las demás les responde 503 con Retry-After.
  • El ledger es un Aurora PostgreSQL Global Database: el primario en us-east-1 y una réplica en eu-west-1, con un retraso de replicación que normalmente es menor a un segundo. Documentado Los receptores de webhooks de las dos regiones escriben en el primario; si no lo alcanzan, responden con error y Stripe reintenta.
  • Si us-east-1 cae más de 10 minutos, se promueve la réplica (M08) y los saldos calientes se reconstruyen en eu-west-1. Lo que se haya perdido en el último segundo de replicación se recupera de fuentes externas: el dinero, con el barrido de eventos de Stripe; el uso, con el log crudo del metering.

Esa última propiedad es la que hace seguro el failover: todo asiento se puede reconstruir desde afuera. Los de dinero, desde Stripe; los de uso, desde el log del M21. El ledger no es el único lugar donde existe un hecho, sino el lugar donde los hechos se cruzan.

Seguridad

  • Claves restringidas de Stripe, una por servicio y con los permisos mínimos, en un gestor de secretos (M37). Documentado El gateway no tiene ninguna: nunca habla con Stripe.
  • Stripe Elements: los datos de tarjeta no tocan los servidores de la empresa, y PCI queda en el SAQ A.
  • Ledger de solo escritura: el rol de la aplicación puede hacer INSERT y no puede hacer UPDATE ni DELETE (M35).
  • Los créditos manuales (por un SLA incumplido o un acuerdo comercial) necesitan la aprobación de dos personas y quedan en el audit log (M10).
  • Las rutas de facturación comprueban que el objeto es de la organización que pregunta, y los PDF salen por URL firmada.
  • Solo el rol de administrador de facturación compra créditos o cambia la recarga, y siempre desde la consola: una API key filtrada puede gastar el saldo, pero no puede comprar más con la tarjeta guardada.
