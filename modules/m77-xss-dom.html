XSS y el DOM

Un XSS es código del atacante corriendo en tu origen, con todos los permisos de tu página. No se arregla con un filtro: se arregla con la regla de que los datos nunca se vuelven código, aplicada en cada lugar donde un string entra al HTML.

  • Elegir el escape correcto para cada contexto de salida: cuerpo HTML, atributo, URL, JavaScript y CSS.

M76 cerró con una advertencia: ningún token frena a código que ya corre en tu origen. Ese código es un XSS (Cross-Site Scripting): el atacante consigue que tu página ejecute su JavaScript, y desde ese momento tiene los mismos permisos que tu propio código. La Same-Origin Policy, SameSite y el token anti-CSRF quedan del lado equivocado de la frontera, porque el atacante ya está adentro. En M10 viste la idea en dos párrafos; aquí va el mecanismo.

77.1Tres formas de llegar a la página

Analogía

Es un formulario en papel donde alguien escribe, en la casilla del nombre, "y además, entregue las llaves al portador". Si el empleado lee las casillas como instrucciones y no como datos, obedece. El XSS es eso: un dato leído como instrucción.

  • Reflejado. El valor llega en la request y vuelve en la respuesta. La víctima tiene que abrir un enlace preparado.
  • Almacenado. El valor se guarda (un título, un comentario, un nombre) y se sirve a todos los que lo ven. No requiere enlace y alcanza a muchas víctimas, incluidos los administradores.
  • Basado en el DOM. El JavaScript de la página toma el valor de una fuente del navegador y lo escribe en el DOM. El servidor nunca lo ve, así que ni los registros ni el WAF lo detectan.
<?php
// buscar.php — MAL: el parámetro vuelve al HTML tal cual
$q = $_GET['q'] ?? '';
echo "<h1>Resultados para $q</h1>";

El payload didáctico de todo este módulo es alert(document.domain): muestra en qué origen corre el código, que es lo único que hay que demostrar.

77.2El contexto decide qué es código

En M73 viste que el parser HTML cambia de modo según dónde está: dentro de un <title> todo es texto; dentro de un atributo, el valor termina en la comilla; dentro de un <script>, el texto lo lee después otro parser, el de JavaScript. Cada lugar donde PHP imprime un dato es un contexto de salida, con sus propios caracteres peligrosos.

ContextoCaracteres que cambian la estructuraEscape
Cuerpo HTML< y &htmlspecialchars
Atributo con comillasLa comilla que lo abre, &htmlspecialchars con ENT_QUOTES; siempre con comillas
URL en href o srcEl esquema: javascript:, data:Lista de esquemas, después el escape de atributo
String en <script>La comilla, \, el salto de línea y </scriptjson_encode con JSON_HEX_TAG y sus pares
Valor CSS;, :, (, la comillaLista de valores permitidos

Un atributo sin comillas no tiene un escape seguro: un espacio termina el valor y empieza otro atributo (lo viste en el widget de M73). La regla es simple: todo atributo con un dato va entre comillas.

77.3El escape correcto en PHP

htmlspecialchars convierte &, <, >, " y, con ENT_QUOTES, también '. ENT_SUBSTITUTE reemplaza las secuencias UTF-8 inválidas en lugar de devolver un string vacío. Desde PHP 8.1, los flags por defecto son ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML401; antes eran ENT_COMPAT, que no escapa la comilla simple Documentado. Tu XAMPP corre PHP 8.0: ahí, htmlspecialchars($v) sin flags deja abierto todo atributo con comillas simples. Pasa los flags siempre, y el código queda igual en cualquier versión.

<?php
// core/escape.php: una función por contexto, con nombre corto para usarla en todas partes
function e(?string $s): string            // cuerpo HTML y atributos con comillas
{
    return htmlspecialchars($s ?? '', ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5, 'UTF-8');
}

function js(mixed $v): string             // dentro de <script>: el valor ya trae sus comillas
{
    return json_encode($v, JSON_HEX_TAG | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_HEX_AMP
                         | JSON_THROW_ON_ERROR);
}

function url(?string $u): string          // un href o src que viene de un dato
{
    $u = trim($u ?? '');
    $esquema = strtolower((string)parse_url($u, PHP_URL_SCHEME));
    $ok = $esquema === '' ? str_starts_with($u, '/') && !str_starts_with($u, '//')
                          : in_array($esquema, ['http', 'https'], true);
    return e($ok ? $u : '#');
}
<p><?= e($o['titulo']) ?></p>
<input name="ubicacion" value="<?= e($o['ubicacion']) ?>">
<a href="<?= url($institucion['sitio_web']) ?>" rel="noopener">Sitio de la institución</a>
<script>const oportunidad = <?= js(['id' => $o['id'], 'titulo' => $o['titulo']]) ?>;</script>
<a href="buscar.php?q=<?= e(rawurlencode($q)) ?>">Buscar de nuevo</a>

Prueba los cinco contextos con seis valores. Fíjate en dos cosas: el escape HTML no detiene un javascript:, y un escape del contexto equivocado a veces no ejecuta nada pero corrompe el texto.

Trade-off

Escapar al imprimir, no al guardar. Si guardas el texto ya escapado, el dato queda atado a un contexto (sirve para HTML, se rompe en un PDF, en un correo o en el JSON de una app móvil) y tarde o temprano alguien lo escapa dos veces y la página muestra &amp;. La base guarda lo que escribió la persona; cada salida aplica su escape.

77.4Tu API y el Content-Type que falta

Tu API responde JSON y no genera HTML, así que parece no tener XSS. Pero Response::json no envía Content-Type, y PHP responde con su valor por defecto, text/html; charset=UTF-8 Documentado. Si alguien abre la URL de la API en el navegador, el JSON se parsea como HTML.

json_encode escapa la barra (\/) pero no < ni >, así que <img src=x onerror=…> llega intacto. El arreglo son dos cabeceras, y un flag de respaldo:

<?php
// core/response.php: la respuesta se declara JSON y el navegador no adivina
public static function json($code, $message = "", $data = [], $httpCode = 200)
{
    http_response_code($httpCode);
    header('Content-Type: application/json; charset=utf-8');
    header('X-Content-Type-Options: nosniff');       // M78
    echo json_encode(['code' => $code, 'message' => $message, 'data' => $data],
                     JSON_HEX_TAG | JSON_UNESCAPED_UNICODE);
    exit;
}

Con application/json, el navegador muestra el texto y no lo interpreta. nosniff impide que lo "adivine" como HTML (M78). JSON_HEX_TAG escribe \u003C en lugar de <: el JSON significa lo mismo, y aunque algo lo sirviera como HTML, no habría etiquetas. Y el frontend que consume ese JSON tiene que tratarlo como texto, que es 77.5.

77.5XSS en el DOM: fuentes y sumideros

Un XSS basado en el DOM une una fuente que controla el atacante con un sumidero (sink): una API del navegador que convierte un string en HTML o en código.

// feed.js — MAL: el título viene del JSON de la API y entra como HTML
for (const o of oportunidades) {
  lista.innerHTML += `<li><b>${o.titulo}</b> · ${o.institucion}</li>`;
}
// y un filtro tomado del hash, peor todavía: no pasa por el servidor
document.querySelector('#filtro').innerHTML = 'Filtro: ' + decodeURIComponent(location.hash.slice(1));
// feed.js — los datos entran como texto, la estructura la crea el código
for (const o of oportunidades) {
  const li = document.createElement('li');
  const b = document.createElement('b');
  b.textContent = o.titulo;                         // texto, nunca HTML
  li.append(b, ' · ', o.institucion);               // append con strings crea nodos de texto
  lista.append(li);
}
document.querySelector('#filtro').textContent = 'Filtro: ' + decodeURIComponent(location.hash.slice(1));

La regla para el frontend: textContent para texto, createElement y append para estructura, setAttribute solo con atributos que no ejecutan (nunca on*, href o src sin validar el esquema). React, Vue y Angular escapan por defecto al interpolar; los huecos son las salidas de emergencia con nombres que avisan, como dangerouslySetInnerHTML y v-html (M84).

Qué pasa si falla

lista.innerHTML += … en un bucle no solo arriesga un XSS: re-parsea toda la lista en cada vuelta y borra los manejadores de eventos que ya tenían los elementos. El arreglo seguro es también el rápido.

77.6Mutation XSS: por qué no se sanitiza con regex

"Quito <script> y los on…= con una expresión regular" falla por la misma razón que M73 dedicó una sección entera al parser: el HTML que escribes no es el árbol que resulta. Hay mil formas de escribir lo mismo (<ScRiPt>, entidades, atributos sin comillas, <svg><script>), y el parser corrige cosas que una regex no ve.

El mutation XSS va un paso más allá: el string pasa un sanitizador correcto y aun así ejecuta, porque el sanitizador lo parsea, lo serializa de nuevo a string y el navegador lo vuelve a parsear en otro contexto, donde el árbol sale distinto.

En 2019 se publicó un bypass de DOMPurify 2.0.0 basado en esto, con una confusión entre los espacios de nombres de SVG y HTML; se corrigió en la versión 2.0.1 Documentado. Dos lecciones: mantén el sanitizador actualizado (es una dependencia de seguridad, M56), y no proceses su salida con nada más antes de insertarla.

77.7Cuando sí hace falta HTML: DOMPurify

Escapar convierte todo en texto. A veces la persona necesita formato: la descripción de una oportunidad con negritas y una lista. Ahí se sanitiza: se parsea el HTML con el parser real y se borra todo lo que no esté en una lista de etiquetas y atributos permitidos.

// Cuando sí necesitas HTML del usuario (una descripción con negritas y listas)
const limpio = DOMPurify.sanitize(o.descripcion, {
  ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'ul', 'ol', 'li', 'p', 'br'],
  ALLOWED_ATTR: [],                       // ni href, ni style, ni on*
});
detalle.innerHTML = limpio;               // sanitizar justo antes de insertar, sin pasos en el medio
  • En el navegador, justo antes de insertar. DOMPurify usa el parser del mismo navegador que va a mostrar el resultado, lo que cierra la mayoría de las diferencias de parseo.
  • Listas cortas. Cada etiqueta y atributo permitido es superficie. Sin style ni href si no los necesitas; si permites enlaces, DOMPurify ya bloquea javascript:.
  • Alternativa más simple: guardar Markdown, convertirlo con un renderizador que escape el HTML crudo, y sanitizar la salida igual.

Los navegadores están incorporando un sanitizador propio, la Sanitizer API (element.setHTML()), que hace lo mismo sin dependencias Documentado. Revisa su soporte en MDN antes de usarla sin respaldo.

77.8Trusted Types: que el navegador no acepte strings

Escapar y sanitizar dependen de que nadie olvide hacerlo en ninguno de los cientos de lugares donde se toca el DOM. Trusted Types cambia la pregunta: con una directiva de CSP, los sumideros peligrosos dejan de aceptar strings y solo aceptan objetos creados por una política con nombre Documentado.

// Con la cabecera: Content-Security-Policy: require-trusted-types-for 'script'; trusted-types feed dompurify
const politica = trustedTypes.createPolicy('feed', {
  createHTML: (s) => DOMPurify.sanitize(s, { ALLOWED_TAGS: ['b', 'i', 'ul', 'li', 'p'], ALLOWED_ATTR: [] }),
});
detalle.innerHTML = politica.createHTML(o.descripcion);   // TrustedHTML: se acepta
detalle.innerHTML = o.descripcion;                         // string: TypeError

Se despliega en modo report-only primero (M78): la consola y los reportes muestran cada sumidero que recibe un string, sin romper nada, hasta que no queda ninguno. Está en Chromium desde 2020 Documentado; en los navegadores que no lo implementan, la directiva se ignora y la página sigue funcionando con sus otras defensas.

77.9DOM clobbering: HTML sin script que cambia tu código

Un sanitizador que deja pasar id y name todavía permite un ataque. El navegador expone los elementos con id como propiedades de window (y los formularios con name, en document). Si tu código lee un global opcional, el HTML inyectado lo define. Eso es DOM clobbering.

<!-- Un comentario con HTML permitido por el sanitizador (solo <a> con id y href) -->
<a id="config"></a><a id="config" name="urlApi" href="https://ofertas-gratis.example/">

<script>
  // El código de la página espera un objeto global opcional
  const base = (window.config && window.config.urlApi) || '/api';
  fetch(base + '/endpoints/login.php', { credentials: 'include' });   // ahora va a otro sitio
</script>

Las defensas: no leer configuración de globales que pueden no existir (declara const config = … en tu script), validar el tipo (config instanceof Object no basta: compara con lo que esperas), y en DOMPurify dejar activas SANITIZE_DOM (por defecto) y SANITIZE_NAMED_PROPS, que agrega un prefijo a id y name Documentado.

77.10Qué roba un XSS, aunque la cookie sea HttpOnly

HttpOnly impide que document.cookie lea la sesión (74.9). Es útil: el atacante no se lleva la cookie para usarla después desde su máquina. Pero mientras la víctima tenga la página abierta, el atacante no necesita la cookie: su código hace fetch a tu API, y el navegador la agrega.

  • Llamar a la API como la víctima: publicar, postular, cambiar el correo de la cuenta.
  • Leer el token CSRF y todo lo que la página muestra: datos personales, CV, otras postulaciones.
  • Leer localStorage: si guardas un JWT ahí, se lo lleva y lo usa desde cualquier lado. Una razón más para la cookie HttpOnly.
  • Cambiar la página: un formulario falso de "tu sesión expiró, escribe tu contraseña" en tu dominio, con tu candado.

Por eso un XSS se mitiga en capas: escape por contexto (no entra), Trusted Types (no llega al sumidero), CSP estricta (si llega, no ejecuta, M78), HttpOnly y sesión revocable (si ejecuta, el daño dura poco, M81).

Busca los sumideros antes que los payloads: grep -rn "innerHTML\|insertAdjacentHTML\|document.write\|eval(" frontend/ y, en PHP, cada echo o <?= que imprime una variable sin e().
