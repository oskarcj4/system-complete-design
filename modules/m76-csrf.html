CSRF

Otro sitio no puede leer tu API, pero sí puede hacer que el navegador de tu usuario le mande una request con su cookie. CSRF es ese ataque de solo escritura, y se cierra con capas que el servidor comprueba.

Al terminar podrás

  • Explicar por qué un sitio ajeno puede hacer que el navegador mande una request con la cookie de tu usuario.
  • Reconocer las cuatro formas de disparar un CSRF: formulario, GET con efecto, fetch sin cors y login CSRF.
  • Decir qué frena SameSite y dónde no alcanza: GET de nivel superior y subdominios del mismo sitio.

  • Comprobar Origin y Fetch Metadata en PHP, y ordenar las capas en el middleware.

En M75 quedó una frase incómoda: el navegador bloquea la lectura, no el envío, y una request simple llega y se ejecuta aunque CORS diga que no. Este módulo trata esa mitad. El ataque se llama CSRF (Cross-Site Request Forgery, falsificación de requests entre sitios): otro sitio hace que el navegador de tu usuario mande una request a tu API, con su cookie, y tu API la toma por legítima.

76.1El ataque, paso a paso

Analogía

Es una carta firmada en blanco. Tu navegador firma (con la cookie) todo lo que sale hacia tu sitio, sin mirar quién la escribió. El atacante escribe la carta; tu navegador la firma y la manda.

Carla es reclutadora en el sistema de prácticas y tiene la sesión abierta. Le llega un correo con un enlace a ofertas-gratis.example. La página tiene esto:

<!-- En https://ofertas-gratis.example, una página que el atacante controla -->
<form id="f" method="POST" action="http://localhost/SistemaControlPracticas/api/endpoints/oportunidades.php">
  <input type="hidden" name="titulo" value="Práctica remota, pago inmediato">
  <input type="hidden" name="descripcion" value="Escribe a este número para aplicar">
</form>
<script>document.getElementById('f').submit();</script>

Tres condiciones hacen posible el ataque, y cada defensa rompe una:

  1. Una acción que vale la penaPublicar una oferta, cambiar el correo, aprobar una postulación, borrar algo.
  2. La sesión va sola en la requestCookies (o autenticación HTTP básica, o un certificado de cliente): algo que el navegador agrega sin que la página lo pida.
  3. Nada impredecible en la requestEl atacante puede escribir todos los parámetros de antemano.

Hoy, ese formulario contra tu sistema falla: requireAuth() exige el token en todo método que no sea GET, HEAD, OPTIONS o QUERY, y el formulario no puede ponerlo. Rompe la tercera condición. Vas a ver por qué funciona, dónde no llega, y qué capas le faltan.

76.2Por qué la cookie viaja sola

Una cookie es autoridad ambiental: no la presenta la página que hace la request, la agrega el navegador según el destino (74.4). El navegador no distingue entre "Carla hizo clic en Publicar" y "una página ajena envió un formulario": las dos requests van a tu sitio, y las dos llevan la cookie, salvo que SameSite diga lo contrario (74.6).

La Same-Origin Policy no ayuda aquí porque CSRF no necesita leer nada (74.3). El ataque es de solo escritura: el efecto ocurre en tu servidor cuando la request llega.

Definición

Request simple (75.2): GET, HEAD o POST con cabeceras de la lista segura y un Content-Type de formulario o texto. Son las que un formulario HTML ya podía mandar antes de CORS, y por eso salen sin preflight.

76.3Cuatro formas de disparar el ataque

  • Formulario POST. La forma clásica. Llega como navegación de nivel superior, con application/x-www-form-urlencoded. PHP llena $_POST igual que si lo mandara tu frontend.
  • GET con efecto. Si un GET cambia algo (?accion=borrar&id=7), alcanza con una etiqueta <img> o un enlace. HTTP define GET como un método seguro: no debe cambiar estado Documentado. Tu oportunidades.php lo respeta: GET solo lee.
  • fetch sin cors. Con mode: "no-cors" y text/plain, la request sigue siendo simple. El cuerpo puede ser un JSON; el atacante no lee la respuesta, pero no le hace falta.
  • Login CSRF. No usa la sesión de la víctima: le inyecta la del atacante (76.8).
// Desde otro sitio: el cuerpo parece JSON, pero el Content-Type es text/plain
fetch('https://api.practicas.edu.gt/v1/postulaciones', {
  method: 'POST', mode: 'no-cors', credentials: 'include',
  headers: { 'Content-Type': 'text/plain' },   // sigue siendo una request simple
  body: '{"oportunidad_id": 7}'
});

Este último caso es la razón de la regla "aceptar solo application/json" (76.8): si tu API exige ese Content-Type, un formulario no puede mandarlo, y un fetch que lo use dispara un preflight que tu política de CORS rechaza (75.3).

76.4SameSite: una capa con huecos conocidos

Con SameSite=Lax, la cookie no viaja en los formularios POST ni en las imágenes o fetch de otro sitio; sí viaja al seguir un enlace (GET de nivel superior). Con Strict tampoco viaja en el enlace. Chrome trata como Lax las cookies que no declaran el atributo desde 2020 Documentado, con una excepción temporal: durante sus primeros dos minutos, una cookie sin atributo sí viaja en un POST de nivel superior ("Lax+POST") Documentado. Por eso conviene declarar el atributo siempre.

Los huecos, en concreto:

  • Mismo sitio no es mismo origen. blog.practicas.edu.gt y api.practicas.edu.gt son el mismo sitio (74.2). Un XSS en el blog, o un subdominio olvidado que alguien tomó, manda formularios con la cookie incluida.
  • En el laboratorio, todo es el mismo sitio. localhost:5173 y localhost comparten sitio: SameSite no frena nada entre ellos. El sitio atacante de WEB00 usa otro host por eso.
  • GET con efecto. Lax deja pasar la navegación. Si un GET cambia algo, el ataque funciona.
  • Method override. Frameworks que aceptan _method=DELETE en un GET convierten la navegación en una escritura.
  • Navegadores y clientes que no lo aplican. Es una protección del navegador; no la exige el servidor.

SameSite es la primera capa, barata y amplia. No es la defensa principal: OWASP la recomienda como defensa en profundidad, junto a un token o a comprobar el origen Documentado.

76.5El token: algo que el atacante no puede leer ni fabricar

Un token anti-CSRF es un valor impredecible que la página legítima manda en cada escritura, normalmente en una cabecera, y que el servidor comprueba. El sitio atacante no lo conoce (no puede leer tu página, por la SOP) y no puede ponerlo en una cabecera de un formulario. Rompe la tercera condición de 76.1.

El token de tu sistema

Tu csrf.php usa el tercer patrón: el token no se guarda, se deriva de la cookie de sesión.

<?php
// api/core/csrf.php, tal como está en tu repositorio (leído el 2026-10-31)
function csrfToken(): string
{
    $cookie = (string)($_COOKIE[COOKIE_NAME] ?? '');
    return hash_hmac('sha256', 'csrf|' . $cookie, COOKIE_KEY);   // (1) (2)
}

function requireCsrfToken(): void
{
    $provided = (string)($_SERVER['HTTP_X_CSRF_TOKEN'] ?? '');     // (3)
    if ($provided === '' || !hash_equals(csrfToken(), $provided)) { // (4)
        header('Content-Type: application/json; charset=utf-8');
        Response::json(-1, 'La solicitud de seguridad expiró. …', [], 403);
    }
}
  1. Atado a la sesión. Cambia cuando cambia la cookie: un login nuevo da un token nuevo, y el token de otra persona no sirve con tu cookie.
  2. Separación de usos. El prefijo 'csrf|' hace que este HMAC no coincida con la firma de la cookie, aunque usen la misma COOKIE_KEY. Mejor todavía, una clave propia (CSRF_KEY), así una filtración de una no compromete la otra (M36).
  3. En una cabecera. Un formulario no puede poner cabeceras, y un fetch de otro origen con X-CSRF-Token dispara un preflight.
  4. Tiempo constante. hash_equals no corta en el primer byte distinto. El vacío se rechaza antes.

Es un buen diseño Diseño de referencia: no necesita estado en el servidor, y el atacante no puede fabricarlo sin la clave. Dos cosas a revisar. Primero, el token vive lo mismo que la cookie; si quieres que caduque antes, incluye una marca de tiempo en el HMAC. Segundo, nadie lo entrega: el comentario del GET de login.php dice que devuelve un csrfToken, pero la respuesta no lo trae, así que un frontend legítimo no tiene cómo mandarlo y todo POST con sesión responde 403.

<?php
// endpoints/login.php, GET: el comentario promete el token, la respuesta no lo trae
Response::success([
    'id'        => $auth_data['id'],
    'username'  => $auth_data['username'],
    'name'      => $auth_data['name'],
    'roles'     => $auth_data['roles'],
    'isAdmin'   => $auth_data['isAdmin'],
    'csrfToken' => csrfToken(),          // (5) lo que falta
]);
// El frontend guarda el token en memoria (no en localStorage) y lo manda en cada escritura
let csrf = null;
async function sesion() {
  const r = await fetch('/api/endpoints/login.php', { credentials: 'same-origin' });
  const j = await r.json();
  csrf = j.data?.csrfToken ?? null;
}
async function publicar(datos) {
  return fetch('/api/endpoints/oportunidades.php', {
    method: 'POST', credentials: 'same-origin',
    headers: { 'X-CSRF-Token': csrf },          // un formulario de otro sitio no puede poner esto
    body: new URLSearchParams(datos)
  });
}

Qué pasa si falla

Un token en la URL (?csrf=…) se filtra en el historial, en los registros del servidor y en la cabecera Referer. Un token en localStorage lo lee cualquier XSS, igual que el que está en memoria: un XSS se salta cualquier token, porque corre en tu origen y puede leer tu página (M77). El token frena a otro sitio, no a código que ya corre en el tuyo.

76.6Comprobar de dónde viene: Origin y Referer

El navegador agrega la cabecera Origin a todo POST, PUT, DELETE y a toda request CORS, y la página no la puede cambiar Documentado. Para frenar un CSRF, alcanza con exigir que sea uno de tus orígenes, en una lista exacta (los mismos de la política de CORS de 75.9).

<?php
// api/core/origen.php: rechaza lo que no viene de un origen propio
const ORIGENES_PROPIOS = ['https://app.practicas.edu.gt', 'http://localhost:5173'];

function requireOrigenPropio(): void
{
    $origin = $_SERVER['HTTP_ORIGIN'] ?? null;
    if ($origin === null) {                         // sin Origin: miramos Referer
        $ref = $_SERVER['HTTP_REFERER'] ?? '';
        $p = parse_url($ref);
        $origin = isset($p['scheme'], $p['host'])
            ? $p['scheme'] . '://' . $p['host'] . (isset($p['port']) ? ':' . $p['port'] : '')
            : null;
    }
    if ($origin === null || !in_array($origin, ORIGENES_PROPIOS, true)) {
        Response::json(-1, 'Origen no permitido', [], 403);   // "null" también cae aquí
    }
}
  • Origin null. Lo mandan los iframes con sandbox, las redirecciones entre orígenes y los documentos data:. Un atacante puede provocarlo a propósito: nunca va en la lista.
  • Sin Origin. Algunos navegadores viejos no lo mandan en ciertos POST. El respaldo es Referer; si tampoco está (una Referrer-Policy: no-referrer lo quita), decides: rechazar es más seguro, aceptar es más compatible.
  • Detrás de un proxy. Compara contra la lista, nunca contra Host o X-Forwarded-Host, que puede escribir el cliente.

76.7Fetch Metadata: el navegador dice la relación

Las cabeceras Fetch Metadata (Sec-Fetch-Site, Sec-Fetch-Mode, Sec-Fetch-Dest y Sec-Fetch-User) le dicen al servidor qué relación hay entre la página que manda y el destino, y qué tipo de request es Documentado. Las pone el navegador; ningún script las puede escribir, porque el prefijo Sec- está prohibido para fetch. Las mandan Chrome, Edge, Firefox y Safari Documentado.

Con ellas se arma una política de aislamiento de recursos: todo lo que viene de otro sitio se rechaza, salvo una navegación GET de nivel superior (alguien siguió un enlace a tu página).

<?php
// api/core/fetch-metadata.php: política de aislamiento de recursos
function requireFetchMetadata(): void
{
    $site = $_SERVER['HTTP_SEC_FETCH_SITE'] ?? null;
    if ($site === null) return;                                     // navegador viejo o curl
    if (in_array($site, ['same-origin', 'same-site', 'none'], true)) return;

    $mode = $_SERVER['HTTP_SEC_FETCH_MODE'] ?? '';
    $dest = $_SERVER['HTTP_SEC_FETCH_DEST'] ?? '';
    $esNavegacion = $mode === 'navigate' && $_SERVER['REQUEST_METHOD'] === 'GET'
                    && in_array($dest, ['document', 'empty'], true);
    if ($esNavegacion) return;                                      // seguir un enlace

    Response::json(-1, 'Request de otro sitio rechazada', [], 403);
}

Trade-off

La política deja pasar same-site, así que no frena al subdominio comprometido de 76.4. Si ningún otro subdominio necesita llamar a tu API, exige same-origin en las escrituras. Si tu frontend y tu API son orígenes distintos del mismo sitio, same-site es justo lo que necesitas dejar pasar, y la diferencia la hace el Origin exacto.

76.8Las capas juntas: qué frena cada una

Ninguna capa frena las cinco formas sola. Enciende y apaga las defensas, y mira qué ataques siguen pasando contra la API del sistema de prácticas.

Login CSRF

El login CSRF invierte el ataque: el atacante no usa tu sesión, te da la suya. Un formulario manda su usuario y su contraseña a tu login, y el navegador de la víctima queda dentro de la cuenta del atacante. Lo que la víctima haga después (subir su CV, escribir su carta de presentación, guardar su teléfono) queda donde el atacante lo lee.

<?php
// endpoints/login.php, POST: antes de buscar al usuario
requireFetchMetadata();      // un formulario de otro sitio llega cross-site
requireOrigenPropio();       // y con un Origin ajeno: 403, sin tocar la base

Con un token sincronizador, la alternativa es una sesión previa al login con su propio token; al iniciar sesión se reemplaza la sesión entera, que además evita la fijación de sesión (M81).

JSON y el Content-Type

"Mi API recibe JSON, así que no hay CSRF" es cierto solo si el servidor rechaza cualquier otro Content-Type. PHP no lo hace por ti: json_decode(file_get_contents('php://input')) decodifica igual un cuerpo que llegó como text/plain. Exígelo:

<?php
$ct = $_SERVER['CONTENT_TYPE'] ?? '';
if (!str_starts_with(strtolower($ct), 'application/json')) {
    Response::json(-1, 'Content-Type no soportado', [], 415);
}

Tu API hoy recibe formularios ($_POST y parse_str para PUT y DELETE), así que esta regla no aplica: la defensa es el token.

76.9La defensa completa en PHP

El orden dentro del middleware, del control más barato al más caro Diseño de referencia:

<?php
// api/core/auth-middleware.php: el orden de las capas (referencia)
function requireAuth(int|array $roles = [])
{
    $method = strtoupper($_SERVER['REQUEST_METHOD'] ?? 'GET');
    $cambia = !in_array($method, ['GET', 'HEAD', 'OPTIONS'], true);

    requireFetchMetadata();              // 1. barato y sin estado: corta lo de otro sitio
    if ($cambia) requireOrigenPropio();  // 2. Origin exacto en todo lo que escribe

    $data = checkAuth();                 // 3. la sesión
    if ($data === null) Response::json(-2, 'Usuario no autenticado', [], 401);

    if ($cambia) requireCsrfToken();     // 4. el token, atado a esa sesión
    // … después, el rol y el dueño del recurso (M80)
    return $data;
}

En producción real

Prueba con DevTools, en la pestaña Network: dispara el formulario desde el segundo origen y mira las cabeceras de la request (Origin, Sec-Fetch-Site, Cookie) y el código de respuesta. Si el efecto ocurrió (la fila apareció en la base) con un código de error, el chequeo está después del modelo y no antes. Que el atacante no pueda leer tu página es lo que sostiene el token; si puede ejecutar código en ella, no queda defensa: es XSS (M77).
