Control de acceso roto

El navegador no te protege aquí. CORS, SameSite y la CSP deciden qué puede hacer otro sitio; el control de acceso decide qué puede hacer tu propio usuario, con su sesión válida, mandando requests a mano. Y esa pregunta solo la puede contestar el servidor.

Al terminar podrás

  • Separar las tres preguntas del control de acceso (sesión, función y objeto) y nombrar la falla de cada una.
  • Reconocer BOLA, BFLA y asignación masiva en el sistema de prácticas, y arreglarlas en el lugar correcto.
  • Escribir una política central que niega por defecto, y consultas que llevan el dueño en el WHERE.
  • Elegir entre 403 y 404, y saber por qué un id difícil de adivinar no es un control.
  • Probar el control de acceso con una matriz de persona por acción, y cerrar el path traversal al servir archivos.

Todo lo de M74 a M78 protege a tu usuario de otro sitio. Este módulo es distinto: el atacante es un usuario legítimo de tu sistema, con su sesión, su cookie y su token CSRF, que abre las herramientas del navegador o curl y cambia un número. El navegador no tiene nada que decir, porque la request es del mismo origen y la manda quien tiene permiso de mandarla. El control de acceso roto encabeza el OWASP Top 10 de 2021 Documentado, y en M10 viste su versión de API en dos párrafos.

80.1Las tres preguntas

Analogía

Es un hotel. La recepción comprueba que eres huésped (la sesión). La tarjeta abre el gimnasio pero no la cocina (la función). Y abre tu habitación, no la del vecino, aunque sea del mismo piso y el mismo tipo (el objeto). Un hotel que solo comprueba lo primero deja a cualquier huésped entrar a cualquier habitación.

La autenticación responde la primera pregunta (M81). La autorización, las otras dos, y es donde fallan la mayoría de las APIs: comprueban que hay sesión y suponen que quien tiene sesión solo pedirá lo suyo. El control de acceso roto es responder mal o no responder alguna de las tres.

80.2Tu API hoy

Antes de los ataques, el estado real. Leído del código del proyecto:

  • Ocho endpoints sin requireAuth. usuarios.php lista los usuarios con sus correos para cualquiera, sin sesión. asignaciones_roles.php permite asignar roles. Es la falla más grave del proyecto y la más fácil de cerrar.
  • oportunidades.php pide rol de reclutador para escribir, pero el UPDATE busca solo por id: cualquier reclutador edita la oportunidad de otro.
  • postulaciones.php toma estudiante_id del body al crear, y busca por id al leer.

80.3BOLA: el objeto de otro

BOLA (Broken Object Level Authorization), también llamada IDOR (Insecure Direct Object Reference), es la falla de la tercera pregunta: el usuario tiene permiso para la función, pero no para ese objeto, y la API no lo comprueba. Es la primera del OWASP API Security Top 10 de 2023 Documentado.

<?php
// models/postulaciones.php: el dueño va en la consulta, no en un if después
public function findByIdPara(int $id, array $sesion): void
{
    $stmt = $this->connection->prepare(
        "SELECT p.id, p.estado_postulacion, p.cv_url, p.fecha_postulacion, o.titulo
           FROM postulaciones p
           JOIN oportunidades o ON o.id = p.oportunidad_id
          WHERE p.id = ? AND p.estado = 1
            AND (p.estudiante_id = ? OR o.creado_por = ? OR ? = 1)");   // alumno, reclutador, admin
    $stmt->execute([$id, $sesion['id'], $sesion['id'], (int)$sesion['isAdmin']]);
    $fila = $stmt->fetch(PDO::FETCH_ASSOC);
    if (!$fila) {
        Response::json(-1, 'No encontrada', [], 404);              // igual si no existe o no es tuya
    }
    $this->response->success($fila);
}
  • El dueño en el WHERE, no en un if después. Un if que compara después de leer se olvida en el siguiente endpoint; una consulta que solo puede devolver lo tuyo, no. Y en las listas (findAll) es la única forma de que no salgan filas de otros.
  • 404, no 403. Si la respuesta dice "existe, pero no es tuya", el atacante aprende qué ids existen. Para un objeto que no te corresponde, la API responde lo mismo que si no existiera.
  • Un id aleatorio no es un control. Un UUID en lugar de 101 hace más difícil adivinar, pero los ids se filtran (en URLs compartidas, en logs, en el Referer) y entonces no queda nada. Los UUID son útiles, como capa extra; la comprobación del dueño es obligatoria.
<?php
// models/oportunidades.php: hoy WHERE id = ? AND estado = 1 deja a Diego editar la 7 de Carla
$query = "UPDATE oportunidades
             SET titulo = ?, descripcion = ?, requisitos = ?, modalidad = ?, ubicacion = ?, fecha_cierre = ?
           WHERE id = ? AND estado = 1 AND (creado_por = ? OR ? = 1)";
$stmt = $this->connection->prepare($query);
$stmt->execute([...$campos, $id, $sesion['id'], (int)$sesion['isAdmin']]);
if ($stmt->rowCount() === 0) {
    Response::json(-1, 'No encontrada', [], 404);
}

80.4BFLA: la función de otro rol

BFLA (Broken Function Level Authorization) es la falla de la segunda pregunta: un estudiante llama a una función de administración porque la API solo comprueba que hay sesión, o porque el frontend esconde el botón y nadie pensó en la request. Es la quinta del Top 10 de APIs Documentado.

La defensa es una política central que niega por defecto: una tabla que dice, por endpoint y por método, qué roles pueden usarlo. Lo que no está en la tabla, se rechaza. Así, un endpoint nuevo sin política queda cerrado, no abierto.

<?php
// core/politica.php: una tabla por endpoint; lo que no está, se niega
const POLITICA = [
    'postulaciones' => [
        'GET'    => [ROL_ESTUDIANTE, ROL_RECLUTADOR, ROL_ADMIN],   // y el modelo filtra por dueño
        'POST'   => [ROL_ESTUDIANTE],
        'PUT'    => [ROL_RECLUTADOR, ROL_ADMIN],                   // cambiar estado
        'DELETE' => [ROL_ESTUDIANTE],                              // retirar la propia
    ],
    'usuarios' => ['GET' => [ROL_ADMIN], 'PUT' => [ROL_ADMIN]],
    'roles'    => ['GET' => [ROL_ADMIN]],
];

function autorizar(string $endpoint): array
{
    $metodo = $_SERVER['REQUEST_METHOD'];
    $roles  = POLITICA[$endpoint][$metodo] ?? null;
    if ($roles === null) {                                         // denegar por defecto
        Response::json(-1, 'Método no permitido', [], 405);
    }
    return requireAuth($roles);                                    // sesión, CSRF y rol (M76)
}

Trade-off

Tu requireAuth deja pasar a isAdmin por encima de la lista de roles. Es cómodo y es un riesgo: cualquier error que ponga isAdmin en verdadero (una asignación masiva, un bug en el login) abre todo. Las funciones peligrosas (asignar roles, borrar usuarios) pueden pedir además una reautenticación (M81) y quedar en el log de auditoría con quién lo hizo.

80.5Asignación masiva: los campos de más

La asignación masiva pasa cuando el código copia los campos del body al modelo sin una lista. El atacante agrega campos que el formulario no tiene: rol_id, isAdmin, estudiante_id, estado_postulacion. El Top 10 de APIs de 2023 la agrupa con la exposición de datos de más en "autorización por propiedad" Documentado: qué campos puedes escribir y qué campos te devuelve la respuesta.

<?php
// endpoints/postulaciones.php POST: hoy estudiante_id sale del body
$sesion = autorizar('postulaciones');
$datos = [
    'oportunidad_id' => (int)($_POST['oportunidad_id'] ?? 0),
    'estudiante_id'  => (int)$sesion['id'],          // de la sesión, nunca del body
    'cv_url'         => $_POST['cv_url'] ?? '',      // se valida en M82
];

// endpoints/usuarios.php PUT: una lista de campos por rol
const CAMPOS_EDITABLES = [
    'propio' => ['nombre', 'apellido', 'telefono'],
    'admin'  => ['nombre', 'apellido', 'telefono', 'rol_id', 'estado_cuenta'],
];
$permitidos = $sesion['isAdmin'] ? CAMPOS_EDITABLES['admin'] : CAMPOS_EDITABLES['propio'];
$extra = array_diff(array_keys($_PUT), [...$permitidos, 'id']);
if ($extra) {
    Response::json(-1, 'Campos no permitidos: ' . implode(', ', $extra), [], 400);
}

La otra mitad es la salida: findAll de usuarios devuelve cada columna, y el frontend muestra tres. Las respuestas también llevan una lista de campos por rol, porque un dato que viaja en el JSON ya se filtró, aunque la pantalla no lo muestre.

80.6Prueba las cuatro comprobaciones

Seis personas, cinco acciones y cuatro comprobaciones que puedes prender y apagar. El botón "lo que hace tu código hoy" pone las que tiene cada endpoint en el proyecto.

80.7Dónde va cada comprobación

  • Middleware: la política por método de 80.4, en la primera línea de cada endpoint.
  • Modelo: cada método recibe la sesión y la usa en el WHERE. Un método sin sesión (findById(int $id)) es una invitación a usarlo mal; renómbralo o quítalo.
  • Base: en M35 viste RLS y vistas por usuario. En MariaDB no hay RLS; un usuario de base para la API con permisos solo sobre las tablas que usa, sin DROP ni GRANT, limita lo que hace una inyección.

Y la prueba: una matriz de persona por acción con el resultado esperado, que corre en el CI de M55 y falla si un endpoint nuevo responde 200 donde debía responder 404.

<?php
// tests/AccesoTest.php (PHPUnit): la matriz como datos; cada fila es un caso
public static function matriz(): array
{
    return [
        //  persona      método  ruta                              esperado
        ['anonimo',    'GET',  'postulaciones.php?id=101',        401],
        ['beto',       'GET',  'postulaciones.php?id=101',        404],   // BOLA
        ['ana',        'GET',  'postulaciones.php?id=101',        200],
        ['diego',      'PUT',  'oportunidades.php?id=7',          404],   // BOLA en escritura
        ['carla',      'PUT',  'oportunidades.php?id=7',          200],
        ['ana',        'GET',  'usuarios.php',                    403],   // BFLA
        ['ana',        'PUT',  'usuarios.php?id=12&rol_id=1',     400],   // asignación masiva
    ];
}

80.8Path traversal: el archivo de otro

El path traversal es la misma falla con archivos: la ruta sale de la request y ../ la saca de la carpeta permitida. Lo viste como caso en M55; aquí aparece al servir los CVs, que hoy son una URL en cv_url y en la guía WEB08 pasan a ser archivos subidos (M82).

<?php
// endpoints/cv.php: descargar el CV de una postulación
$sesion = autorizar('cv');
$fila = $postulaciones->cvPara((int)($_GET['postulacion'] ?? 0), $sesion);   // dueño en el WHERE
$base = realpath(__DIR__ . '/../../storage/cvs');
$real = realpath($base . '/' . $fila['archivo']);                           // el nombre lo dio la base
if ($real === false || !str_starts_with($real, $base . DIRECTORY_SEPARATOR)) {
    Response::json(-1, 'No encontrado', [], 404);
}
header('Content-Type: application/pdf');
header('Content-Disposition: attachment; filename="cv.pdf"');
header('X-Content-Type-Options: nosniff');
readfile($real);

El orden importa: primero el control de acceso (la postulación es tuya), después la ruta. Comprobar solo la ruta deja descargar cualquier CV de la carpeta, que es un BOLA con archivos.

En producción real

El control de acceso no se encuentra con escáneres: un DAST no sabe que la postulación 101 no es de Beto. Se encuentra con la matriz, con revisión de código buscando consultas por id sin sesión (grep -rn "WHERE id = ?" api/models/) y con pruebas manuales con dos cuentas del mismo rol. La guía WEB06 pone autorizar() en los once endpoints, el dueño en cada consulta y la matriz en PHPUnit. Con quién eres respondido por la sesión, falta ver qué tan buena es esa sesión: M81.
