Anatomía de un harness

El harness de 40 líneas de M62 funciona y se rompe en la primera tarea seria: reescribe archivos enteros, se ahoga con la salida de un build, se olvida del plan y no sabe nada de tu proyecto. Cada pieza de un harness de verdad es la respuesta a una de esas fallas.

64.1Las piezas de un harness

En M62.6 escribiste un harness en 40 líneas y viste una tabla: cada falla del harness mínimo y lo que agregan los de verdad. Este módulo abre esa tabla. Todas las piezas giran alrededor del mismo bucle (M25.2) y de las llamadas que viste por dentro en M63.

Analogía

Un cirujano muy bueno que entra a un quirófano que no conoce. El talento es el modelo. El harness es todo lo demás: la ficha del paciente que le dan al entrar (memoria), el instrumental a mano y bien ordenado (herramientas), la enfermera que pregunta antes de cortar (permisos), la lista de pasos en la pared (tareas) y alguien que anota todo lo que pasa (sesión).

  1. Ensamblador del promptArma el system por capas en cada request, en un orden que se puede cachear. 64.2
  2. Archivos de memoriaLo que el proyecto le cuenta al agente al empezar: comandos, reglas, trampas. 64.9
  3. Registro de herramientasLeer, editar, buscar, ejecutar: qué existe y cómo está descrito. 64.3
  4. PermisosQué se hace solo, qué se pregunta y qué no se hace nunca; a fondo en M66. M62.10
  5. Gestor de contextoRecorta resultados, compacta la conversación y marca el prefijo cacheable. 64.8
  6. Tareas y subagentesUn plan que no se olvida y un contexto aparte para explorar. 64.7
  7. Sesión en discoEl transcript para reanudar, retroceder y auditar. 64.11
  8. InterfazTerminal, IDE o modo headless: el mismo núcleo con otra cara. M69.2
  9. BucleLlamar al modelo, ejecutar lo que pidió, repetir hasta que termine o se acabe el presupuesto. M63.9

64.2El system prompt por capas

El system prompt de un harness no es un párrafo: es un documento que se arma en cada request a partir de varias fuentes. En el de Claude Code, por ejemplo, entran las reglas del harness, las definiciones de herramientas, datos del entorno (sistema operativo, directorio de trabajo, si es un repositorio de git), los archivos de memoria y la lista de skills y servidores MCP disponibles Documentado. Lo que no entra en el system llega como mensajes, incluidos recordatorios que el harness intercala durante la sesión.

Dos reglas salen de la figura:

  • Lo estable primero. El prompt caching (M16) guarda el prefijo: todo lo que está antes del primer byte que cambia. Si la fecha y la hora con segundos estuvieran en la primera línea, ninguna request compartiría caché. Por eso los harnesses ponen lo variable al final, y por eso cambiar una herramienta o editar el CLAUDE.md a mitad de sesión hace que el turno siguiente se pague entero.
  • Lo importante, cerca del final. Un modelo atiende peor lo que está en el medio de un contexto largo (lost in the middle, M16). Los harnesses repiten lo crítico cerca del final con recordatorios cortos: "hay una lista de tareas abierta", "este archivo cambió desde que lo leíste".

64.3Las herramientas de un agente de código

Con bash solo, un modelo puede hacer todo: leer con cat, editar con sed, buscar con grep. Los harnesses igual definen herramientas dedicadas, por tres razones: el resultado es predecible (un formato fijo que el modelo aprende), el permiso es fino (leer se aprueba solo, ejecutar se pregunta) y el harness puede validar antes de actuar (la edición falla si el texto no coincide). Las de Claude Code son un buen catálogo Documentado:

HerramientaQué haceLa decisión de diseño
ReadLee un archivo con números de línea, por tramos con offset y limitLos números de línea permiten citar y ubicar; los tramos evitan meter un archivo de 20 000 líneas
EditReemplaza un fragmento exacto por otroEl modelo escribe solo lo que cambia, y la herramienta falla si el fragmento no es único
WriteCrea o reemplaza un archivo enteroPara archivos nuevos; sobre uno existente, exige haberlo leído antes
Glob, GrepBuscar archivos por patrón y contenido (Grep usa ripgrep)Búsqueda exacta y barata, sin índice
BashEjecuta un comando con timeoutTodo lo que no tiene herramienta propia; se recorta la salida
TodoWriteEscribe y actualiza una lista de tareasEl plan como estado visible, no como recuerdo
Task (subagentes)Lanza otro agente con contexto propioExplorar sin ensuciar el contexto principal

Así se ve un Read por dentro: el formato de cat -n, con el número de línea y una tabulación antes de cada línea Documentado.

     1	def precio(item):
     2	    if item is None:
     3	        return None
     4	    return item.precio * 1.21

El número de línea no es para el humano: sirve para que el modelo pueda decir "en la línea 4" y para que el harness detecte cuando el modelo, al editar, copia el número por error junto con el código. Las tres herramientas que más deciden cómo trabaja un agente son las de editar, buscar y ejecutar.

64.4Editar: reescribir, reemplazar o parchear

Reemplazo exacto. La herramienta recibe old_string y new_string, busca el viejo en el archivo y lo cambia. Falla en tres casos, y los tres son a propósito: si no aparece (el modelo recordó mal el código), si aparece más de una vez (no se sabe cuál cambiar) y si el archivo cambió desde la última lectura (el modelo trabaja sobre una versión vieja). El error vuelve al modelo, que relee y reintenta. Es la edición por reemplazo exacto que usan Claude Code y OpenCode, y la de str_replace en la herramienta de editor de texto de Anthropic Documentado.

Parche. Codex CLI edita con apply_patch, un formato de diff propio que los modelos de OpenAI aprendieron en el entrenamiento: encabezados por archivo, una línea @@ con contexto y líneas con - y + Documentado. Un parche puede tocar varios archivos de una vez, crear y borrar.

*** Begin Patch
*** Update File: src/precios.py
@@ def precio(item):
     if item is None:
         return None
-    return item.precio * 1.21
+    return round(item.precio * 1.21, 2)
*** End Patch

Varios formatos, elegidos por modelo. Aider soporta archivos enteros (whole), bloques SEARCH/REPLACE (diff) y diffs unificados (udiff), y elige el formato según el modelo con los resultados de su propio benchmark de edición: un mismo modelo puede rendir bastante distinto según el formato Documentado.

src/precios.py
<<<<<<< SEARCH
    return item.precio * 1.21
=======
    return round(item.precio * 1.21, 2)
>>>>>>> REPLACE

Trade-off

Reescribir el archivo entero es lo que mejor sale con modelos chicos (no hay formato que romper) y lo peor con archivos largos: 400 líneas de salida para cambiar una, que cuestan tiempo y tokens de salida (los más caros) y pueden perder una línea sin que nadie lo note. El reemplazo exacto es el término medio para la mayoría; el parche gana cuando un cambio toca muchos archivos a la vez y el modelo fue entrenado con ese formato. La lección de M63.11 se repite: el mejor formato es el que el modelo practicó.

64.5Buscar: grep contra un índice

Para editar, primero hay que encontrar. Hay dos familias de respuesta, y los harnesses populares eligieron distinto.

La búsqueda agéntica es la que hace el agente con glob, grep y read, refinando en cada vuelta como lo harías tú en una terminal. Claude Code trabaja así, sin un índice de embeddings del repositorio Documentado. Cursor, en cambio, indexa el código con embeddings para la búsqueda semántica, y también tiene grep Documentado. Aider usa un tercer camino: un repo map, un resumen de las definiciones del repositorio extraídas con tree-sitter y ordenadas por cuánto se usan, que entra al contexto como un mapa Documentado.

Grep y globÍndice de embeddingsRepo map
FrescuraSiempre el código de ahoraLo que había al indexarSe recalcula al cambiar
Encuentra verifyTokenExactoPuede traer algo parecidoSi es una definición
Encuentra "dónde se valida la sesión"Si el modelo adivina las palabrasBienPor los nombres
CostoTurnos del modeloIndexar y un servicioTokens del mapa en cada request
PrivacidadNada sale de la máquina salvo lo leídoLos embeddings se calculan en algún ladoLocal

Con un modelo bueno usando herramientas, la búsqueda agéntica rinde muy bien en repositorios medianos y no tiene nada que se desactualice. En un monorepo de millones de líneas, un índice o un mapa ahorra muchas vueltas. Lo que RAG sobre documentos es y cuándo conviene está en M16; la comparación a fondo de cómo entra el contexto es M68.

64.6Ejecutar: timeout, recorte y nada interactivo

La herramienta de comandos es la más poderosa y la que más formas tiene de fallar. Las decisiones que la vuelven usable:

import subprocess

def bash(cmd: str, timeout_s: int = 120, cabeza: int = 50, cola: int = 50) -> str:
    try:
        p = subprocess.run(cmd, shell=True, capture_output=True, text=True,
                           timeout=timeout_s, stdin=subprocess.DEVNULL)    # (1) sin stdin
    except subprocess.TimeoutExpired:
        return f"Error: el comando superó {timeout_s} s y se detuvo."      # (2) el modelo decide qué hacer
    lineas = (p.stdout + p.stderr).splitlines()
    if len(lineas) > cabeza + cola:                                        # (3) cabeza y cola
        omitidas = len(lineas) - cabeza - cola
        lineas = lineas[:cabeza] + [f"[… {omitidas} líneas omitidas …]"] + lineas[-cola:]
    return "\n".join(lineas) + f"\n(exit code {p.returncode})"             # (4) el código, siempre
  1. Sin entrada estándar. Un comando que espera una respuesta (npm init, un git rebase -i, una confirmación) se cuelga para siempre; sin stdin falla enseguida.
  2. Timeout con mensaje claro. En Claude Code el valor por defecto es de 2 minutos y se configura (BASH_DEFAULT_TIMEOUT_MS, BASH_MAX_TIMEOUT_MS) Documentado. Un servidor de desarrollo no termina nunca: va en segundo plano, no en esta herramienta.
  3. Cabeza y cola. El error de un build suele estar al final y el contexto, al principio.
  4. El exit code, siempre. Es la señal más confiable de si algo funcionó.

Hay una decisión más, menos visible: si cada comando corre en un proceso nuevo o en una shell que persiste. Con una shell persistente, un cd o un export sigue valiendo en el comando siguiente, como en tu terminal; con procesos nuevos, cada comando empieza limpio y el modelo tiene que repetir el contexto. Claude Code conserva el directorio de trabajo entre comandos, pero no las variables de entorno ni la shell Documentado.

64.7La lista de tareas

En una tarea de 80 turnos, el plan del turno 3 queda enterrado bajo 70 resultados de herramientas. Un modelo que no lo ve, lo olvida: arregla el bug, se distrae con un warning y termina sin agregar el test que había prometido. La solución de los harnesses es convertir el plan en estado: una herramienta como TodoWrite con la que el modelo escribe la lista, y que el harness vuelve a poner delante en cada turno.

Es la misma idea que el estado explícito de LangGraph en IA00: lo que importa para seguir no puede vivir solo en la memoria implícita de una conversación larga. Y sirve para la persona: ver la lista avanzar es la forma más barata de saber si el agente va por buen camino o hay que frenarlo.

64.8Gestionar el contexto

Cada turno reenvía todo lo anterior (M62.5). La ventana tiene un tope y la factura crece con cada vuelta. Un harness tiene tres herramientas para eso, y las usa en este orden:

  1. Recortar en la entradaNingún resultado entra entero si es grande: lectura por tramos, salida de comandos con cabeza y cola, búsquedas con un máximo de resultados.
  2. Cachear el prefijoMarcar dónde termina la parte estable para que el proveedor no la vuelva a procesar. La lectura de caché cuesta un décimo del precio de entrada en Anthropic, y escribirla, 1.25 veces Documentado.
  3. CompactarCuando la conversación se acerca al límite, resumirla y seguir con el resumen en lugar del historial. Claude Code lo hace solo al acercarse al tope, y con /compact se puede pedir antes, con instrucciones de qué conservar Documentado.

La compactación (M25.7) tiene un costo doble que conviene ver con números: pierde detalles (el nombre exacto de un archivo, un error que ya se probó) y tira la caché de todo lo que venía después del prefijo fijo. Mueve los escenarios:

El escenario "Muchos servidores MCP" muestra el problema que menos se ve: 40 000 tokens de definiciones de herramientas son un 20 % de una ventana de 200 000 ocupado antes de empezar, pagado en cada turno, y una compactación que llega antes. Por eso los harnesses cargan herramientas bajo demanda (M67). Qué se pone en la ventana, en qué orden y qué se pierde al compactar, a fondo, es M68.

64.9Archivos de memoria

Un agente empieza cada sesión sin saber nada de tu proyecto: ni cómo se corren las pruebas, ni que los precios se guardan en centavos, ni que la carpeta de migraciones no se toca. Un archivo de memoria es un Markdown que el harness lee al empezar y pone en el system prompt. Claude Code lee CLAUDE.md; Codex CLI, OpenCode, Cursor y otros leen AGENTS.md, un formato abierto pensado para eso Documentado.

# CLAUDE.md

## Comandos
- Pruebas: `pnpm test -- --run` (no uses `pnpm test` solo: queda en modo watch)
- Lint: `pnpm lint --fix`

## Reglas
- Los precios se guardan en centavos (enteros), nunca en float.
- No toques `migrations/`: las migraciones se generan con `pnpm db:gen`.
- Antes de terminar, corre las pruebas del paquete que cambiaste.

@docs/arquitectura.md

Lo que funciona en un archivo de memoria es lo que un colega nuevo necesitaría en su primer día y no puede deducir leyendo el código: comandos exactos (con la trampa del modo watch), reglas que no se ven (centavos), lugares prohibidos y cómo saber que terminó. Lo que no funciona: descripciones largas del código, que el agente puede leer solo y que cuestan tokens en cada request. La línea @docs/arquitectura.md importa otro archivo Documentado; un import es cómodo y es tamaño, así que conviene que lo importado sea corto.

En producción real

Un ejemplo a mano: el CLAUDE.md de este mismo curso tiene las reglas de cada tipo de página, la tabla de widgets y los comandos de prueba. Funciona porque son cosas que no se deducen del código (que no se usa fetch para que todo ande con file://, que los colores van siempre con tokens). Un archivo de memoria es también una superficie de ataque: lo escribe quien controla el repositorio, y un harness que lo carga sin preguntar ejecuta las instrucciones de un tercero si clonaste algo ajeno. Por eso claude --bare no lo carga (M69.2).

64.10Subagentes

Un subagente (M25.3) es otra sesión de agente que el principal lanza con una tarea en texto. Tiene su propio contexto, sus herramientas (a veces menos) y devuelve un resumen. El beneficio es de contexto: la exploración que llena 80 000 tokens queda del otro lado.

Conviene un subagenteNo conviene
Explorar mucho para responder poco: "¿dónde se valida la sesión?"Una edición que necesita todo lo que el principal ya sabe
Trabajos independientes en paralelo: revisar tres módulosPasos que dependen uno del otro
Una revisión con otro punto de vista, sin el sesgo de lo ya hechoTareas cortas: el arranque cuesta su system prompt entero

El costo está en lo que se pierde al resumir: si el subagente encontró tres lugares y el resumen nombra dos, el principal nunca sabrá del tercero. Un subagente bien usado devuelve un resultado con forma (rutas, líneas, conclusión), no una narración. Es la misma idea que el esquema común de los orquestadores (M69.8), en pequeño.

64.11La sesión: reanudar, retroceder y auditar

Todo lo que pasa en una sesión se guarda en disco: los mensajes, las llamadas y sus resultados. En Claude Code, como un transcript por sesión que se retoma con --resume o --continue; Codex CLI y OpenCode hacen lo mismo con sus propios formatos Documentado. Eso da tres capacidades:

  • Reanudar: cerrar la terminal no pierde el trabajo. Es lo que usan los orquestadores con el session_id (M69.2).
  • Retroceder: volver a un punto anterior de la conversación y de los archivos. Claude Code guarda checkpoints de las ediciones que hace y permite volver con /rewind Documentado. No cubre lo que hizo un comando de bash (una migración, un rm): para eso está git, y la buena práctica es que el agente trabaje sobre una rama o un worktree.
  • Auditar: qué leyó, qué ejecutó y por qué. Es la materia prima de los evals de trayectoria de M72.

En producción real

Construir un harness propio es la mejor forma de entender estas decisiones y, para casi todos los equipos, la peor forma de tener uno: los harnesses maduros acumulan cientos de arreglos a fallas como las de esta tabla.
