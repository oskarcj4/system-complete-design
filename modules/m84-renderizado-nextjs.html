Modelos de renderizado: PHP, SPA y Next.js

Cambiar de framework no cambia las preguntas de seguridad: qué se ve, qué viaja, qué se ejecuta y quién lo autoriza. Cambia dónde está cada respuesta, y en Next.js la línea entre servidor y navegador pasa por dentro del mismo archivo.

La pregunta que abrió la Parte IX en M73 fue dónde corre cada línea de código, porque de eso depende quién la controla. En PHP clásico la respuesta es fácil; en el sistema de prácticas, que es una SPA que pide JSON a una API en PHP, ya hay dos lugares; en Next.js, los dos lugares conviven en el mismo archivo. Este módulo recorre los tres modelos y vuelve a las mismas cuatro preguntas: qué se ve, qué viaja, qué se ejecuta y quién lo autoriza.

84.1Tres formas de armar una página

El renderizado es convertir datos en el HTML que el usuario ve. Lo que cambia entre modelos es quién lo hace y cuándo:

  • PHP clásico (una página por request, a veces llamado MPA): el servidor arma la página entera y el navegador la muestra.
  • SPA (single-page application): el servidor manda un HTML casi vacío y un bundle de JavaScript, y el navegador pide los datos a una API y arma el DOM. Es el sistema de prácticas.
  • SSR (server-side rendering) con hidratación: el servidor arma el HTML con los datos, como PHP, y además manda el JavaScript; el navegador muestra el HTML de inmediato y después lo "hidrata": conecta los eventos para que responda a los clics como una SPA.

Analogía

PHP clásico es un restaurante que sirve el plato armado. La SPA te da los ingredientes y la receta, y cocinas en tu mesa. SSR te sirve el plato armado y además te deja la receta para que puedas seguir cocinando. En los tres, la cocina decide qué ingredientes te da: nadie confía en que el cliente no los cambie.

// app.js del sistema de prácticas: una SPA que pide JSON y arma el DOM
const r = await fetch('api/endpoints/oportunidades.php', { credentials: 'same-origin' });
const { data } = await r.json();              // la API autoriza; este código no
for (const o of data) {
  const li = document.createElement('li');
  li.textContent = o.titulo;                  // el escape es tuyo (M77)
  feed.append(li);
}

En la SPA del proyecto, la API en PHP es la única barrera: el app.js lo puede leer y cambiar cualquiera, y la API se puede llamar sin él (M80). El escape, en cambio, ya no lo hace htmlspecialchars sino el JavaScript que arma el DOM, con textContent (M77).

84.2El estado que viaja dentro del HTML

Para hidratar, el JavaScript del cliente necesita los mismos datos con los que el servidor armó el HTML. Los frameworks los dejan dentro de la página, en un <script> con JSON (Next.js manda el payload de React Server Components en scripts como self.__next_f.push(…)) Documentado. Ese script es un contexto de salida nuevo, y es el más traicionero de M77: dentro de una cadena de JSON, el parser de HTML sigue buscando </script>.

Next.js y React escapan el < dentro de ese JSON. El riesgo aparece cuando lo haces tú: un <script> con JSON.stringify armado a mano en un layout, o PHP que deja datos para el frontend.

<?php
// Si PHP deja datos para el JavaScript dentro de la página, escapa también '<'
$json = json_encode($oportunidades,
    JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_THROW_ON_ERROR);
?>
<script nonce="<?= $nonce ?>">window.__DATOS__ = <?= $json ?>;</script>

JSON_HEX_TAG convierte < y > en \u003C y \u003E, que el JavaScript lee igual y el parser de HTML no ve como etiqueta Documentado. El nonce es el de la CSP de M78.

84.3Server Components y la frontera 'use client'

En el App Router de Next.js, cada componente es un Server Component salvo que su archivo empiece con 'use client' Documentado. Un Server Component corre solo en el servidor: puede leer la base y usar secretos, y su código nunca llega al navegador. Un Client Component corre en el servidor para el primer HTML y también en el navegador, así que su código está en el bundle.

// app/oportunidades/[id]/page.tsx: Server Component, corre solo en el servidor
import { obtenerOportunidad } from '@/datos/oportunidades';   // import 'server-only' adentro
import { BotonPostular } from './boton-postular';

export default async function Pagina({ params }) {
  const { id } = await params;
  const o = await obtenerOportunidad(Number(id));              // autoriza y lee la base
  return (
    <article>
      <h1>{o.titulo}</h1>                                       {/* React escapa */}
      <BotonPostular oportunidadId={o.id} yaPostulado={o.yaPostulado} />
    </article>
  );
}
// app/oportunidades/[id]/boton-postular.tsx: Client Component
'use client';
import { postular } from './acciones';

export function BotonPostular({ oportunidadId, yaPostulado }) {
  return (
    <form action={postular}>
      <input type="hidden" name="oportunidadId" value={oportunidadId} />
      <button disabled={yaPostulado}>Postular</button>
    </form>
  );
}

El error típico no es de código sino de forma: pasar usuario={usuario} a un Client Component porque "solo usa el nombre". La fila entera, con contrasena e id_rol, viaja en el payload y se lee en la pestaña Red. La defensa es la misma que en la API del proyecto: devolver un objeto armado a propósito (un DTO, data transfer object), nunca la fila de la base, como en el SELECT con columnas explícitas de M80.

// datos/oportunidades.ts: la capa de acceso a datos (DAL)
import 'server-only';                       // si un Client Component lo importa, el build falla
import { sql } from './db';
import { verificarSesion } from './sesion';

export async function obtenerOportunidad(id: number) {
  const sesion = await verificarSesion();   // lee y valida la cookie; sin sesión, lanza
  const [o] = await sql`SELECT id, titulo, modalidad FROM oportunidades WHERE id = ${id} AND estado = 1`;
  if (!o) throw new Error('No existe');
  const [p] = await sql`SELECT 1 FROM postulaciones WHERE oportunidad_id = ${id} AND estudiante_id = ${sesion.id}`;
  return { id: o.id, titulo: o.titulo, modalidad: o.modalidad, yaPostulado: Boolean(p) };   // DTO, no la fila
}

El paquete server-only hace que el build falle si un Client Component importa ese módulo Documentado. Next.js recomienda concentrar la autorización en esta capa de acceso a datos (DAL): cada lectura comprueba la sesión, sin depender de que la página lo haya hecho antes Documentado.

84.4Secretos que llegan al bundle

En Next.js, las variables de entorno con el prefijo NEXT_PUBLIC_ se reemplazan por su valor literal en el JavaScript del cliente durante el build Documentado. Las demás solo existen en el servidor; en el navegador valen undefined.

# .env.local
NEXT_PUBLIC_API_URL=https://practicas.edu.gt/api    # pública: va al bundle
DATABASE_URL=mysql://app:…@db/practicas             # solo servidor
COOKIE_KEY=…                                        # solo servidor; nunca con NEXT_PUBLIC_

# Comprobar qué quedó publicado después del build
$ grep -r "COOKIE_KEY\|DATABASE_URL" .next/static/ && echo "FUGA"

Es la versión de Next.js del hallazgo 1 del proyecto, el .env con COOKIE_KEY que Apache sirve como texto: un secreto donde el cliente lo alcanza. El arreglo es el mismo en los dos: el secreto vive solo donde corre el código que lo usa, y se comprueba buscándolo en lo que se publica.

84.5Server Actions: endpoints públicos con forma de función

Una Server Action es una función con 'use server' que un Client Component llama como si fuera local. Por debajo, Next.js la convierte en un POST a la ruta de la página con un identificador de acción Documentado. Eso la hace un endpoint público: cualquiera que conozca el identificador puede llamarla con cualquier argumento, sin pasar por el botón.

// app/oportunidades/[id]/acciones.ts: cada función exportada es un endpoint POST
'use server';
import { z } from 'zod';
import { verificarSesion } from '@/datos/sesion';
import { crearPostulacion } from '@/datos/postulaciones';

const Entrada = z.object({ oportunidadId: z.coerce.number().int().positive() });

export async function postular(formData: FormData) {
  const sesion = await verificarSesion();                 // 1. quién: nunca un id del formulario
  if (sesion.rol !== 'estudiante') throw new Error('No autorizado');   // 2. puede hacer esto
  const { oportunidadId } = Entrada.parse(Object.fromEntries(formData)); // 3. validar la forma
  await crearPostulacion(oportunidadId, sesion.id);       // 4. el dueño sale de la sesión (M80)
}

Las cuatro líneas numeradas son las preguntas de M80 escritas en TypeScript. Lo que Next.js sí hace solo:

  • CSRF: las acciones solo aceptan POST y Next.js compara Origin con Host (o X-Forwarded-Host); si no coinciden, no ejecuta la acción Documentado. Junto con SameSite=Lax, cubre lo que en M76 armaste a mano.
  • Identificadores: cifrados y no deterministas, y las acciones que nadie usa no se publican Documentado. Eso reduce la superficie, pero no es autorización: el identificador está en el bundle.
  • Variables de la clausura: si una acción se define dentro de un componente y usa una variable de afuera, Next.js la cifra para el viaje de ida y vuelta Documentado. Aun así, no pongas secretos ahí: la regla es leerlos dentro de la acción.
// next.config.ts: si la app va detrás de un proxy que cambia el Host
export default {
  experimental: {
    serverActions: { allowedOrigins: ['practicas.edu.gt'] },   // la lista exacta, sin comodines amplios
  },
};

Si la app va detrás de un proxy que cambia el Host, la comparación falla y hay que declarar los orígenes permitidos. Una lista amplia, como *.edu.gt, devuelve el problema de M75: confiar en subdominios que no controlas.

84.6El middleware es un chequeo optimista

El middleware de Next.js corre antes de cada request que coincide con su matcher, y es tentador poner ahí todo el control de acceso, como el requireAuth centralizado de M80. La documentación lo describe como un chequeo optimista: rápido, para redirigir pronto, sin consultar la base Documentado. En Next.js 16 el archivo pasó a llamarse proxy.ts Documentado.

// middleware.ts (proxy.ts desde Next.js 16): chequeo optimista y barato
import { NextResponse } from 'next/server';
export function middleware(req) {
  if (!req.cookies.has('sesion')) {                 // solo mira si existe; no la valida contra la base
    return NextResponse.redirect(new URL('/login', req.url));
  }
}
export const config = { matcher: ['/admin/:path*', '/panel/:path*'] };
// La comprobación de verdad está en verificarSesion(), que llama cada acción y cada lectura.

En marzo de 2025 se publicó CVE-2025-29927 (CVSS 9.1): una request con la cabecera interna x-middleware-subrequest hacía que el middleware no corriera Documentado. Afectaba a Next.js autoalojado; se corrigió en 15.2.3, 14.2.25, 13.5.9 y 12.3.5, y la mitigación temporal era quitar esa cabecera en el proxy de entrada. Las apps que solo autorizaban en el middleware quedaron abiertas; las que repetían la comprobación cerca de los datos, no. Es defensa en profundidad con un ejemplo real.

84.7React escapa, salvo cuando le pides que no

Al interpolar {o.titulo}, React crea un nodo de texto: es el textContent de M77 hecho por defecto. Los huecos tienen nombres que avisan, como prometía M77: dangerouslySetInnerHTML en React y v-html en Vue.

// La salida de emergencia de React avisa con el nombre
<div dangerouslySetInnerHTML={{ __html: o.descripcionHtml }} />            // XSS si no se sanea
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(o.descripcionHtml) }} />  // M77

// href con datos del usuario: React escapa las comillas, no el esquema
<a href={o.sitioWeb}>Sitio</a>                                              // javascript:… (M82)
<a href={esHttp(o.sitioWeb) ? o.sitioWeb : undefined}>Sitio</a>

El segundo hueco es más sutil: React escapa el valor de un atributo, pero no decide si el esquema de una URL es seguro. Un sitio_web con javascript: en un href es el caso de M82. React 16.9 empezó a avisar en consola y React 19 bloquea esas URLs Documentado; validar el esquema al guardar sigue siendo la defensa que no depende de la versión.

84.8Cuando la falla está en el framework

El 3 de diciembre de 2025, React publicó CVE-2025-55182 (CVSS 10.0): el decodificador del protocolo de Server Components, que convierte el cuerpo de una llamada a una Server Function en objetos, podía terminar ejecutando código en el servidor con una request sin sesión Documentado. Afectaba a react-server-dom-webpack, -parcel y -turbopack 19.0.0, 19.1.0, 19.1.1 y 19.2.0, y a los frameworks que los incluyen, Next.js 15 y 16 entre ellos; se corrigió en 19.0.1, 19.1.2 y 19.2.1, con versiones nuevas de Next.js el mismo día. CISA la agregó a su catálogo de vulnerabilidades explotadas Documentado.

La lección para el diseño: cada capa que agrega un framework es código que corre con los datos del atacante antes que el tuyo. Ninguna validación en la acción frena una falla en el decodificador. Lo que sí sirve es saber qué versiones corren (el SBOM y el SCA de M56) y poder actualizar en horas, con la priorización por KEV de M58.

84.9Qué modelo para el sistema de prácticas

Migrar el frontend del proyecto a Next.js no lo haría más seguro ni menos: haría que el escape lo hiciera React en lugar de textContent, que el CSRF de las acciones lo cubriera el framework, y agregaría tres superficies nuevas (el payload de RSC, el bundle con sus variables y el propio framework). Lo que sí lo haría más seguro es lo de los módulos anteriores: autorizar en cada endpoint (M80), la sesión revocable (M81) y la CSP (M78). Diseño de referencia

Si el proyecto migra, la revisión de un PR en Next.js suma tres preguntas a las de siempre: ¿qué props cruzan a un Client Component?, ¿alguna variable nueva lleva NEXT_PUBLIC_?, ¿cada 'use server' nuevo comprueba sesión, rol y entrada?
