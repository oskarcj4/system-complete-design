Autenticación y sesiones

Una sesión es una promesa del servidor: "esta request viene de quien demostró ser Ana". Se rompe de cuatro formas: alguien obtiene la promesa (robo de sesión), alguien la fabrica (firma débil), la promesa no se puede retirar (sin revocación) o la demostración era débil (contraseñas, sin MFA).

  • Revocar una sesión firmada con una versión de sesión, y evitar la fijación de sesión.

  • Cerrar la enumeración de usuarios por mensajes y por tiempos, y frenar la fuerza bruta y el credential stuffing.
  • Explicar por qué una passkey resiste el phishing y diseñar una recuperación de contraseña segura.

En M80 la primera pregunta, quién eres, se dio por respondida: requireAuth() devuelve la sesión y el resto del código confía en ella. Este módulo abre esa caja. En M10 viste tokens y JWT desde la arquitectura; aquí va la sesión de una aplicación web concreta, la tuya, y los ataques contra el login.

81.1Dos formas de recordar quién eres

Analogía

Una sesión con estado es la pulsera de un hotel con un número: en recepción hay un libro que dice de quién es cada número, y si la pierdes, tachan la línea. Una sesión firmada es una credencial plastificada con tu nombre y un sello difícil de falsificar: nadie consulta el libro, pero si te la roban, sirve hasta la fecha impresa.

81.2La cookie del sistema, pieza por pieza

El sistema usa una sesión firmada propia: un JSON en base64, una barra y un HMAC-SHA256 del JSON con COOKIE_KEY. Es, en la práctica, un JWT casero con un solo algoritmo, lo que evita la familia de errores de alg que viste en M10.

El payload está firmado, no cifrado: cualquiera que tenga la cookie lee su contenido decodificando el base64. Por eso no lleva nada secreto. Y una corrección concreta, la de la IP:

<?php
// Hoy: strpos(REMOTE_ADDR, $data['ip']) === 0 acepta cualquier IP que EMPIECE igual
// '10.0.0.1' firmada deja pasar '10.0.0.12', '10.0.0.100'…
if (isset($data['ip']) && !hash_equals($data['ip'], $_SERVER['REMOTE_ADDR'] ?? '')) {
    return null;
}
// Y aun exacta, la IP cambia en el celular y detrás de un proxy (M03): no es un control fuerte.

La misma COOKIE_KEY firma la sesión y deriva el token CSRF de 76.5. Las dos firmas usan prefijos distintos, así que no se pueden intercambiar, pero una clave por propósito (SESSION_KEY, CSRF_KEY) permite rotarlas por separado (M36).

81.3Cerrar sesión de verdad

Hoy, DELETE login.php borra la cookie del navegador de Ana. Si alguien la copió antes (un XSS de M77, un equipo compartido, un log que la guardó), la copia sigue sirviendo hasta exp. Lo mismo con los roles: si la coordinación le quita a alguien el rol de reclutador, la cookie dice lo contrario hasta que vence.

<?php
// core/auth.php: la cookie firmada, más una lectura barata para poder revocar
function checkAuth(PDO $db): ?array
{
    $data = verificarCookie();                       // lo que hoy hace checkAuth(): formato, HMAC, exp
    if ($data === null) {
        return null;
    }
    $stmt = $db->prepare('SELECT version_sesion, rol_id, estado_cuenta FROM usuarios WHERE id = ?');
    $stmt->execute([$data['id']]);
    $u = $stmt->fetch(PDO::FETCH_ASSOC);
    if (!$u || $u['estado_cuenta'] !== 'activo' || (int)$u['version_sesion'] !== $data['v']) {
        return null;                                 // logout, cambio de contraseña o cuenta bloqueada
    }
    $data['roles'] = rolesActuales($db, $data['id']);   // los roles de hoy, no los del login
    return $data;
}
// logout, cambio de contraseña y "cerrar todas las sesiones":
// UPDATE usuarios SET version_sesion = version_sesion + 1 WHERE id = ?

Es un híbrido: la firma evita buscar una sesión por id, y la lectura de una fila por clave primaria agrega revocación. Para la carga de este sistema, una lectura por request es despreciable. Junto con eso, una vida corta: COOKIE_LIFETIME de horas, no de semanas, y "recordarme" como una cookie aparte, más larga, que solo sirve para emitir una sesión nueva.

81.4Fijación de sesión

La fijación de sesión es el ataque inverso al robo: en lugar de robar el id de la víctima, el atacante le hace usar uno que él ya conoce, y espera a que inicie sesión.

Tu cookie firmada no tiene este problema: el login emite una cookie nueva, con su firma, y la que hubiera antes no significa nada. Pero configuration.php también llama a session_start(): si algún día guardas algo en $_SESSION, aplica esto.

<?php
// Si usas las sesiones de PHP ($_SESSION), además de la cookie firmada
ini_set('session.use_strict_mode', '1');     // rechaza ids que el servidor no creó
ini_set('session.use_only_cookies', '1');    // nunca el id en la URL
session_start();
// … después de verificar la contraseña:
session_regenerate_id(true);                  // id nuevo; el viejo se borra
$_SESSION['usuario_id'] = $id;

El prefijo __Host- de 74.6 impide que un subdominio plante la cookie, que es como el atacante suele fijarla.

81.5Contraseñas: qué pedir y cómo guardarlas

Cómo se guardan ya lo viste en M36: password_hash con Argon2id o bcrypt, nunca un hash rápido. Tu proyecto ya usa password_verify. Lo que cambia es qué pedir. La guía de NIST, SP 800-63B, dice Documentado:

  • Largo, no complejidad. La revisión 4 (2025) pide al menos 15 caracteres cuando la contraseña es el único factor, y 8 cuando hay MFA, y admitir al menos 64. Nada de "una mayúscula, un número y un símbolo": producen Practicas2026!.
  • Comparar contra contraseñas filtradas y rechazar las que aparecen.
  • Sin rotación periódica: se cambia cuando hay evidencia de que se filtró.
  • Permitir pegar, para que funcionen los gestores de contraseñas.
<?php
// Registro y cambio de contraseña
if (mb_strlen($nueva) < 15 && !$tieneMfa) {                      // NIST 800-63B-4: 15 sin MFA
    Response::json(-1, 'Usa una frase de al menos 15 caracteres', [], 400);
}
if (mb_strlen($nueva) > 64 && PASSWORD_DEFAULT === PASSWORD_BCRYPT && strlen($nueva) > 72) {
    Response::json(-1, 'Máximo 72 bytes', [], 400);              // bcrypt corta en 72 bytes
}
if (estaFiltrada($nueva)) {                                       // lista de contraseñas filtradas
    Response::json(-1, 'Esa contraseña apareció en una filtración', [], 400);
}
$hash = password_hash($nueva, PASSWORD_ARGON2ID);                 // M36

// En cada login correcto: subir el costo de los hashes viejos sin pedir nada al usuario
if (password_needs_rehash($fila['password_hash'], PASSWORD_ARGON2ID)) {
    $nuevoHash = password_hash($contrasena, PASSWORD_ARGON2ID);   // UPDATE usuarios SET password_hash = ?
}

Para la lista de filtradas, el servicio Pwned Passwords permite consultar por k-anonimato: mandas los primeros 5 caracteres del SHA-1 de la contraseña y recibes todos los sufijos que empiezan así; la comparación la haces tú, y la contraseña no sale de tu servidor Documentado.

81.6Enumeración de usuarios

La enumeración de usuarios es averiguar qué cuentas existen. Sirve para el siguiente ataque: probar contraseñas solo contra cuentas reales, o mandar phishing dirigido a quien sí usa el sistema. Se filtra por tres lados:

  • Mensajes distintos. "El usuario no existe" contra "contraseña incorrecta". Tu login ya responde lo mismo en los dos casos.
  • Tiempos distintos. Tu login hace password_verify solo si el usuario existe. Esa función es lenta a propósito (M36), así que la diferencia se mide desde afuera.
  • Otros formularios. El registro ("ese correo ya está en uso") y la recuperación ("te mandamos un correo").
<?php
// models/login.php: los dos caminos hacen el mismo trabajo
const HASH_RELLENO = '$argon2id$v=19$m=65536,t=4,p=1$…';   // password_hash('relleno', …), generado una vez

$fila = $stmt->fetch(PDO::FETCH_ASSOC);
$ok = password_verify($contrasena, $fila['password_hash'] ?? HASH_RELLENO);
if (!$fila || !$ok) {
    Response::json(-1, 'Usuario o contraseña incorrectos', [], 401);    // mismo mensaje, mismo código
}

El registro es más difícil: si el correo ya existe, hay que decirlo de alguna forma. La salida es mandar un correo en los dos casos ("si no tenías cuenta, confirma aquí"; "ya tienes una cuenta, ¿olvidaste tu contraseña?") y mostrar siempre el mismo mensaje en pantalla.

81.7Fuerza bruta y credential stuffing

El credential stuffing es el más común hoy: el atacante tiene millones de pares de usuario y contraseña de filtraciones de otros sitios, y los prueba uno por cuenta, desde muchas IPs. Funciona porque la gente reutiliza contraseñas. No hay patrón por cuenta ni por IP que lo delate fácil; lo frenan MFA, la lista de filtradas al registrarse y la detección de inicios de sesión raros (M59 escribió una regla para el password spraying).

<?php
// core/limite.php: contador por clave en una ventana fija, en la base (o en Redis, M08)
function excedeLimite(PDO $db, string $clave, int $max, int $ventanaSeg): bool
{
    $db->prepare('INSERT INTO intentos (clave, ventana, n) VALUES (?, ?, 1)
                  ON DUPLICATE KEY UPDATE n = n + 1')
       ->execute([$clave, intdiv(time(), $ventanaSeg)]);
    $stmt = $db->prepare('SELECT n FROM intentos WHERE clave = ? AND ventana = ?');
    $stmt->execute([$clave, intdiv(time(), $ventanaSeg)]);
    return (int)$stmt->fetchColumn() > $max;
}
// En el login, antes de buscar al usuario:
if (excedeLimite($db, 'ip:' . $_SERVER['REMOTE_ADDR'], 30, 300)
 || excedeLimite($db, 'cuenta:' . mb_strtolower($identificador), 10, 900)) {
    header('Retry-After: 300');
    Response::json(-1, 'Demasiados intentos, espera unos minutos', [], 429);
}

Trade-off

Bloquear la cuenta tras N fallos frena la fuerza bruta y regala una denegación de servicio: cualquiera bloquea la cuenta de la coordinadora el día del cierre de postulaciones escribiendo mal su contraseña diez veces. Mejor un retardo creciente y un 429 temporal por cuenta, que expira solo, más el límite por IP del rate limiting de M08.

81.8MFA y passkeys

El MFA pide algo más que la contraseña. No todos los segundos factores valen lo mismo:

FactorCómo funcionaResiste el phishing
SMSUn código por mensajeNo; además, SIM swapping
TOTP (RFC 6238)Un código de 6 dígitos que cambia cada 30 s, de un secreto compartidoNo: la víctima escribe el código en el sitio falso
Notificación pushAprobar en el teléfonoNo del todo: fatiga de MFA, aprobar sin mirar
Passkey (WebAuthn)Firma un desafío con una clave privada del dispositivo, atada al origenSí: el origen va dentro de la firma

Una passkey es una credencial de WebAuthn: un par de claves por cuenta y por sitio. La privada vive en el dispositivo o en el gestor de contraseñas y firma, como en M36; el servidor guarda solo la pública Documentado.

No hay secreto compartido que robar de tu base: una filtración de la tabla de passkeys no sirve para entrar. Para un sistema universitario, un camino razonable es TOTP opcional para todos y obligatorio (o passkeys) para administradores, que son quienes pueden asignar roles.

81.9Recuperar la contraseña

El flujo de "olvidé mi contraseña" es un login alternativo: quien controla el enlace controla la cuenta. Las reglas:

<?php
// Pedir el restablecimiento: misma respuesta exista o no la cuenta
$token = bin2hex(random_bytes(32));                              // 256 bits (M36)
$db->prepare('INSERT INTO restablecimientos (usuario_id, token_hash, vence) VALUES (?, ?, ?)')
   ->execute([$usuarioId, hash('sha256', $token), time() + 30 * 60]);   // se guarda el hash, 30 min
$enlace = URL_APP . '/restablecer?t=' . $token;                  // URL fija: nunca $_SERVER['HTTP_HOST']
// Usarlo: buscar por hash('sha256', $t), vigente y sin usar; marcarlo usado en la misma transacción;
// cambiar la contraseña y subir version_sesion: se cierran todas las sesiones abiertas.
  • Token aleatorio de 256 bits, guardado como hash: si se filtra la tabla, los enlaces no sirven.
  • Corto y de un solo uso: 30 minutos, marcado como usado en la misma transacción que cambia la contraseña.
  • URL fija. Armar el enlace con la cabecera Host de la request permite que un atacante pida el restablecimiento de Ana con Host: ofertas-gratis.example y reciba el token cuando ella haga clic (password reset poisoning).
  • Cerrar todas las sesiones al cambiar la contraseña, con la versión de sesión de 81.3.
  • Misma respuesta exista o no la cuenta (81.6).

En producción real

Mide antes de cambiar: cuántos logins fallidos por hora, cuántos por IP, cuántos por cuenta. Con eso eliges los límites, y la regla de detección de M59 alerta cuando se pasan. La guía WEB02 agrega version_sesion, el hash de relleno, la tabla intentos con su límite y TOTP para administradores, y prueba cada uno con una falla provocada. Con quién eres y qué puedes hacer resueltos, quedan los archivos y las URLs que el servidor visita por ti: M82.
