WebAssembly

WebAssembly es una caja con paredes buenas y sin nada adentro que la proteja de sí misma. El navegador garantiza que el módulo no salga de su memoria; no garantiza que el módulo no se rompa por dentro, ni que lo que tú le das por la ranura de los imports sea poco.

En M73 quedó una pestaña pendiente: WebAssembly, código compilado que corre en el mismo motor que tu JavaScript y con sus mismas reglas. Este módulo la abre. La conclusión adelantada: Wasm no agrega permisos a la página, así que no cambia lo que un atacante puede hacer desde el navegador; lo que cambia es que trae código escrito en C y otros lenguajes, con las fallas de memoria de esos lenguajes, a un lugar donde antes solo había JavaScript.

85.1Qué es un módulo

WebAssembly (Wasm) es un formato binario de instrucciones para una máquina virtual de pila, pensado como destino de compiladores Documentado. Un archivo .wasm es un módulo: funciones, una memoria, una tabla y la lista de lo que importa y exporta. El navegador lo descarga, lo valida, lo compila a código de máquina y crea una instancia.

;; El formato de texto de Wasm (WAT): un módulo con una página de memoria y una función
(module
  (memory (export "memory") 1)            ;; 1 página = 64 KiB = 65 536 bytes
  (func (export "sumar") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))

Wasm 3.0 se dio por terminado en septiembre de 2025, con memorias de 64 bits, recolección de basura y excepciones Documentado. Para este módulo alcanza la parte que no cambió: una memoria, imports, exports y las reglas que el motor comprueba.

Analogía

Un módulo de Wasm es un empleado nuevo en una oficina con una sola mesa. Puede hacer lo que quiera sobre su mesa, pero no tiene llave de ningún cajón: si necesita algo de afuera, lo pide por una ventanilla, y tú decides qué ventanillas abre. Si desordena su mesa, el desorden es suyo; si le das la llave de la caja fuerte por la ventanilla, el problema es tuyo.

85.2La memoria lineal

La memoria lineal de un módulo es un único arreglo de bytes, numerado desde 0, que crece de a páginas de 64 KiB Documentado. Todo lo que el programa en C guarda (cadenas, estructuras, la parte de la pila que usa el compilador) vive ahí. Cada acceso se comprueba contra el tamaño de ese arreglo: un acceso fuera produce un trap, un error que detiene la ejecución del módulo.

// validar.c: el buffer y la bandera, uno detrás del otro en la memoria lineal
#include <string.h>
struct perfil { char nombre[16]; int es_admin; };

int registrar(struct perfil *p, const char *entrada) {
    strcpy(p->nombre, entrada);      // copia hasta el 0 final, mida lo que mida
    return p->es_admin;              // con 17 letras o más, ya no vale 0
}

La comprobación es contra el final de la memoria, no contra el final de cada variable. Un strcpy de 20 letras en un buffer de 16 no sale de la memoria: pisa la variable de al lado, que es del mismo módulo. Pruébalo:

Es el desbordamiento clásico de C, con una diferencia que juega en contra: en un proceso nativo hay canarios en la pila, direcciones al azar (ASLR) y páginas de solo lectura que hacen más difícil aprovecharlo, y dentro de la memoria lineal de Wasm no los hay Documentado. Un estudio de 2020 compiló programas vulnerables a Wasm y mostró que fallas que en nativo eran difíciles de explotar se volvían más fáciles dentro del módulo (Lehmann, Kinder y Pradel, USENIX Security) Documentado.

// La misma función, con el largo controlado
#include <stdio.h>
int registrar(struct perfil *p, const char *entrada) {
    snprintf(p->nombre, sizeof p->nombre, "%s", entrada);   // nunca más de 15 letras y el 0
    return p->es_admin;
}

85.3Imports y exports: la única puerta

Un módulo no tiene instrucciones para tocar el DOM, la red ni las cookies. Lo único que puede hacer afuera es llamar a las funciones que el host le pasa como imports, y lo único que el host ve de adentro son los exports. En el navegador, el host es tu JavaScript.

// Instanciar con imports mínimos y leer el resultado como datos, no como HTML
const { instance } = await WebAssembly.instantiateStreaming(
  fetch('/wasm/validar.wasm', { integrity: 'sha384-…' }),       // SRI también para el .wasm
  { env: { log: (ptr, len) => console.log(leer(ptr, len)) } }   // lo único que puede hacer afuera
);
function leer(ptr, len) {
  const bytes = new Uint8Array(instance.exports.memory.buffer, ptr, len);
  return new TextDecoder().decode(bytes);
}
salida.textContent = leer(instance.exports.mensaje(), instance.exports.largo());   // nunca innerHTML
// Un import que convierte el sandbox en decoración
const imports = { env: {
  ejecutar: (ptr, len) => eval(leer(ptr, len)),                 // el módulo ahora corre JavaScript
  pedir: (ptr, len) => fetch(leer(ptr, len), { credentials: 'include' }),   // y llama a tu API con la sesión
} };

La regla es la de mínimo privilegio de M66 aplicada a funciones: cada import es un poder, y un módulo de terceros con un import que llama a tu API con la sesión puede hacer lo mismo que un XSS. Al revés también vale: lo que sale del módulo son datos que escribió código en C con la entrada del usuario. Se muestran con textContent, como cualquier dato (M77).

85.4Qué protege el sandbox y qué no

Lo que el motor garantiza viene de la especificación: la memoria comprobada, el control de flujo estructurado (no hay saltos a direcciones arbitrarias), las llamadas indirectas que comprueban el tipo de la función y la pila de llamadas fuera de la memoria lineal Documentado. Lo que queda tiene tres fuentes:

  • El programa: un buffer desbordado o un if al revés funcionan igual de mal compilados a Wasm. Se cuida con el mismo código seguro, sanitizadores en las pruebas y dependencias al día (M56).
  • Los canales laterales: Wasm, como JavaScript, puede medir tiempos. Spectre no respeta el sandbox del lenguaje; lo que lo frena es el proceso por sitio de M73 y el aislamiento con COOP y COEP de M78.
  • El host: los imports que le das y lo que haces con lo que devuelve.

Qué pasa si falla

Wasm también se usó para esconder: entre 2017 y 2019, Coinhive ofrecía un minero de criptomonedas en Wasm que muchos sitios comprometidos cargaban sin que sus dueños lo supieran, hasta que el servicio cerró en marzo de 2019 Documentado. El binario era más difícil de leer que JavaScript, pero el problema de fondo era el de M83: un script de terceros corriendo en tu origen.

85.5PHP en el navegador

El intérprete de PHP está escrito en C, así que se puede compilar a Wasm con Emscripten. Así funciona WordPress Playground: WordPress entero corriendo en una pestaña, con SQLite en lugar de MySQL y un sistema de archivos virtual, sin servidor Documentado.

Las cuatro preguntas de M73 tienen aquí una respuesta extrema: se ve todo, nada viaja al servidor, todo se ejecuta en el cliente y no hay nadie que autorice. Para el sistema de prácticas sirve como laboratorio desechable (un curso de PHP, una demo sin instalar XAMPP), con datos de ejemplo. 85.6Wasm en el servidor: WASI

Fuera del navegador, el host es un runtime como Wasmtime o Wasmer, y la interfaz con el sistema es WASI (WebAssembly System Interface). WASI 0.2, publicado en enero de 2024, se basa en el modelo de componentes Documentado. Su idea de seguridad es la de capacidades: el módulo no tiene acceso a nada salvo lo que el runtime le pasa al arrancar, como una carpeta concreta.

# Correr un validador de PDF compilado a WASI con solo la carpeta del archivo
$ wasmtime run --dir=./subidas/tmp::/entrada validar-pdf.wasm /entrada/cv-8f3a.pdf
# Sin --dir no ve ningún archivo; sin --env no ve COOKIE_KEY; sin permisos de red, no tiene sockets.

Es una forma barata de aislar el código que procesa archivos de terceros, como el validador de CVs de M82: si la librería de PDF tiene una falla, quien la aproveche queda dentro de una carpeta temporal, sin red y sin variables de entorno. Proxies como Envoy y plataformas de borde también cargan extensiones en Wasm por la misma razón Documentado.

85.7Las cabeceras que Wasm necesita

<?php
// core/cabeceras.php (M78): la CSP estricta con la palabra para compilar Wasm
header("Content-Security-Policy: script-src 'nonce-$nonce' 'strict-dynamic' 'wasm-unsafe-eval'; "
     . "object-src 'none'; base-uri 'none'; frame-ancestors 'none'");
// Si la página usa hilos de Wasm (SharedArrayBuffer), además:
header('Cross-Origin-Opener-Policy: same-origin');
header('Cross-Origin-Embedder-Policy: require-corp');

Con una CSP estricta, el navegador no compila Wasm salvo que script-src tenga 'wasm-unsafe-eval' Documentado. La palabra existe para no tener que usar 'unsafe-eval', que además habilita eval() de JavaScript a cualquier XSS. El .wasm se descarga con fetch y su opción integrity (el SRI de M83), y los hilos de Wasm, que usan SharedArrayBuffer, solo están disponibles en una página aislada con COOP y COEP Documentado.
