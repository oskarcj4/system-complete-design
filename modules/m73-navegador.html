El navegador por dentro

Casi todos los ataques web son una regla del navegador usada a favor de otro: un string que el parser convierte en código, una cookie que viaja sola, un botón oculto que igual se puede apretar. Antes de defenderte, tienes que saber qué hace el navegador con lo que le mandas.

Todos los ejemplos salen del sistema de control de prácticas, una API en PHP sobre MariaDB con estudiantes, reclutadores, oportunidades y postulaciones.

Analogía

Una imprenta y un lector. El servidor es la imprenta: tiene los originales, las planchas y la lista de suscriptores, y nada de eso sale de ahí. Lo que llega a tu casa es el periódico impreso. Con el periódico en la mano puedes recortarlo, tacharlo o pegarle hojas: es tuyo. El navegador es la casa del lector. Todo lo que mandas ahí, el lector lo puede leer y cambiar. Lo único que no puede tocar es lo que quedó en la imprenta.

73.1El viaje de una página y de un fetch

Una aplicación web moderna hace dos tipos de viaje. En el primero, el navegador pide una página y el servidor la arma: Apache ve que es un .php, PHP ejecuta el script, consulta la base y escribe HTML. En el segundo, la página ya cargada pide datos con fetch y los pinta ella misma. El sistema de prácticas es del segundo tipo: su api/ solo devuelve JSON, y un frontend en JavaScript lo pinta.

Tres cosas para quedarte de esta figura. El navegador empieza a construir la página antes de que termine de llegar: el parser trabaja sobre lo que va recibiendo. El servidor nunca manda PHP, manda lo que PHP imprimió. Y la cookie viaja sola en cada request al mismo sitio, la pida tu código o no; cómo lo decide el navegador es M74.

73.2Del HTML al DOM: un parser que no falla

El parser de HTML convierte bytes en un árbol en dos etapas. El tokenizer lee caracteres y produce tokens (una etiqueta que abre, texto, una que cierra). El constructor del árbol toma esos tokens y arma nodos. A diferencia de un parser de JSON, este nunca rechaza la entrada: si falta un cierre, lo agrega; si una etiqueta está donde no puede ir, la mueve. La especificación de HTML de WHATWG dice exactamente qué hacer con cada error, y por eso todos los navegadores arman el mismo árbol con el mismo HTML roto Documentado.

Lo importante para la seguridad es el contexto. El tokenizer cambia de modo según dónde está: dentro de un <title> o un <textarea> no reconoce etiquetas, todo es texto; dentro de un atributo, el valor termina en la comilla (o en el primer espacio, si no hay comillas); dentro de un <script>, el texto es JavaScript hasta que aparece </script>. El mismo string puede ser texto inofensivo en un lugar y estructura nueva en otro. Escapar bien es escapar para el contexto donde va el dato, y M77 lo hace contexto por contexto.

Prueba los ejemplos. Cada uno muestra una corrección que el navegador hace sin avisar: un tbody que aparece, un div que se muda fuera de la tabla, un atributo que se parte en dos. Ninguno es un ataque, pero los ataques reales de XSS (incluido el mutation XSS de M77) usan justamente estas reglas.

73.3El DOM y las dos formas de meterle un string

El DOM (Document Object Model) es el árbol que arma el parser, convertido en objetos que JavaScript puede leer y cambiar: document, elementos, nodos de texto, atributos. Lo que ves en pantalla es el DOM, no el HTML que llegó: si JavaScript cambia un nodo, la página cambia, y el HTML original ya no importa.

Para poner texto en la página hay dos caminos, y la diferencia es si interviene el parser:

API¿Llama al parser?Úsala para
el.textContent = sNoCualquier dato: nombres, títulos, descripciones
document.createElement + setAttributeNoArmar estructura con datos adentro (ojo con href y src, M77)
el.innerHTML = sSíSolo HTML que escribiste tú, nunca con datos de usuarios sin sanitizar

En el sistema de prácticas, el título y la descripción de una oportunidad los escribe un reclutador. Si el frontend los pinta con innerHTML, el reclutador escribe HTML en la página de todos los estudiantes. Esa es la puerta del XSS almacenado, y se cierra en M77 (y en la guía WEB05).

73.4Del árbol a los píxeles

Con el DOM y las reglas de CSS (el CSSOM), el navegador arma el árbol de render, calcula posiciones y tamaños (layout), pinta y compone las capas. No es un tema de seguridad en sí, pero explica dos cosas que vas a ver. Primero, por qué el render espera: un <script> sin defer detiene el parser hasta que se descarga y corre. Segundo, por qué existen ataques que miden tiempos de render o de carga para deducir datos de otro sitio (los XS-Leaks de M83).

73.5El event loop: un solo hilo

Todo el JavaScript de una página corre en un solo hilo, el mismo que hace el render. El event loop decide qué corre: toma una tarea de la cola (un clic, un setTimeout, la llegada de una respuesta), la corre entera, después corre todas las microtareas pendientes (los then de las promesas), y recién entonces deja que el navegador pinte y toma la siguiente tarea. La especificación de HTML define este orden Documentado.

console.log('1');
setTimeout(() => console.log('2'), 0);         // una tarea nueva
Promise.resolve().then(() => console.log('3')); // una microtarea
console.log('4');
// En la consola: 1, 4, 3, 2

El 3 sale antes que el 2 aunque el setTimeout diga cero milisegundos: la microtarea se corre al terminar la tarea actual, y el setTimeout espera a la siguiente vuelta. Para la seguridad, esto importa por dos motivos. Una tarea larga (un bucle que tarda tres segundos, una expresión regular mal escrita sobre un texto grande, el ReDoS de M83) congela clics y render, y la página deja de responder. Y un script ajeno que llega a ejecutarse en la página comparte este hilo y este DOM con el tuyo: no hay "mi JavaScript" y "el de otro", hay un solo programa.

73.6Un proceso por sitio

Los navegadores modernos reparten el trabajo en procesos. El proceso del navegador no tiene sandbox: hace la red, guarda las cookies y el almacenamiento, y decide qué recibe cada página. Las páginas corren en procesos renderer, cada uno en un sandbox del sistema operativo, sin acceso directo al disco ni a la red. Con Site Isolation, Chromium usa un renderer distinto para cada sitio, incluso para un iframe de otro sitio dentro de tu página Documentado.

Site Isolation existe por Spectre (2018): un ataque de canal lateral que deja leer memoria del propio proceso. Si dos sitios comparten proceso, uno podría leer datos del otro; separados, lo que se lee es solo lo propio. Las cabeceras COOP y COEP de M78 piden ese aislamiento de forma explícita.

Lo que no protege

El sandbox y Site Isolation protegen a un sitio de otro sitio y a tu máquina de una página. No protegen a tu sitio de sí mismo: un script que logra correr en tu página corre en tu renderer, con tu DOM, tus cookies sin HttpOnly y tus permisos. Esa es la razón de que el XSS sea tan grave.

73.7Quién ejecuta qué: servidor, navegador y Wasm

La pregunta que ordena toda esta parte es dónde corre cada línea de código, porque de eso depende quién la controla.

PHP corre en el servidor. Lo que imprime es la respuesta. El navegador recibe el resultado, nunca el script:

<?php // oportunidad.php: esto corre en el servidor y el navegador nunca lo ve
require __DIR__ . '/api/core/connection.php';
$stmt = Connection::load()->prepare('SELECT titulo, modalidad FROM oportunidades WHERE id = ?');
$stmt->execute([(int)($_GET['id'] ?? 0)]);
$o = $stmt->fetch(PDO::FETCH_ASSOC);
?>
<h1><?= htmlspecialchars($o['titulo'], ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8') ?></h1>
<p>Modalidad: <?= htmlspecialchars($o['modalidad'], ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8') ?></p>

Lo que llega al navegador:

<h1>Práctica de backend en Java</h1>
<p>Modalidad: remoto</p>

El htmlspecialchars con ENT_QUOTES | ENT_SUBSTITUTE y UTF-8 convierte <, >, & y las comillas en entidades, para que un título con marcado se vea como texto. Es el escape del contexto "texto dentro de HTML"; los otros contextos están en M77.

JavaScript corre en el navegador, con el código a la vista de quien lo usa:

// app.js: esto corre en el navegador, y quien lo usa puede leerlo y cambiarlo
const r = await fetch('api/endpoints/oportunidades.php', { credentials: 'same-origin' });
const { data } = await r.json();
const lista = document.querySelector('#feed');
for (const o of data) {
  const li = document.createElement('li');
  li.textContent = o.titulo;          // texto: el parser no interviene
  lista.append(li);
}

Cualquiera puede abrir este archivo, ponerle un punto de interrupción, cambiar una variable o llamar a la API sin pasar por él. Lo que hace este código es comodidad para el usuario honesto, no una barrera para el que no lo es.

Frameworks como Next.js mezclan los dos mundos en el mismo archivo: unos componentes corren solo en el servidor (Server Components) y otros también en el navegador (Client Components). La línea sigue existiendo, solo que es menos visible, y un secreto que cruza al lado del cliente queda publicado. Es el tema de M84.

WebAssembly es código compilado (de C, Rust, Go, incluso el intérprete de PHP entero) que corre en el motor de JavaScript, dentro del mismo renderer y con las mismas reglas de la página: no tiene más permisos que tu JavaScript. Se puede correr PHP dentro del navegador así, y en ese caso el servidor desaparece y todo queda del lado del cliente. Es el tema de M85.

73.8La frontera de confianza

De todo lo anterior sale la regla más importante de la seguridad web: el navegador está del otro lado de la frontera de confianza. Todo lo que mandas ahí lo controla quien usa el navegador, y todo lo que llega desde ahí puede haber sido escrito a mano.

Consecuencias directas, con el sistema de prácticas:

  • Ocultar un botón no es control de acceso. Si el frontend esconde "Publicar oferta" a los estudiantes pero el endpoint no comprueba el rol, un estudiante publica igual.
  • Validar en el formulario es para la comodidad. La fecha de cierre, el largo del título y la modalidad se validan otra vez en el servidor. El modelo Oportunidades ya lo hace con su lista de modalidades: bien.
  • Nada que identifique al usuario puede venir del body. Hoy oportunidades.php toma creado_por de $_POST. Quien lo cambie publica a nombre de otro. Se arregla en M80 y en la guía WEB06.
// Diseño de referencia: el servidor decide, no el botón ni el body
$auth = requireAuth([ROL_RECLUTADOR]);      // rol leído de la cookie firmada
$data = validarOportunidad($_POST);         // tipos, largos y fechas, otra vez
$data['creado_por'] = (int)$auth['id'];     // el autor sale de la sesión, nunca del body

Diseño de referencia El código de arriba es la forma del arreglo; las funciones validarOportunidad y la constante del rol las escribe la guía WEB06.

73.9DevTools: lo que ve un atacante

Las herramientas de desarrollo del navegador (F12) son también la primera herramienta de seguridad, porque muestran exactamente lo mismo que puede ver y cambiar un atacante con tu aplicación:

  1. ElementsEl DOM actual, no el HTML que llegó. Se puede editar cualquier nodo, mostrar un botón oculto o quitar un disabled.
  2. NetworkCada request con sus cabeceras, sus cookies y su respuesta. Revisa aquí que la API mande Content-Type: application/json: hoy Response::json no lo manda (hallazgo 5 del plan, M77).
  3. ApplicationLas cookies con sus atributos (HttpOnly, Secure, SameSite), localStorage y sessionStorage. M74 explica cada columna.
  4. ConsoleJavaScript con los mismos permisos que la página: lo que se puede hacer desde aquí lo puede hacer cualquier script que logre correr en ella.
  5. Copy as cURLClic derecho en una request de Network: la copia como comando, con cookies y cabeceras, lista para repetirla o cambiarla.
# Lo que hace el formulario, sin el formulario: cualquiera puede mandar esto
curl -i -X POST "http://localhost/SistemaControlPracticas/api/endpoints/oportunidades.php" \
  -H "X-CSRF-Token: <el token de su propia sesión>" \
  --cookie "<COOKIE_NAME>=<su propia cookie>" \
  --data "titulo=Prueba&descripcion=x&fecha_cierre=2026-12-31&creado_por=7"
# creado_por=7 no es su id: si el servidor lo acepta, publica a nombre de otro

Esto no es un ataque contra nadie: es tu propia sesión, contra tu propio servidor local. Muestra que el servidor recibe lo que el cliente quiera mandar, y que la única defensa está en lo que el servidor comprueba.

En producción real

La pregunta de revisión de cualquier cambio web es la misma: ¿esta comprobación corre del lado derecho de la figura 73.7? Si la respuesta es "en el frontend", no es una comprobación, es una sugerencia. Lo que sigue en esta parte es cómo el navegador decide qué viaja (origen y cookies, M74), cuándo deja leer una respuesta de otro sitio (CORS, M75) y cuándo manda tu cookie sin que lo pidas (CSRF, M76).
