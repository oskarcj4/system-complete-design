Permisos, sandbox y autonomía

En M62 viste que "menos restricción" mezcla cuatro capas y que solo dos están en tus manos. Este módulo las configura a fondo: qué decide el harness antes de ejecutar, qué impone el sistema operativo mientras el comando corre, y cómo se arma una caja donde el agente puede hacer cualquier cosa sin que eso sea un problema.

Duración

Requisitos previos

Estado
Sin empezar

Al terminar podrás

  • Recorrer una llamada a herramienta por las nueve capas que pueden frenarla y decir cuáles dependen del texto del comando.
  • Escribir reglas allow, ask y deny sabiendo en qué orden se evalúan y qué formas del mismo comando no ven.
  • Elegir un modo de permiso para cada situación: trabajo diario, exploración, CI y autonomía total.
  • Configurar el sandbox del sistema (Seatbelt, bubblewrap) y saber cuándo hace falta un contenedor o una microVM.
  • Cerrar la salida con un proxy y una lista de dominios, y sacar las credenciales de la caja.
  • Escribir un hook que imponga una política que el modelo no puede saltear.

66.1Nueve lugares donde se puede frenar una llamada

En M62.10 separaste cuatro capas: lo que aprendió el modelo, las reglas del proveedor, los permisos del harness y la caja del sistema operativo. Las dos primeras no se configuran. Este módulo abre las otras dos y muestra que, por dentro, son varias piezas en fila. Cada llamada que el modelo propone (M63.9) las recorre en orden.

Analogía

Un empleado nuevo en un banco. Antes de actuar, hay un manual (reglas), un supervisor que firma lo dudoso (la persona) y un sistema que no deja operar sin firma (el modo). Pero además la bóveda tiene paredes, la puerta solo abre a ciertas salas y las llaves no las tiene él: aunque el manual tenga un hueco o el supervisor firme sin leer, hay cosas que físicamente no puede hacer. Este módulo es sobre las dos mitades, y sobre por qué la segunda importa más.

  1. El modelo proponeUna llamada con su nombre y argumentos; todavía no pasó nada. M63.9
  2. Hook previoUn programa tuyo que ve la llamada y puede bloquearla, siempre igual. 66.9
  3. ReglasListas allow, ask y deny por herramienta y patrón. 66.2
  4. ModoQué pasa con lo que ninguna regla resolvió. 66.3
  5. PersonaLa que contesta cuando el harness pregunta, y se cansa. 66.3
  6. Sandbox del sistemaSeatbelt o bubblewrap limitan archivos y red del proceso. 66.4
  7. Contenedor o VMQué máquina, qué disco y qué kernel ve el agente. 66.5
  8. Proxy de salidaSolo los dominios de la lista. 66.6
  9. Credenciales fueraLa clave se agrega afuera; dentro no hay nada que robar. 66.7

La diferencia que organiza todo el módulo: las piezas de arriba deciden por el texto de la llamada. Si el modelo escribe lo mismo de otra forma, o una prompt injection lo convence de hacerlo, pueden no verlo. Las de abajo deciden por lo que el proceso hace: abrir un archivo, conectarse a un host. No importa cómo se escribió el comando. Por eso la regla de oro de M62 se sostiene: si quitas preguntas arriba, pon paredes abajo.

66.2Reglas: allow, ask y deny

Una regla de permiso es un patrón sobre una herramienta y sus argumentos, con uno de tres efectos: allow (se ejecuta sin preguntar), ask (se pregunta) o deny (no se ejecuta). En Claude Code se escriben como Herramienta(patrón) Documentado:

{
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": ["Bash(npm test)", "Bash(npm test *)", "Bash(git diff *)", "Bash(git status)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(./secrets/**)", "Bash(curl *)", "WebFetch"]
  }
}

El orden de evaluación es fijo y no depende de cuán específica sea la regla: primero deny, después ask, después allow, y decide la primera que coincide Documentado. Un allow no puede abrir una excepción dentro de un deny.

Dónde viven y quién gana

Las reglas se suman desde varios archivos: los de la organización (managed settings), los flags de la línea de comandos, .claude/settings.local.json (tuyo, sin versionar), .claude/settings.json (del proyecto, versionado) y ~/.claude/settings.json (todos tus proyectos). Para las demás opciones gana el más específico, pero con los permisos manda el deny: un deny en cualquier nivel bloquea aunque otro nivel lo permita, y nada puede saltar un deny de la organización, tampoco --allowedTools Documentado. Esa asimetría es la que permite que una empresa imponga sus límites y cada persona los ajuste solo hacia más restricción.

Las reglas de bash miran el texto

Bash(npm test *) coincide con cualquier comando que empiece así. Claude Code entiende la estructura del shell: separa los comandos compuestos por &&, ||, ;, | y saltos de línea, exige que cada parte esté permitida, aplica los deny a cualquier parte (también dentro de $( ) o de un for) y quita envoltorios como timeout, nice o nohup antes de comparar Documentado. Aun así, la documentación lo dice sin rodeos: una regla de bash mira el texto que escribe el modelo y no es un límite de seguridad alrededor del programa Documentado.

Regla en denyFrenaNo frena
Bash(curl *)curl https://x.example/usr/bin/curl …, sh -c 'curl …'
Bash(rm *)rm -rf build//bin/rm -rf build/, bash -c 'rm …'
Bash(git push *)git push origin maingit -C . push …, git 'push' …

Ejemplos de la documentación de permisos de Claude Code Documentado.

Esto cambia para qué sirve cada lista. Un allow es una comodidad que se piensa como si el agente pudiera abusar de él: Bash(npm test *) es seguro; Bash(npm *) permite npm publish y npm exec de cualquier paquete, y Bash(python *) es permitir cualquier cosa. Un deny frena la forma habitual de un error honesto y orienta al modelo, pero no a quien busca un camino: para eso está el sandbox (66.4). Un ask sirve para lo que tiene efectos fuera del repositorio, como un push.

Qué pasa si falla

Un clásico de los modos sin persona: en M69.2 viste que --allowedTools aprueba herramientas sin preguntar, pero no restringe las demás. Un orquestador que pasa --allowedTools "Read,Grep" pensando que el agente solo puede leer le está dejando todo lo demás a lo que decida el modo. Para restringir, --disallowedTools o reglas deny, y dontAsk para que lo no aprobado se niegue.

Lo mismo en Codex y OpenCode

# ~/.codex/config.toml o .codex/config.toml del proyecto
sandbox_mode    = "workspace-write"   # read-only | workspace-write | danger-full-access
approval_policy = "on-request"        # on-request | never

[sandbox_workspace_write]
writable_roots = ["/home/ana/.cache/pnpm"]   # además del workspace

Codex no tiene listas por comando: separa qué permite el sistema operativo (sandbox_mode) de cuándo te pregunta (approval_policy). read-only lee y no edita ni ejecuta sin aprobación; workspace-write lee, edita en el workspace y corre comandos dentro de ese límite; danger-full-access quita los límites de archivos y red. Con on-request pide aprobación para salir del límite; con never no se detiene Documentado. El diseño pone el peso en la segunda mitad de la lámina, que es la que no depende del texto.

{ "permission": { "edit": "ask", "bash": { "*": "ask", "git status": "allow", "git diff *": "allow", "rm *": "deny" } } }

Cada herramienta lleva allow, ask o deny, y bash acepta un mapa de patrones Documentado. Es política sobre el texto, como las reglas de Claude Code, sin un sandbox propio: para la mitad de abajo hace falta un contenedor (66.5).

66.3Modos: quién decide lo que ninguna regla resolvió

Un modo de permiso es la política por defecto de la sesión: qué pasa con una llamada que no coincide con ninguna regla. Claude Code tiene seis Documentado:

  • plan: lee y corre comandos de solo lectura; no edita. Para entender un problema antes de tocar nada.
  • default (Manual): pregunta la primera vez por cada herramienta que no es de lectura.
  • acceptEdits: edita dentro del directorio de trabajo sin preguntar, y aprueba mkdir, touch, rm, mv, cp y sed en esas rutas. Los demás comandos preguntan.
  • auto: un clasificador, otro modelo, revisa cada acción antes de ejecutarla en lugar de preguntarte. Bloquea por defecto cosas como descargar y ejecutar código (curl | bash), mandar datos sensibles afuera, deploys a producción, force push y borrar lo que existía antes de la sesión. No ve los resultados de las herramientas, para que un contenido hostil no lo convenza Documentado.
  • dontAsk: niega todo lo que preguntaría. Solo corre lo aprobado por reglas. Es el modo de CI.
  • bypassPermissions: no pregunta. Los deny siguen bloqueando y los ask siguen preguntando, y unos pocos borrados críticos nunca se aprueban solos; los allow dejan de importar porque todo está permitido Documentado.

La documentación es explícita con el último: solo en entornos aislados, como contenedores, VMs o devcontainers sin internet, y no protege contra prompt injection. Claude Code se niega a arrancarlo como root Documentado. Una organización puede deshabilitarlo con permissions.disableBypassPermissionsMode, y auto con permissions.disableAutoMode, en managed settings Documentado.

La persona es la capa más débil

El modo default parece el más seguro y en la práctica se degrada: una sesión de una hora puede hacer cien preguntas, y a la décima la persona aprueba sin leer. Esa es la razón de ser de acceptEdits, de auto y de las reglas allow: bajar la cantidad de preguntas para que las que quedan se lean. Una buena configuración pregunta poco y pregunta lo que importa: un push, un comando con red, algo fuera del repositorio. Diseño de referencia

66.4El sandbox del sistema operativo

Un sandbox del sistema operativo es un límite que el kernel impone a un proceso y a todos sus hijos: qué archivos puede leer y escribir, y a dónde se puede conectar. Como lo aplica el kernel mientras el comando corre, no importa si el modelo escribió curl, /usr/bin/curl o un script de Python: el connect() se rechaza igual. Es lo que en M25.10 llamaste sandbox de código, aplicado a la máquina del desarrollador.

Las primitivas

El framework de sandbox de macOS. Un perfil en SBPL, un lenguaje con forma de Lisp, dice qué operaciones se permiten; se aplica con sandbox-exec, cuya página de manual lo marca como obsoleto aunque sigue funcionando y lo usan Claude Code y Codex Documentado.

; perfil.sb: perfil de Seatbelt simplificado (uno real necesita más permisos del sistema)
(version 1)
(deny default)                                    ; todo lo que no se permite, se niega
(allow process-exec process-fork)
(allow file-read*)                                ; leer, sí (y por eso conviene negar ~/.ssh)
(deny file-read* (subpath "/Users/ana/.ssh"))
(allow file-write* (subpath "/Users/ana/repo") (subpath "/private/tmp"))
(allow network-outbound (remote ip "localhost:8888"))   ; solo hacia el proxy

bwrap arma una vista del sistema con namespaces de usuario, de montajes, de PID y de red, sin necesitar root: monta lo que el proceso puede ver, en solo lectura o con escritura, y le da una red vacía. Es lo que usan Claude Code y Codex en Linux y WSL2 Documentado.

# La vista de la figura 66.5, a mano. Los montajes posteriores pisan a los anteriores.
bwrap --ro-bind / / \
      --dev /dev --proc /proc \
      --bind "$PWD" "$PWD" \
      --tmpfs /tmp \
      --tmpfs "$HOME/.ssh" \
      --unshare-net --unshare-pid \
      --die-with-parent --new-session \
      bash -c 'npm test'

Landlock es un módulo de seguridad del kernel (desde Linux 5.13) que deja a un proceso sin privilegios restringirse a sí mismo: qué rutas puede leer o escribir y, desde la ABI 4 (Linux 6.7), a qué puertos TCP puede conectarse. Es irreversible para ese proceso y sus hijos. seccomp filtra llamadas al sistema; el sandbox de Claude Code lo usa de forma opcional para bloquear sockets Unix Documentado. Ninguno de los dos arma una vista de archivos como bubblewrap: se combinan.

El sandbox de Claude Code

Viene apagado y se enciende con /sandbox o en la configuración. Cubre los comandos de shell y lo que ellos lancen; no cubre las herramientas Read, Edit y WebFetch, los servidores MCP ni los hooks, que se controlan con las reglas Documentado. Por defecto:

  • Escritura: el directorio de trabajo, un temporal propio y lo agregado con --add-dir. Rutas como .claude/settings*, .mcp.json, .bashrc y .gitconfig quedan protegidas: un comando no puede escribir su propia configuración para darse más permisos.
  • Lectura: casi toda la máquina, incluidos ~/.ssh y ~/.aws/credentials, salvo que los niegues con denyRead.
  • Red: sin ruta directa; todo pasa por un proxy local que compara el host con una lista que arranca vacía. UDP, QUIC e ICMP no salen.
{
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false,
    "failIfUnavailable": true,
    "filesystem": { "denyRead": ["~/.ssh", "~/.aws"] },
    "network": { "allowedDomains": ["registry.npmjs.org", "github.com"] }
  },
  "permissions": { "deny": ["Read(~/.ssh/**)", "Read(~/.aws/**)"] }
}

Tres opciones de esa configuración cierran huecos. allowUnsandboxedCommands: false apaga la vía de escape: si un comando falla dentro del sandbox, el modelo puede reintentarlo con dangerouslyDisableSandbox, que corre fuera y pasa por el flujo de permisos normal; con la opción en false, el parámetro se ignora. failIfUnavailable hace que Claude Code no arranque si el sandbox no puede iniciarse, en lugar de seguir sin él. Y el deny de Read cubre la herramienta Read, que el sandbox no ve Documentado. Con el sandbox encendido, autoAllowBashIfSandboxed (activo por defecto) aprueba los comandos que corren dentro: preguntar menos es seguro porque la pared está abajo.

Trade-off

El sandbox rompe cosas: docker no funciona dentro, ssh y la mayoría de los drivers de base de datos ignoran el proxy, y en Linux localhost es privado de la caja. La salida fácil es excludedCommands, que corre esos comandos fuera con acceso total; un patrón amplio, o uno que incluya un intérprete, deshace todo el sandbox Documentado. Excluye lo mínimo y con el comando completo, no con python *.

66.5Contenedores, devcontainers y microVMs

El sandbox del proceso corre en tu máquina, con tu usuario y tu kernel. Una caja más gruesa cambia qué máquina ve el agente: en un contenedor no existe tu $HOME, ni tus llaves, ni tus otros proyectos, salvo que los montes. Cada caja más gruesa cuesta algo y protege de una clase de error más.

Un devcontainer es la forma cómoda de vivir dentro de un contenedor: el editor abre el proyecto adentro, y el harness corre ahí. La especificación es abierta y la entienden VS Code, JetBrains y la CLI devcontainer. Las opciones que importan para un agente son las de M57: usuario sin privilegios, sin capabilities, sin no-new-privileges desactivado, límites de memoria y procesos, y nada del host montado salvo el repositorio.

// .devcontainer/devcontainer.json
{
  "name": "agente",
  "image": "mcr.microsoft.com/devcontainers/typescript-node:22",
  "remoteUser": "node",                                   // nunca root
  "runArgs": ["--cap-drop=ALL", "--security-opt=no-new-privileges",
              "--pids-limit=512", "--memory=4g", "--network=agente-interna"],
  "mounts": [],                                           // nada del $HOME del host
  "containerEnv": { "HTTPS_PROXY": "http://proxy:3128", "HTTP_PROXY": "http://proxy:3128" },
  "postCreateCommand": "npm ci"
}

Un contenedor comparte el kernel: un error del kernel es una salida. Para código que no es tuyo (revisar un PR de un desconocido, un orquestador que analiza repositorios ajenos) la caja adecuada es una microVM por tarea, como hace DeepSec con Vercel Sandbox (M69.10), o gVisor, que intercepta las llamadas al sistema con un kernel en espacio de usuario. Para tu propio repositorio en tu laptop, un contenedor bien configurado alcanza. Diseño de referencia

CajaProtege deNo protege deCuándo

66.6Salida: un proxy con lista de dominios

Una caja sin red es la más segura y la menos útil: npm install, git fetch y la propia API del modelo necesitan salir. La solución es una lista de dominios de salida: la caja no tiene ruta a internet salvo un proxy que deja pasar solo ciertos hosts. Es el filtrado de salida de M32 con una regla por dominio en lugar de por IP, porque las IPs de un registro de paquetes cambian.

Con Docker se arma con dos redes: una interna sin ruta a internet, donde vive el agente, y el proxy conectado a las dos.

# compose.yaml: el agente solo ve una red interna; el proxy es la única puerta
services:
  agente:
    build: .
    networks: [interna]
    environment:
      HTTPS_PROXY: http://proxy:3128
      HTTP_PROXY: http://proxy:3128
  proxy:
    image: ubuntu/squid:6.10-24.10_beta
    volumes: ["./squid.conf:/etc/squid/squid.conf:ro"]
    networks: [interna, salida]
networks:
  interna: { internal: true }      # sin ruta a internet
  salida: {}
# squid.conf: lista de dominios, nada más
http_port 3128
acl permitidos dstdomain registry.npmjs.org .github.com api.anthropic.com
acl SSL_ports port 443
acl CONNECT method CONNECT
http_access deny CONNECT !SSL_ports
http_access allow permitidos
http_access deny all

El proxy decide por el nombre que llega en el CONNECT (o en el SNI, si es transparente) y no ve el contenido: es la contracara de no tener que confiar en un certificado propio dentro de la caja. Eso deja tres huecos que conviene conocer Diseño de referencia:

  • Un dominio permitido es un canal. Si github.com está en la lista y en la caja hay un token, el agente puede crear un gist con lo que leyó. La lista corta y sin tokens de escritura van juntos.
  • El DNS también sale. Si la caja resuelve nombres con un DNS externo, un subdominio como secreto.x.example lleva datos en la consulta. Con una red interna, el DNS lo resuelve el proxy.
  • Lo que ignora el proxy no sale, y eso es bueno y molesto: ssh, UDP y muchos drivers no usan las variables HTTPS_PROXY, así que no conectan.

66.7Credenciales fuera de la caja

La pregunta que decide cuánto daño puede hacer un agente comprometido no es qué puede ejecutar sino qué credenciales tiene a mano. Una clave en una variable de entorno se imprime con env, se lee en /proc/self/environ y viaja en cualquier request. Tres prácticas, de la más simple a la más completa:

  1. Una clave propia de la cajaNo la tuya: una clave de API creada para el agente, con tope de gasto, que puedas revocar sin afectar nada más. Si se filtra, el daño tiene techo.
  2. Tokens de vida cortaEn CI, el proveedor de identidad emite un token por corrida (OIDC, M56) con permisos de solo lectura; para la nube, roles con sesiones de minutos (M37). Lo que dura una hora vale una hora.
  3. La clave no entraUn proxy de credenciales en el host recibe la request de la caja con un valor de relleno y le agrega la clave real solo si el destino es el permitido. Dentro de la caja no hay nada que robar.

Es el patrón de DeepSec (M69.10) y el del modo mask del sandbox de Claude Code: sandbox.credentials puede negar archivos y variables, o reemplazarlas por un valor centinela que el proxy cambia por el real solo hacia los hosts permitidos Documentado. Lo mismo vale para lo que no es la API del modelo: el token de GitHub con permiso de escritura no entra; el push lo hace el sistema que revisa el resultado (66.8).

Qué pasa si falla

El secreto que más se olvida es el que está dentro del repositorio: el .env de desarrollo. Ninguna caja lo protege, porque el repositorio es justo lo que se monta. Un deny de Read(./.env) frena la forma habitual; lo único que lo resuelve es que la caja tenga un .env de mentira, con credenciales de un entorno de prueba que no importa perder.

66.8Autonomía total dentro de una caja desechable

Con las piezas anteriores se puede hacer lo que en M62 se prometió: dejar al agente trabajar una hora sin preguntar nada, con bypassPermissions, y que eso no sea un riesgo. La idea no es confiar en el modelo sino que lo peor que puede pasar sea tirar la caja. Mira la trifecta de M25.11: con datos privados, contenido no confiable y comunicación hacia afuera a la vez, una injection puede robar. La caja corta dos patas.

# Autonomía total, dentro de una caja desechable
git worktree add ../tarea-1234 -b agente/tarea-1234     # (1) una rama y una copia propias
docker compose run --rm agente \
  claude -p "Actualiza las dependencias con vulnerabilidades y deja las pruebas en verde" \
  --permission-mode bypassPermissions --output-format json --max-turns 80
# (2) dentro: sin credenciales de la nube, sin token de push, salida solo por el proxy
git -C ../tarea-1234 diff main --stat                    # (3) una persona revisa el diff
  1. Una rama y una copia del repositorio solo para esta tarea: lo que haga no toca tu árbol de trabajo.
  2. La caja de 66.5 a 66.7: contenedor sin $HOME, red interna con proxy, clave propia con tope y sin token de push.
  3. El resultado es un diff. Lo publica una persona, o un CI que corre las pruebas en limpio; el agente no publica nada.

La lista de comprobación de una caja para autonomía total Diseño de referencia:

  • Usuario sin privilegios, sin capabilities, sin el socket de Docker montado (con él, la caja crea otra caja sin límites).
  • Solo el repositorio montado, en una rama o un worktree propio; un .env de prueba.
  • Red interna y salida por proxy con lista corta: el registro de paquetes, el servidor del modelo y, si hace falta, lectura de GitHub.
  • Clave del modelo con tope de gasto o inyectada desde afuera; ninguna credencial de nube ni de escritura.
  • Límites de tiempo, turnos y presupuesto (M69.7), y el transcript guardado para auditar.
  • El resultado sale como diff y lo revisa alguien o algo que no es el agente.

66.9Hooks como política determinista

Lo que escribes en CLAUDE.md cambia lo que el modelo intenta; lo que escribes en un hook cambia lo que el harness permite. Un hook PreToolUse es un programa tuyo que recibe cada llamada como JSON antes de que se ejecute y puede bloquearla: si sale con código 2, la llamada se cancela y lo que escribió en stderr vuelve al modelo como razón Documentado. No es una sugerencia: corre siempre, igual, y el modelo no puede negociar con él. Cómo funcionan los hooks en general (eventos, entrada, salida) es M67.5; aquí, cómo se usan para imponer una política.

#!/usr/bin/env python3
# .claude/hooks/politica.py: bloquea force push y borrados fuera del repositorio
import json, os, re, shlex, sys

evento = json.load(sys.stdin)                       # (1) el harness manda el evento por stdin
cmd = evento.get("tool_input", {}).get("command", "")
repo = os.path.realpath(evento.get("cwd", "."))

def fuera_del_repo(ruta):
    destino = os.path.realpath(os.path.join(repo, os.path.expanduser(ruta)))
    return not (destino == repo or destino.startswith(repo + os.sep))

if re.search(r"\bpush\b.*(--force\b|-f\b|--force-with-lease\b|\+\S+)", cmd):
    print("Force push bloqueado por política: abre un PR.", file=sys.stderr)
    sys.exit(2)                                     # (2) exit 2: bloquea y stderr vuelve al modelo

try:
    partes = shlex.split(cmd)
except ValueError:                                  # (3) si no se puede leer, no se adivina
    print("Comando que no se puede analizar: reescríbelo más simple.", file=sys.stderr)
    sys.exit(2)
if partes[:1] == ["rm"] and any(fuera_del_repo(p) for p in partes[1:] if not p.startswith("-")):
    print("rm fuera del repositorio bloqueado por política.", file=sys.stderr)
    sys.exit(2)

sys.exit(0)                                         # (4) exit 0: sigue el flujo normal (reglas y modo)
  1. Claude Code manda por stdin un JSON con tool_name, tool_input, cwd, session_id y el modo de permiso.
  2. Código 2 es el único que bloquea. Un código 1, o una excepción de Python sin capturar, es un error que no bloquea: la llamada sigue Documentado.
  3. Ante la duda, el hook bloquea y pide un comando más simple. Una política que adivina falla abierta.
  4. Código 0 no aprueba nada: deja que sigan las reglas y el modo.
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [ { "type": "command", "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/politica.py\"", "timeout": 10 } ] }
    ]
  }
}

Tres propiedades que hay que tener presentes Documentado:

  • Un hook que bloquea gana sobre un allow: el bloqueo ocurre antes de evaluar las reglas. Eso permite el patrón "todo bash permitido salvo esto": Bash en allow y un hook que rechaza lo puntual.
  • Un hook que aprueba no salta un deny: si el hook devuelve "permissionDecision": "allow", las reglas deny y ask se siguen aplicando.
  • El hook ve el mismo texto que las reglas. Es más expresivo (puedes resolver rutas, como el ejemplo), pero sh -c o un script escriben lo mismo de otra forma. El hook ordena; el límite sigue siendo el sandbox.

En producción real

Un hook es código que corre con tus permisos en cada llamada, fuera del sandbox. Si viene en el .claude/settings.json de un repositorio que clonaste, es código de un tercero que se ejecuta en tu máquina: por eso Claude Code pide confiar en la carpeta antes de cargar la configuración del proyecto, y claude --bare no la carga (M69.2). En una empresa, los hooks de política van en managed settings, donde el proyecto no los puede quitar.

66.10Un pedido contra todas las capas

Junta todo. Elige un pedido, un modo y qué capas están encendidas, y mira cuál lo frena. Prueba primero /usr/bin/curl con todo apagado y después enciende una capa por vez; después python3 -c con el .env, que ninguna caja frena.

Tres cosas para ver en el widget. Las reglas frenan curl pero no /usr/bin/curl. El sandbox frena las dos, sin importar el modo, porque decide en el kernel. Y en bypassPermissions con todas las cajas encendidas, ningún pedido produce daño: esa es la configuración de 66.8.
