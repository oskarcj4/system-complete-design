Inyecciones en el servidor

Toda inyección es un dato que cruza a otro intérprete sin que nadie le diga que es un dato. El XSS fue el caso del navegador; aquí están los del servidor, y la defensa es siempre la misma: mandar el código y el dato por canales separados.

Al terminar podrás

  • Reconocer la causa común de toda inyección: un dato que llega a un intérprete mezclado con el código.
  • Usar consultas preparadas, y resolver lo que no cubren: identificadores, ORDER BY, LIMIT, IN y LIKE.
  • Ejecutar programas externos sin shell, e incluir archivos sin que el usuario elija la ruta.
  • Distinguir un dato dentro de una plantilla de una plantilla hecha de datos (SSTI).
  • Cerrar la inyección de saltos de línea en cabeceras y logs, las entidades externas de XML y la deserialización de objetos.

En M77 viste que un string es texto en un lugar y código en otro, según quién lo lea. En el servidor hay más lectores que en el navegador: el motor SQL, la shell, el include de PHP, el motor de plantillas, las cabeceras HTTP, el archivo de log y el parser XML. Cada uno tiene su sintaxis y sus caracteres especiales, y cada uno tiene su inyección.

79.1La raíz común: código y dato en el mismo canal

Analogía

Es dictar una carta a alguien que escribe todo lo que oye. Si dices "escribe: el monto es cien; y después firma el cheque", ¿la segunda parte es parte del texto o una orden? Para no depender de cómo suena, el dato se entrega en un sobre aparte. Una consulta preparada es ese sobre.

Las defensas, en orden de preferencia, se repiten en todos los casos:

  1. Canales separados. La API del intérprete recibe el código y los datos por separado: parámetros en SQL, un arreglo de argumentos sin shell, variables en una plantilla.
  2. Lista de valores permitidos. Donde el dato tiene que ser parte del código (un nombre de columna, un archivo), el usuario elige una clave y el código pone el valor.
  3. Escape del contexto. El último recurso, cuando no hay otro canal. Funciona si se aplica bien en cada lugar.

79.2SQL: lo que hace una consulta preparada

La inyección SQL la viste desde la base en M35 y en dos párrafos en M10. El mecanismo: si la consulta se arma pegando strings, el motor recibe uno solo y no sabe dónde termina tu SQL y empieza el valor.

Tu proyecto ya lo hace bien: todos los modelos usan prepare y execute, y los filtros opcionales se arman con fragmentos fijos y una lista de parámetros aparte Diseño de referencia.

<?php
// models/oportunidades.php (tu código actual): filtros opcionales sin concatenar datos
$query = "SELECT … FROM oportunidades o … WHERE o.estado = 1 AND o.estado_oportunidad = 'activa'";
$params = [];
if ($carrera_id > 0) {
    $query .= " AND (o.carrera_id = ? OR o.carrera_id IS NULL)";   // fragmento fijo
    $params[] = $carrera_id;                                        // el dato va aparte
}
if ($modalidad !== '') {                                            // ya validada contra MODALIDADES
    $query .= " AND o.modalidad = ?";
    $params[] = $modalidad;
}
$stmt = $this->connection->prepare($query);
$stmt->execute($params);

Dos ajustes a la conexión: ATTR_EMULATE_PREPARES en false, para que la plantilla y los datos viajen separados de verdad (el valor por defecto de pdo_mysql es emular Documentado), y el charset en el DSN, que tu connection.php ya tiene. Sin charset en el DSN, la emulación escapa con un charset distinto al de la conexión, y con algunos charsets multibyte (GBK) eso permitió saltarse el escape Documentado.

<?php
// core/connection.php: el charset en el DSN y preparadas reales
$dsn = "mysql:host=" . HOST_DB . ";dbname=" . DATABASE . ";charset=utf8mb4";
parent::__construct($dsn, USER_DB, PASSWORD_DB, [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_EMULATE_PREPARES   => false,     // la plantilla y el dato viajan separados
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
]);

79.3Lo que un parámetro no puede ser

Un parámetro reemplaza un valor. No puede ser un nombre de columna, de tabla, una palabra clave (ASC, DESC) ni una lista. Ahí es donde aparecen las inyecciones en código que "ya usa preparadas".

CasoPor qué el parámetro no sirveSolución
ORDER BY elegido por el usuarioEs un identificador, no un valorLista: la clave la ve el usuario, el SQL es fijo
LIMIT ? con emulaciónPDO lo manda como '20' y MySQL lo rechazabindValue con PDO::PARAM_INT
IN (?) con una listaUn parámetro es un solo valorUn ? por elemento, generado por el código
LIKE ?No hay inyección, pero % y _ son comodinesEscaparlos con addcslashes
Nombre de tabla por tenantEs un identificadorLista, o mejor una columna tenant_id (M35)
 
<?php
// Un ORDER BY elegido por el usuario: los identificadores no pueden ser parámetros
const ORDEN = [                                  // lista de valores permitidos: clave pública, SQL privado
    'recientes' => 'o.fecha_publicacion DESC, o.id DESC',
    'cierre'    => 'o.fecha_cierre ASC, o.id ASC',
    'titulo'    => 'o.titulo ASC, o.id ASC',
];
$orden = ORDEN[$_GET['orden'] ?? 'recientes'] ?? ORDEN['recientes'];
$query .= " ORDER BY $orden LIMIT ? OFFSET ?";   // $orden nunca viene de la request

$stmt = $this->connection->prepare($query);
$i = 1;
foreach ($params as $p) { $stmt->bindValue($i++, $p); }
$stmt->bindValue($i++, min(100, max(1, (int)($_GET['limite'] ?? 20))), PDO::PARAM_INT);  // con emulación,
$stmt->bindValue($i++, max(0, (int)($_GET['desde'] ?? 0)), PDO::PARAM_INT);               // LIMIT '20' falla
$stmt->execute();
<?php
// IN con una lista: un ? por elemento, generado por el código
$ids = array_map('intval', $ids);
$marcas = implode(',', array_fill(0, count($ids), '?'));
$stmt = $pdo->prepare("SELECT … FROM carreras WHERE id IN ($marcas)");
$stmt->execute($ids);

// LIKE: el parámetro evita la inyección, pero % y _ siguen siendo comodines
$busqueda = addcslashes($_GET['q'] ?? '', '%_\\');
$stmt = $pdo->prepare("SELECT … FROM oportunidades WHERE titulo LIKE ?");
$stmt->execute(['%' . $busqueda . '%']);

Qué pasa si falla

Inyección de segundo orden. Un dato se guarda bien, con parámetros, y más tarde otro proceso lo lee de la base y lo concatena en otra consulta, porque "viene de la base, es de confianza". Un dato de la base es tan del usuario como el de la request: el canal separado se usa en cada consulta, no solo en la que recibe el formulario.

79.4Comandos del sistema

La inyección de comandos pasa cuando PHP arma una línea de comando con un dato y se la da a la shell (exec, system, shell_exec, passthru y las comillas invertidas). La shell interpreta ;, |, &&, $( ) y las redirecciones.

<?php
// MAL: un string completo a la shell
exec("pdftotext " . $rutaCv . " -", $salida);

// Menos mal: escapar cada argumento (una comilla de más o un -- olvidado y vuelve el problema)
exec('pdftotext ' . escapeshellarg($rutaCv) . ' -', $salida);

// Bien: sin shell. Con un arreglo, proc_open llama al programa directamente (PHP 7.4+)
$proc = proc_open(['pdftotext', '--', $rutaCv, '-'], [1 => ['pipe', 'w'], 2 => ['pipe', 'w']], $pipes);
$texto = stream_get_contents($pipes[1]);
proc_close($proc);
  • Sin shell es la regla. proc_open con un arreglo existe desde PHP 7.4 Documentado.
  • -- antes de los argumentos que vienen de datos: un nombre de archivo que empieza con - no se puede leer como opción del programa (inyección de argumentos).
  • Mejor todavía: una librería de PHP en lugar del programa externo, o un worker aparte (M07) que procesa el archivo con un usuario sin permisos (M33).

79.5Inclusión de archivos

La inclusión de archivos (LFI, Local File Inclusion) aparece cuando la ruta de un include o require sale de la request. include no lee un archivo: lo ejecuta como PHP. Si el atacante logra escribir algo en un archivo del servidor (un log de Apache con su User-Agent, un archivo subido, una sesión) y después lo incluye, ejecuta su código.

<?php
// MAL: index.php?pagina=../../../../xampp/apache/logs/access.log
include __DIR__ . '/paginas/' . $_GET['pagina'] . '.php';

// Bien: el usuario elige una clave; el código decide el archivo
const PAGINAS = ['inicio' => 'inicio.php', 'ofertas' => 'ofertas.php', 'perfil' => 'perfil.php'];
$archivo = PAGINAS[$_GET['pagina'] ?? 'inicio'] ?? 'inicio.php';
include __DIR__ . '/paginas/' . $archivo;

La inclusión remota (RFI, un include de una URL) necesita allow_url_include, que está apagado por defecto y obsoleto desde PHP 7.4 Documentado. Los wrappers como php://filter siguen funcionando con allow_url_include apagado, y sirven para leer el código fuente de tus archivos: la lista de valores permitidos los cierra igual que a ../. Leer archivos fuera de la carpeta, sin ejecutarlos, es el path traversal, que vuelve en M80 y en M82.

79.6Plantillas del servidor (SSTI)

Un motor de plantillas (Twig, Blade, Smarty) compila un texto con expresiones a código. Si el dato del usuario es una variable de la plantilla, el motor lo escapa. Si el dato del usuario es la plantilla, el motor evalúa lo que escribió: eso es SSTI (Server-Side Template Injection).

<?php
// Correos con texto personalizable por cada institución
// MAL: el texto que escribió la institución se compila como plantilla
$tpl = $twig->createTemplate($institucion['plantilla_correo']);
echo $tpl->render(['estudiante' => $estudiante, 'app' => $app]);

// Bien: el texto es texto, con marcadores fijos que reemplaza el código
$cuerpo = strtr($institucion['plantilla_correo'], [
    '[nombre]'      => $estudiante['nombre'],
    '[oportunidad]' => $oportunidad['titulo'],
]);

Si el negocio de verdad necesita plantillas que escriben los usuarios, Twig tiene un modo sandbox con una lista de etiquetas, filtros, métodos y propiedades permitidos Documentado. Es una superficie grande y con historia de bypasses: marcadores fijos con strtr cubren casi todos los casos.

79.7Saltos de línea: cabeceras, logs y correo

HTTP, los logs de texto y los correos separan sus partes con saltos de línea. Un \r\n dentro de un dato crea una parte nueva: es la inyección CRLF.

  • Cabeceras HTTP. header("Location: " . $_GET['volver']) con un salto de línea podía agregar cabeceras o un cuerpo. La función header() de PHP rechaza un valor con más de una cabecera desde la versión 5.1.2 Documentado. Sigue quedando la redirección abierta, que es M82.
  • Correo. El cuarto parámetro de mail(), las cabeceras adicionales, con un dato del usuario permite agregar Bcc: y mandar spam desde tu servidor. Usa una librería (PHPMailer, Symfony Mailer) que valida cada dirección.
  • Logs. Un salto de línea en un dato escrito con error_log crea una entrada falsa.
<?php
// Un registro por línea, en JSON: los saltos de línea del dato quedan escapados
function registrar(string $evento, array $datos): void
{
    $linea = json_encode(['t' => date(DATE_ATOM), 'evento' => $evento] + $datos,
                         JSON_UNESCAPED_UNICODE | JSON_INVALID_UTF8_SUBSTITUTE);
    error_log($linea);
}
registrar('login_fallido', ['usuario' => $usuario, 'ip' => $_SERVER['REMOTE_ADDR']]);

79.8XML y las entidades externas (XXE)

XML permite declarar entidades en una DTD, y una entidad externa toma su valor de un archivo o una URL. Un parser que las resuelve lee file:///etc/passwd o hace una request a la red interna por ti: es XXE, que apareció con SOAP en M02.

En PHP 8, con libxml 2.9 o posterior, las entidades externas no se cargan salvo que pidas LIBXML_NOENT o LIBXML_DTDLOAD, y la función libxml_disable_entity_loader quedó obsoleta Documentado. El riesgo hoy está en copiar esos flags de un ejemplo viejo, y en las bombas de expansión de entidades internas.

<?php
// Importar oportunidades desde un XML que sube una institución
$doc = new DOMDocument();
$doc->loadXML($xml, LIBXML_NONET);           // sin red; y NUNCA LIBXML_NOENT ni LIBXML_DTDLOAD
if ($doc->doctype !== null) {                // un XML de datos no necesita DTD
    throw new InvalidArgumentException('DTD no permitida');
}

79.9Deserialización: crear objetos desde un string

unserialize crea objetos de cualquier clase cargada, con las propiedades que diga el string, y PHP llama después a sus métodos mágicos (__wakeup, __destruct, __toString). Si el string viene del usuario, el atacante elige qué objetos se crean: la deserialización insegura que viste en M55, en su versión de PHP.

<?php
// MAL: preferencias del usuario en una cookie, serializadas con PHP
$prefs = unserialize($_COOKIE['prefs']);

// Bien: JSON, que solo produce arreglos y valores
$prefs = json_decode($_COOKIE['prefs'] ?? '{}', true, 4, JSON_THROW_ON_ERROR);

// Si heredas código con unserialize y no puedes cambiarlo todavía
$prefs = unserialize($dato, ['allowed_classes' => false]);   // objetos como __PHP_Incomplete_Class

La opción allowed_classes existe desde PHP 7.0 Documentado. Ojo con lo que no es unserialize: los archivos phar:// también deserializan sus metadatos al abrirse con funciones de archivos en versiones anteriores a PHP 8.0 Documentado; en tu XAMPP con PHP 8.0 eso ya no pasa, pero es otra razón para no abrir rutas que elige el usuario.

En producción real

Busca los intérpretes, no los payloads: grep -rnE "exec\(|system\(|shell_exec|passthru|`|include .*\$|unserialize|createTemplate|LIBXML_NOENT" api/, y en SQL cada ->query( o cada prepare( cuyo string tenga una variable que no sea un fragmento fijo. Las herramientas SAST de M55 hacen lo mismo con reglas para PHP. La guía WEB07 agrega ORDER BY con lista a la búsqueda de oportunidades, apaga la emulación y cambia los logs a JSON. Con los datos a salvo de los intérpretes, la pregunta siguiente es quién puede tocar cada dato: el control de acceso (M80).
