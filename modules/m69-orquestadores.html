Orquestadores: agentes que lanzan agentes

Un agente revisa un archivo. Revisar un repositorio entero, cada noche, sin pagar dos veces lo mismo y sin darle tu clave a un código que no conoces, es otro problema: un sistema distribuido cuyos workers son agentes.

69.1Cuándo un agente no alcanza

En M62 viste qué es un orquestador de agentes: un programa que vive fuera de los harnesses, los lanza uno por tarea y junta lo que devuelven. Aquí se abre por dentro. La pregunta previa es cuándo hace falta, porque la alternativa obvia (un solo agente con una ventana de contexto enorme) suena más simple.

Un agente solo deja de alcanzar por cuatro razones, y cualquiera basta:

RazónQué pasa con un agente soloQué hace el orquestador
ContextoCada archivo leído queda en la ventana. Al llenarse, el harness compacta y lo primero que se pierde son los detalles (M25.7)Cada tarea tiene su propia ventana, y solo con lo que necesita
DuraciónUna sesión de horas que falla en la hora 3 pierde las 3 horasGuarda el resultado de cada tarea; un corte cuesta una tarea
ParalelismoUna sesión es secuencialN tareas a la vez, con el tope que permite tu límite
RepetibilidadQué miró y qué no depende de lo que el modelo decidió en el caminoLa lista de tareas sale de un paso sin IA: se sabe qué se revisó

Dicho de otra forma: un orquestador es un sistema distribuido cuyos workers son agentes. Todo lo que aprendiste en la Parte I sobre colas, estado, reintentos, leases y topes aplica tal cual, con dos diferencias que cambian los números: cada tarea dura minutos y cuesta dólares, no milisegundos y fracciones de centavo, y el worker no es determinista.

Analogía

Una auditoría contable grande no la hace una persona leyendo todos los libros de corrido. Un jefe de equipo arma la lista de cuentas a revisar con un filtro simple, reparte carpetas entre auditores, anota en una planilla qué carpeta tiene cada uno y cuál está terminada, fija cuántas horas puede facturar el trabajo, y al final un socio revisa los hallazgos graves antes de firmar. El jefe no audita nada: reparte, limita, guarda y junta.

69.2El harness como proceso

La pieza que hace posible todo esto es el modo headless: el mismo harness que usas en la terminal, corriendo como un proceso más, con un contrato de entrada y salida que un programa puede leer.

Claude Code con -p

Con -p, Claude Code corre el bucle completo sin interfaz y termina. Una investigación de un orquestador se ve así Documentado:

# Una investigación, sin interfaz. --bare necesita ANTHROPIC_API_KEY en el entorno.
claude --bare -p "Investiga si src/api/auth.ts:42 es explotable. Sigue los datos hasta su origen." \
  --output-format json \
  --json-schema "$(cat hallazgo.schema.json)" \
  --disallowedTools "Bash,Edit,Write" \
  --permission-mode dontAsk \
  --max-turns 30 \
  --max-budget-usd 3

Y esto es lo que vuelve por stdout. Los campos son los del mensaje de resultado del SDK; los valores, de ejemplo Documentado:

{
  "type": "result",
  "subtype": "success",
  "is_error": false,
  "num_turns": 23,
  "duration_ms": 361000,
  "total_cost_usd": 1.42,
  "session_id": "4f1c…",
  "result": "La consulta concatena el id…",
  "structured_output": { "vulnerable": true, "severidad": "alta", "razon": "…" }
}

Cinco cosas de ese comando no son obvias y cada una evita una falla real:

  1. --bare no es un detalle de velocidadSin él, claude -p carga lo mismo que una sesión interactiva: los hooks de .claude/settings.json y los servidores de .mcp.json del proyecto, sin el diálogo de confianza ni la aprobación de cada servidor Documentado. Si tu orquestador escanea repositorios de terceros, sin --bare el repositorio decide qué código corre en tu máquina. Con --bare se ignoran, y también los CLAUDE.md y la memoria: el resultado no depende de la máquina. La documentación lo recomienda para scripts y anuncia que será el valor por defecto de -p.
  2. --allowedTools aprueba, no restringeLista herramientas que se usan sin preguntar; no impide las demás Documentado. Lo que da solo lectura en este comando es --disallowedTools, que quita Bash y las de edición, más --permission-mode dontAsk, que niega todo lo que pediría permiso. En headless nadie aprueba: lo que no está resuelto por las reglas se niega.
  3. La salida estructurada puede faltarCon --json-schema, el resultado validado llega en structured_output. Si la corrida termina sin una salida válida (por ejemplo, porque el modelo se negó), ese campo no está Documentado. Un orquestador que lo interpreta como "sin hallazgos" marca como revisado algo que nadie revisó.
  4. El costo es una estimacióntotal_cost_usd lo calcula el cliente y puede diferir de la factura Documentado. Sirve para topes y para comparar corridas; la conciliación con lo que cobra el proveedor es otra cosa (M21).
  5. Cómo termina importaEl exit code es 0 si la corrida salió bien y distinto de 0 si falló. Un SIGTERM sale con 143 y deja el turno en curso sin resultado; para terminar el turno, se manda SIGINT antes Documentado. Un orquestador que mata procesos por timeout tiene que saber cuál de las dos cosas hizo.

El transcript queda en disco y se retoma con --resume <session_id> Documentado. Para un orquestador eso es útil para depurar una tarea concreta, no para reintentar: reintentar sobre una sesión que falló arrastra su contexto, y casi siempre conviene empezar limpio.

Codex con codex exec

Codex tiene el mismo contrato con otros nombres Documentado:

# La clave solo para este comando, no para todo el job
CODEX_API_KEY="$CLAVE_CODEX" codex exec --json \
  --output-schema hallazgo.schema.json \
  -o resultado.json \
  "Investiga si src/api/auth.ts:42 es explotable. Sigue los datos hasta su origen."
  • Sandbox por defecto: codex exec corre en modo de solo lectura salvo que pidas otro con --sandbox. En Claude Code la restricción la ponen los flags de herramientas; en Codex, además, el sandbox del sistema operativo (M62.10).
  • Eventos: con --json, stdout es JSONL con thread.started, turn.started, item.*, turn.completed, turn.failed y error.
  • Salida: --output-schema fija el esquema de la respuesta final y -o la escribe en un archivo.
  • Credencial en CI: CODEX_API_KEY en línea, para un solo comando. La documentación advierte que no se ponga como variable de todo el job si el job corre código del repositorio, porque otros pasos podrían leerla.
  • Retomar: codex exec resume --last o con el id de la sesión.

69.3Proceso, SDK o API

Lanzar un proceso por tarea es la forma más simple de usar un harness desde un programa, pero no la única. El Agent SDK es el mismo harness como librería: el bucle, las herramientas y el manejo del contexto de Claude Code, que se llaman desde Python o TypeScript y devuelven mensajes tipados en lugar de texto Documentado. Codex tiene su equivalente. DeepSec no lanza claude -p: usa @anthropic-ai/claude-agent-sdk o @openai/codex-sdk según el agente elegido Documentado.

Este es el worker de un orquestador con el SDK de Python: investiga un lote y devuelve lo que el resto del sistema necesita guardar. Diseño de referencia

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage

ESQUEMA = {"type": "object", "required": ["hallazgos"], "properties": {"hallazgos": {"type": "array", "items": {
    "type": "object", "required": ["archivo", "linea", "slug", "severidad", "fragmento", "razon"],
    "properties": {"archivo": {"type": "string"}, "linea": {"type": "integer"}, "slug": {"type": "string"},
                   "severidad": {"enum": ["alta", "media", "baja"]}, "fragmento": {"type": "string"},
                   "razon": {"type": "string"}}}}}}

async def investigar(lote: list[str], repo: str) -> dict:
    opciones = ClaudeAgentOptions(
        cwd=repo,                                        # (1) el agente ve este directorio
        setting_sources=[],                              # (2) nada de la configuración del repositorio
        disallowed_tools=["Bash", "Edit", "Write"],      # (3) solo lectura
        permission_mode="dontAsk",
        max_turns=40, max_budget_usd=3.0,                # (4) topes de esta tarea
        output_format={"type": "json_schema", "schema": ESQUEMA})
    prompt = "Investiga estos archivos y reporta solo vulnerabilidades explotables:\n" + "\n".join(lote)
    async for m in query(prompt=prompt, options=opciones):
        if isinstance(m, ResultMessage):                 # (5) el último mensaje trae el resultado
            ok = m.subtype == "success" and m.structured_output is not None
            return {"ok": ok, "subtype": m.subtype, "costo": m.total_cost_usd or 0.0,
                    "turnos": m.num_turns, "sesion": m.session_id, "salida": m.structured_output}
    return {"ok": False, "subtype": "sin_resultado", "costo": 0.0}
  1. cwd es el directorio de trabajo del agente. En un orquestador serio es la copia del repositorio dentro de una caja (69.10), no tu checkout.
  2. setting_sources=[] desactiva la configuración del sistema de archivos: ni la tuya ni la del repositorio. Es lo mismo que pide --bare por la misma razón.
  3. Bash y edición fuera, y dontAsk para que nada quede esperando una aprobación que no va a llegar.
  4. max_budget_usd corta la tarea cuando la estimación llega a ese valor, pero la estimación puede pasarlo: la documentación pide dejar margen Documentado. Es el tope por tarea; el de la corrida está en 69.7.
  5. El último mensaje es un ResultMessage. Su subtype dice cómo terminó: success, error_max_turns, error_max_budget_usd, error_during_execution o error_max_structured_output_retries Documentado. Solo success con structured_output cuenta como tarea hecha.

Python de por medio

async def y async for son la forma de Python de esperar respuestas de red sin bloquear: query() va entregando mensajes a medida que el agente trabaja. Para correr varias tareas a la vez se lanzan con asyncio.gather y se limita cuántas hay en vuelo con un asyncio.Semaphore.

69.4La unidad de trabajo

La primera decisión de diseño es qué recibe cada agente. En el mínimo de M62 era un candidato: una línea sospechosa. DeepSec usa otra unidad: el archivo, agrupado en lotes de --batch-size archivos, con --concurrency lotes en vuelo; con 5 y 5 hay 25 archivos investigándose a la vez Documentado.

La razón es el costo fijo de cada sesión. Antes de leer una línea de tu código, cada sesión manda el system prompt del harness, la descripción de las herramientas y la del proyecto. Supón 15 000 tokens de arranque y 3 USD por millón de tokens de entrada (los dos son supuestos; mide los tuyos):

UnidadSesionesTokens de arranqueCosto solo de arrancar
Un candidato3 00045 millones135 USD
Un archivo1 20018 millones54 USD
Un lote de 5 archivos2403.6 millones10.80 USD

La cuenta es sesiones × 15 000 × 3 ÷ 1 000 000. El prompt caching baja ese costo (el prefijo es el mismo en todas las sesiones, M16), pero no la latencia de arranque ni las vueltas que el agente gasta en orientarse.

Trade-off

Una unidad más grande paga menos arranques y deja que el agente vea relaciones entre archivos del mismo lote. A cambio, llena más rápido su ventana, una falla repite más trabajo y un hallazgo se atribuye peor. Una unidad más chica aísla mejor y se reintenta barato, pero paga muchos arranques. Los lotes funcionan mejor cuando agrupan archivos que se relacionan (el mismo módulo, el mismo endpoint) que cuando se arman por orden alfabético.

69.5Estado en disco y reanudación

Una corrida completa dura horas. Si el estado viviera en la memoria del orquestador, cualquier corte (un Ctrl-C, la laptop que se duerme, el runner de CI que se recicla) obligaría a empezar de cero y a pagar todo otra vez. DeepSec guarda un JSON por archivo fuente, el FileRecord, y uno por corrida, el RunMeta, bajo .deepsec/data/ Documentado.

CampoPara qué
statuspending, processing, analyzed o error
lockedByRunIdQué corrida tiene el archivo; se limpia al terminar
candidatesLo que encontraron los matchers, con su slug y sus líneas
findingsEl último juego de hallazgos; revalidate y triage los anotan sin reemplazarlos
analysisHistoryUna entrada por análisis, que solo se agrega: corrida, agente, modelo, costUsd, durationMs, uso de tokens y, si pasó, la negativa del modelo
fileHashSHA-256 del contenido en el último scan: dice si el archivo cambió

Tres propiedades de ese diseño son las que hacen barato reintentar. El historial solo se agrega, así que un análisis repetido no borra el anterior. El reclamo es atómico, así que dos workers no investigan el mismo archivo. Y el estado describe el trabajo, no al proceso que lo hace: cualquier corrida nueva sabe qué falta leyendo el disco. Es la ejecución durable de M25.8 con la granularidad de un archivo.

El lock huérfano

La documentación de DeepSec describe el lock pero no qué pasa si el proceso que lo tiene muere sin escribir error (un kill -9, un corte de luz): el archivo quedaría en processing para siempre. Es el problema clásico del lock sin plazo, y la respuesta clásica es un lease: el reclamo vence solo. En un orquestador propio, el claim de una tarea se puede hacer en SQLite con dos sentencias. Diseño de referencia

CREATE TABLE tareas (
  id        INTEGER PRIMARY KEY,
  archivos  TEXT    NOT NULL,                    -- el lote, como JSON
  estado    TEXT    NOT NULL DEFAULT 'pending',  -- pending | processing | analyzed | error
  intentos  INTEGER NOT NULL DEFAULT 0,
  run_id    TEXT,                                -- quién la tiene
  vence     REAL                                 -- hasta cuándo (lease)
);
-- (1) Reclamar: una tarea libre, fallida o con el lease vencido
UPDATE tareas
   SET estado = 'processing', run_id = :run, vence = :ahora + 900, intentos = intentos + 1
 WHERE id = (SELECT id FROM tareas
              WHERE (estado IN ('pending', 'error') OR (estado = 'processing' AND vence < :ahora))
                AND intentos < 3
              ORDER BY id LIMIT 1)
RETURNING id, archivos;

-- (2) Cerrar: solo si la tarea sigue siendo de este run
UPDATE tareas SET estado = 'analyzed', vence = NULL
 WHERE id = :id AND run_id = :run;
  1. El UPDATE … RETURNING reclama y devuelve en una sola sentencia, así que dos workers no pueden tomar la misma fila. Una tarea con el lease vencido vuelve a estar disponible, y intentos < 3 evita que un lote que siempre rompe al agente se reintente para siempre: después de tres, queda para mirarlo a mano, como en una DLQ.
  2. El cierre comprueba run_id. Si este worker tardó tanto que su lease venció y otro tomó la tarea, su escritura no afecta a nada: el run_id hace de fencing token (M06.1).

Con leases, una misma tarea puede terminar dos veces: el worker lento y el que la retomó. Es entrega "al menos una vez" (M07), y la consecuencia es la misma de siempre: lo que se escribe al terminar tiene que ser idempotente. Guardar un hallazgo con una clave estable (69.8) lo es; mandar un comentario al PR desde el worker no lo es.

69.6Concurrencia y límites

Más agentes a la vez terminan antes, hasta que choca contra el límite de requests por minuto de tu clave (M18). Cada lote en vuelo no hace una request: hace decenas, una por vuelta del bucle. Con las cifras de ejemplo de la primera corrida (40 llamadas al modelo en 6 minutos por lote), un lote pide unas 6.7 requests por minuto, y la cuenta es la ley de Little al revés:

Lotes en vueloRequests por minutoCon un límite de 50
533Entra, con margen para reintentos
747El máximo: 50 ÷ 6.7 = 7.5
20133429 constantes: los agentes reintentan con backoff y la corrida no termina antes

Pasado el límite, subir la concurrencia no acelera nada: las requests que sobran vuelven con 429, cada agente espera su backoff (M08) y el throughput queda en lo que el límite permite. Peor: los reintentos de muchos agentes a la vez se sincronizan y forman la tormenta de M08. La concurrencia correcta se calcula con el límite y se deja un margen; los tokens por minuto se calculan igual, con los tokens de cada vuelta.

69.7Presupuesto por tarea y por corrida

Hay dos topes y protegen de cosas distintas. El de la tarea (max_turns, max_budget_usd o --max-budget-usd) protege de un agente que se pierde: un bucle que relee los mismos archivos, una herramienta que devuelve algo gigante (M25.6). El de la corrida protege de tu propio error de cálculo: un matcher demasiado amplio, un repositorio más grande de lo que pensabas.

El sobrepaso tiene una cota: como mucho, (lotes en vuelo − 1) × el costo máximo de un lote. Con 5 en vuelo y 1.50 USD por lote son 6 USD sobre un tope de 20, un 30 %. Si eso no es aceptable, se hace lo mismo que con las cuotas de tokens de M18 y los créditos de M21: reservar el máximo de cada tarea antes de lanzarla y cerrar con lo real. Diseño de referencia

import threading

class Presupuesto:
    """Tope de una corrida con reservas: nunca se lanza un lote que podría pasarlo."""
    def __init__(self, tope_usd: float):
        self.tope, self.gastado, self.reservado = tope_usd, 0.0, 0.0
        self.lock = threading.Lock()

    def reservar(self, maximo: float) -> bool:          # (1) antes de lanzar
        with self.lock:
            if self.gastado + self.reservado + maximo > self.tope:
                return False
            self.reservado += maximo
            return True

    def cerrar(self, maximo: float, real: float):       # (2) cuando termina
        with self.lock:
            self.reservado -= maximo
            self.gastado += real
  1. Se reserva el tope de la tarea, el mismo valor que se pasa como max_budget_usd. Si no entra, no se lanza: la corrida termina de forma ordenada y lo que falta queda en pending.
  2. Al terminar se libera la reserva y se suma el costo real, que casi siempre es menor. Como max_budget_usd puede pasarse un poco, el tope de la tarea que se reserva lleva margen.

Con reservas, el gasto de la corrida nunca pasa del tope, al precio de dejar lotes sin lanzar aunque al final hubieran entrado. El tercer tope es el del tiempo (--max-duration en DeepSec Documentado): en CI, un escaneo que no termina antes que el resto del pipeline no sirve.

69.8Salida estructurada y deduplicación

Un agente que responde en prosa obliga a un segundo modelo a interpretarlo. Por eso todos los agentes de DeepSec reciben el mismo prompt y devuelven el mismo esquema, sea Codex o Claude, y los hallazgos de backends distintos se mezclan en el mismo proyecto Documentado. Cada hallazgo trae severidad, slug de la vulnerabilidad, título, descripción, líneas, recomendación y confianza.

Pedir un esquema no es lo mismo que recibirlo. Las salidas estructuradas garantizan la forma cuando hay salida, pero una tarea puede terminar sin ella: por turnos, por presupuesto o porque el modelo se negó. La regla para el orquestador es simple: sin structured_output la tarea quedó en error, no en "sin hallazgos". DeepSec guarda la negativa en la entrada del historial, para que se vea.

El segundo problema es el mismo hallazgo visto dos veces: en dos corridas, en dos lotes que comparten una función, o por dos backends. DeepSec deduplica por slug y título Documentado. En un diseño propio conviene una clave que sobreviva a que el archivo cambie: los números de línea se mueven con cada commit, el fragmento de código no. Diseño de referencia

import hashlib, re

def clave(h: dict) -> str:
    # El mismo problema conserva su clave aunque se muevan los números de línea
    fragmento = re.sub(r"\s+", " ", h["fragmento"]).strip()
    return hashlib.sha256(f'{h["archivo"]}|{h["slug"]}|{fragmento}'.encode()).hexdigest()[:16]

Con esa clave, guardar un hallazgo es un upsert idempotente: repetir la tarea, o que dos workers la terminen, deja un solo registro. Y "hallazgos nuevos" para el PR es una diferencia de conjuntos entre las claves de hoy y las ya conocidas.

69.9Segunda opinión y triage

Los agentes que buscan vulnerabilidades encuentran muchas que no lo son: una entrada que parece del usuario pero ya se validó tres llamadas antes, un código que nunca se ejecuta. DeepSec ataca esos falsos positivos con una revalidación de hallazgos: otro agente relee el código de cada hallazgo, consulta el historial de git para ver si ya se arregló y emite un veredicto: true-positive, false-positive, fixed o uncertain Documentado.

  • Por qué otro contexto: el revalidador recibe el hallazgo, no la conversación que lo produjo. Si heredara el razonamiento del primero, heredaría sus errores. Es la misma idea que un juez separado del modelo que se evalúa.
  • Cuánto cuesta: parecido a investigar, porque relee el código. La documentación recomienda usarlo en severidad alta o más, y reporta que baja los falsos positivos en más del 50 % en la mayoría de los repositorios Documentado.
  • Triage: clasifica en P0, P1 y P2 con un modelo más barato, sin una investigación completa Documentado. No decide si algo es real; decide qué mira primero una persona.
  • Lo que no hace: ninguna de las dos etapas encuentra lo que el scan no marcó. El techo de recall lo ponen los matchers, y una revalidación perfecta solo mejora la precisión.

69.10Aislamiento por tarea

Un orquestador de seguridad tiene una propiedad incómoda: su trabajo es leer código que no es de confianza. Ese código puede traer instrucciones escritas para el agente que lo lee, la injection indirecta de M25. Un buen modelo suele ignorarlas; el diseño supone que alguna vez no lo hace.

En modo sandbox, DeepSec reparte el trabajo en microVMs de Vercel Sandbox: empaqueta el árbol local sin .git, lo sube a cada caja, mantiene las credenciales del modelo en el host y las inyecta solo en el host de salida elegido, y limita la salida de la caja a los hosts de los agentes de código Documentado. Cada decisión cierra un camino distinto:

DecisiónQué cierra
Una microVM por lote, desechableLo que un agente rompa o deje (un archivo, un proceso) no afecta al siguiente ni a tu máquina
Copia sin .gitEl historial, los remotos y sus credenciales no entran
La credencial fuera de la cajaUna injection que lee el entorno no encuentra nada que robar
Salida solo hacia el modeloAunque el agente obedezca, no tiene adónde mandar lo que lee
--bare o setting_sources=[]El repositorio no decide qué hooks ni qué servidores MCP corren

Sin modo sandbox, los agentes corren en el host con lo que el host tenga. Para tu propio repositorio, en tu laptop, puede ser aceptable; para el código de un tercero, no. Las capas de control (pesos, proveedor, harness y sistema operativo) son las de M62.10; cómo se arma la caja con bubblewrap, Seatbelt, contenedores o microVMs es M66.

Qué pasa si falla

La caja protege tu máquina, no lo que ya está en el código. Un secreto versionado en el repositorio entra en la copia como cualquier otro archivo y el agente lo lee; si la salida permite algún host genérico (un almacenamiento de objetos, un pastebin), puede salir por ahí. Los secretos se buscan con otra herramienta antes (M55) y la lista de hosts permitidos se mantiene tan corta como sea posible.

69.11En CI

El mismo orquestador se usa de dos formas. El escaneo completo del repositorio se corre aparte, con tope, cada tanto. En cada pull request se corre solo sobre lo que cambió (process --diff Documentado): pocos lotes, pocos dólares, y una respuesta antes de que alguien apruebe el merge.

on: pull_request

jobs:
  deepsec:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - run: pnpm install --frozen-lockfile
      # Solo PR del mismo repositorio: un fork no recibe la clave
      - name: Escaneo del diff
        if: github.event.pull_request.head.repo.full_name == github.repository
        env:
          MODELO_API_KEY: ${{ secrets.MODELO_API_KEY }}
        run: pnpm deepsec process --diff

Tres decisiones de ese job son de seguridad, no de comodidad Diseño de referencia:

  • Permisos mínimos del token del job: leer el código y comentar en el PR, nada más.
  • La clave solo en el paso que la usa. pnpm install corre scripts de dependencias; si la clave fuera una variable de todo el job, esos scripts podrían leerla. Es la misma advertencia que hace la documentación de Codex para CODEX_API_KEY Documentado. MODELO_API_KEY es el nombre que hayas configurado con --ai-api-key-env: DeepSec guarda el nombre de la variable, nunca la clave Documentado.
  • Los forks no reciben la clave. Un PR desde un fork trae código de un tercero; escanearlo con tu clave es darle la clave a ese código. Ese escaneo va en un job aparte que una persona aprueba, o con el modo sandbox.

Dónde encaja en el pipeline respecto del SAST tradicional está en M55.8: el SAST es rápido, determinista y barato, y corre siempre; el escaneo con agentes es lento y caro, encuentra fallas de lógica que el SAST no ve, y corre sobre el diff.

Haz clic en cualquier pieza para ver qué hace, qué guarda, cómo falla y sus números.

En producción real

Antes de escalar un orquestador, mide tres números con una corrida acotada: costo y minutos por tarea, tasa de tareas que terminan en error y tasa de falsos positivos después de revalidar. Con esos tres, el widget de 69.6 te dice la duración y la factura de la corrida completa, y sabes si el resultado vale lo que cuesta.
