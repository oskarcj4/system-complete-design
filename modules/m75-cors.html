CORS a fondo

CORS no es una defensa: es una excepción. La Same-Origin Policy ya bloquea leer respuestas de otro origen, y CORS es la forma de que tu servidor diga a quién se lo permite. Configurarlo mal es regalar ese permiso.

En M74 quedó la regla base: el JavaScript de un origen puede enviar a otro, pero no puede leer lo que vuelve. Eso está bien hasta que tu frontend y tu API viven en orígenes distintos, como app.practicas.edu.gt y api.practicas.edu.gt. Entonces tu propio frontend no puede leer tu propia API. CORS (Cross-Origin Resource Sharing) es la forma de que la API diga "a este origen sí le dejo leer".

75.1Qué relaja CORS y quién lo hace cumplir

Analogía

Es la lista de invitados en la puerta de un edificio. El dueño del departamento (el servidor) escribe la lista. El portero (el navegador) la lee y decide quién pasa. Quien entra por la puerta del garaje (curl, un script en otro servidor) no pasa por el portero.

CORS es un conjunto de cabeceras con las que el servidor le dice al navegador qué orígenes pueden leer sus respuestas Documentado. El navegador agrega la cabecera Origin a la request, y al recibir la respuesta compara ese valor con Access-Control-Allow-Origin. Si no coinciden, le esconde la respuesta al JavaScript y le da un TypeError.

Esto tiene una consecuencia que conviene fijar desde ya: CORS no es una protección del servidor. Una API sin ninguna cabecera CORS sigue recibiendo requests de cualquier lado, y una API con Access-Control-Allow-Origin: * no queda "más abierta" para curl, que nunca miró esa cabecera. CORS protege los datos que el navegador de tu usuario puede traer con su sesión.

El mensaje que ves en la consola cuando falla:

Access to fetch at 'https://api.practicas.edu.gt/v1/postulaciones' from origin
'https://app.practicas.edu.gt' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.

Si todo vive en el mismo origen, no necesitas CORS. Es el caso de tu sistema hoy: el frontend y la API están bajo http://localhost, y response.php no manda ninguna cabecera CORS, y está bien. Lo necesitarás en el laboratorio de WEB00, donde el frontend corre en otro puerto.

75.2La request simple: sale sin preguntar

Para no romper la web anterior a CORS, el navegador deja salir sin consulta previa las requests que un formulario HTML ya podía mandar: método GET, HEAD o POST, solo cabeceras de una lista segura y un Content-Type de formulario o texto (application/x-www-form-urlencoded, multipart/form-data o text/plain) Documentado.

// Una request simple: método POST y Content-Type de formulario, sin cabeceras propias
await fetch('https://api.practicas.edu.gt/v1/postulaciones', {
  method: 'POST',
  credentials: 'include',                       // manda la cookie, si SameSite la deja
  body: new URLSearchParams({ oportunidad: '7' })
});

Mira la nota del medio: el efecto ocurre antes de cualquier comprobación de CORS. Por eso una request simple que cambia datos es una request que cualquier sitio puede disparar. Es exactamente la forma de CSRF (75.7).

75.3El preflight: preguntar antes

Todo lo que un formulario no podía mandar (un PUT, un DELETE, un cuerpo application/json, una cabecera propia como X-CSRF-Token) necesita permiso antes de salir. El navegador manda primero un preflight: una request OPTIONS sin cookies ni body que pregunta por el método y las cabeceras Documentado.

OPTIONS /v1/oportunidades/7 HTTP/1.1
Host: api.practicas.edu.gt
Origin: https://app.practicas.edu.gt
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, x-csrf-token

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.practicas.edu.gt
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, X-CSRF-Token
Access-Control-Max-Age: 600
Vary: Origin

Access-Control-Max-Age deja que el navegador recuerde la respuesta del preflight por unos segundos y no lo repita en cada request. Cada navegador pone su propio tope: Chrome lo limita a dos horas Documentado.

Qué pasa si falla

El preflight no lleva cookies. Si el endpoint llama a requireAuth() antes de responder el OPTIONS, contesta 401 y el navegador nunca manda la request real. El síntoma es un frontend que "no puede" hacer PUT aunque la sesión esté bien. El OPTIONS se responde primero, sin autenticar (75.9).

75.4Credenciales: cookies con CORS

Por defecto, un fetch a otro origen no manda cookies. Con credentials: 'include' sí, y entonces el servidor tiene que cumplir dos reglas más para que el JavaScript lea la respuesta Documentado:

  • responder Access-Control-Allow-Credentials: true;
  • poner en Access-Control-Allow-Origin el origen exacto, nunca *.

La prohibición del comodín es deliberada: "cualquier origen puede leer con la sesión del usuario" es el agujero más grande que se puede abrir, y la especificación no deja escribirlo de una vez. Lo que sí deja es escribirlo a mano, origen por origen, y ese es el error de 75.6.

Y una capa más, de M74: aunque CORS lo permita, la cookie viaja solo si su SameSite lo deja. Con Lax, un fetch desde otro sitio va sin la cookie. Entre app. y api. del mismo dominio sí viaja, porque son el mismo sitio.

75.5Vary: Origin y las cachés

Si la respuesta cambia según el Origin, una caché intermedia (un CDN, un proxy, la del propio navegador) tiene que saberlo. Si no, guarda la respuesta que se pidió desde un origen y se la sirve a otro Documentado.

La regla práctica: si Access-Control-Allow-Origin depende del Origin, manda Vary: Origin siempre, también cuando el origen no está permitido. Ese es el tipo de envenenamiento de caché que M83 retoma.

75.6Los errores que abren una API

Casi todos los fallos reales de CORS son el mismo: aceptar más orígenes de los que se quería Documentado. Los típicos:

  • Reflejar el Origin. Copiarlo en la respuesta es aceptar a todos, con credenciales.
  • Aceptar null. Lo manda una página dentro de un iframe con sandbox, un archivo local o algunas redirecciones. Cualquiera puede producirlo.
  • Expresiones sin ancla. /practicas\.edu\.gt/ también acepta practicas.edu.gt.ofertas-gratis.example.
  • Confiar en todos los subdominios. Si un subdominio cualquiera tiene un XSS, ese XSS lee tu API con la sesión del usuario.
<?php
// MAL: refleja cualquier Origin y además permite credenciales
header('Access-Control-Allow-Origin: ' . ($_SERVER['HTTP_ORIGIN'] ?? '*'));
header('Access-Control-Allow-Credentials: true');
<?php
// MAL: la expresión no tiene ancla, así que acepta
// https://practicas.edu.gt.ofertas-gratis.example y https://evilpracticas.edu.gt
if (preg_match('/practicas\.edu\.gt/', $_SERVER['HTTP_ORIGIN'] ?? '')) {
    header('Access-Control-Allow-Origin: ' . $_SERVER['HTTP_ORIGIN']);
    header('Access-Control-Allow-Credentials: true');
}

Prueba cada política con cada origen. Mira tres cosas: si hubo preflight, si la request llegó a PHP y si el JavaScript leyó la respuesta.

Tres lecturas. Con la política "reflejar", el frontend del blog lee la respuesta con la cookie: la política tiene un agujero, aunque la cookie sea Lax, porque el blog es el mismo sitio. Con "otro sitio" y un POST de formulario, ninguna política impide que la request llegue: solo cambia si se lee. Y con application/json, la política "sin cabeceras" frena el PUT en el preflight: un efecto secundario útil, pero no una defensa que puedas dar por sentada.

75.7CORS no protege contra CSRF

Es la confusión más común de esta parte. CORS decide quién lee; CSRF es alguien que envía con tu sesión. Un formulario de otro sitio manda una request simple, sin preflight, y el efecto ocurre antes de que el navegador mire CORS.

Que un endpoint exija application/json o una cabecera propia fuerza el preflight y, de rebote, frena los formularios de otros sitios. Es una capa útil, y tu X-CSRF-Token ya tiene ese efecto. Pero depende de que el servidor rechace los otros Content-Type, algo que PHP no hace solo: $_POST se llena con cualquier formulario. Las defensas de verdad son las de M76.

75.8Las requests a la red local

Una página pública puede hacer requests a http://localhost o a 192.168.1.1: a tu XAMPP, a tu router. Son requests simples que llegan, y si ese servicio no autentica, el efecto ocurre. Chrome agregó primero preflights especiales para esto (Private Network Access) y después los reemplazó por un permiso que el usuario concede, Local Network Access Documentado.

No cuentes con eso para tu laboratorio: es una protección del navegador, cambia entre versiones y no existe igual en todos. Un servicio local que no autentica es un servicio que cualquier página puede usar. La guía WEB00 deja Apache escuchando solo en 127.0.0.1, y eso evita que lo usen otras máquinas de la red, no otras páginas de tu navegador.

75.9La política en PHP

La política de referencia para el sistema de prácticas, cuando el frontend viva en otro origen Diseño de referencia:

<?php
// api/core/cors.php (diseño de referencia): se incluye primero en cada endpoint
declare(strict_types=1);

const CORS_ORIGINS = [                       // comparación exacta, sin expresiones
    'https://app.practicas.edu.gt',
    'http://localhost:5173',                 // el frontend del laboratorio (WEB00)
];

function applyCors(): void
{
    header('Vary: Origin', false);           // la respuesta cambia según el Origin
    $origin = $_SERVER['HTTP_ORIGIN'] ?? '';
    $allowed = in_array($origin, CORS_ORIGINS, true);

    if ($allowed) {
        header('Access-Control-Allow-Origin: ' . $origin);
        header('Access-Control-Allow-Credentials: true');
    }

    if ($_SERVER['REQUEST_METHOD'] === 'OPTIONS') {   // preflight: sin cookie ni body
        if ($allowed) {
            header('Access-Control-Allow-Methods: GET, POST, PUT, DELETE');
            header('Access-Control-Allow-Headers: Content-Type, X-CSRF-Token');
            header('Access-Control-Max-Age: 600');
        }
        http_response_code(204);
        exit;                                // nunca llega a requireAuth ni al modelo
    }
}

Y el orden dentro del endpoint importa: primero el preflight, que no trae sesión; después la autenticación, y después el token, solo en lo que cambia datos.

<?php
// Al principio de endpoints/oportunidades.php
require_once __DIR__ . '/../core/cors.php';
applyCors();                                 // 1. el preflight termina aquí
require_once __DIR__ . '/../core/auth-middleware.php';
$auth = requireAuth([ROL_RECLUTADOR]);       // 2. después, la sesión
if ($_SERVER['REQUEST_METHOD'] !== 'GET') {
    requireCsrfToken();                      // 3. y el token, solo si cambia algo
}

Hoy tus endpoints piden el token CSRF también en los GET (hallazgo 8 del plan). Con el orden de arriba, los GET no lo piden, y no deben cambiar nada. La guía WEB04 escribe cors.php completo, con sus pruebas desde los dos orígenes del laboratorio.

Trade-off

Poner el frontend y la API en el mismo origen, con un proxy que manda /api a PHP, elimina CORS del todo: sin preflight, sin política que mantener, sin errores de configuración. A cambio, el proxy es una pieza más. Para un sistema como el tuyo, el mismo origen suele ser la opción más simple y segura.

Prueba la política con curl, cambiando el Origin a mano: curl -i -H "Origin: https://ofertas-gratis.example" ….
