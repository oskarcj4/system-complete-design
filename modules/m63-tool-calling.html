Tool calling por dentro

Para la API, una llamada a herramienta es un bloque JSON prolijo. Para el modelo es texto con unos tokens raros en el medio. Entre las dos cosas hay un template, un parser y a veces una gramática, y casi todas las fallas de un agente con un modelo local viven ahí.

63.1La vida de una llamada

En M17.6 viste el tool calling desde la API: declaras funciones con JSON Schema, el modelo responde con una llamada, tu código la ejecuta y devuelve el resultado con el mismo id. En M62.5 ese intercambio se volvió el bucle de un agente. Este módulo abre lo que pasa entre la API y los pesos: allí está la diferencia entre un agente que funciona con Claude y se rompe con un modelo local, o entre una llamada que siempre parsea y una que falla una de cada cincuenta veces.

Analogía

Un traductor en una reunión. Tú hablas en JSON, el modelo solo entiende un idioma de texto con sus propias convenciones. El chat template traduce de ida; el parser traduce de vuelta. Si el traductor no conoce el dialecto del modelo, la reunión sigue, pero nadie entiende lo que se pidió.

  1. Definición de la herramientaNombre, descripción y JSON Schema de los argumentos. Es prompt y es contrato. 63.5
  2. Chat templateEl programa que convierte mensajes y herramientas en el texto que lee el modelo. 63.2
  3. Tokens especialesMarcas que el tokenizer reserva para los bordes: turnos, llamadas, resultados. 63.2
  4. Decodificación restringidaUna máscara que en cada paso deja pasar solo los tokens que cumplen el esquema. 63.6
  5. Parser de llamadasLee el texto que generó el modelo y arma la llamada estructurada. 63.4
  6. tool_use o tool_callsLa llamada como la entrega la API, con id, nombre y argumentos. 63.3
  7. stop_reasonPor qué terminó el turno: llamada, fin, corte por tokens, pausa o rechazo. 63.9
  8. tool_resultEl resultado que vuelve al modelo atado al id de su llamada. 63.8
  9. tool_choiceSi el modelo puede, debe o no puede llamar, y a cuál. 63.7

63.2Chat templates y tokens especiales

Un modelo de lenguaje no recibe JSON: recibe una secuencia de tokens y predice el siguiente (M12.2). Lo que llamas "mensajes" y "herramientas" es una comodidad de la API. Antes de la primera pasada, el servidor arma un solo texto con un chat template: un programa en Jinja que viene con el modelo, en su tokenizer_config.json, y que decide cómo se escribe cada turno, dónde van las herramientas y cómo empieza la respuesta Documentado.

Los bordes se marcan con tokens especiales: piezas del vocabulario reservadas que el texto normal no produce, como <|im_start|> y <|im_end|> en Qwen, o <|start_header_id|> y <|eot_id|> en Llama 3. Son un solo token cada uno, y el modelo aprendió en el entrenamiento qué significa cada uno. Este es el texto que arma Qwen3 para una request con una herramienta, abreviado Documentado:

<|im_start|>system
Eres un agente de programación.

# Tools

You may call one or more functions to assist with the user query.

You are provided with function signatures within <tools></tools> XML tags:
<tools>
{"type": "function", "function": {"name": "leer_archivo", "description": "Lee un archivo…", "parameters": {…}}}
</tools>

For each function call, return a json object with function name and arguments within <tool_call></tool_call> XML tags:
<tool_call>
{"name": <function-name>, "arguments": <args-json-object>}
</tool_call><|im_end|>
<|im_start|>user
Lee src/app.py<|im_end|>
<|im_start|>assistant

Tres consecuencias que importan al construir:

  • Las herramientas son prompt. No hay un canal aparte: la lista entera viaja como texto de entrada, en cada request. Diez herramientas con buenas descripciones pueden ser 2 000 tokens antes de que el usuario escriba nada. Anthropic hace lo mismo del lado del proveedor: con tools, la API arma un system prompt especial con las definiciones, que también se factura Documentado.
  • El template es parte del modelo. Un modelo afinado con un formato de llamada lo usa bien solo si recibe ese formato. Servirlo con otro template, o con uno incompleto (un GGUF convertido sin la parte de herramientas, por ejemplo), produce un modelo que "no sabe usar herramientas" aunque sí sepa.
  • Lo puedes ver. El tokenizer aplica el template sin GPU, y es la forma más barata de depurar un agente con un modelo abierto:
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-8B")
tools = [{"type": "function", "function": {"name": "leer_archivo", "description": "Lee un archivo del proyecto.",
          "parameters": {"type": "object", "properties": {"ruta": {"type": "string"}}, "required": ["ruta"]}}}]
mensajes = [{"role": "user", "content": "Lee src/app.py"}]

# El mismo template que usa el servidor, sin GPU ni modelo: solo el tokenizer.
texto = tok.apply_chat_template(mensajes, tools=tools, tokenize=False, add_generation_prompt=True)
print(texto)
print(len(tok(texto)["input_ids"]), "tokens de entrada")

Qué pasa si falla

Ollama responde does not support tools cuando el template del modelo que bajaste no tiene la sección de herramientas, aunque el modelo base las soporte. El arreglo no está en tu harness: es usar una variante del modelo con el template correcto, o escribir un Modelfile con el template oficial.

63.3Cada familia, su formato

No hay un estándar de cómo se escribe una llamada dentro del texto. Cada familia de modelos eligió el suyo al entrenar, y el servidor tiene que conocerlo para encontrarla. Tres ejemplos documentados en sus model cards Documentado:

FamiliaCómo escribe la llamadaCómo vuelve el resultadoId de la llamada
Qwen 2.5 y 3 (estilo Hermes)JSON con name y arguments entre <tool_call> y </tool_call>En un turno user, entre <tool_response>No hay: se empareja por orden
Llama 3.1JSON suelto con name y parameters, una llamada por turnoRol propio, ipythonNo hay
Kimi K2Tokens especiales: <|tool_calls_section_begin|>, <|tool_call_begin|>, id, <|tool_call_argument_begin|>, JSONMensaje con rol tool y tool_call_idfunctions.nombre:índice

Elige un formato y un caso: la misma llamada a leer_archivo en los dos dialectos de API (M62.3) y en el texto de tres templates.

Lo que el widget muestra con "Dos en paralelo" es la razón de muchas sorpresas: un harness que espera varias llamadas por turno (Claude Code pide varias lecturas a la vez) funciona con un modelo que las emite así y tarda el doble con uno que emite de a una. No es un error: es el formato con el que se entrenó cada modelo.

63.4Del texto al JSON: el parser

Cuando el modelo termina de generar, la API tiene que devolver tool_calls, no texto con etiquetas. Ese trabajo lo hace un parser de llamadas del servidor, específico para cada formato. En vLLM se activa con dos flags y se elige por nombre Documentado:

# Qwen3 con el parser de llamadas estilo Hermes (documentación de Qwen y vLLM)
vllm serve Qwen/Qwen3-8B --enable-auto-tool-choice --tool-call-parser hermes

# Sin los dos flags, el servidor devuelve el <tool_call> como texto en content

La rama de abajo de la figura explica una falla típica con modelos chicos: el modelo escribió <tool_call>, se equivocó en una coma, y el harness recibió una respuesta de texto sin llamadas. Para el bucle de M62.6, "sin llamadas" significa "terminó", así que el agente se detiene en mitad de la tarea y dice algo como "voy a leer el archivo" sin leerlo. Tres defensas, de la más barata a la más cara:

  • En el harness: si la respuesta final contiene restos de una llamada (<tool_call>, {"name":), no terminar: devolverle al modelo un mensaje que diga que la llamada no se pudo leer.
  • En el servidor: el parser correcto para el modelo, y la versión del servidor que lo trae. Un parser de Hermes sobre un modelo con formato propio no encuentra nada.
  • En la generación: decodificación restringida dentro de la llamada (63.6), que hace imposible el JSON roto.

63.5Describir una herramienta

La definición de una herramienta hace tres trabajos a la vez, y conviene escribirla pensando en los tres.

Es prompt. El modelo decide si llamar, a cuál y con qué argumentos leyendo el nombre y las descripciones. Anthropic dice que la descripción detallada es "por lejos" el factor más importante del rendimiento con herramientas, y pide tres o cuatro oraciones por herramienta: qué hace, cuándo usarla y cuándo no, qué significa cada parámetro y qué no devuelve Documentado. También recomienda agrupar operaciones relacionadas en menos herramientas y usar prefijos por servicio (github_list_prs) cuando son muchas Documentado.

Es contrato. Lo que el esquema dice (tipos, obligatorios, enum, sin campos extra) es lo que tu código puede suponer, y lo que una gramática puede imponer. El modo estricto de OpenAI exige additionalProperties: false y que todos los campos estén en required; un campo opcional se escribe como un tipo que admite null Documentado:

{
  "type": "function",
  "function": {
    "name": "leer_archivo",
    "description": "Lee un archivo del proyecto y devuelve su contenido con números de línea. Úsala antes de editar. No sirve para directorios: para eso está listar.",
    "strict": true,
    "parameters": {
      "type": "object",
      "properties": {
        "ruta":  {"type": "string", "description": "Ruta relativa a la raíz del proyecto, como src/app.py"},
        "desde": {"type": ["integer", "null"], "description": "Primera línea a leer; null para empezar en la 1"}
      },
      "required": ["ruta", "desde"],
      "additionalProperties": false
    }
  }
}

Es costo. Viaja en cada request, en el prefijo. Si el orden de las herramientas cambia entre requests, se rompe el prompt caching de todo lo que viene después (M16). Una herramienta de más que nadie usa es una factura fija.

Trade-off

Más herramientas dan más capacidad y más confusión: con cincuenta, el modelo elige mal más seguido y el prefijo crece. Los harnesses resuelven esto cargando herramientas bajo demanda (las de un servidor MCP solo cuando hacen falta), un tema de M67.

63.6Decodificación restringida a fondo

En M17.7 viste la idea: la decodificación restringida compila el esquema y, en cada paso, enmascara los tokens que dejarían la salida fuera de él. Aquí va el mecanismo, porque explica tanto lo que garantiza como lo que no.

  1. CompilarEl esquema se convierte en una gramática y la gramática en un autómata. Se hace una vez por esquema y se guarda en caché: compilar un esquema grande puede tardar más que generar la respuesta.
  2. EnmascararEn cada paso, el motor recorre el vocabulario (100 000 tokens o más) y marca cuáles pueden seguir sin salir de la gramática. Los demás reciben −∞ en sus logits, y la softmax les da probabilidad cero.
  3. AvanzarEl token muestreado mueve el autómata, y el estado nuevo define la máscara siguiente.

La dificultad está en que los tokens no coinciden con la gramática: un token puede ser ":", ta": o /app.py"}, y cruzar varios símbolos de una vez. Por eso los motores trabajan sobre bytes y precalculan qué tokens son válidos en cada estado. Las implementaciones conocidas son XGrammar (el backend por defecto de vLLM para salidas estructuradas), Outlines y las gramáticas GBNF de llama.cpp Documentado:

# Una gramática GBNF de llama.cpp para el mismo esquema (simplificada)
root   ::= "{" ws "\"ruta\":" ws string "," ws "\"modo\":" ws modo ws "}"
modo   ::= "\"leer\"" | "\"contar\""
string ::= "\"" ( [^"\\] | "\\" ["\\/bfnrt] )* "\""
ws     ::= [ \t\n]*

Avanza la generación token por token y compara con la restricción apagada:

Lo que muestra el paso 11 es la frontera exacta de la garantía. La gramática sabe que modo es "leer" o "contar", pero no sabe si src/app.py existe ni si leer era la decisión correcta. Garantiza la forma, no el contenido. Y tiene un costo menos obvio: si el modelo "quería" decir otra cosa (editar), la máscara lo obliga a una opción que no eligió, y la calidad puede bajar. Por eso conviene que el esquema no pelee con lo que el modelo haría naturalmente: nombres de campo obvios y enums que cubran los casos reales.

Del lado de los proveedores, OpenAI aplica la restricción con "strict": true en la herramienta, y Anthropic ofrece strict: true en la definición ("strict tool use") para garantizar argumentos que cumplen el esquema Documentado. Con un modelo propio en vLLM o llama.cpp, la activas tú en el servidor.

63.7tool_choice: puede, debe o no puede

tool_choice le dice al servidor qué está permitido en este turno. Los dos dialectos tienen las mismas cuatro opciones con nombres distintos Documentado:

Cómo se implementa "debe llamar" es instructivo. Anthropic documenta que con any o tool la API pre-llena el turno del asistente para forzar la llamada: el modelo no puede escribir texto antes, y tampoco piensa, porque la respuesta empieza directamente con el bloque tool_use Documentado. Con un servidor propio, "debe llamar" se implementa con la gramática de 63.6: la máscara no deja escribir nada que no sea una llamada.

En producción real

No todos los modelos aceptan forzar una herramienta. La documentación de Anthropic dice que con thinking manual activado any y tool dan error, y que en los modelos más nuevos (Claude Opus 5.5, Sonnet 5.5 y Fable 5.1) devuelven un 400: la alternativa recomendada es auto con strict tool use, o salidas estructuradas si lo que necesitas es JSON con forma fija Documentado. Un harness que funciona con un modelo puede romperse al cambiar de versión por un parámetro como este. Además, cambiar tool_choice entre requests invalida la caché de los mensajes Documentado.

63.8Llamadas en paralelo

Un modelo puede pedir varias herramientas en el mismo turno: varios bloques tool_use, o varias entradas en tool_calls. Si las tres lecturas que necesita salen en un turno, el agente se ahorra dos idas y vueltas al modelo, que son lo más lento del bucle.

Tres reglas que el harness tiene que cumplir:

  • Un resultado por llamada. Cada tool_use necesita su tool_result con el mismo id. En el dialecto de Anthropic van todos juntos en un solo mensaje user, y los tool_result tienen que ir primero en su contenido; en el de OpenAI, un mensaje tool por llamada Documentado. Si falta uno, la API responde 400.
  • Paralelo en el modelo no significa paralelo en tu máquina. Dos lecturas pueden correr a la vez; dos ediciones del mismo archivo no. El harness decide.
  • Se puede apagar. disable_parallel_tool_use: true dentro de tool_choice en Anthropic, parallel_tool_calls: false en OpenAI Documentado. Sirve cuando cada acción depende de la anterior o cuando una herramienta no es segura en concurrencia.
import asyncio

SOLO_LECTURA = {"leer_archivo", "buscar", "listar"}

async def ejecutar_todas(llamadas):
    lecturas = [c for c in llamadas if c.name in SOLO_LECTURA]
    efectos = [c for c in llamadas if c.name not in SOLO_LECTURA]
    res = dict(zip([c.id for c in lecturas],
                   await asyncio.gather(*(ejecutar(c) for c in lecturas))))   # (1) a la vez
    for c in efectos:                                                        # (2) en orden, de a una
        res[c.id] = await ejecutar(c)
    # (3) un resultado por cada llamada, en el orden en que llegaron
    return [{"type": "tool_result", "tool_use_id": c.id, **res[c.id]} for c in llamadas]
  1. Las herramientas sin efectos se ejecutan a la vez.
  2. Las que escriben, en el orden en que el modelo las pidió: si pidió "crear el archivo" y después "editarlo", el orden importa.
  3. El resultado conserva el orden de las llamadas, y cada uno lleva su id.

63.9Por qué terminó el turno

El bucle de un harness no decide "seguir o terminar" mirando si hay texto. Lo decide con el motivo de fin que devuelve la API: stop_reason en Anthropic, finish_reason en OpenAI. Cada valor pide una reacción distinta Documentado:

AnthropicOpenAIQué pasóQué hace el harness
tool_usetool_callsPidió herramientasEjecutarlas y seguir
end_turnstopTerminóMostrar la respuesta y esperar al usuario
max_tokenslengthSe quedó sin tokens de salidaNo ejecutar nada: la llamada puede estar cortada a la mitad
stop_sequencestopApareció una secuencia de parada tuyaLo que hayas definido
pause_turn(sin equivalente)Una herramienta del servidor necesita más tiempoReenviar la conversación tal cual para que siga
refusalcontent_filter (parecido)Se negó o lo frenó un filtroTerminar y no reintentar a ciegas
 
def turno(client, mensajes, tools):
    r = client.messages.create(model=MODELO, max_tokens=8192, system=SYSTEM,
                               tools=tools, messages=mensajes)
    mensajes.append({"role": "assistant", "content": r.content})   # (1) todo, también thinking
    match r.stop_reason:
        case "tool_use":                                              # (2) hay trabajo
            resultados = ejecutar_todas([b for b in r.content if b.type == "tool_use"])
            mensajes.append({"role": "user", "content": resultados})
            return "seguir"
        case "end_turn" | "stop_sequence":                            # (3) terminó
            return "fin"
        case "max_tokens":                                            # (4) cortado a la mitad
            return "subir_max_tokens_o_compactar"
        case "pause_turn":                                            # (5) herramienta del servidor en curso
            return "reenviar_igual"
        case "refusal":                                               # (6) el modelo se negó
            return "fin_con_rechazo"
  1. El turno del asistente se guarda entero, con los bloques de thinking si los hay: Anthropic exige devolverlos sin cambios cuando el turno siguió con herramientas.
  2. Hay llamadas: se ejecutan y se sigue.
  3. Respuesta final.
  4. El caso traicionero. Con max_tokens, el último bloque puede ser una llamada con el JSON a medias. Ejecutarla es ejecutar algo que el modelo no terminó de pedir.
  5. Propio de las herramientas que corre el proveedor, como la búsqueda web.
  6. Un rechazo no es un error transitorio: reintentarlo igual da lo mismo y cuesta.

63.10Argumentos en streaming

Con streaming (M17.5), los argumentos de una llamada no llegan enteros: llegan en fragmentos de JSON parcial. En Anthropic, un content_block_start con el nombre y el id, varios content_block_delta de tipo input_json_delta con partial_json, y un content_block_stop. En OpenAI, entradas en delta.tool_calls con un index y pedazos de arguments Documentado.

buffers = {}                                      # índice del bloque -> {"id", "name", "json"}

for ev in stream:
    if ev.type == "content_block_start" and ev.content_block.type == "tool_use":
        b = ev.content_block
        buffers[ev.index] = {"id": b.id, "name": b.name, "json": ""}
    elif ev.type == "content_block_delta" and ev.delta.type == "input_json_delta":
        buffers[ev.index]["json"] += ev.delta.partial_json    # (1) concatenar, no parsear
    elif ev.type == "content_block_stop" and ev.index in buffers:
        b = buffers.pop(ev.index)
        b["input"] = json.loads(b["json"] or "{}")             # (2) recién ahora es JSON completo
        listas.append(b)
  1. Un fragmento como {"ru no es JSON. Se concatena en el buffer de su índice.
  2. Recién al cierre del bloque el JSON está completo. Parsear antes es la causa de errores que aparecen "solo con streaming".

¿Para qué sirve el stream si no se puede ejecutar nada hasta el final? Para la interfaz. Un harness puede mostrar "editando src/app.py…" en cuanto llega el nombre del archivo, y una edición larga de 300 líneas se ve escribirse en lugar de aparecer de golpe tras 20 segundos. Algunos parsers incrementales leen JSON parcial para eso; la ejecución, igual, espera al cierre.

63.11Por qué unos modelos son mejores agentes

Dos modelos con resultados parecidos en preguntas y respuestas pueden ser muy distintos como agentes. La diferencia no está en saber más, sino en haber practicado el bucle: decidir cuándo llamar, leer un resultado largo, recuperarse de un error, no abandonar a la mitad. Eso se entrena con trayectorias: secuencias completas de llamadas y resultados en entornos con herramientas.

  • Ajuste supervisado con trayectorias: miles de ejemplos de uso correcto de herramientas, en el formato exacto del template (M26). De ahí sale que el modelo escriba bien <tool_call>: lo vio miles de veces.
  • Refuerzo con entornos verificables: el modelo intenta tareas reales (arreglar un test, completar un flujo) y recibe recompensa si un verificador las da por buenas. El informe técnico de Kimi K2 describe un pipeline de síntesis de datos de uso de herramientas a gran escala, con miles de herramientas y entornos simulados, seguido de aprendizaje por refuerzo Documentado.
  • Se mide aparte. El Berkeley Function Calling Leaderboard (BFCL) mide si las llamadas son correctas; τ-bench mide conversaciones completas con herramientas y reglas de negocio, y reporta pass^k para la consistencia Documentado. Un modelo puede ir bien en el primero y mal en el segundo.

Consecuencia práctica: el mismo modelo rinde mejor con el formato y el estilo de herramientas con que se entrenó. Por eso Anthropic define herramientas con tipo propio (un editor de texto y bash "versionados") que Claude conoce de su entrenamiento, y por eso el mismo harness con dos modelos de calidad parecida da resultados distintos. Medirlo con tus tareas es tema de M65 y M72.

63.12Traducir entre dialectos sin perder nada

Un gateway como LiteLLM (M62.3) deja que un harness que habla Anthropic use un modelo que habla OpenAI, y al revés. La mayoría de los campos tienen equivalente directo. Algunos no, y ahí se pierde información en silencio.

DiferenciaQué se rompe si se traduce malCómo resolverlo

En producción real

Antes de confiar en un traductor, corre una conversación de prueba con las tres cosas difíciles: dos llamadas en paralelo, una herramienta que falla y un turno con thinking. Si las tres vuelven bien al harness, el resto suele andar Diseño de referencia.
