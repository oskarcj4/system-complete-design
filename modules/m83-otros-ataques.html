Otros ataques que toda web debe cerrar

Cada ataque de este módulo aprovecha una pieza que hace bien su trabajo: un iframe que muestra otra página, una caché que ahorra trabajo, un proxy que reenvía, una regex que busca. La falla está en el supuesto que nadie escribió.

Los módulos anteriores cubrieron las familias grandes: CSRF (M76), XSS (M77), inyecciones (M79), control de acceso (M80), sesiones (M81) y lo que el servidor hace con URLs y archivos (M82). 83.1Clickjacking

El clickjacking carga tu página en un iframe transparente sobre otra que invita a hacer clic. La víctima cree que hace clic en el sitio del atacante y lo hace en el tuyo, con su sesión. SameSite no ayuda del todo: el iframe es una navegación de tu propio sitio dentro de otro, y con SameSite=None lleva la cookie.

<?php
// core/cabeceras.php (M78): la página no se deja enmarcar por nadie
header("Content-Security-Policy: frame-ancestors 'none'; " . CSP_RESTO);
header('X-Frame-Options: DENY');                 // navegadores que no conocen frame-ancestors

Es la directiva frame-ancestors que M78 dejó en la política, más X-Frame-Options para navegadores viejos. Si una página tiene que poder enmarcarse (un widget para otro sitio), frame-ancestors lleva la lista exacta de quién, y las acciones sensibles piden una confirmación que no se puede hacer con un solo clic.

83.2postMessage sin origen

postMessage es la forma correcta de que dos ventanas de orígenes distintos se hablen (M74). El problema es el receptor que no pregunta quién le habla: cualquier página que tenga una referencia a tu ventana, porque la abrió o porque te enmarca, puede mandarte mensajes.

// js/ayuda.js: solo mensajes del origen esperado, y solo acciones conocidas
const ORIGEN_AYUDA = 'https://ayuda.practicas.edu.gt';
window.addEventListener('message', (e) => {
  if (e.origin !== ORIGEN_AYUDA) return;                       // comparación exacta, no includes()
  const d = e.data;
  if (d?.accion === 'irA' && ['perfil', 'postulaciones'].includes(d.pantalla)) {
    location.assign('/' + d.pantalla);                         // nunca una URL que venga en el mensaje
  }
});
// Y al mandar: el origen de destino explícito, nunca '*'
ventanaPrincipal.postMessage({ accion: 'irA', pantalla: 'perfil' }, 'https://practicas.edu.gt');

Dos detalles: la comparación es exacta (e.origin.includes('practicas.edu.gt') acepta practicas.edu.gt.evil.example), y el contenido del mensaje se trata como cualquier dato del usuario, con una lista de acciones y nunca como una URL o un HTML.

83.3Prototype pollution

En JavaScript, cada objeto hereda de Object.prototype. La prototype pollution pasa cuando una función que mezcla objetos de forma recursiva recibe la clave __proto__ y, en lugar de crear una propiedad con ese nombre, escribe en el prototipo de todos los objetos.

// Mezclar opciones del usuario sin tocar el prototipo
const PROHIBIDAS = new Set(['__proto__', 'constructor', 'prototype']);
function mezclar(destino, origen) {
  for (const k of Object.keys(origen)) {
    if (PROHIBIDAS.has(k)) continue;
    const v = origen[k];
    destino[k] = (v && typeof v === 'object' && !Array.isArray(v))
      ? mezclar(destino[k] ?? Object.create(null), v)
      : v;
  }
  return destino;
}
const filtros = mezclar(Object.create(null), JSON.parse(texto));   // sin prototipo que contaminar

Las librerías de mezcla profunda tuvieron este error durante años (lodash lo corrigió en merge y defaultsDeep) Documentado. En el frontend del proyecto, el riesgo está en leer parámetros de la URL o un JSON y mezclarlos con la configuración. El SCA de M56 avisa cuando una dependencia tiene la falla conocida.

83.4Envenenar y engañar a la caché

Una caché compartida (Cloudflare, Varnish, un proxy de la universidad) guarda una respuesta bajo una clave, normalmente método, host y ruta, y se la sirve a todos los que piden lo mismo. Las dos fallas son desacuerdos entre la caché y el origen:

  • Envenenamiento de caché: el origen usa en la respuesta algo que la caché no usa en la clave (una cabecera como X-Forwarded-Host), y la respuesta armada para el atacante se guarda para todos. En M75 viste el caso suave: una respuesta con Access-Control-Allow-Origin sin Vary: Origin.
  • Engaño de caché: el origen y la caché leen distinto la ruta. El origen ignora lo que sobra y devuelve contenido personal; la caché ve .css y lo guarda como público.
<?php
// Respuestas personales: nunca en una caché compartida
header('Cache-Control: private, no-store');
// Respuestas públicas que dependen de una cabecera: decláralo (M75)
header('Vary: Origin');
// Y nunca armar URLs con cabeceras que la caché no usa como clave
$base = URL_APP;                                  // no $_SERVER['HTTP_X_FORWARDED_HOST']

83.5Request smuggling

El request smuggling lo viste en M32 como forma de pasar por debajo de un WAF. El mecanismo: el proxy y el origen comparten una conexión y no están de acuerdo en dónde termina cada request, porque una lleva Content-Length y Transfer-Encoding: chunked a la vez.

No se arregla en PHP sino en la infraestructura: HTTP/2 hasta el origen (que no tiene Content-Length ambiguo), un proxy que rechaza requests con las dos cabeceras (el RFC 9112 manda tratarlas como error o quitar Content-Length) Documentado, y versiones al día del proxy y del servidor. En XAMPP con Apache solo, sin proxy delante, no hay dos lecturas que comparar.

83.6Condiciones de carrera de negocio

Una condición de carrera de negocio no rompe la base: cada request hace lo correcto por separado. Lo que falla es una regla del negocio (un cupo, un cupón de un solo uso, un saldo) porque dos requests leen el mismo estado antes de que cualquiera lo cambie. El atacante las provoca a propósito, mandando 20 requests iguales en el mismo milisegundo.

<?php
// models/postulaciones.php: tomar el cupo y postular en una transacción
$this->connection->beginTransaction();
$stmt = $this->connection->prepare(
    'UPDATE oportunidades SET cupos = cupos - 1 WHERE id = ? AND estado = 1 AND cupos > 0');
$stmt->execute([$oportunidadId]);
if ($stmt->rowCount() === 0) {                             // otra request se llevó el último
    $this->connection->rollBack();
    Response::json(-1, 'Sin cupos', [], 409);
}
$this->connection->prepare('INSERT INTO postulaciones (oportunidad_id, estudiante_id, cv_url) VALUES (?, ?, ?)')
    ->execute([$oportunidadId, $sesion['id'], $cv]);      // UNIQUE (oportunidad_id, estudiante_id)
$this->connection->commit();

Es la misma idea que el UPDATE condicional del asiento de M39: que la base decida, en una sola sentencia o con una restricción UNIQUE, en lugar de un if en PHP. La restricción UNIQUE (oportunidad_id, estudiante_id) cubre además el doble clic que postula dos veces.

83.7ReDoS

Los motores de expresiones regulares de PHP (PCRE) y de JavaScript prueban caminos y vuelven atrás cuando uno falla. Con cuantificadores anidados, como (a+)+, la cantidad de caminos crece de forma exponencial con el largo de la entrada. El ReDoS (Regular expression Denial of Service) es mandar la entrada que fuerza el peor caso.

<?php
// Validar con un largo máximo antes de la regex, y tratar false como error
if (strlen($texto) > 200) {
    Response::json(-1, 'Demasiado largo', [], 400);
}
$r = preg_match('/^[a-z0-9._-]+@[a-z0-9-]+(\.[a-z0-9-]+)+$/i', $texto);   // sin (x+)+
if ($r === false) {                                       // pcre.backtrack_limit alcanzado
    error_log('regex: ' . preg_last_error_msg());
    Response::json(-1, 'Entrada no válida', [], 400);
}

En PHP, pcre.backtrack_limit (un millón por defecto) corta la búsqueda y preg_match devuelve false Documentado; el error clásico es tratar false como "no coincide" y seguir. En el navegador no hay límite: una regex mala sobre un texto pegado congela el hilo principal, como viste en el event loop de M73.

83.8Scripts de terceros y SRI

Un <script src> de otro dominio corre en tu origen con los mismos poderes que tu código: lee el DOM, manda requests con la sesión, reemplaza formularios. Confiar en el script es confiar en el dominio, en su dueño de mañana y en su CDN. En 2024, el dominio polyfill.io cambió de dueño y empezó a servir código que redirigía a algunos visitantes a otros sitios, en miles de páginas que lo cargaban Documentado.

# Calcular el hash de un archivo para el atributo integrity
$ openssl dgst -sha384 -binary lib.min.js | openssl base64 -A
# Y la CSP limita además de dónde pueden venir los scripts (M78)

SRI solo sirve para archivos que no cambian; un script que el proveedor actualiza solo (analítica, chat de soporte) no puede llevarlo. Para esos, la CSP con nonce de M78 limita quién los carga, y la pregunta de fondo es si hace falta que corran en tu origen o pueden ir en un iframe de otro dominio.

83.9XS-Leaks

Los XS-Leaks (cross-site leaks) son la familia que M73 anunció: el atacante no puede leer tus respuestas, pero sí observar sus efectos, y con eso hace preguntas de sí o no sobre lo que ve la víctima.

Las defensas ya las tienes de módulos anteriores, y aquí se ve por qué van juntas: SameSite (M74) hace que la request del atacante llegue sin sesión, Fetch Metadata (M76) deja rechazar en el servidor lo que viene de otro sitio, y COOP (M78) corta la referencia a la ventana. Responder igual en los dos casos (mismo tamaño, mismo tiempo) cierra lo que queda, como el hash de relleno de M81.
