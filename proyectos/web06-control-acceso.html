Tu API ya autoriza rama por rama. Los huecos que quedan tienen la misma forma: la regla existe, pero se aplica sobre algo distinto de lo que se ejecuta.

Al terminar podrás

  • Leer cómo autoriza hoy tu API (rama por rama, con el dueño del recurso) y reconocer por qué está bien hecho.
  • Encontrar los dos huecos que sobreviven: una búsqueda vacía en usuarios.php que entrega la lista completa de usuarios con su correo, y una oferta cancelada que se reabre después de perder el permiso de publicar.
  • Cerrarlos con una sola idea: autorizar la acción que se va a ejecutar, decidida una vez con los mismos valores, y pedir el mismo permiso en todo camino que produce el mismo efecto.
  • Dejar una matriz de curl con cuatro sesiones que prueba quién puede qué, para que el próximo hueco lo encuentre un script y no una lectura.

La excusa

La auditoría de octubre encontró el control de acceso roto de punta a punta: endpoints que autorizaban con el rol del propio usuario y un creado_por que venía del cuerpo. La re-auditoría encontró otra cosa. Hoy cada endpoint pide sesión, cada rama de cada switch pregunta quién es el dueño antes de consultar (duenosPostulacion, creadorOportunidad, duenoSolicitud), creado_por sale de la cookie y la institución de una oferta la fija el servidor. Es el patrón que recomienda M80, y está bien.

Leyendo con cuidado, quedan dos huecos. Ninguno es obvio, y los dos tienen la misma forma: la regla existe, pero se aplica sobre algo distinto de lo que se ejecuta.

  • H1. La búsqueda vacía. usuarios.php deja pasar a cualquier sesión si la request "es una búsqueda", y lo decide con isset($_GET['q']). El switch, en cambio, busca solo si el término no está vacío. Con ?q=, la autorización ve una búsqueda y el switch ejecuta findAll(): la lista de todos los usuarios con su correo, para un estudiante. Con ?q=&rol_id=2, la lista de administradores. Es una BOLA sobre la tabla entera.
  • H2. Reabrir es volver a publicar. Publicar una oferta exige permiso (autorizado_publicar o el rol de reclutador). Editarla solo exige ser su creador. Cuando un administrador le quita el permiso a alguien y cancela sus ofertas, esa persona sigue siendo la creadora y el botón "Reabrir" de "Mis ofertas" las devuelve al feed. Es una BFLA: la función "publicar" tiene dos puertas y solo una tiene cerradura.

Paso a paso

Paso 1. Las reglas de GET usuarios.php, sin base

Dos funciones puras: una decide qué consulta hace la request, con el mismo orden que el switch; la otra decide quién puede hacerla. Como no tocan la base, se prueban con PHP solo.

  1. El término de búsqueda es q si trae texto, si no buscar. Un valor que no es texto (?q[]=x) cuenta como vacío.
  2. La acción sale en el orden del switch: publicadores, perfil, buscar (solo con término), id, email, rol, todos.
  3. Perfil y búsqueda devuelven datos públicos: cualquier sesión. Un id: el admin o el propio. El resto (publicadores, email, rol, todos): solo el admin.
<?php

declare(strict_types=1);

/** El término de búsqueda: q si trae texto, si no buscar. Lo que no es texto cuenta como vacío. */
function terminoBusqueda(array $q): string
{
    foreach (['q', 'buscar'] as $clave) {
        $v = $q[$clave] ?? '';
        if (is_string($v) && trim($v) !== '') {
            return trim($v);
        }
    }
    return '';
}

/**
 * Qué consulta hace un GET a usuarios.php. Se decide UNA vez, y la usan la autorización
 * y el switch. El orden es el del switch de siempre.
 */
function accionGetUsuarios(array $q): string
{
    if (isset($q['publicadores']))        return 'publicadores';
    if (isset($q['perfil']))              return 'perfil';
    if (terminoBusqueda($q) !== '')       return 'buscar';
    if ((int)($q['id'] ?? 0) > 0)         return 'id';
    if (is_string($q['email'] ?? null) && trim($q['email']) !== '') return 'email';
    if ((int)($q['rol_id'] ?? 0) > 0)     return 'rol';
    return 'todos';
}

/** Quién puede cada acción. Perfil y búsqueda usan SELECT_USUARIO_PUBLICO para quien no es admin. */
function puedeGetUsuarios(string $accion, bool $esAdmin, int $propio, int $id): bool
{
    return match ($accion) {
        'perfil', 'buscar' => true,
        'id'               => $esAdmin || $id === $propio,
        default            => $esAdmin,
    };
}

Fíjate en el default de puedeGetUsuarios: lo que no está nombrado es solo del administrador. Si mañana alguien agrega una acción y se olvida de la regla, la acción nueva queda cerrada, no abierta. Es fallar cerrado, la misma idea que WEB01 aplicó a los errores.

Paso 3. Una sola regla para "puede publicar"

La regla hoy vive dentro de Oportunidades::add(), como una consulta. Para pedirla también al reabrir, pasa a core/permisos.php como función, y add() la usa. Agrega al final de api/core/permisos.php:

/**
 * ¿Puede este usuario tener ofertas activas en el feed? Es la regla de publicar:
 * cuenta activa y, o permiso explícito (autorizado_publicar), o rol de administrador o reclutador.
 * La usan publicar (Oportunidades::add) y reabrir (PUT oportunidades.php).
 */
function puedePublicar(PDO $connection, int $usuario_id): bool
{
    $fila = filaUnica($connection,
        "SELECT u.autorizado_publicar,
                EXISTS (SELECT 1 FROM asignaciones_roles ar
                        INNER JOIN roles r ON r.id = ar.id_rol
                        WHERE ar.id_usuario = u.id AND ar.estado = 1
                          AND r.nombre IN ('administrador', 'reclutador')) AS publica_por_rol
           FROM usuarios u
          WHERE u.id = ? AND u.estado = 1 AND u.estado_cuenta = 'activo'",
        [$usuario_id]);

    return $fila !== null
        && ((int)$fila['autorizado_publicar'] === 1 || (int)$fila['publica_por_rol'] === 1);
}

El caso de la oferta cancelada

H2 necesita una secuencia con dos personas, y se hace desde el frontend, que es por donde pasa de verdad:

  1. Dar el permisoComo admin, en el panel de administración, autoriza a estudiante2 a publicar.
  2. PublicarComo estudiante2, publica una oferta.
  3. Quitar el permisoComo admin, quítale el permiso con la opción de cancelar sus ofertas.
  4. ReabrirComo estudiante2, en "Mis ofertas", aprieta "Reabrir" en la oferta cancelada.
  5. Mirar el feedComo estudiante, busca la oferta en el feed.

Fallas provocadas

Falla 1. Fallar abierto. En puedeGetUsuarios, cambia default => $esAdmin por default => true. Corre la prueba: fallan los casos de publicadores, sin parámetros y "una acción que nadie nombró", y en la matriz dan MAL las filas 2 a 4. Es la diferencia entre una lista de lo prohibido y una de lo permitido. Vuelve la línea.

Falla 2. La BOLA de manual. En postulaciones.php, en la rama elseif ($estudiante_id > 0), comenta el exigirPermiso(...). La fila estudiante2 GET postulaciones.php?estudiante_id=3 da 200: una estudiante lee las postulaciones de otra, con sus CV, cambiando un número en la URL. Es la falla que M80 llama IDOR, y por eso cada rama lleva su comprobación. Vuelve la línea.

Falla 3. La defensa en el botón. Comenta el bloque del paso 4 en oportunidades.php y, en su lugar, imagina que el frontend escondió "Reabrir" a quien no tiene permiso. Repite el caso H2 hasta el paso 3 y, en vez del botón, manda el PUT desde la consola de DevTools de la pestaña de estudiante2 (el mismo origen, así que van la cookie y el token):

Limitaciones

  • La matriz prueba lo que nombra. Dieciocho filas no son todas las combinaciones (14 endpoints, cuatro métodos, varias ramas, cuatro sesiones). Cubren una de cada familia; un hueco en una rama sin fila sigue sin verse. Cuando agregues una rama, agrega su fila.
  • La búsqueda pública sigue enumerando nombres. Con ?q=a, una sesión recibe los usuarios cuyo nombre tiene una "a", con datos públicos. Es lo que pide el producto (buscar personas); si no lo fuera, el límite está en search(), con un mínimo de caracteres y un tope de resultados.
  • Otras reglas de negocio no se revisaron. Por ejemplo, si un estudiante puede cambiar su propia carrera para ver ofertas de otra. Eso no es control de acceso a un recurso; es una pregunta para quien define el sistema.
  • Las carreras al postularse. Dos postulaciones a la misma oferta en el mismo instante son otra clase de falla, de concurrencia: WEB10.
  • Costo. puedePublicar suma una consulta por PUT que deja una oferta activa, con un índice por clave primaria; no hay nada que medir.
  • Nada se ejecutó al escribir esta guía. Los estados esperados salen de leer los switch; la salida de la matriz y las tablas son tuyas.

Cómo conectar

Esta guía funciona sola. Si quieres juntarla con otras:

  • Con WEB01, lo que no debe verse

    Los 403 y 401 de la matriz existen porque WEB01 cambió invalidAccess y checkAuth a códigos HTTP reales; antes, todo era 200 y la matriz no habría podido distinguir nada.

  • Con WEB02, la sesión

    refrescarAuthDesdeBD relee los roles en cada request, así que quitar el permiso o el rol tiene efecto en la siguiente request, sin esperar a que venza la cookie.

  • Con WEB05, XSS

    La falla 3 usa la consola de DevTools como lo haría un script inyectado: mismo origen, misma cookie, mismo token. Lo que frena las dos cosas es el servidor.

  • Con M80, control de acceso roto

    BOLA, BFLA y fallar cerrado están en M80, con el simulador de la matriz sobre este mismo sistema.
