El laboratorio de IA

Antes de construir un agente que investiga incidentes, armas el laboratorio donde vas a trabajar toda la serie y lo pruebas con un agente pequeño: consulta el stock de un almacén y, si falta algo, propone reponerlo y espera a que lo apruebes. Instalas cada herramienta, entiendes cada archivo línea por línea y ves cada pieza fallar a propósito.

La excusa

Una tienda en línea vende tazas, playeras, libretas, termos y gorras. Cada producto tiene un stock y un mínimo: si el stock baja del mínimo, hay que pedir más. Hoy lo revisa una persona con una hoja de cálculo. Quieres un asistente al que le preguntes «¿hay algo por debajo del mínimo?» y que conteste con los números reales, y que, si falta algo, proponga cuánto reponer y espere a que digas que sí.

Es un problema chico a propósito. Tiene todas las piezas de un agente de verdad (un modelo, herramientas, una base, una acción con efecto, una aprobación, memoria entre pasos, pruebas y evals), pero cada archivo se lee en minutos. Las guías que siguen usan este mismo laboratorio para cosas más grandes.

La terminal

Todos los comandos de la guía son de bash. En macOS y Linux ya lo tienes. En Windows, instala Git para Windows, que trae Git Bash, y corre ahí los comandos, no en PowerShell ni en cmd: la sintaxis cambia. Crea una carpeta para el proyecto y entra:

mkdir ia00-laboratorio
cd ia00-laboratorio

uv y Python

uv instala Python y los paquetes de tu proyecto. Reemplaza a pip, a venv y a instalar Python a mano. Cada proyecto tiene su propia carpeta .venv con su versión de Python y sus paquetes, así dos proyectos no se pisan. Documentado

Para instalarlo, en macOS, Linux o Git Bash:

curl -LsSf https://astral.sh/uv/install.sh | sh

En Windows también puedes usar PowerShell: powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex". Después, cierra la terminal y abre una nueva para que vea el comando.

Pruébalo ahora

uv --version

Imprime uv y un número de versión. Si dice command not found, abre una terminal nueva.

Docker y Docker Compose

Docker corre programas en contenedores: cada uno con sus archivos y su red, separado de tu sistema. Aquí lo usas para PostgreSQL, así no tienes que instalarlo. Docker Compose levanta los contenedores que describe un archivo, compose.yaml. Instala Docker Desktop, que trae los dos, y ábrelo. Documentado

Pruébalo ahora

docker --version
docker compose version

Dos líneas con versiones. Si sale Cannot connect to the Docker daemon, Docker Desktop no está abierto.

Ollama y el modelo local

Ollama corre modelos de lenguaje en tu máquina y los sirve por HTTP en el puerto 11434. Va instalado en tu sistema, no en Docker, para que pueda usar tu GPU si tienes una; sin GPU funciona igual, más lento. Instálalo, ábrelo y descarga el modelo de la guía, qwen3:8b, de unos 5 GB. Documentado

ollama pull qwen3:8b
ollama list
curl http://localhost:11434/api/tags

ollama list tiene que mostrar qwen3:8b, y el curl devuelve un JSON con la lista de modelos: eso es lo que ve tu código por la flecha 5.

Claude y la clave de la API (opcional)

Todo funciona solo con Ollama. Para comparar con Claude, crea una clave en la consola de Anthropic. Cada llamada cuesta según los tokens que mandas y recibes. La clave va en un archivo .env que nunca se sube a git, y uv la carga si le dices dónde está con la variable UV_ENV_FILE. Documentado

cp .env.example .env        # después de crear .env.example en La infraestructura
# edita .env y pega tu clave después de ANTHROPIC_API_KEY=
export UV_ENV_FILE=.env

Qué pasa si falla

Una clave en el código, en un commit o en una captura de pantalla está filtrada: bórrala en la consola y crea otra. No alcanza con borrar el commit, porque el historial y las copias ya la tienen.

Cómo habla un programa con un modelo

Un modelo de chat recibe una lista de mensajes y devuelve un mensaje nuevo. No tiene memoria: en cada llamada le mandas la conversación entera. Si además le describes herramientas (nombre, parámetros y para qué sirven), puede contestar con un pedido en lugar de un texto: «corre bajo_minimo con estos argumentos». Ese pedido se llama tool call. Tu código lo corre, le devuelve el resultado y le vuelve a preguntar. Ese ir y venir es un agente.

Esto es lo que explica a fondo el bucle de M25. En esta guía lo escribes dos veces: a mano en el paso 5 y como grafo en el paso 7.

Códigos de respuesta

  • 200La respuesta, con texto o con llamadas a herramientas.
  • 400La conversación está mal formada; por ejemplo, una llamada sin su resultado.
  • 401Falta la clave o no es válida.
  • 429Pasaste tu límite de uso; max_retries reintenta.
  • 529La API está sobrecargada; también se reintenta.

Fíjate en la diferencia: las dos APIs dicen lo mismo con otra forma (tools con parameters o con input_schema, tool_calls o un bloque tool_use). init_chat_model las traduce a los mismos objetos de Python, y por eso el resto del código es uno solo.

Trade-off

uv, no pip con venv. Con pip tienes que instalar Python 3.13 a mano, crear el entorno, activarlo en cada terminal y acordarte de congelar las versiones. uv hace todo eso con uv sync y deja un uv.lock que reproduce la misma instalación en otra máquina. Lo que pierdes es costumbre: muchos tutoriales en Internet usan pip, y tienes que traducir pip install x a uv add x.

from lab.config import CFG

def modelo_chat(proveedor: str = CFG.modelo):
    if proveedor == "claude":
        # Sonnet 5.5 rechaza una temperature distinta de la de fábrica: no se pasa.
        # (3)
        return init_chat_model("claude-sonnet-5-5", model_provider="anthropic",
                               max_tokens=4000, timeout=60, max_retries=2)
    if proveedor == "ollama":

        # reasoning: qwen3 piensa antes de responder, y el pensamiento queda aparte del texto.
        # (4)
        return init_chat_model("qwen3:8b", model_provider="ollama", base_url=CFG.ollama,
                               temperature=0, num_ctx=16384, reasoning=True)
    # (5)
    raise ValueError(f"Modelo desconocido: {proveedor}. Usa claude u ollama.")

  2. Si no le pasas nada, usa LAB_MODELO. El valor por defecto se calcula una sola vez, al importar el módulo.

"""El agente como un grafo de LangGraph.

    START → modelo ─┬→ herramientas → modelo           (lectura: corre sin permiso)
                    ├→ aprobar (interrupt) → actuar → modelo
                    ├→ sin_pasos → END                  (se acabaron los pasos)
                    └→ END                              (respondió sin pedir herramientas)

El modelo, las herramientas y aplicar() llegan por parámetro: las pruebas pasan unos falsos.
"""
from typing import Annotated, Callable, Literal, TypedDict

from langchain_core.messages import AnyMessage, SystemMessage, ToolMessage
from langchain_core.runnables import RunnableConfig
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.types import interrupt

from lab.acciones import Reponer
from lab.prompts import SISTEMA


class Estado(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]
    pasos: int
    decision: dict | None


def construir(modelo, lectura: list, aplicar: Callable[..., str], max_pasos: int = 8, checkpointer=None):

    con_herramientas = modelo.bind_tools([*lectura, Reponer])

    def llamar_modelo(estado: Estado):
        respuesta = con_herramientas.invoke([SystemMessage(SISTEMA), *estado["messages"]])
        return {"messages": [respuesta], "pasos": estado["pasos"] + 1}

    def despues_del_modelo(estado: Estado) -> Literal["herramientas", "aprobar", "sin_pasos", "__end__"]:
        llamadas = estado["messages"][-1].tool_calls
        if not llamadas:
            return END
        if estado["pasos"] >= max_pasos:
            return "sin_pasos"
        if any(c["name"] == "Reponer" for c in llamadas):
            return "aprobar"
        return "herramientas"

    def ejecutar(llamada: dict) -> ToolMessage:
        try:
            texto = str(por_nombre[llamada["name"]].invoke(llamada["args"]))

        return {"decision": decision}

        mensajes = []

            mensajes.append(ToolMessage(texto, tool_call_id=c["id"], name=c["name"]))

                             for c in estado["messages"][-1].tool_calls]}

    g.add_node("modelo", llamar_modelo)
    g.add_node("herramientas", herramientas)
    g.add_node("aprobar", aprobar)
    g.add_node("actuar", actuar)

    g.add_edge("actuar", "modelo")
    g.add_edge("sin_pasos", END)

Un nodo aprobar que solo pregunta y un nodo actuar que aplica. Al reanudar, LangGraph vuelve a correr el nodo del interrupt desde el principio: si el efecto estuviera ahí, correría dos veces.

La decisión
durability="sync": cada checkpoint se escribe antes del paso siguiente. Una pausa de días, o un proceso que se cae, retoma desde el último paso guardado.
Lo que descartas
Guardar el estado en un archivo o en memoria: un archivo no aguanta dos procesos a la vez, y la memoria se pierde con el proceso.
Qué puede salir mal
Un hilo guarda todo: si usas siempre hilo-1, la conversación crece y cada llamada manda más tokens. Usa un hilo por tarea.

Limitaciones

Lo que este laboratorio no resuelve, a propósito. Cada punto es un tema de una guía posterior o de un módulo del curso.

  • Quien aprueba no está autenticado. --quien es lo que escribas. En un sistema real, la aprobación llega de una persona identificada, por un canal que el modelo no controla.
  • El tope es de pasos, no de dinero. Con Claude, cada paso cuesta tokens y la conversación crece. No hay un límite de tokens ni de costo por hilo; lo trae IA01.
  • El modo de solo lectura es un cinturón. default_transaction_read_only lo puede apagar el mismo rol. La barrera son los GRANT, y además las herramientas solo corren SQL fijo.
  • Los resultados del modelo no se repiten. Ni con temperature=0: tres intentos dicen poco. Los evals de verdad tienen decenas de casos.
  • Un solo proceso a la vez por hilo. Si corres lab aprobar dos veces a la vez en el mismo hilo, la clave impide sumar dos veces, pero los dos procesos llaman al modelo.
  • Los checkpoints no se borran. Cada paso suma filas en la base. Para limpiar, docker compose down -v borra todo.
  • Nadie revisa la cantidad. Pydantic comprueba que esté entre 1 y 100, no que sea la correcta. Esa revisión es tuya, al aprobar, y la mide el eval reponer.
