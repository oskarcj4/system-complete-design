Cien asientos con locks pesimistas

Cien asientos, doscientas personas que quieren el mismo, dos réplicas de la api y un banco que a veces pide verificar la tarjeta justo cuando se acaba el tiempo. Vas a construir la venta completa de un cine, con locks de PostgreSQL que duran milisegundos y apartados que duran minutos, para que ningún asiento se venda dos veces y ningún cliente pague por un asiento que ya es de otro. Todo con Stripe en modo de prueba, sin gastar un centavo.

  • Pasar al checkout en tres fases con una clave determinista hacia Stripe, y vencer los checkouts con un barrido que nunca libera un asiento sin saber qué pasó con su pago.
  • Dar una prórroga única de 60 s cuando el banco pide 3D Secure al borde del plazo, y manejar en el navegador cada forma en que puede terminar un pago.
  • Mandar el mapa en vivo por SSE a través de dos réplicas con Redis Pub/Sub, con una versión por asiento que ordena los eventos sin un contador central.

La excusa

Un cine vende una función de 100 asientos, de A1 a J10, a 8.50 USD cada uno. Elegir asientos tiene dos etapas: los reservas y quedan apartados 30 s; pasas al pago y quedan apartados 3 minutos más, mientras escribes la tarjeta. Si pagas, cada asiento es tuyo para siempre y recibe un código. Si no, vuelve a estar libre para los demás. Detrás de esas reglas hay cinco formas de vender un asiento dos veces o de cobrar uno que no entregas:

  • El mismo milisegundo. Doscientas personas aprietan F7 cuando se abre la venta. Si dos transacciones leen "libre" antes de que alguna escriba, las dos lo apartan.
  • El apartado que no termina. Alguien reserva y cierra la pestaña. Si nadie vence su reserva, el asiento queda apartado para siempre.
  • El pago tardío. El checkout vence en el segundo 180 y el cliente aprieta pagar en el 179. Si liberas el asiento sin preguntarle a Stripe, otro lo reserva, y el primero termina pagando un asiento ajeno.
  • El banco lento. El banco abre la ventana de 3D Secure cuando quedan 20 s. El cliente sí estaba pagando, y el plazo se le acaba por culpa de otro.
  • El mapa viejo. Dos réplicas de la api, cada una con sus navegadores conectados. Un cambio en una tiene que verse en los navegadores de la otra, en orden.

El proyecto separa dos cosas que suelen confundirse. El lock de PostgreSQL protege el instante en que un asiento cambia de estado, y dura milisegundos. El apartado es una columna con un vencimiento, y dura minutos. El primero impide que dos transacciones decidan a la vez; el segundo dice a todos que el asiento no está libre entre una request y otra. El dinero manda sobre el reloj: un asiento en pago solo se libera cuando Stripe confirma que ese pago ya no puede ocurrir.

En producción real

Todo este proyecto corre en el modo de prueba de Stripe, que no cuesta nada y no mueve dinero Documentado. El paso 1 lo configura. La aplicación se niega a arrancar con una clave que contenga _live_, y con una clave publicable que no empiece con pk_test_.

Trade-off

Payment Element con un PaymentIntent propio, no Checkout como en A15. Una Checkout Session no puede vencer antes de 30 minutos Documentado, y aquí el pago dura 3. Además, el PaymentIntent de una Checkout Session solo se cancela directamente en requires_capture; en los demás estados hay que vencer la sesión entera Documentado, y el barrido necesita leer y cancelar el pago en cualquier estado. El precio es que la página de pago es tuya: confirmas el PaymentIntent desde el navegador con Stripe.js y manejas cada resultado. La tarjeta igual se escribe dentro de un iframe de Stripe y nunca pasa por tu servidor (M27).

Dos réplicas de la api
api y api2 son la misma imagen con el mismo perfil, en los puertos 8080 y 8082. Están para que el mapa en vivo tenga que cruzar de una réplica a otra: un cambio hecho en la 2 lo tiene que ver un navegador conectado a la 1. Las sesiones viven en la memoria de cada réplica, así que ana entra por localhost:8080 y beto por 127.0.0.1:8082: son otro host para el navegador y no comparten la cookie.
Un rol y una clave por proceso
Como en A15. cine_api no puede borrar reservas ni leer la inbox; cine_webhook solo inserta eventos; cine_worker no ve las claves de idempotencia; cine_jobs solo ve las claves. Nadie, salvo la migración, puede insertar o borrar asientos. El webhook no recibe clave de Stripe; la api y el worker reciben una restringida cada uno.
Los plazos en .env
RESERVE_TTL, CHECKOUT_TTL y THREE_DS_GRACE llegan a la api y al worker desde el mismo ancla x-holds, para que los dos usen siempre los mismos. El experimento de 3D Secure los acorta, y con ellos la espera.
Sin restart

Hilos virtuales
Un stream SSE abierto es una request que no termina. Con hilos de plataforma, cada espectador ocuparía uno de los 200 hilos de Tomcat; con hilos virtuales de Java 25, un stream que espera no ocupa un hilo del sistema operativo.
Un pool de 10 para 4 conexiones reales
Cada réplica tiene un Hikari de 10, pero PgBouncer abre 4 conexiones a PostgreSQL (DEFAULT_POOL_SIZE). Las transacciones de este proyecto duran milisegundos, así que 4 alcanzan para muchas requests. Por eso ningún stream SSE toma una conexión: 4 espectadores mirando el mapa dejarían sin base a todos los demás.
Los plazos como Duration
30s, 3m y 60s se pasan a la base como segundos (make_interval(secs => :ttl)), nunca como un literal en el SQL. Así las pruebas no esperan 4 minutos: vencen una reserva moviendo su expires_at.
Los límites de streams
3 por usuario y 2 000 por réplica son parámetros de diseño, no mediciones. Cuántos aguanta una réplica de verdad depende de la memoria y de la red, y se mide.

import java.sql.SQLException;
import java.util.Collection;

/** Lo que dice PostgreSQL cuando algo falla, sin depender de cómo lo traduzca Spring. */
public final class Sql {

    /** 55P03: lock_not_available, lo que responde FOR UPDATE NOWAIT si otra transacción tiene la fila. */
    public static final String LOCK_NOT_AVAILABLE = "55P03";
    /** 23505: unique_violation. */
    public static final String UNIQUE_VIOLATION = "23505";

    private Sql() {
    }

    /**
     * Una lista como String[] para el driver, que la manda como text[]; el SQL la convierte con
     * CAST(:ids AS bigint[]) o CAST(:ids AS uuid[]). Así no depende de cómo el driver tipa un Long[] o un UUID[].
     */
    public static String[] textArray(Collection<?> values) {
        return values.stream().map(String::valueOf).toArray(String[]::new);
    }

    public static String state(Throwable e) {
        for (Throwable t = e; t != null; t = t.getCause()) {
            if (t instanceof SQLException s && s.getSQLState() != null) {
                return s.getSQLState();
            }
        }
        return null;
    }

    /** Una violación de la restricción con ese nombre. El nombre va entre comillas en el mensaje de PostgreSQL. */
    public static boolean violates(Throwable e, String constraint) {
        if (!UNIQUE_VIOLATION.equals(state(e))) {
            return false;
        }
        for (Throwable t = e; t != null; t = t.getCause()) {
            if (t instanceof SQLException s && s.getMessage() != null && s.getMessage().contains("\"" + constraint + "\"")) {
                return true;
            }
        }
        return false;
    }
}

Paso a paso

Paso 1. Stripe gratis, solo para pruebas

Stripe tiene dos mundos separados: el modo live, que cobra tarjetas reales, y los sandboxes, donde todo funciona igual, con webhooks, rechazos y 3D Secure, pero con tarjetas de mentira que no mueven dinero Documentado. Crear la cuenta y usar un sandbox no cuesta nada, y no hace falta dar los datos de un negocio. Si ya hiciste A15, usa el mismo sandbox y crea dos claves nuevas: los permisos de este proyecto son otros.

  1. La cuentaRegístrate en dashboard.stripe.com/register con tu correo. Al entrar, el Dashboard te ofrece activar pagos: no lo hagas. En el selector de cuenta, arriba a la izquierda, entra a un sandbox; si no hay ninguno, créalo desde ahí. Todo lo que sigue se hace dentro del sandbox, que el Dashboard marca con un aviso de entorno de prueba.
  2. La clave publicableEn la sección de claves de API (en Workbench o en Developers, según la versión del Dashboard) está la clave publicable del sandbox, que empieza con pk_test_. Cópiala a STRIPE_PUBLISHABLE_KEY. Es pública por diseño: Stripe.js la usa en el navegador para montar el formulario y confirmar el pago.
  3. La clave de la apiCrea una clave restringida, que empieza con rk_test_, con el nombre a27-api. Dale escritura en PaymentIntents y deja todo lo demás en None. Va a STRIPE_API_KEY_API. Con esa clave, la api crea, lee y cancela PaymentIntents.
  4. La clave del workerCrea otra, a27-worker, con escritura en PaymentIntents, lectura en Charges y escritura en Refunds. Va a STRIPE_API_KEY_WORKER. El worker lee y cancela pagos en el barrido, lee el cargo cuando llega un charge.refunded y reembolsa los pagos huérfanos. Los nombres exactos de cada fila pueden cambiar entre versiones del Dashboard; si no encuentras uno, busca el recurso por su nombre en inglés.
  5. El Stripe CLIInstálalo como en A15: en Windows, con scoop install stripe o con el zip de la página de releases; en macOS, con brew install stripe/stripe-cli/stripe Documentado. Después, stripe login y elige el sandbox.
  6. El secreto del webhookCorre stripe listen --print-secret. El whsec_ que imprime va a STRIPE_WEBHOOK_SECRET.

Qué pasa si falla

Nunca escribas una tarjeta real en un sandbox, y nunca pongas una sk_live_, una rk_live_ o una pk_live_ en .env: StripeConfig y MeController se niegan a arrancar, pero la clave ya quedó escrita en tu disco. Si una clave de prueba se escapa a un repositorio, revócala en el Dashboard y crea otra; es gratis.

La decisión
Las mismas piezas de A15 más la clave publicable, porque aquí el formulario de pago está en tu página. Las dos claves restringidas dejan a cada proceso con lo mínimo: una clave de la api filtrada puede crear y cancelar pagos, pero no reembolsar ni leer clientes.
Lo que descartas
La sk_test_ estándar, porque puede todo. Darle a la api permiso de reembolsar "por si acaso": los reembolsos de este proyecto son una red de seguridad del worker, y la api no tiene por qué tocarlos.
Qué puede salir mal
Que la api falle al arrancar con "STRIPE_PUBLISHABLE_KEY tiene que ser una pk_test_": pegaste la clave del modo live o la dejaste en pk_test_reemplazame, que pasa la validación pero Stripe.js rechaza. Que el Payment Element no aparezca y la consola del navegador hable de una clave inválida: la publicable es de otro sandbox que las restringidas, y el client_secret no corresponde a esa cuenta.

    user_id           bigint      NOT NULL REFERENCES customers (id),
    showing_id        bigint      NOT NULL REFERENCES showings (id),

La decisión
Los 100 asientos existen desde la migración y nunca se crean ni se borran: solo cambian de estado. Así "apartar F7" es un UPDATE de una fila que ya existe, y el lock de esa fila es el punto donde dos compradores se encuentran. seat_labels en la reserva guarda lo que se pidió aunque los asientos se liberen, para mostrar una reserva vencida con sus asientos. Lo que descartas

Paso 3. Dos niveles de lock

Un lock de fila de PostgreSQL, el que toma SELECT … FOR UPDATE, dura lo que dura su transacción. Mantener una transacción abierta 30 s o 3 minutos mientras alguien mira la pantalla es inviable: ocuparía una de las 4 conexiones de PgBouncer por cada comprador, y el quinto esperaría. Por eso el diseño tiene dos niveles. El lock de fila protege la transición, y dura milisegundos. El apartado es la columna status con su hold_expires_at, y dura minutos.

Cada proceso pide el lock de la forma que le conviene:

  • NOWAIT, en las requests del navegador. Si dos personas aprietan F7 en el mismo milisegundo, la segunda no espera a la primera para descubrir después que el asiento ya está apartado: recibe el error 55P03, lock_not_available, al instante Documentado, y la api responde 409.
  • SKIP LOCKED, en los barridos. El barrido no compite con un comprador: si una fila está tomada, la salta y la ve en la vuelta siguiente, 5 s después. Con dos workers, cada uno toma filas distintas sin elegir un líder.
  • Esperar, al vender y al liberar desde el worker. Quien tiene el lock termina en milisegundos, y estas transacciones no pueden fallar por llegar segundas: un pago que llegó tiene que venderse.

Y todos toman los locks en el mismo orden: primero los asientos, por id, después la reserva. Dos transacciones que piden los mismos locks en el mismo orden no pueden esperarse en círculo, así que no hay deadlocks, aunque algunas esperen.

package lab.cine.showing;

/**
 * Las piezas de SQL que comparten todas las transacciones que tocan asientos.
 * Cada UPDATE de seats escribe updated_at con clock_timestamp() y devuelve el asiento como quedó.
 */
public final class SeatSql {

    /**
     * La versión de un asiento. clock_timestamp() es la hora real en el momento del UPDATE, no la del inicio de
     * la transacción (now()). Como el UPDATE espera el lock de la fila, el segundo que cambia un asiento lo
     * escribe después de que el primero confirmó: las versiones de un mismo asiento solo crecen.
     */
    public static final String TOUCH = "updated_at = clock_timestamp()";

    /** Lo que se publica después del commit, sin volver a leer la base. */
    public static final String RETURNING = """
            RETURNING showing_id, label, status,
                      CASE WHEN status IN ('held', 'checkout') THEN hold_expires_at END AS held_until,
                      (extract(epoch FROM updated_at) * 1000000)::bigint AS version""";

    /** Bloquea los asientos de una reserva, en orden de id. Primero los asientos, después la reserva: siempre. */
    public static final String LOCK_OF_RESERVATION = """
            SELECT id FROM seats WHERE reservation_id = :res ORDER BY id FOR UPDATE""";

    private SeatSql() {
    }
}
La decisión
READ COMMITTED, el nivel por defecto. FOR UPDATE lee la última versión confirmada de la fila y la bloquea, así que no hace falta SERIALIZABLE para que dos transacciones no decidan sobre el mismo asiento (M05). Cada UPDATE de un asiento escribe updated_at = clock_timestamp(), la hora real del momento, y lo devuelve con RETURNING: esa es la versión que viaja al navegador en el paso 9.
Lo que descartas
El lock optimista con una columna de versión y un UPDATE … WHERE version = :v. Con 200 personas sobre el mismo asiento, 199 leen, deciden y fallan al escribir, y el que reintenta vuelve a competir. Con NOWAIT fallan igual, pero antes de hacer nada. Y un lock_timeout de unos cientos de milisegundos en lugar de NOWAIT: es una alternativa razonable, que convierte algunos 409 en esperas cortas; aquí se elige la respuesta inmediata para que la carrera se vea.
Qué puede salir mal
Que alguien cambie el orden en un camino nuevo, primero la reserva y después los asientos: con esperas, dos transacciones podrían bloquearse en círculo, y PostgreSQL abortaría una con 40P01 (M05). Por eso el orden vive en una constante, LOCK_OF_RESERVATION, que usan todos.

Paso 4. Reservar en una sola transacción

Reservar no llama a nadie de afuera, así que cabe entero en una transacción: la clave de idempotencia, los locks, la reserva y los asientos se confirman juntos o no queda nada. Es el protocolo de claves de A15, pero aquí el lease no entra en juego: como la clave se inserta en la misma transacción, una segunda request con la misma clave espera en el INSERT hasta que la primera termina, y después ve la respuesta guardada.

    public ApiResult reserve(long userId, UUID key, ReserveRequest req) {
        if (req.hasDuplicates()) {
            throw new ApiError(HttpStatus.BAD_REQUEST, "VALIDATION_FAILED", "Pediste el mismo asiento dos veces.");
        }
        byte[] hash = RequestHash.of(RESERVE, req.canonical());
        try {
            return tx.execute(s -> {
                // Si algo espera más de 2 s (un lock que no se suelta), la transacción falla en lugar de colgarse.
                jdbc.sql("SET LOCAL statement_timeout = '2s'").update();
                // Resume no puede pasar aquí: la clave y la reserva se confirman en la misma transacción.
                if (keys.begin(userId, key, RESERVE, hash) instanceof Begin.Replay r) {
                    return new ApiResult(r.status(), r.body(), true);
                }
                return reserveInTx(userId, key, req);
            });
        } catch (DataAccessException e) {
            if (Sql.LOCK_NOT_AVAILABLE.equals(Sql.state(e))) {
                // Otra transacción tiene alguno de esos asientos en este instante. No se espera: se avisa.
                throw new ApiError(HttpStatus.CONFLICT, "SEAT_UNAVAILABLE",
                        "Alguien está tomando uno de esos asientos en este momento.", Map.of("reason", "locked"), 1);
            }
            if (Sql.violates(e, "one_active_reservation")) {
                // La transacción ya se deshizo; esta lectura es aparte.
                Map<String, Object> details = reservations.active(userId, req.showingId())
                        .<Map<String, Object>>map(id -> Map.of("reservation_id", id.toString()))
                        .orElse(Map.of());
                throw new ApiError(HttpStatus.CONFLICT, "ACTIVE_RESERVATION_EXISTS",
                        "Ya tienes una reserva activa en esta función. Págala o cancélala antes de pedir otra.",
                        details, null);
            }
            throw e;
        }
    }

    private ApiResult reserveInTx(long userId, UUID key, ReserveRequest req) {
        List<String> labels = req.labels();
        // 1. Los asientos pedidos, bloqueados en orden de id. NOWAIT: si otro los tiene, 55P03 al instante.
        List<LockedSeat> seats = jdbc.sql("""
                SELECT id, label, status, reservation_id, hold_expires_at,
                       coalesce(hold_expires_at <= now(), false) AS lapsed
                FROM seats
                WHERE showing_id = :sh AND label = ANY(CAST(:labels AS text[]))
                ORDER BY id
                FOR UPDATE NOWAIT
                """)
                .param("sh", req.showingId()).param("labels", labels.toArray(String[]::new))
                .query(LockedSeat.class)
                .list();
        if (seats.isEmpty()) {
            throw ApiError.notFound();
        }
        // 2. ¿Se pueden tomar todos? Si uno no, no se toma ninguno, y se dice cuáles y hasta cuándo.
        List<Map<String, Object>> unavailable = new ArrayList<>();
        for (LockedSeat seat : seats) {
            if (!seat.takeable()) {
                Map<String, Object> u = new LinkedHashMap<>();
                u.put("seat", seat.label());
                u.put("status", seat.status());
                if (seat.holdExpiresAt() != null && !seat.lapsed()) {
                    u.put("held_until", seat.holdExpiresAt().toString());
                }
                unavailable.add(u);
            }
        }
        if (!unavailable.isEmpty()) {
            throw new ApiError(HttpStatus.CONFLICT, "SEAT_UNAVAILABLE", "Alguno de esos asientos ya no está libre.",
                    Map.of("unavailable", unavailable), null);
        }
        // 3. Toma perezosa: las reservas vencidas dueñas de estos asientos pasan a expired. Solo la reserva:
        //    sus otros asientos los libera el barrido.
        List<UUID> previous = seats.stream().map(LockedSeat::reservationId).filter(id -> id != null).distinct()
                .toList();
        if (!previous.isEmpty()) {
            List<Owner> expired = jdbc.sql("""
                    UPDATE reservations SET status = 'expired', updated_at = now()
                    WHERE id = ANY(CAST(:ids AS uuid[])) AND status = 'held' AND expires_at <= now()
                    RETURNING id, user_id
                    """)
                    .param("ids", Sql.textArray(previous))
                    .query(Owner.class)
                    .list();
            expired.forEach(o -> events.toOwner(o.userId(), new ReservationEvent(o.id(), "expired", null)));
        }
        // 4. Mi propia reserva vencida en esta función no me bloquea: también pasa a expired.
        jdbc.sql("""
                UPDATE reservations SET status = 'expired', updated_at = now()
                WHERE user_id = :u AND showing_id = :sh AND status = 'held' AND expires_at <= now()
                """)
                .param("u", userId).param("sh", req.showingId())
                .update();
        // 5. La reserva. El monto sale de la función y se congela. Si ya tengo una activa: 23505 en one_active_reservation.
        Created created = jdbc.sql("""
                INSERT INTO reservations (user_id, showing_id, status, seat_labels, seat_count, amount_minor, currency,
                                          expires_at)
                SELECT :u, sh.id, 'held', CAST(:labels AS text[]), :n, sh.price_minor * :n, sh.currency,
                       now() + make_interval(secs => :ttl)
                FROM showings sh
                WHERE sh.id = :sh
                RETURNING id, expires_at
                """)
                .param("u", userId).param("labels", labels.toArray(String[]::new)).param("n", labels.size())
                .param("ttl", CineProps.secs(props.holds().reserveTtl())).param("sh", req.showingId())
                .query(Created.class)
                .single();
        // 6. Los asientos, con la versión nueva.
        List<ChangedSeat> taken = jdbc.sql("""
                UPDATE seats
                SET status = 'held', reservation_id = :res, hold_expires_at = :exp, %s
                WHERE id = ANY(CAST(:ids AS bigint[]))
                %s
                """.formatted(SeatSql.TOUCH, SeatSql.RETURNING))
                .param("res", created.id()).param("exp", created.expiresAt())
                .param("ids", Sql.textArray(seats.stream().map(LockedSeat::id).toList()))
                .query(ChangedSeat.class)
                .list();
        events.seatsChanged(taken);
        // 7. La respuesta, guardada con la clave en la misma transacción.
        keys.attach(userId, key, created.id());
        String body = json.writeValueAsString(reservations.byId(created.id()).orElseThrow().view());
        keys.finish(userId, key, 201, body);
        return new ApiResult(201, body, false);
    }

    /**
     * DELETE /v1/reservations/{id}. Es idempotente por naturaleza: cancelar una reserva ya cerrada devuelve su
     * estado. Una en checkout primero cancela el PaymentIntent en Stripe, fuera de toda transacción: si Stripe dice
     * que ya no se puede, el pago llegó y la reserva se vende en lugar de cancelarse.
     */
    public ReservationView cancel(long userId, UUID id) {
        ReservationRow r = reservations.find(userId, id).orElseThrow(ApiError::notFound);
        switch (r.status()) {
            case "held" -> releaseNow(id, Set.of("held"));
            case "checkout" -> {
                if (r.paymentIntentId() == null) {
                    releaseNow(id, Set.of("checkout"));
                } else {
                    cancelPaymentThenRelease(id, r.paymentIntentId());
                }
            }
            case "paid", "refunded" -> throw invalidState("Esta reserva ya está pagada.", r.status());
            default -> {
                // expired o canceled: ya no tiene asientos. Repetir el DELETE no es un error.
            }
        }
        return get(userId, id);
    }

    private void releaseNow(UUID id, Set<String> from) {
        try {
            if (!releases.release(id, "canceled", from, true)) {
                throw invalidState("La reserva cambió de estado mientras la cancelabas. Vuelve a cargarla.", "changed");
            }
        } catch (DataAccessException e) {
            if (Sql.LOCK_NOT_AVAILABLE.equals(Sql.state(e))) {
                throw seatsBusy();
            }
            throw e;
        }
    }

    private void cancelPaymentThenRelease(UUID id, String paymentIntentId) {
        try {
            gateway.cancelPaymentIntent(paymentIntentId);
        } catch (GatewayException e) {
            // No se interpreta el error: se vuelve a leer el PaymentIntent y se decide por su estado.
            PaymentIntentView pi = retrieveOr503(paymentIntentId);
            switch (pi.status()) {
                case "succeeded" -> {
                    finalizer.finalize(pi);
                    throw invalidState("El pago se completó antes de cancelar: tus entradas están listas.", "paid");
                }
                case "processing" -> throw invalidState(
                        "El banco está procesando el pago; no se puede cancelar ahora.", "processing");
                case "canceled" -> log.info("{} ya estaba cancelado", paymentIntentId);
                default -> throw unavailable();
            }
        }
        releaseNow(id, Set.of("checkout"));
    }

    /**
     * POST /v1/reservations/{id}/confirm. El navegador lo llama cuando stripe.confirmPayment termina. No cree lo
     * que diga el navegador: lee el PaymentIntent en Stripe y, si está succeeded, vende. Repetirlo es seguro.
     */
    public ConfirmResult confirm(long userId, UUID id) {
        ReservationRow r = reservations.find(userId, id).orElseThrow(ApiError::notFound);
        if (r.is("paid") || r.is("refunded")) {
            return new ConfirmResult(200, get(userId, id));
        }
        if (r.paymentIntentId() == null) {
            throw invalidState("Esta reserva no tiene un pago iniciado.", r.status());
        }
        Outcome o;
        try {
            o = finalizer.finalize(r.paymentIntentId());
        } catch (GatewayException e) {
            throw unavailable();
        }
        return switch (o.kind()) {
            case SOLD, ALREADY_PAID -> new ConfirmResult(200, get(userId, id));
            case PROCESSING -> new ConfirmResult(202, get(userId, id));
            case FAILED -> throw new ApiError(HttpStatus.PAYMENT_REQUIRED, "PAYMENT_FAILED",
                    "La tarjeta fue rechazada. Puedes probar con otra mientras la reserva no venza.",
                    o.declineCode() == null ? Map.of() : Map.of("decline_code", o.declineCode()), null);
            case INCOMPLETE -> throw invalidState("Falta completar el pago (por ejemplo, la verificación del banco).",
                    "incomplete");
            case CANCELED, ORPHAN -> throw gone(
                    "La reserva venció antes de que llegara el pago. Si se cobró, se reembolsa solo.");
        };
    }

    private PaymentIntentView retrieveOr503(String paymentIntentId) {

        } catch (GatewayException e) {

        }
    }

    static ApiError invalidState(String message, String reason) {

    static ApiError gone(String message) {

    }

/**
 * La huella de una request: SHA-256 de su forma canónica, no de los bytes que llegaron.
 * {"quantity":1,"product_id":1} y {"product_id":1, "quantity":1} son la misma compra y tienen que dar el mismo hash.
 * Por eso cada endpoint arma su forma canónica con los campos ya validados, en un orden fijo.
 */
public final class RequestHash {

    private RequestHash() {
    }

    public static byte[] of(String methodPath, String canonical) {
        try {
            return MessageDigest.getInstance("SHA-256")
                    .digest((methodPath + "\n" + canonical).getBytes(StandardCharsets.UTF_8));
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("La JVM no trae SHA-256", e);
        }
    }
}

import java.util.Arrays;
import java.util.Map;
import java.util.UUID;

import org.springframework.http.HttpStatus;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Component;

import org.springframework.transaction.annotation.Transactional;

import lab.cine.web.ApiError;

/**
 * La tabla idempotency_keys. Todos los métodos corren dentro de la transacción de quien los llama
 * (Propagation.MANDATORY): la clave y el efecto se confirman o se deshacen juntos.
 * La exclusión entre dos requests con la misma clave es el lease locked_until, no un advisory lock:
 * detrás de PgBouncer en modo transaction, un lock de sesión queda en una conexión que ya es de otro.
 */
@Component
@Transactional(propagation = Propagation.MANDATORY)
public class IdempotencyKeys {

    /**
     * Cuánto dura el lease de una request: más que la peor llamada a Stripe (unos 40 s, ver StripeConfig).
     * Si el proceso muere, a los 60 s otra request con la misma clave puede retomarla.
     */
    static final int LEASE_SECONDS = 60;

    record Existing(String methodPath, byte[] requestHash, String recoveryPoint, UUID resourceId,
                    Integer responseStatus, String responseBody, boolean busy) {
    }

    private final JdbcClient jdbc;

    public IdempotencyKeys(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    public Begin begin(long userId, UUID key, String methodPath, byte[] hash) {
        // Si otra transacción está insertando la misma clave sin confirmar, este INSERT espera a que termine.
        int inserted = jdbc.sql("""
                INSERT INTO idempotency_keys (user_id, idem_key, method_path, request_hash, locked_until)
                VALUES (:u, :k, :mp, :h, now() + make_interval(secs => :lease))
                ON CONFLICT (user_id, idem_key) DO NOTHING
                """)
                .param("u", userId).param("k", key).param("mp", methodPath).param("h", hash)
                .param("lease", LEASE_SECONDS)
                .update();
        if (inserted == 1) {
            return new Begin.Fresh();
        }
        Existing e = jdbc.sql("""
                SELECT method_path, request_hash, recovery_point, resource_id, response_status,
                       response_body::text AS response_body,
                       (locked_until IS NOT NULL AND locked_until > now()) AS busy
                FROM idempotency_keys
                WHERE user_id = :u AND idem_key = :k
                FOR UPDATE
                """)
                .param("u", userId).param("k", key)
                .query(Existing.class)
                .single();
        if (!e.methodPath().equals(methodPath) || !Arrays.equals(e.requestHash(), hash)) {
            throw new ApiError(HttpStatus.UNPROCESSABLE_CONTENT, "IDEMPOTENCY_KEY_REUSED",
                    "Esa Idempotency-Key ya se usó con otra request. Genera una nueva para una acción nueva.");
        }
        if ("finished".equals(e.recoveryPoint())) {
            return new Begin.Replay(e.responseStatus(), e.responseBody());
        }
        if (e.busy()) {
            throw new ApiError(HttpStatus.CONFLICT, "IDEMPOTENCY_IN_PROGRESS",
                    "Otra request con esta clave se está ejecutando. Reintenta en un segundo.", Map.of(), 1);
        }
        jdbc.sql("""
                UPDATE idempotency_keys SET locked_until = now() + make_interval(secs => :lease)
                WHERE user_id = :u AND idem_key = :k
                """)
                .param("u", userId).param("k", key).param("lease", LEASE_SECONDS)
                .update();
        return new Begin.Resume(e.resourceId());
    }

    public void attach(long userId, UUID key, UUID resourceId) {
        jdbc.sql("UPDATE idempotency_keys SET resource_id = :r WHERE user_id = :u AND idem_key = :k")
                .param("r", resourceId).param("u", userId).param("k", key)
                .update();
    }

    /** Guarda la respuesta y suelta el lease. Desde aquí, la misma clave repite esta respuesta. */
    public void finish(long userId, UUID key, int status, String body) {
        jdbc.sql("""
                UPDATE idempotency_keys
                SET recovery_point = 'finished', response_status = :s, response_body = CAST(:b AS jsonb),
                    locked_until = NULL
                WHERE user_id = :u AND idem_key = :k
                """)
                .param("s", status).param("b", body).param("u", userId).param("k", key)
                .update();
    }

    /** Suelta el lease sin terminar: el reintento del cliente puede retomar enseguida, sin esperar los 60 s del lease. */
    public void release(long userId, UUID key) {
        jdbc.sql("UPDATE idempotency_keys SET locked_until = NULL WHERE user_id = :u AND idem_key = :k")
                .param("u", userId).param("k", key)
                .update();
    }
}

Todo o nada. Si F7 está libre y F8 no, la respuesta es 409 con la lista de los que no están, y nadie ve a F7 apartado ni por un instante, porque la transacción se deshace antes del commit. La toma perezosa: un asiento held con el plazo vencido se puede tomar en el momento, sin esperar al barrido, y la reserva vencida que lo tenía pasa a expired en la misma transacción. Así el mapa muestra libre un asiento vencido, y quien lo pide lo obtiene. SET LOCAL statement_timeout = '2s': si algo se traba, la request falla rápido en lugar de ocupar una conexión.
Lo que descartas
Leer el estado sin lock y escribir después con un WHERE status = 'available': con varios asientos, F7 podría quedar apartado y F8 no, y tendrías que deshacer a mano. Y dejar que la toma perezosa también tome asientos en checkout vencidos: el cliente podría estar pagando en ese instante.
Qué puede salir mal
Que el usuario tenga una reserva propia vencida que sigue en held porque el barrido no pasó: el índice único lo bloquearía. El paso 4 de reserveInTx la vence antes de insertar la nueva. Y que la toma perezosa deje a la reserva vieja con otros asientos todavía apartados: el barrido de held los libera por asiento, no por reserva, así que tampoco quedan colgados.

/**
 * Pasar una reserva de held a checkout y crear su PaymentIntent. Tres fases, como el pedido de A15, porque la
 * llamada a Stripe no puede ir dentro de una transacción (retendría los locks de los asientos medio minuto):
 * <ol>
 *   <li>TX1: la clave, los locks (asientos y después la reserva) y el cambio a checkout con su plazo de 3 min.</li>
 *   <li>Stripe, sin transacción, con la clave pi-create:{reserva}. Repetirla devuelve el mismo PaymentIntent.</li>
 *   <li>TX3: el id del PaymentIntent en la reserva, solo si sigue en checkout, y la respuesta en la clave.</li>
 * </ol>
 */
@Service
@Profile("api")
public class CheckoutService {

    private static final Logger log = LoggerFactory.getLogger(CheckoutService.class);

    private final JdbcClient jdbc;
    private final TransactionTemplate tx;
    private final IdempotencyKeys keys;
    private final Reservations reservations;
    private final Releases releases;
    private final PaymentGateway gateway;
    private final SeatEvents events;
    private final JsonMapper json;
    private final CineProps props;

    public CheckoutService(JdbcClient jdbc, TransactionTemplate tx, IdempotencyKeys keys, Reservations reservations,
                           Releases releases, PaymentGateway gateway, SeatEvents events,
                           JsonMapper json, CineProps props) {
        this.jdbc = jdbc;
        this.tx = tx;
        this.keys = keys;
        this.reservations = reservations;
        this.releases = releases;
        this.gateway = gateway;
        this.events = events;
        this.json = json;
        this.props = props;
    }

    static String methodPath(UUID id) {
        return "POST /v1/reservations/" + id + "/checkout";
    }

    public ApiResult checkout(long userId, String email, UUID key, UUID id) {
        String methodPath = methodPath(id);
        byte[] hash = RequestHash.of(methodPath, "");

        // Fase 1
        Begin.Replay replayed;
        try {
            replayed = tx.execute(s -> {
                Begin begin = keys.begin(userId, key, methodPath, hash);
                if (begin instanceof Begin.Replay r) {
                    return r;
                }
                // Sin lock, para saber si existe y es tuya. Un 404 deshace también la clave.
                reservations.find(userId, id).orElseThrow(ApiError::notFound);
                if (begin instanceof Begin.Resume) {
                    // Una request anterior con esta clave ya hizo la TX1 y no terminó. La fase 2 relee el estado.
                    return null;
                }
                toCheckout(id);
                keys.attach(userId, key, id);
                return null;
            });
        } catch (DataAccessException e) {
            if (Sql.LOCK_NOT_AVAILABLE.equals(Sql.state(e))) {
                throw ReservationService.seatsBusy();
            }
            throw e;
        }
        if (replayed != null) {
            // Fuera de la transacción: el replay de un 200 llama a Stripe.
            return replay(replayed);
        }

        // Fase 2
        ReservationRow r = reservations.find(userId, id).orElseThrow(ApiError::notFound);
        if (!r.is("checkout")) {
            // El barrido la liberó mientras esta clave estaba a medias (el proceso murió y el plazo venció).
            return finishError(userId, key, 410, "RESERVATION_EXPIRED", "La reserva venció. Elige tus asientos de nuevo.",
                    Map.of("reservation_id", id.toString()));
        }
        PaymentIntentView pi;
        try {
            pi = gateway.createPaymentIntent(request(r, email), "pi-create:" + id);
        } catch (GatewayException e) {
            return switch (e.kind()) {
                case RETRYABLE, CONFIG -> {
                    if (e.kind() == GatewayException.Kind.CONFIG) {
                        log.error("ALERTA: la clave de Stripe de la api no sirve para crear PaymentIntents: {}",
                                e.getMessage());
                    }
                    // La reserva sigue en checkout y la clave en started: el reintento retoma desde aquí.
                    tx.executeWithoutResult(s -> keys.release(userId, key));
                    throw ReservationService.unavailable();
                }
                case PROVIDER_ERROR, REJECTED -> {
                    // Stripe guardó ese error con nuestra clave: reintentarla daría lo mismo durante 24 h.
                    releases.release(id, "canceled", Set.of("checkout"), false);
                    Map<String, Object> details = e.code() == null
                            ? Map.of("reservation_id", id.toString())
                            : Map.of("reservation_id", id.toString(), "stripe_code", e.code());
                    yield finishError(userId, key, 502, "PAYMENT_PROVIDER_ERROR",
                            "El procesador de pagos rechazó el cobro. Liberamos tus asientos; elige de nuevo.", details);
                }
            };
        }
        CrashPoints.haltIfAsked("tras-stripe");

        // Fase 3
        PaymentIntentView created = pi;
        ApiResult done = tx.execute(s -> {
            int linked = jdbc.sql("""
                    UPDATE reservations SET payment_intent_id = :pi, updated_at = now()
                    WHERE id = :id AND status = 'checkout' AND (payment_intent_id IS NULL OR payment_intent_id = :pi)
                    """)
                    .param("pi", created.id()).param("id", id)
                    .update();
            if (linked == 0) {
                return null;
            }
            ReservationView v = reservations.byId(id).orElseThrow().view();
            // Lo que se guarda no lleva el client_secret: Stripe pide no guardarlo ni loguearlo.
            String stored = json.writeValueAsString(v.withPayment(payment(created, null)));
            keys.finish(userId, key, 200, stored);
            return new ApiResult(200, json.writeValueAsString(v.withPayment(payment(created, created.clientSecret()))),
                    false);
        });
        if (done != null) {
            return done;
        }
        // La reserva dejó de estar en checkout mientras hablábamos con Stripe: ese PaymentIntent no tiene qué vender.
        cancelQuietly(created.id());
        return finishError(userId, key, 410, "RESERVATION_EXPIRED", "La reserva venció mientras se preparaba el pago.",
                Map.of("reservation_id", id.toString()));
    }

    /** Dentro de la TX1. Primero los asientos (NOWAIT), después la reserva: el orden de siempre. */
    private void toCheckout(UUID id) {
        List<Long> seatIds = jdbc.sql(SeatSql.LOCK_OF_RESERVATION + " NOWAIT")
                .param("res", id)
                .query(Long.class)
                .list();
        ReservationRow r = reservations.lock(id);
        switch (r.status()) {
            case "held" -> {
                if (!r.expiresAt().isAfter(r.serverTime()) || seatIds.size() != r.seatCount()) {
                    // Venció, o venció y otro tomó alguno de sus asientos (toma perezosa).
                    throw ReservationService.gone("La reserva venció. Elige tus asientos de nuevo.");
                }
            }
            case "checkout" -> throw new ApiError(HttpStatus.CONFLICT, "INVALID_STATE",
                    "Esta reserva ya tiene un pago iniciado desde otra pestaña. Termínalo ahí o cancélala.",
                    Map.of("reason", "checkout_other_key"), null);
            case "paid", "refunded" -> throw ReservationService.invalidState("Esta reserva ya está pagada.", "paid");
            default -> throw ReservationService.gone("La reserva venció. Elige tus asientos de nuevo.");
        }
        OffsetDateTime expires = jdbc.sql("""
                UPDATE reservations
                SET status = 'checkout', expires_at = now() + make_interval(secs => :ttl), updated_at = now()
                WHERE id = :id
                RETURNING expires_at
                """)
                .param("ttl", CineProps.secs(props.holds().checkoutTtl())).param("id", id)
                .query(OffsetDateTime.class)
                .single();
        List<ChangedSeat> changed = jdbc.sql("""
                UPDATE seats SET status = 'checkout', hold_expires_at = :exp, %s
                WHERE reservation_id = :id AND status = 'held'
                %s
                """.formatted(SeatSql.TOUCH, SeatSql.RETURNING))
                .param("exp", expires).param("id", id)
                .query(ChangedSeat.class)
                .list();
        events.seatsChanged(changed);
    }

    /**
     * El replay de un 200 vuelve a pedir el PaymentIntent para devolver el client_secret, que no está guardado.
     * Cualquier otra respuesta guardada (410, 502) se repite tal cual.
     */
    private ApiResult replay(Begin.Replay r) {
        if (r.status() != 200) {
            return new ApiResult(r.status(), r.body(), true);
        }
        ReservationView v = json.readValue(r.body(), ReservationView.class);
        PaymentIntentView pi;
        try {
            pi = gateway.retrievePaymentIntent(v.payment().paymentIntentId());
        } catch (GatewayException e) {
            throw ReservationService.unavailable();
        }
        return new ApiResult(200, json.writeValueAsString(v.withPayment(payment(pi, pi.clientSecret()))), true);
    }

    private static ReservationView.Payment payment(PaymentIntentView pi, String clientSecret) {
        return new ReservationView.Payment(pi.id(), clientSecret, new ReservationView.Amount(pi.amount(), pi.currency()));
    }

    /** Todo sale de la reserva congelada en la base: el mismo request en cada reintento con la misma clave. */
    private PaymentIntentRequest request(ReservationRow r, String email) {
        String description = "Función " + r.showingId() + ", asientos " + String.join(" ", r.labels());
        return new PaymentIntentRequest(r.id(), r.showingId(), r.amountMinor(), r.currency(), description,
                email);
    }

    private void cancelQuietly(String paymentIntentId) {
        try {
            gateway.cancelPaymentIntent(paymentIntentId);
        } catch (GatewayException e) {
            // Nadie tiene su client_secret, así que nadie puede pagarlo. Si se pagara igual, finalize lo anota
            // como huérfano y el worker lo reembolsa.
            log.warn("No pude cancelar {}: {}", paymentIntentId, e.getMessage());
        }
    }

    private ApiResult finishError(long userId, UUID key, int status, String code, String message,
                                  Map<String, Object> details) {
        String body = json.writeValueAsString(ErrorBody.of(code, message, details));
        tx.executeWithoutResult(s -> keys.finish(userId, key, status, body));
        return new ApiResult(status, body, false);
    }
}

        // allowed_payment_method_types filtra los métodos de pago que acepta este PaymentIntent.
        // Solo tarjeta: así el Payment Element no ofrece métodos que tardan días en confirmarse.
        PaymentIntentCreateParams params = PaymentIntentCreateParams.builder()
                .setAmount(r.amountMinor())
                .setCurrency(r.currency())
                .addAllowedPaymentMethodType(PaymentIntentCreateParams.AllowedPaymentMethodType.CARD)
                .putMetadata("reservation_id", r.reservationId().toString())
                .putMetadata("showing_id", Long.toString(r.showingId()))
                .setDescription(r.description())
                .setReceiptEmail(r.receiptEmail())
                .build();
        return call("payment_intents.create", () ->
                view(stripe.v1().paymentIntents().create(params, options(idempotencyKey))));
    }

    public PaymentIntentView retrievePaymentIntent(String id) {
        return call("payment_intents.retrieve", () -> view(stripe.v1().paymentIntents().retrieve(id)));
    }

     * un error: con pi-cancel:{pi}, un cancel rechazado mientras el pago estaba en processing se repetiría igual
     * aunque el PaymentIntent volviera después a requires_payment_method. Cancelar dos veces no hace daño (el
     * segundo intento falla con payment_intent_unexpected_state) y quien llama nunca interpreta la respuesta:
     * vuelve a leer el PaymentIntent. Los reintentos de red del SDK llevan su propia clave.
     */

        PaymentIntentCancelParams params = PaymentIntentCancelParams.builder()
                .setCancellationReason(PaymentIntentCancelParams.CancellationReason.ABANDONED)
                .build();
        return call("payment_intents.cancel", () -> view(stripe.v1().paymentIntents().cancel(id, params)));
    }

    @Override
    public RefundView createRefund(String paymentIntentId, String reservationId, String idempotencyKey) {

        RefundCreateParams.Builder b = RefundCreateParams.builder().setPaymentIntent(paymentIntentId);
        if (reservationId != null) {

        RefundCreateParams params = b.build();

            Refund f = stripe.v1().refunds().create(params, options(idempotencyKey));
            return new RefundView(f.getId(), f.getStatus(), f.getAmount(), f.getPaymentIntent());
        });
    }

        T run() throws StripeException;
    }

    /** Traduce cada excepción de Stripe por su tipo, nunca por el texto del mensaje. */
    private static <T> T call(String what, StripeCall<T> body) {
        try {
            return body.run();
        } catch (ApiConnectionException | RateLimitException e) {
            // RateLimitException incluye lock_timeout: otra request de Stripe tiene el objeto en ese instante.
            throw fail(what, Kind.RETRYABLE, e);
        } catch (IdempotencyException e) {
            throw fail(what, Integer.valueOf(409).equals(e.getStatusCode()) ? Kind.RETRYABLE : Kind.REJECTED, e);
        } catch (AuthenticationException e) {
            // También atrapa PermissionException, que la extiende: la clave restringida no tiene ese permiso.
            throw fail(what, Kind.CONFIG, e);
        } catch (ApiException e) {
            throw fail(what, Kind.PROVIDER_ERROR, e);
        } catch (StripeException e) {
            throw fail(what, Kind.REJECTED, e);
        }
    }

    private static GatewayException fail(String what, Kind kind, StripeException e) {
        // Se loguea el request id de Stripe (req_…), que es lo que pide soporte; nunca el cuerpo ni el client_secret.
        log.warn("Stripe {} falló: {} code={} status={} request={}", what, kind, e.getCode(), e.getStatusCode(),
                e.getRequestId());
        return new GatewayException(kind, e.getCode(), what + ": " + e.getMessage(), e);
    }
}

La decisión
La clave hacia Stripe es pi-create:{reserva}: cualquier reintento del checkout de esa reserva manda la misma, y Stripe devuelve el mismo PaymentIntent. El client_secret no se guarda en la base: Stripe pide no guardarlo, no loguearlo y no mostrárselo a nadie más que al cliente Documentado. Por eso el replay de un 200 vuelve a leer el PaymentIntent en Stripe para devolverlo. El PaymentIntent solo acepta tarjeta, con allowed_payment_method_types Documentado: un débito bancario puede tardar días en confirmarse, y el apartado dura 3 minutos.
Lo que descartas
Crear el PaymentIntent al reservar: la mitad de las reservas no llega al pago, y cada una dejaría un PaymentIntent que cancelar. Y guardar el client_secret para responder el replay sin llamar a Stripe: es una llamada menos, a cambio de tener en la base un secreto que permite confirmar el pago de otro.
Qué puede salir mal
Que el cliente abra el pago en dos pestañas. La segunda no tiene la clave de la primera, su POST llega con otra y recibe 409 checkout_other_key: app.js le dice que termine en la otra pestaña o cancele. Y que el barrido libere la reserva mientras la api estaba caída entre la TX1 y Stripe: al reintentar, la fase 2 ve que ya no está en checkout y responde 410 sin crear el PaymentIntent.

Paso 6. Vender: finalize y el código de cada asiento

Vender lo dispara cualquiera de cuatro caminos: el navegador al volver de confirmPayment, el webhook payment_intent.succeeded, el barrido que encuentra un pago terminado y el DELETE que llegó tarde. Pueden llegar a la vez. Todos llaman a PaymentFinalizer.finalize, que lee el PaymentIntent en Stripe, fuera de toda transacción, y vende solo si está succeeded.

/**
 * Cierra la venta cuando el PaymentIntent quedó en succeeded. Lo llaman cuatro caminos: el navegador al volver de
 * confirmar, el webhook payment_intent.succeeded, el barrido y el DELETE que llegó tarde. Pueden llegar a la vez:
 * el lock de los asientos y el chequeo de estado hacen que solo uno venda y los demás vean ALREADY_PAID.
 * <p>
 * El estado del pago se lee siempre de Stripe con un retrieve, fuera de toda transacción. Nunca del navegador
 * ni del cuerpo del webhook: los dos dicen lo que pasó, pero no se les cree.
 */
@Component
@Profile({"api", "worker"})
public class PaymentFinalizer {

    private static final Logger log = LoggerFactory.getLogger(PaymentFinalizer.class);
    /** Una colisión de ticket_code (60 bits al azar) casi no ocurre; si ocurre, se generan otros. */
    static final int CODE_ATTEMPTS = 3;

    private final JdbcClient jdbc;
    private final TransactionTemplate tx;
    private final PaymentGateway gateway;
    private final Reservations reservations;
    private final Releases releases;
    private final SeatEvents events;

    public PaymentFinalizer(JdbcClient jdbc, TransactionTemplate tx, PaymentGateway gateway,
                            Reservations reservations, Releases releases, SeatEvents events) {
        this.jdbc = jdbc;
        this.tx = tx;
        this.gateway = gateway;
        this.reservations = reservations;
        this.releases = releases;
        this.events = events;
    }

    /** Lanza GatewayException si Stripe no responde: quien llama decide si reintenta. */
    public Outcome finalize(String paymentIntentId) {
        return finalize(gateway.retrievePaymentIntent(paymentIntentId));
    }

    public Outcome finalize(PaymentIntentView pi) {
        return switch (pi.status()) {
            case "succeeded" -> sell(pi);
            case "processing" -> Outcome.of(Kind.PROCESSING);
            case "requires_payment_method" -> new Outcome(Kind.FAILED,
                    pi.declineCode() != null ? pi.declineCode() : pi.errorCode());
            case "canceled" -> Outcome.of(Kind.CANCELED);
            default -> Outcome.of(Kind.INCOMPLETE);
        };
    }

    private Outcome sell(PaymentIntentView pi) {
        // Sin lock: solo para saber qué asientos bloquear. Después se vuelve a leer con lock.
        Optional<UUID> res = jdbc.sql("SELECT id FROM reservations WHERE payment_intent_id = :pi")
                .param("pi", pi.id())
                .query(UUID.class)
                .optional();
        if (res.isEmpty()) {
            return orphan(pi, null, "sin_reserva");
        }
        for (int attempt = 1; ; attempt++) {
            try {
                return tx.execute(s -> sellInTx(pi, res.get()));
            } catch (DataAccessException e) {
                if (attempt < CODE_ATTEMPTS && Sql.violates(e, "seats_ticket_code_key")) {
                    log.warn("Colisión de ticket_code en la reserva {}: genero otros", res.get());
                    continue;
                }
                throw e;
            }
        }
    }

    private Outcome sellInTx(PaymentIntentView pi, UUID id) {
        // Primero los asientos, después la reserva. Con espera: quien los tiene termina en milisegundos.
        List<Long> seatIds = jdbc.sql(SeatSql.LOCK_OF_RESERVATION).param("res", id).query(Long.class).list();
        ReservationRow r = reservations.lock(id);
        if (r.is("paid") || r.is("refunded")) {
            return Outcome.of(Kind.ALREADY_PAID);
        }
        // Lo que se cobró tiene que ser lo que se vende: monto, moneda y la reserva que va en la metadata.
        boolean matches = pi.amount() == r.amountMinor() && r.currency().equalsIgnoreCase(pi.currency())
                && id.toString().equals(pi.reservationId());
        if (!r.is("checkout")) {
            return orphan(pi, id, "reserva_" + r.status());
        }
        if (!matches || seatIds.size() != r.seatCount()) {
            // Algo está muy mal (un bug, o alguien tocó la base). No se vende: se devuelve el dinero y se liberan
            // los asientos, para que el barrido no vuelva a encontrar este pago cada 5 s.
            releases.release(id, "canceled", Set.of("checkout"), false);
            return orphan(pi, id, !matches ? "monto_o_metadata_distintos" : "asientos_incompletos");
        }
        String[] codes = TicketCodes.next(seatIds.size());
        List<ChangedSeat> sold = jdbc.sql("""
                UPDATE seats s
                SET status = 'sold', ticket_code = v.code, hold_expires_at = NULL, %s
                FROM unnest(CAST(:ids AS bigint[]), CAST(:codes AS text[])) AS v(id, code)
                WHERE s.id = v.id AND s.reservation_id = :res AND s.status = 'checkout'
                %s
                """.formatted(SeatSql.TOUCH, SeatSql.RETURNING))
                .param("ids", Sql.textArray(seatIds)).param("codes", codes).param("res", id)
                .query(ChangedSeat.class)
                .list();
        if (sold.size() != r.seatCount()) {
            // Los CHECK de la base hacen esto imposible; si pasa, que no quede una venta a medias.
            throw new IllegalStateException("Vendí " + sold.size() + " de " + r.seatCount() + " asientos en " + id);
        }
        jdbc.sql("UPDATE reservations SET status = 'paid', paid_at = now(), updated_at = now() WHERE id = :id")
                .param("id", id)
                .update();
        events.seatsChanged(sold);
        events.toOwner(r.userId(), new ReservationEvent(id, "paid", null));
        log.info("Vendí {} asientos de la reserva {} con {}", sold.size(), id, pi.id());
        return Outcome.of(Kind.SOLD);
    }

    /**
     * Un pago que no tiene qué venderle. No debería pasar; si pasa, el dinero se devuelve.
     * ON CONFLICT DO NOTHING sin columnas: el rol de la api solo tiene INSERT en esta tabla, y anotarlo dos veces
     * (el navegador y el webhook a la vez) no es un error.
     */
    private Outcome orphan(PaymentIntentView pi, UUID reservationId, String reason) {
        jdbc.sql("""
                INSERT INTO orphan_payments (payment_intent_id, reservation_id, reason)
                VALUES (:pi, :res, :reason)
                ON CONFLICT DO NOTHING
                """)
                .param("pi", pi.id()).param("res", reservationId).param("reason", reason)
                .update();
        log.error("ALERTA: pago {} sin venta ({}), reserva {}. Queda para reembolso", pi.id(), reason, reservationId);
        return Outcome.of(Kind.ORPHAN);
    }
}

import java.security.SecureRandom;

/**
 * El código de una entrada: TK- y 12 caracteres del alfabeto de Crockford (sin I, L, O ni U, que se confunden
 * al dictarlos). 12 caracteres de 5 bits son 60 bits al azar: adivinar uno válido entre 100 vendidos es una
 * probabilidad de 100 / 2^60. Sale de SecureRandom, no de Random: un código predecible es una entrada gratis.
 */
public final class TicketCodes {

    static final String ALPHABET = "0123456789ABCDEFGHJKMNPQRSTVWXYZ";
    static final int LENGTH = 12;
    private static final SecureRandom RANDOM = new SecureRandom();

    private TicketCodes() {
    }

    public static String next() {
        StringBuilder b = new StringBuilder("TK-");
        for (int i = 0; i < LENGTH; i++) {
            b.append(ALPHABET.charAt(RANDOM.nextInt(ALPHABET.length())));
        }
        return b.toString();
    }

    public static String[] next(int n) {
        String[] codes = new String[n];
        for (int i = 0; i < n; i++) {
            codes[i] = next();
        }
        return codes;
    }
}

                    .param("res", id)
                    .query(Long.class)
                    .list();

            if (!from.contains(r.status())) {
                return false;
            }
            jdbc.sql("UPDATE reservations SET status = :to, updated_at = now() WHERE id = :id")
                    .param("to", toStatus).param("id", id)
                    .update();

            List<ChangedSeat> freed = jdbc.sql("""
                    UPDATE seats
                    SET status = 'available', reservation_id = NULL, hold_expires_at = NULL, %s
                    WHERE reservation_id = :id AND status IN ('held', 'checkout')
                    %s
                    """.formatted(SeatSql.TOUCH, SeatSql.RETURNING))

                    .query(ChangedSeat.class)
                    .list();

            events.toOwner(r.userId(), new ReservationEvent(id, toStatus, null));
            return true;
        }));

El código es TK- y 12 caracteres del alfabeto de Crockford, que deja afuera I, L, O y U para que nadie confunda un 1 con una I al dictarlo. Cada carácter lleva 5 bits, así que son 60 bits de SecureRandom: 260, unos 1.15·1018 códigos posibles. La probabilidad de que dos de n códigos coincidan es de unos n²/261: con 100 000 boletos, 1010/2.3·1018 ≈ 4.3·10-9. Si pasa igual, el UNIQUE de ticket_code hace fallar la transacción y finalize vuelve a intentar con otros códigos.

La decisión
finalize no mira el reloj. Si Stripe dice succeeded y la reserva sigue en checkout, vende aunque hayan pasado los 3 minutos: solo puede pasar si el barrido intentó cancelar y el pago ganó la carrera, y entonces el asiento sigue siendo de quien pagó. Antes de vender compara el monto, la moneda y el reservation_id de la metadata con la reserva. El lock de los asientos y el chequeo de estado hacen que, de cuatro llamadas a la vez, una venda y las otras vean ALREADY_PAID.
Lo que descartas
Vender con lo que dice el navegador o el cuerpo del webhook: los dos cuentan lo que pasó, y cualquiera de los dos se puede inventar o llegar viejo. Y un código secuencial o con Random: con el número de un boleto, se adivinan los demás.
Qué puede salir mal
Un pago que llega sin asientos que venderle: la reserva ya está expired, o el monto no coincide. No debería pasar, porque el barrido cancela antes de liberar. Si pasa, finalize no vende: lo anota en orphan_payments con un ALERTA, y el worker lo reembolsa en el paso 11. Es la red de seguridad, y una alerta, no el camino normal: este diseño nunca reembolsa por tiempo.

Paso 7. El barrido: cancelar antes de liberar

El worker corre el barrido cada 5 s, con dos trabajos distintos. Las reservas held vencidas no tienen dinero en juego: se marcan expired y sus asientos vuelven a available en una transacción, con SKIP LOCKED. Las reservas en checkout vencidas pueden tener un pago en vuelo, y ahí está la regla más importante del proyecto: un asiento en pago no se libera hasta que Stripe confirme que el pago ya no puede ocurrir.

            expired.forEach(o -> events.toOwner(o.userId(), new ReservationEvent(o.id(), "expired", null)));
            // Por asiento, no por reserva: también libera los que quedaron de una reserva que ya venció por la toma
            // perezosa de otro asiento (esa reserva ya está en expired y no saldría en la consulta de arriba).
            List<ChangedSeat> seats = jdbc.sql("""
                    UPDATE seats
                    SET status = 'available', reservation_id = NULL, hold_expires_at = NULL, %s
                    WHERE id IN (
                        SELECT id FROM seats
                        WHERE status = 'held' AND hold_expires_at <= now()
                        ORDER BY id
                        LIMIT :n
                        FOR UPDATE SKIP LOCKED)
                    %s
                    """.formatted(SeatSql.TOUCH, SeatSql.RETURNING))
                    .param("n", props.holds().sweeperBatch())
                    .query(ChangedSeat.class)
                    .list();
            events.seatsChanged(seats);
            return seats.size();
        });
        return freed == null ? 0 : freed;
    }

    /** Devuelve cuántas reservas en checkout vencidas revisó. */
    public int sweepCheckout() {
        List<Due> due = jdbc.sql("""
                SELECT id, payment_intent_id, grace_used FROM reservations
                WHERE status = 'checkout' AND expires_at <= now()
                ORDER BY expires_at
                LIMIT :n
                """)
                .param("n", props.holds().sweeperBatch())
                .query(Due.class)
                .list();
        for (Due d : due) {
            try {
                checkout(d);
            } catch (RuntimeException e) {
                // Stripe no responde, o un lock: la reserva sigue vencida y la vuelta siguiente lo intenta otra vez.
                log.warn("No pude cerrar la reserva vencida {}: {}", d.id(), e.getMessage());
            }
        }
        return due.size();
    }

    private void checkout(Due d) {
        if (d.paymentIntentId() == null) {
            // Nunca llegó a crearse el PaymentIntent (el proceso murió en la fase 2): no hay pago posible.
            releases.release(d.id(), "expired", Set.of("checkout"), false);
            return;
        }
        act(d, gateway.retrievePaymentIntent(d.paymentIntentId()), true);
    }

    /** La tabla de decisión del barrido. mayCancel es false después de un cancel fallido: no se insiste. */
    private void act(Due d, PaymentIntentView pi, boolean mayCancel) {
        switch (pi.status()) {
            case "requires_payment_method", "requires_confirmation" -> cancel(d, mayCancel);
            case "requires_action" -> {
                if (!d.graceUsed()) {
                    grant(d);
                } else {
                    cancel(d, mayCancel);
                }
            }
            case "processing" -> log.info("La reserva {} venció con el pago en processing: espero al banco", d.id());
            case "succeeded" -> finalizer.finalize(pi);
            case "canceled" -> releases.release(d.id(), "expired", Set.of("checkout"), false);
            default -> log.warn("La reserva {} venció con su pago en {}: no sé qué hacer", d.id(), pi.status());
        }
    }

    private void cancel(Due d, boolean mayCancel) {
        if (!mayCancel) {
            log.warn("El cancel de {} falló y sigue cancelable: lo intento en la vuelta siguiente", d.paymentIntentId());
            return;
        }
        PaymentIntentView after;
        try {
            after = gateway.cancelPaymentIntent(d.paymentIntentId());
        } catch (GatewayException e) {
            // Lo típico: payment_intent_unexpected_state, porque el cliente pagó justo ahora. Se vuelve a leer y
            // se decide por el estado nuevo, sin cancelar otra vez.
            log.info("El cancel de {} falló ({}): vuelvo a leerlo", d.paymentIntentId(), e.code());
            after = gateway.retrievePaymentIntent(d.paymentIntentId());
        }
        act(d, after, false);
    }

    /**
     * La prórroga de 3D Secure: una sola vez, solo si el pago espera la autenticación del cliente.
     * Primero los asientos, después la reserva, como todos. NOT grace_used en el WHERE: con dos barridos a la vez,
     * solo uno la concede.
     */
    private void grant(Due d) {
        tx.executeWithoutResult(s -> {
            jdbc.sql(SeatSql.LOCK_OF_RESERVATION).param("res", d.id()).query(Long.class).list();
            Optional<Granted> g = jdbc.sql("""
                    UPDATE reservations
                    SET expires_at = now() + make_interval(secs => :grace), grace_used = true, updated_at = now()
                    WHERE id = :id AND status = 'checkout' AND NOT grace_used
                    RETURNING expires_at, user_id
                    """)
                    .param("grace", CineProps.secs(props.holds().threeDsGrace())).param("id", d.id())
                    .query(Granted.class)
                    .optional();
            if (g.isEmpty()) {
                return;
            }
            List<ChangedSeat> seats = jdbc.sql("""
                    UPDATE seats SET hold_expires_at = :exp, %s
                    WHERE reservation_id = :id AND status = 'checkout'
                    %s
                    """.formatted(SeatSql.TOUCH, SeatSql.RETURNING))
                    .param("exp", g.get().expiresAt()).param("id", d.id())
                    .query(ChangedSeat.class)
                    .list();
            events.seatsChanged(seats);
            events.toOwner(g.get().userId(), new ReservationEvent(d.id(), "grace", g.get().expiresAt()));
            log.info("Prórroga de 3D Secure para la reserva {} hasta {}", d.id(), g.get().expiresAt());
        });
    }
}
La decisión
Cancelar primero, liberar después. Un PaymentIntent cancelado ya no se puede confirmar Documentado, así que después del cancel no hay pago tardío posible y liberar es seguro. Si el cancel falla, lo más común es que el cliente pagó en ese instante: el barrido no interpreta el error, vuelve a leer el PaymentIntent, lo ve succeeded y vende. Un PaymentIntent de tarjeta en processing no se puede cancelar Documentado: el barrido espera, y el webhook decide cuando el banco conteste.
Lo que descartas
Liberar por tiempo y reembolsar si el pago llega después. Es más simple, pero el asiento ya pudo venderse a otro, y el primer cliente ve un cargo y un reembolso por algo que no compró. Y cancelar con una clave fija, pi-cancel:{pi}: Stripe guarda también la respuesta de error con cada clave Documentado, así que un cancel rechazado mientras el pago estaba en processing se repetiría rechazado aunque el pago volviera a requires_payment_method. Cancelar dos veces no hace daño: el segundo falla con payment_intent_unexpected_state Documentado.
Qué puede salir mal
Que Stripe no responda: la reserva sigue vencida, en checkout, y el mapa la sigue mostrando apartada hasta la vuelta siguiente. Es lo correcto: es preferible que un asiento quede apartado unos segundos de más a venderlo dos veces. Y que el webhook payment_intent.canceled llegue antes que la transacción del barrido: el worker libera, y el barrido no encuentra la reserva en checkout y no hace nada.

Paso 8. La prórroga de 3D Secure y cómo se maneja el error

3D Secure es la verificación del banco: una ventana del emisor donde el cliente confirma la compra en su app o con un código (M27). Mientras esa ventana está abierta, el PaymentIntent está en requires_action Documentado. Si el plazo vence en ese momento, cancelar castiga a quien sí estaba pagando. La regla: una sola prórroga de 60 s, solo si al vencer el pago está en requires_action. Con la prórroga, el pago dura como mucho 4 minutos.

La extensión es grant en HoldSweeper: bloquea los asientos y la reserva, mueve expires_at y hold_expires_at juntos y marca grace_used. El WHERE … AND NOT grace_used hace que, con dos barridos a la vez, solo uno la conceda. Después del commit, el dueño recibe un evento privado reservation con type: grace, y el mapa público muestra el nuevo held_until sin decir de quién es el asiento.

El navegador nunca decide qué pasó con un pago solo con el código de un error. stripe.confirmPayment puede terminar con un pago, con un error o no terminar nunca, y ante cualquier cosa que no sea un pago, app.js pregunta a GET /v1/reservations/{id}:

La decisión
Extender solo en requires_action, porque es el único estado donde la demora no es del cliente: el pago está en manos del banco. Una sola vez, para que el apartado tenga un máximo conocido, 4 minutos. Y sin riesgo de pisar a otro: un asiento en checkout no se puede tomar con la toma perezosa, así que nadie pudo apartarlo entre el vencimiento y la extensión.
Lo que descartas
Un plazo más largo para todos, por ejemplo 5 minutos: el 3D Secure es la excepción, y alargar todos los apartados deja más asientos bloqueados por gente que ya se fue. Y extender cada vez que el banco vuelve a pedir el desafío: un cliente podría retener los asientos indefinidamente con una tarjeta que nunca se verifica.
Qué puede salir mal
Que el cliente termine el desafío justo cuando vence la prórroga y el barrido cancela. Stripe resuelve las dos operaciones sobre el mismo PaymentIntent una después de la otra: si el pago llegó primero, el cancel falla, el barrido relee succeeded y vende; si el cancel llegó primero, el confirm del cliente falla y su pantalla dice "Se acabó el tiempo". El código exacto que devuelve Stripe.js en ese caso lo vas a anotar en el experimento de 3D Secure.

Paso 9. El mapa en vivo con SSE y Redis Pub/Sub

SSE (Server-Sent Events) es una respuesta HTTP que no termina, por la que el servidor manda eventos de texto; el navegador la abre con EventSource y se reconecta solo (M17). Con dos réplicas, cada navegador está conectado a una sola. Después de cada commit que cambia asientos, quien hizo el cambio publica en Redis Pub/Sub, y cada réplica reenvía el mensaje a sus streams.

import tools.jackson.databind.json.JsonMapper;

/**
 * Publica en Redis Pub/Sub lo que cambió, después del commit: nunca un estado que podría deshacerse.
 * Si Redis no está, se loguea y la request sigue: el mapa se corrige con la foto (resync o recarga), y la base
 * es la que decide quién tiene cada asiento. Por eso publicar no está dentro de la transacción.
 */
@Component
@Profile({"api", "worker"})
public class SeatEvents {

    private static final Logger log = LoggerFactory.getLogger(SeatEvents.class);

    public record SeatsMessage(@JsonProperty("showing_id") long showingId, List<SeatState> seats) {
    }

    private final StringRedisTemplate redis;
    private final JsonMapper json;

    public SeatEvents(StringRedisTemplate redis, JsonMapper json) {
        this.redis = redis;
        this.json = json;
    }

    public static String seatsChannel(long showingId) {
        return "showing:" + showingId + ":seats";
    }

    public static String userChannel(long userId) {
        return "user:" + userId + ":reservations";
    }

    /** Los asientos que devolvió el RETURNING, agrupados por función. */
    public void seatsChanged(Collection<ChangedSeat> changed) {
        if (changed.isEmpty()) {
            return;
        }
        Map<Long, List<SeatState>> byShowing = changed.stream().collect(Collectors.groupingBy(
                ChangedSeat::showingId, Collectors.mapping(ChangedSeat::state, Collectors.toList())));
        afterCommit(() -> byShowing.forEach((showingId, seats) ->
                send(seatsChannel(showingId), () -> json.writeValueAsString(new SeatsMessage(showingId, seats)))));
    }

    public void toOwner(long userId, ReservationEvent event) {
        afterCommit(() -> send(userChannel(userId), () -> json.writeValueAsString(event)));
    }

    private static void afterCommit(Runnable publish) {
        if (TransactionSynchronizationManager.isSynchronizationActive()) {
            TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    publish.run();
                }
            });
        } else {
            publish.run();
        }
    }

    /** Corre después del commit: un error aquí ya no puede deshacer nada, así que se loguea y no se lanza. */
    private void send(String channel, Supplier<String> message) {
        try {
            redis.convertAndSend(channel, message.get());
        } catch (RuntimeException e) {
            log.warn("No pude publicar en {}: {}. El mapa se corrige con la foto", channel, e.getMessage());
        }
    }
}

/**
 * Los streams SSE abiertos en esta réplica, por función y por usuario. Un stream no retiene una conexión de base:
 * solo escribe lo que llega de Redis. Si retuviera una, 20 espectadores agotarían el pool de PgBouncer.
 */
@Component
@Profile("api")
public class StreamRegistry {

    private static final Logger log = LoggerFactory.getLogger(StreamRegistry.class);

    /** Lo que el navegador espera antes de reconectarse si el stream se corta, en milisegundos. */
    static final long RETRY_MILLIS = 3_000;

    record Stream(long showingId, long userId, SseEmitter emitter) {
    }

    private final Map<Long, Set<Stream>> byShowing = new ConcurrentHashMap<>();
    private final Map<Long, Set<Stream>> byUser = new ConcurrentHashMap<>();
    private final AtomicInteger open = new AtomicInteger();
    private final CineProps props;

    public StreamRegistry(CineProps props) {
        this.props = props;
    }

    /** Las pruebas lo reemplazan por un emisor que guarda lo que se le manda. */
    protected SseEmitter newEmitter(long timeoutMillis) {
        return new SseEmitter(timeoutMillis);
    }

    public SseEmitter open(long showingId, long userId) {
        Set<Stream> mine = byUser.computeIfAbsent(userId, k -> ConcurrentHashMap.newKeySet());
        if (mine.size() >= props.streams().maxPerUser()) {
            throw new ApiError(HttpStatus.TOO_MANY_REQUESTS, "TOO_MANY_STREAMS",
                    "Ya tienes el mapa abierto en varias pestañas. Cierra alguna.", Map.of(), 5);
        }
        if (open.get() >= props.streams().maxPerReplica()) {
            throw new ApiError(HttpStatus.SERVICE_UNAVAILABLE, "STREAMS_FULL",
                    "Esta réplica no acepta más streams. Reintenta en unos segundos.", Map.of(), 5);
        }
        SseEmitter emitter = newEmitter(props.streams().timeout().toMillis());
        Stream s = new Stream(showingId, userId, emitter);
        mine.add(s);
        byShowing.computeIfAbsent(showingId, k -> ConcurrentHashMap.newKeySet()).add(s);
        open.incrementAndGet();
        emitter.onCompletion(() -> remove(s));
        emitter.onTimeout(() -> remove(s));
        emitter.onError(e -> remove(s));
        // La primera línea del stream: retry: 3000. Es lo que espera EventSource antes de reconectarse.
        send(s, SseEmitter.event().reconnectTime(RETRY_MILLIS).comment("conectado"));
        return emitter;
    }

    /** event: seats, a todos los que miran esa función. */
    public void toShowing(long showingId, String json) {
        for (Stream s : byShowing.getOrDefault(showingId, Set.of())) {
            send(s, SseEmitter.event().name("seats").data(json));
        }
    }

    /** event: reservation, solo a las conexiones de ese usuario. */
    public void toUser(long userId, String json) {
        for (Stream s : byUser.getOrDefault(userId, Set.of())) {
            send(s, SseEmitter.event().name("reservation").data(json));
        }
    }

    /** event: resync, "perdí mensajes, vuelve a pedir la foto". Lo pide el suscriptor de Redis al reconectarse. */
    public void resyncAll() {
        for (Set<Stream> streams : byShowing.values()) {
            for (Stream s : streams) {
                send(s, SseEmitter.event().name("resync").data("{}"));
            }
        }
    }

    /** : ping cada 15 s. Un comentario que mantiene viva la conexión a través de proxies que cortan el silencio. */
    @Scheduled(fixedDelayString = "${cine.streams.heartbeat}")
    void heartbeat() {
        for (Set<Stream> streams : byShowing.values()) {
            for (Stream s : streams) {
                send(s, SseEmitter.event().comment("ping"));
            }
        }
    }

    public int openStreams() {
        return open.get();
    }

    private void send(Stream s, SseEmitter.SseEventBuilder event) {
        try {
            s.emitter().send(event);
        } catch (IOException | IllegalStateException e) {
            // El navegador se fue (o el emisor ya terminó): se quita y no se le escribe más.
            log.debug("Stream cerrado de {} en la función {}: {}", s.userId(), s.showingId(), e.getMessage());
            remove(s);
        }
    }

    private void remove(Stream s) {
        boolean removed = byShowing.getOrDefault(s.showingId(), Set.of()).remove(s);
        byUser.getOrDefault(s.userId(), Set.of()).remove(s);
        if (removed) {
            open.decrementAndGet();
        }
    }
}

/**
 * Cada réplica de la api escucha los dos patrones y reenvía a sus streams. Así un cambio hecho en la réplica 2
 * llega al navegador conectado a la réplica 1.
 * <p>
 * Redis Pub/Sub entrega como máximo una vez: lo que se publicó mientras esta réplica estaba desconectada se perdió.
 * Por eso, cuando Redis vuelve a confirmar una suscripción que ya teníamos (una reconexión), se manda resync a todos.
 */
@Component
@Profile("api")
public class SeatEventsSubscriber implements MessageListener, SubscriptionListener {

    private static final Logger log = LoggerFactory.getLogger(SeatEventsSubscriber.class);
    public static final String SEATS = "showing:*:seats";
    public static final String RESERVATIONS = "user:*:reservations";

    private final StreamRegistry streams;
    private final Set<String> confirmed = ConcurrentHashMap.newKeySet();

    public SeatEventsSubscriber(StreamRegistry streams) {
        this.streams = streams;
    }

    @Override
    public void onMessage(Message message, byte[] pattern) {
        String channel = new String(message.getChannel(), StandardCharsets.UTF_8);
        String body = new String(message.getBody(), StandardCharsets.UTF_8);
        String[] parts = channel.split(":");
        try {
            long id = Long.parseLong(parts[1]);
            if (channel.startsWith("showing:")) {
                streams.toShowing(id, body);
            } else {
                streams.toUser(id, body);
            }
        } catch (RuntimeException e) {
            log.warn("Mensaje de Redis que no entiendo en {}: {}", channel, e.getMessage());
        }
    }

    @Override
    public void onPatternSubscribed(byte[] pattern, long count) {
        String p = new String(pattern, StandardCharsets.UTF_8);
        if (!confirmed.add(p)) {
            log.warn("Redis volvió a confirmar la suscripción a {}: mando resync a los streams", p);
            streams.resyncAll();
        }
    }
}

La decisión
El orden sin un contador central. Cada asiento viaja con su version, el updated_at que escribió clock_timestamp(), en microsegundos. Como el UPDATE espera el lock de la fila, el segundo cambio de un asiento se escribe después de que el primero confirmó, así que las versiones de un mismo asiento solo crecen. El navegador descarta un evento con una versión menor o igual a la que tiene, y los mensajes pueden llegar desordenados sin dejar el mapa mal. LISTEN/NOTIFY de PostgreSQL: necesita una sesión dedicada, que PgBouncer en modo transaction no da. Un contador por función, showings.version + 1 en cada transacción: esa fila se volvería un lock que serializa todas las reservas de la sala. Y consultar el mapa cada segundo desde cada navegador: 200 espectadores serían 200 consultas por segundo para enterarse, casi siempre, de que nada cambió.
Qué puede salir mal
Que la conexión de una réplica con Redis se corte. Pub/Sub entrega como mucho una vez, y lo publicado mientras tanto se pierde Documentado. Que el cliente de Redis vuelva a suscribirse solo al reconectarse y llame otra vez a onPatternSubscribed es lo esperado de Lettuce Diseño de referencia; lo compruebas reiniciando Redis. Y que un proxy delante junte los eventos en su buffer: X-Accel-Buffering: no se lo pide a Nginx.

    /** Solo lo que hace falta para encolar. Lo demás del evento queda en payload, para auditoría. */
    @JsonIgnoreProperties(ignoreUnknown = true)
    record EventHead(String id, String type, boolean livemode, Data data) {

        @JsonIgnoreProperties(ignoreUnknown = true)
        record Data(StripeObject object) {
        }

        @JsonIgnoreProperties(ignoreUnknown = true)
        record StripeObject(String id) {
        }
    }

    private final JdbcClient jdbc;
    private final JsonMapper json;
    private final CineProps props;

    public StripeWebhookController(JdbcClient jdbc, JsonMapper json, CineProps props) {
        this.jdbc = jdbc;
        this.json = json;
        this.props = props;
        if (props.stripe().webhookSecret() == null || !props.stripe().webhookSecret().startsWith("whsec_")) {
            throw new IllegalStateException("Falta STRIPE_WEBHOOK_SECRET (whsec_…): revisa tu .env");
        }
    }

    /**
     * byte[] y no un objeto: la firma se calcula sobre los bytes exactos que mandó Stripe.
     * Si Spring los parseara y volviera a serializar, un espacio distinto bastaría para que la firma no coincida.
     */
    @PostMapping("/webhooks/stripe")
    ResponseEntity<Void> receive(@RequestBody byte[] body,
                                 @RequestHeader(name = "Stripe-Signature", required = false) String signature) {
        String payload = new String(body, StandardCharsets.UTF_8);
        if (signature == null) {
            log.warn("Webhook sin Stripe-Signature: rechazado");
            return ResponseEntity.badRequest().build();
        }
        try {
            // Comprueba el HMAC-SHA256 con el whsec_ y que t= no tenga más de tolerance segundos (contra replays).
            Webhook.Signature.verifyHeader(payload, signature, props.stripe().webhookSecret(),
                    props.stripe().tolerance());
        } catch (SignatureVerificationException e) {
            log.warn("Firma de webhook inválida: {}", e.getMessage());
            return ResponseEntity.badRequest().build();
        }
        EventHead e = json.readValue(payload, EventHead.class);
        if (e.id() == null || e.type() == null || e.data() == null || e.data().object() == null) {
            log.warn("Evento firmado pero sin id, type u objeto: lo ignoro");
            return ResponseEntity.ok().build();
        }
        // Sin conflict target ni RETURNING: este rol solo tiene INSERT. Un evento repetido choca con la PK y no hace nada.
        int inserted = jdbc.sql("""
                INSERT INTO stripe_events (event_id, type, object_id, livemode, payload)
                VALUES (:id, :type, :obj, :live, CAST(:payload AS jsonb))
                ON CONFLICT DO NOTHING
                """)
                .param("id", e.id()).param("type", e.type()).param("obj", e.data().object().id())
                .param("live", e.livemode()).param("payload", payload)
                .update();
        log.info("Webhook {} {} {}", e.id(), e.type(), inserted == 1 ? "encolado" : "repetido: ya estaba");
        return ResponseEntity.ok().build();
    }

 * queda muerto y lo avisa el log.
 */
@Component
@Profile("worker")
public class StripeEventWorker {

    private static final Logger log = LoggerFactory.getLogger(StripeEventWorker.class);
    static final int MAX_ATTEMPTS = 10;

    record Leased(String eventId, String type, String objectId, boolean livemode, int attempts) {
    }

    private final JdbcClient jdbc;
    private final PaymentGateway gateway;
    private final PaymentFinalizer finalizer;
    private final Releases releases;
    private final CineProps props;

    public StripeEventWorker(JdbcClient jdbc, PaymentGateway gateway, PaymentFinalizer finalizer, Releases releases,
                             CineProps props) {
        this.jdbc = jdbc;
        this.gateway = gateway;
        this.finalizer = finalizer;
        this.releases = releases;
        this.props = props;
    }

    @Scheduled(fixedDelay = 1_000)
    void tick() {
        if (props.background()) {
            drain(20);
        }
    }

    /** Devuelve cuántos eventos tomó. Las pruebas lo llaman directo. */
    public int drain(int limit) {
        // SKIP LOCKED: dos workers a la vez se reparten el lote en lugar de esperar uno al otro.
        List<Leased> batch = jdbc.sql("""
                UPDATE stripe_events
                SET locked_until = now() + interval '60 seconds', attempts = attempts + 1
                WHERE event_id IN (
                    SELECT event_id FROM stripe_events
                    WHERE processed_at IS NULL AND attempts < :max
                      AND (locked_until IS NULL OR locked_until < now())
                    ORDER BY received_at
                    LIMIT :n
                    FOR UPDATE SKIP LOCKED)
                RETURNING event_id, type, object_id, livemode, attempts
                """)
                .param("max", MAX_ATTEMPTS).param("n", limit)
                .query(Leased.class)
                .list();
        for (Leased e : batch) {
            process(e);
        }
        return batch.size();
    }

    private void process(Leased e) {
        if (e.livemode() != props.stripe().livemode()) {
            // Un evento de live en un entorno de prueba (o al revés) es una configuración cruzada, no un pago.
            log.error("ALERTA: el evento {} tiene livemode={} y este entorno espera {}", e.eventId(), e.livemode(),
                    props.stripe().livemode());
            done(e, "livemode distinto: no se procesa");
            return;
        }
        try {
            handle(e.type(), e.objectId());
            done(e, null);
        } catch (RuntimeException ex) {
            retryLater(e, ex);
        }
    }

    /** Cada caso vuelve a leer el objeto en Stripe: el cuerpo del evento puede ser viejo (llegan desordenados). */
    private void handle(String type, String objectId) {
        switch (type) {
            case "payment_intent.succeeded" -> finalizer.finalize(objectId);
            case "payment_intent.canceled" -> onCanceled(objectId);
            case "payment_intent.payment_failed" ->
                    log.info("{}: tarjeta rechazada. La reserva sigue en checkout hasta que venza", objectId);
            case "charge.refunded" -> onRefunded(objectId);
            default -> log.debug("Evento {} sin manejador: se marca procesado", type);
        }
    }

    private void onCanceled(String paymentIntentId) {
        PaymentIntentView pi = gateway.retrievePaymentIntent(paymentIntentId);
        if (!pi.is("canceled")) {
            return;
        }
        reservationOf(paymentIntentId).ifPresent(id -> releases.release(id, "expired", Set.of("checkout"), false));
    }

    /**
     * Un reembolso total, hecho por nosotros (huérfanos) o desde el Dashboard. La reserva pasa a refunded y sus
     * asientos siguen vendidos: el reembolso no devuelve el asiento a la venta. Que pase fuera del sistema
     * merece una alerta.
     */
    private void onRefunded(String chargeId) {
        ChargeView c = gateway.retrieveCharge(chargeId);
        if (c.amountRefunded() < c.amount()) {
            log.warn("Reembolso parcial de {} en {}: esta guía no los maneja", c.amountRefunded(), c.paymentIntentId());
            return;
        }
        int refunded = jdbc.sql("""
                UPDATE reservations SET status = 'refunded', updated_at = now()
                WHERE payment_intent_id = :pi AND status = 'paid'
                """)
                .param("pi", c.paymentIntentId())
                .update();
        if (refunded == 1) {
            log.error("ALERTA: el pago {} de una reserva vendida se reembolsó fuera del sistema", c.paymentIntentId());
        }
        jdbc.sql("""
                UPDATE orphan_payments SET refunded_at = coalesce(refunded_at, now())
                WHERE payment_intent_id = :pi
                """)
                .param("pi", c.paymentIntentId())
                .update();
    }

    private Optional<UUID> reservationOf(String paymentIntentId) {
        return jdbc.sql("SELECT id FROM reservations WHERE payment_intent_id = :pi")
                .param("pi", paymentIntentId)
                .query(UUID.class)
                .optional();
    }

    private void done(Leased e, String note) {
        jdbc.sql("""
                UPDATE stripe_events SET processed_at = now(), locked_until = NULL, last_error = :note
                WHERE event_id = :id
                """)
                .param("note", note).param("id", e.eventId())
                .update();
    }

    private void retryLater(Leased e, RuntimeException ex) {
        String error = ex.getClass().getSimpleName() + ": " + ex.getMessage();
        jdbc.sql("""
                UPDATE stripe_events
                SET locked_until = now() + make_interval(secs => least(power(2, attempts), 300)), last_error = :err
                WHERE event_id = :id
                """)
                .param("err", error.length() > 500 ? error.substring(0, 500) : error).param("id", e.eventId())
                .update();
        if (e.attempts() >= MAX_ATTEMPTS) {
            log.error("ALERTA: el evento {} ({}) falló {} veces y no se reintenta más: {}", e.eventId(), e.type(),
                    e.attempts(), error);
        } else {
            log.warn("El evento {} falló (intento {}): {}", e.eventId(), e.attempts(), error);
        }
    }
}

/**
 * La red de seguridad: reembolsa los pagos que quedaron en orphan_payments. La clave refund:{payment_intent} hace
 * que dos workers, o dos vueltas, no reembolsen dos veces: Stripe devuelve el mismo reembolso.
 * refunded_at lo marca el reembolso si ya salió succeeded, o el evento charge.refunded cuando llega.
 */
@Component
@Profile("worker")
public class OrphanRefunds {

    private static final Logger log = LoggerFactory.getLogger(OrphanRefunds.class);
    static final int MAX_ATTEMPTS = 10;

    record Orphan(String paymentIntentId, UUID reservationId, int attempts) {
    }

    private final JdbcClient jdbc;
    private final PaymentGateway gateway;
    private final CineProps props;

    public OrphanRefunds(JdbcClient jdbc, PaymentGateway gateway, CineProps props) {
        this.jdbc = jdbc;
        this.gateway = gateway;
        this.props = props;
    }

    @Scheduled(fixedDelay = 10_000)
    void tick() {
        if (props.background()) {
            drain(10);
        }
    }

    /** Devuelve cuántos huérfanos intentó reembolsar. Las pruebas lo llaman directo. */
    public int drain(int limit) {
        List<Orphan> batch = jdbc.sql("""
                UPDATE orphan_payments SET attempts = attempts + 1
                WHERE payment_intent_id IN (
                    SELECT payment_intent_id FROM orphan_payments
                    WHERE refund_id IS NULL AND refunded_at IS NULL AND attempts < :max
                    ORDER BY detected_at
                    LIMIT :n
                    FOR UPDATE SKIP LOCKED)
                RETURNING payment_intent_id, reservation_id, attempts
                """)
                .param("max", MAX_ATTEMPTS).param("n", limit)
                .query(Orphan.class)
                .list();
        for (Orphan o : batch) {
            refund(o);
        }
        return batch.size();
    }

    private void refund(Orphan o) {
        String reservation = o.reservationId() == null ? null : o.reservationId().toString();
        try {
            RefundView f = gateway.createRefund(o.paymentIntentId(), reservation, "refund:" + o.paymentIntentId());
            jdbc.sql("""
                    UPDATE orphan_payments
                    SET refund_id = :rid, last_error = NULL,
                        refunded_at = CASE WHEN :ok THEN coalesce(refunded_at, now()) ELSE refunded_at END
                    WHERE payment_intent_id = :pi
                    """)
                    .param("rid", f.id()).param("ok", "succeeded".equals(f.status())).param("pi", o.paymentIntentId())
                    .update();
            log.warn("Reembolsé el pago huérfano {} ({}): {}", o.paymentIntentId(), f.id(), f.status());
        } catch (GatewayException e) {
            if ("charge_already_refunded".equals(e.code())) {
                // Alguien lo reembolsó antes (otro worker, o a mano en el Dashboard): ya está hecho.
                jdbc.sql("""
                        UPDATE orphan_payments SET refunded_at = coalesce(refunded_at, now()), last_error = :err
                        WHERE payment_intent_id = :pi
                        """)
                        .param("err", e.code()).param("pi", o.paymentIntentId())
                        .update();
                return;
            }
            String error = e.kind() + ": " + e.getMessage();
            jdbc.sql("UPDATE orphan_payments SET last_error = :err WHERE payment_intent_id = :pi")
                    .param("err", error.length() > 500 ? error.substring(0, 500) : error)
                    .param("pi", o.paymentIntentId())
                    .update();
            if (o.attempts() >= MAX_ATTEMPTS) {
                log.error("ALERTA: no pude reembolsar el pago huérfano {} en {} intentos: {}", o.paymentIntentId(),
                        o.attempts(), error);
            }
        }
    }
}
La decisión
Los boletos no se reembolsan desde la aplicación. Si alguien del equipo reembolsa desde el Dashboard, la reserva pasa a refunded, los asientos siguen vendidos, porque un reembolso no devuelve el asiento a la venta solo, y el log dice ALERTA. El único reembolso automático es el de orphan_payments, con la clave refund:{payment_intent}: dos workers, o dos vueltas, mandan la misma, y Stripe hace un solo reembolso.
Lo que descartas
Liberar en el webhook payment_intent.canceled con lo que trae el evento: un evento viejo podría llegar después de que el cliente pagó con otra tarjeta. El worker lee el PaymentIntent y libera solo si sigue cancelado.
Qué puede salir mal
Que la clave del worker no tenga permiso de leer cargos: el charge.refunded falla, se reintenta con espera, y a los 10 intentos queda apartado con un ALERTA. Y que el reembolso de un huérfano falle con charge_already_refunded Documentado: alguien lo hizo antes, y el huérfano queda marcado como reembolsado, que es la verdad.

Paso 12. El navegador

app.js dibuja el mapa de 10 por 10 y lo mantiene con el stream, guarda una Idempotency-Key por acción en sessionStorage, como en A15, cuenta los plazos con la hora del servidor y monta el Payment Element con el client_secret. La cuenta regresiva usa expires_at - server_time, corregido por el desfase del reloj de tu computadora: si tu reloj está 40 s adelantado, el plazo igual se ve bien.

// El cine: el mapa en vivo por SSE, la reserva con su cuenta regresiva y el pago con el Payment Element.

// El navegador nunca decide qué pasó con un pago por su cuenta: ante cualquier duda, pregunta GET /v1/reservations/{id}.
(() => {
  const $ = (s) => document.querySelector(s);
  const SHOWING = 1;
  const FILAS = 'ABCDEFGHIJ';
  const memoria = {};

  // ---------- Claves de idempotencia ----------
  // Una por acción, que sobrevive a una recarga: si la red falla, el reintento manda la misma.
  // sessionStorage puede no existir (modo privado estricto): entonces vive solo en memoria.
  function claveDe(accion) {
    try {
      let k = sessionStorage.getItem(accion);
      if (!k) { k = crypto.randomUUID(); sessionStorage.setItem(accion, k); }
      return k;
    } catch {
      return (memoria[accion] ??= crypto.randomUUID());
    }
  }
  function tieneClave(accion) {
    try { return sessionStorage.getItem(accion) !== null || accion in memoria; } catch { return accion in memoria; }
  }
  function olvidar(accion) {
    try { sessionStorage.removeItem(accion); } catch { /* sin sessionStorage */ }
    delete memoria[accion];
  }

  // ---------- HTTP ----------
  let yo = null;
  async function pedir(metodo, path, clave, body) {
    const headers = { Accept: 'application/json' };
    if (metodo !== 'GET') headers[yo.csrf_header] = yo.csrf_token;
    if (clave) headers['Idempotency-Key'] = clave;
    if (body !== undefined) headers['Content-Type'] = 'application/json';
    const r = await fetch(path, { method: metodo, headers, body: body === undefined ? undefined : JSON.stringify(body) });
    let json = null;
    try { json = await r.json(); } catch { /* sin body */ }
    return { status: r.status, body: json };
  }
  const codigo = (r) => (r.body && r.body.error ? r.body.error.code : null);
  const mensaje = (r) => (r.body && r.body.error ? r.body.error.message : 'Error ' + r.status);
  const dolares = (a) => (a.minor / 100).toFixed(2) + ' ' + a.currency.toUpperCase();

  // ---------- El reloj ----------
  // offset = hora del servidor - hora de este navegador. La cuenta regresiva usa la hora corregida:
  // si el reloj de la computadora está 40 s adelantado, el plazo no se ve vencido antes de tiempo.
  let offset = 0;
  const ahora = () => Date.now() + offset;
  function sincronizar(serverTime) {
    if (serverTime) offset = Date.parse(serverTime) - Date.now();
  }

  // ---------- El mapa ----------
  // asientos: label → { status, held_until, version }. La versión es seats.updated_at en microsegundos:
  // un evento con una versión menor o igual a la que ya hay se descarta (llegó tarde o repetido).
  const asientos = new Map();
  const elegidos = new Set();
  let fotoLista = false;
  let buffer = [];

  function aplicar(lista) {
    if (!fotoLista) { buffer.push(...lista); return; }
    for (const s of lista) {
      const actual = asientos.get(s.label);
      if (!actual || s.version > actual.version) asientos.set(s.label, s);

El navegador muestra, no decide. Paso 13. Vencer las claves

Las claves de idempotencia se borran a las 24 h, en lotes de 1 000, con el proceso jobs, el único que tiene permiso de borrar. Es el mismo de A15.

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.CommandLineRunner;
import org.springframework.context.annotation.Profile;
import org.springframework.core.annotation.Order;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Component;

/**
 * Borra las claves de idempotencia con más de 24 h, en lotes de 1000 para no tener una transacción larga
 * que retenga locks. 24 h es también lo que Stripe guarda sus claves: pasado ese plazo, un reintento ya no
 * recibiría el mismo PaymentIntent, así que guardar la nuestra más tiempo no protege de nada.
 */
@Component
@Profile("jobs")
@Order(10)
public class KeyJanitor implements CommandLineRunner {

    private static final Logger log = LoggerFactory.getLogger(KeyJanitor.class);

    private final JdbcClient jdbc;

    public KeyJanitor(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public void run(String... args) {
        int total = 0;
        int n;
        do {
            n = jdbc.sql("""
                    DELETE FROM idempotency_keys
                    WHERE (user_id, idem_key) IN (
                        SELECT user_id, idem_key FROM idempotency_keys
                        WHERE created_at < now() - interval '24 hours'
                        LIMIT 1000)
                    """)
                    .update();
            total += n;
        } while (n > 0);
        log.info("Borré {} claves de idempotencia vencidas", total);
    }
}
La decisión
Un proceso que corre, borra y termina: docker compose run --rm jobs, a mano o desde un cron. Las reservas no se borran nunca: son el historial de lo que pasó con cada asiento.
Lo que descartas
Borrar las reservas vencidas para que la tabla no crezca. Son unas pocas filas por espectador y función, y sin ellas no sabrías explicar por qué un asiento cambió de manos.
Qué puede salir mal
Que alguien reintente una reserva de hace más de 24 h con la misma clave: ya no es un replay, y se ejecuta como nueva. Nadie reintenta un clic de ayer.

La decisión
Los scripts entran como el navegador, con sesión y token CSRF, así que prueban la misma API que la página, con su rate limit. vencer.sh no espera 30 s ni 3 minutos: mueve el plazo a "hace un segundo", bloqueando primero los asientos y después la reserva, el mismo orden que la aplicación. invariantes.sh son las reglas del diseño como consultas que tienen que devolver cero filas.
Lo que descartas
Acortar los plazos en el código para probar: el experimento dejaría de parecerse a lo real. Para el único caso que necesita esperar de verdad, el de 3D Secure, los plazos se cambian en .env.
Qué puede salir mal
Que carrera.sh diga "No pude entrar como u017": abrir 50 sesiones a la vez puede tardar; vuelve a correrlo. Y que vencer.sh no haga nada: la reserva ya no estaba en held ni en checkout, y el SELECT del final muestra su estado.

/**
 * Un Stripe en memoria para las pruebas, sin red ni claves. Imita lo que importa aquí: la misma Idempotency-Key
 * devuelve el mismo PaymentIntent, una respuesta puede perderse después de crearlo, cancelar solo funciona desde
 * los estados cancelables, y el cliente o el banco cambian el estado cuando la prueba lo dice.
 */
public class FakePaymentGateway implements PaymentGateway {

    private final AtomicInteger seq = new AtomicInteger();
    private final AtomicInteger createCalls = new AtomicInteger();
    private final AtomicInteger cancelCalls = new AtomicInteger();
    private final AtomicInteger refundCalls = new AtomicInteger();
    private final Map<String, String> pisByKey = new ConcurrentHashMap<>();
    private final Map<String, PaymentIntentView> pis = new ConcurrentHashMap<>();
    private final Map<String, String> requests = new ConcurrentHashMap<>();
    private final Map<String, RefundView> refundsByKey = new ConcurrentHashMap<>();
    private final Map<String, ChargeView> charges = new ConcurrentHashMap<>();
    private final Map<String, Queue<GatewayException>> failures = new ConcurrentHashMap<>();
    private volatile boolean loseNextResponse;
    private volatile boolean crashAfterCreate;
    private volatile Consumer<PaymentIntentRequest> onCreate;
    private volatile String succeedBeforeCancel;

    @Override
    public PaymentIntentView createPaymentIntent(PaymentIntentRequest r, String idempotencyKey) {
        createCalls.incrementAndGet();
        failIfAsked("create");
        String id = pisByKey.computeIfAbsent(idempotencyKey, k -> {
            String pi = "pi_test_" + seq.incrementAndGet();
            pis.put(pi, new PaymentIntentView(pi, "requires_payment_method", r.amountMinor(), r.currency(),
                    pi + "_secret_prueba", r.reservationId().toString(), null, null, null));
            requests.put(pi, idempotencyKey + " " + r);
            return pi;
        });
        Consumer<PaymentIntentRequest> hook = onCreate;
        if (hook != null) {
            onCreate = null;
            hook.accept(r);
        }
        if (crashAfterCreate) {
            // Stripe lo creó y el proceso murió antes de la fase 3. En la prueba no se puede matar la JVM:
            // se lanza algo que no es una GatewayException, y la request termina con 500 sin tocar la base.
            crashAfterCreate = false;
            throw new IllegalStateException("el proceso murió (simulado)");
        }
        if (loseNextResponse) {
            // Stripe creó el PaymentIntent, pero la respuesta no llegó: para la app, es un error de red.
            loseNextResponse = false;
            throw new GatewayException(Kind.RETRYABLE, null, "connection reset (falla provocada)");
        }
        return pis.get(id);
    }

    @Override
    public PaymentIntentView retrievePaymentIntent(String id) {
        failIfAsked("retrieve");
        PaymentIntentView p = pis.get(id);
        if (p == null) {
            throw new GatewayException(Kind.REJECTED, "resource_missing", "No such payment_intent");
        }
        return p;
    }

    @Override
    public PaymentIntentView cancelPaymentIntent(String id) {
        cancelCalls.incrementAndGet();
        failIfAsked("cancel");
        if (id.equals(succeedBeforeCancel)) {
            // La carrera del segundo 179: el pago llega a Stripe un instante antes que el cancel.
            succeedBeforeCancel = null;
            pay(id);
        }
        PaymentIntentView p = retrievePaymentIntent(id);
        boolean cancelable = switch (p.status()) {
            case "requires_payment_method", "requires_confirmation", "requires_action" -> true;
            default -> false;
        };
        if (!cancelable) {
            throw new GatewayException(Kind.REJECTED, "payment_intent_unexpected_state",
                    "You cannot cancel this PaymentIntent because it has a status of " + p.status());
        }
        return set(id, "canceled");
    }

    @Override
    public RefundView createRefund(String paymentIntentId, String reservationId, String idempotencyKey) {
        refundCalls.incrementAndGet();
        failIfAsked("refund");
        return refundsByKey.computeIfAbsent(idempotencyKey, k -> {
            PaymentIntentView p = pis.get(paymentIntentId);
            ChargeView c = charges.get(p.latestChargeId());
            charges.put(c.id(), new ChargeView(c.id(), c.paymentIntentId(), c.amount(), c.amount(), c.currency()));
            return new RefundView("re_test_" + seq.incrementAndGet(), "succeeded", c.amount(), paymentIntentId);
        });
    }

    @Override
    public ChargeView retrieveCharge(String chargeId) {
        return charges.get(chargeId);
    }

    // ---- Lo que hacen el cliente o el banco en la prueba ----

    /** El cliente pagó con 4242: succeeded, con su cargo. */
    public String pay(String id) {
        PaymentIntentView p = pis.get(id);
        String charge = "ch_test_" + seq.incrementAndGet();
        charges.put(charge, new ChargeView(charge, id, p.amount(), 0, p.currency()));
        pis.put(id, new PaymentIntentView(id, "succeeded", p.amount(), p.currency(), p.clientSecret(),
                p.reservationId(), charge, null, null));
        return charge;
    }

    /** Stripe cobró otro monto: lo que vería la app si alguien manipulara el PaymentIntent. */
    public void payWithAmount(String id, long amount) {
        pay(id);
        PaymentIntentView p = pis.get(id);
        pis.put(id, new PaymentIntentView(id, p.status(), amount, p.currency(), p.clientSecret(), p.reservationId(),
                p.latestChargeId(), null, null));
    }

    /** La tarjeta fue rechazada: el PaymentIntent vuelve a requires_payment_method con el motivo. */
    public void decline(String id, String declineCode) {
        PaymentIntentView p = pis.get(id);
        pis.put(id, new PaymentIntentView(id, "requires_payment_method", p.amount(), p.currency(), p.clientSecret(),
                p.reservationId(), null, "card_declined", declineCode));
    }

    public PaymentIntentView set(String id, String status) {
        PaymentIntentView p = pis.get(id);
        PaymentIntentView n = new PaymentIntentView(id, status, p.amount(), p.currency(), p.clientSecret(),
                p.reservationId(), p.latestChargeId(), p.errorCode(), p.declineCode());
        pis.put(id, n);
        return n;
    }

    /** Un reembolso total hecho a mano en el Dashboard. Devuelve el id del cargo, para el evento charge.refunded. */
    public String refundFromDashboard(String id) {
        ChargeView c = charges.get(pis.get(id).latestChargeId());
        charges.put(c.id(), new ChargeView(c.id(), c.paymentIntentId(), c.amount(), c.amount(), c.currency()));
        return c.id();
    }

    public PaymentIntentView get(String id) {
        return pis.get(id);
    }

    /** Con qué Idempotency-Key y qué parámetros se creó. */
    public String requestOf(String id) {
        return requests.get(id);
    }

    // ---- Fallas a pedido ----

    /** La próxima llamada a op (create, retrieve, cancel o refund) falla así. */
    public void failNext(String op, Kind kind, String code) {
        failures.computeIfAbsent(op, k -> new ConcurrentLinkedQueue<>())
                .add(new GatewayException(kind, code, "falla provocada en " + op + ": " + kind));
    }

    private void failIfAsked(String op) {
        Queue<GatewayException> q = failures.get(op);
        GatewayException f = q == null ? null : q.poll();
        if (f != null) {
            throw f;
        }
    }

    public void loseNextResponse() {
        loseNextResponse = true;
    }

    public void crashAfterCreate() {
        crashAfterCreate = true;
    }

    /** Corre dentro de la próxima creación, mientras la app espera la respuesta de Stripe. */
    public void onNextCreate(Consumer<PaymentIntentRequest> hook) {
        onCreate = hook;
    }

    public void succeedBeforeCancel(String id) {
        succeedBeforeCancel = id;
    }

    public int createCalls() {
        return createCalls.get();
    }

    public int cancelCalls() {
        return cancelCalls.get();
    }

    public int refundCalls() {
        return refundCalls.get();
    }

    public int paymentIntentCount() {
        return pis.size();
    }

    public void reset() {
        seq.set(0);
        createCalls.set(0);
        cancelCalls.set(0);
        refundCalls.set(0);
        pisByKey.clear();
        pis.clear();
        requests.clear();
        refundsByKey.clear();
        charges.clear();
        failures.clear();
        loseNextResponse = false;
        crashAfterCreate = false;
        onCreate = null;
        succeedBeforeCancel = null;
    }

    @TestConfiguration(proxyBeanMethods = false)
    public static class Config {

        @Bean
        @Primary
        FakePaymentGateway fakePaymentGateway() {
            return new FakePaymentGateway();
        }
    }

                throw new IOException("Broken pipe (el navegador se fue)");
            }
            StringBuilder text = new StringBuilder();
            for (DataWithMediaType d : event.build()) {
                text.append(d.getData());
            }
            received.add(text.toString());
        }

        public List<String> received() {
            return received;
        }

        /** Los eventos con ese nombre: "seats", "reservation" o "resync". */
        public List<String> events(String name) {
            return received.stream().filter(e -> e.contains("event:" + name + "\n")).toList();
        }
    }

    private final List<Browser> browsers = new CopyOnWriteArrayList<>();

    public CapturingStreams(CineProps props) {
        super(props);
    }

    @Override
    protected SseEmitter newEmitter(long timeoutMillis) {

        browsers.add(b);
        return b;
    }

    }

    /** Entre pruebas: todos los navegadores se van, y el primer envío los saca del registro. */
    public void reset() {

    }

import java.util.ArrayList;

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.ThreadLocalRandom;
import java.util.function.Function;
import java.util.stream.Collectors;

import org.junit.jupiter.api.Test;

import com.jayway.jsonpath.JsonPath;

/**
 * Las carreras de verdad: cientos de requests a la vez, cada una de un espectador distinto (u001…u200), que salen
 * juntas de una barrera. Lo que se prueba no es la velocidad sino el resultado: un asiento, un dueño, y ningún 500.
 */
class ConcurrencyTest extends IntegrationTest {

    /** Corre n tareas a la vez desde una barrera y devuelve los status HTTP. */
    private List<Integer> race(int n, Function<Integer, Integer> task) throws Exception {
        CountDownLatch start = new CountDownLatch(1);
        List<Future<Integer>> futures = new ArrayList<>();
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 1; i <= n; i++) {
                int user = i;
                futures.add(pool.submit(() -> {
                    start.await();
                    return task.apply(user);
                }));
            }
            start.countDown();
            List<Integer> statuses = new ArrayList<>();
            for (Future<Integer> f : futures) {
                statuses.add(f.get());
            }
            return statuses;
        }
    }

    private static String username(int n) {
        return "u%03d".formatted(n);
    }

    @Test
    void doscientosPorElMismoAsientoGanaUnoSolo() throws Exception {
        List<Integer> statuses = race(200, i -> reserve(username(i), "F7").getResponse().getStatus());

        Map<Integer, Long> byStatus = statuses.stream()
                .collect(Collectors.groupingBy(s -> s, Collectors.counting()));
        // Los perdedores reciben 409: unos porque F7 ya estaba held, otros porque estaba bloqueado (NOWAIT).
        assertThat(byStatus).containsOnlyKeys(201, 409);
        assertThat(byStatus.get(201)).isEqualTo(1);
        assertThat(count("SELECT count(*) FROM reservations")).isEqualTo(1);
        assertThat(seat("F7")).isEqualTo("held");
        assertThat(violations()).isZero();
    }

    @Test
    void paresQueSeCruzanNoProducenDeadlocks() throws Exception {
        // Cuatro asientos y cien espectadores que piden dos cualquiera, en cualquier orden. Sin un orden de locks
        // fijo, "E5 y luego E6" contra "E6 y luego E5" es un deadlock (40P01) y un 500.
        String[] seats = {"E5", "E6", "E7", "E8"};
        List<Integer> statuses = race(100, i -> {
            ThreadLocalRandom rnd = ThreadLocalRandom.current();
            int a = rnd.nextInt(4);
            int b = (a + 1 + rnd.nextInt(3)) % 4;
            return reserve(username(i), seats[a], seats[b]).getResponse().getStatus();
        });

        assertThat(statuses).allMatch(s -> s == 201 || s == 409);
        long winners = statuses.stream().filter(s -> s == 201).count();
        assertThat(winners).isBetween(1L, 2L);
        assertThat(count("SELECT count(*) FROM seats WHERE status = 'held'")).isEqualTo(winners * 2);
        assertThat(violations()).isZero();
    }

    @Test
    void elMismoEspectadorConDiezPestanasTieneUnaSolaReserva() throws Exception {
        // Diez clics de ana, cada uno con su clave, por asientos distintos: one_active_reservation deja uno.
        String[] seats = {"A1", "A2", "A3", "A4", "A5", "A6", "A7", "A8", "A9", "A10"};
        List<Integer> statuses = race(10, i -> reserve("ana", seats[i - 1]).getResponse().getStatus());

        assertThat(statuses.stream().filter(s -> s == 201).count()).isEqualTo(1);
        assertThat(statuses).allMatch(s -> s == 201 || s == 409);
        assertThat(count("SELECT count(*) FROM seats WHERE status = 'held'")).isEqualTo(1);
    }

    @Test
    void elBarridoYLasRequestsAlMismoTiempoNoSePisan() throws Exception {
        // Cincuenta reservas vencidas, y cincuenta espectadores que quieren esos asientos mientras barre el worker.
        List<String> labels = new ArrayList<>();
        for (char row = 'A'; row <= 'E'; row++) {
            for (int col = 1; col <= 10; col++) {
                labels.add("" + row + col);
            }
        }
        for (int i = 0; i < 50; i++) {
            String id = JsonPath.read(body(reserve(username(101 + i), labels.get(i))),
                    "$.reservation_id");
            lapse(id);
        }
        List<Integer> statuses = race(51, i -> {
            if (i == 51) {
                sweeper.sweepHeld();
                return 0;
            }
            return reserve(username(i), labels.get(i - 1)).getResponse().getStatus();
        });

        // Cada espectador toma su asiento: libre (si el barrido llegó antes) o vencido (toma perezosa).
        // Si el barrido tenía la fila bloqueada, NOWAIT da 409 y el navegador reintenta en un segundo.
        assertThat(statuses.subList(0, 50)).allMatch(s -> s == 201 || s == 409);
        sweeper.sweepHeld();
        assertThat(violations()).isZero();
        assertThat(count("SELECT count(*) FROM reservations WHERE status = 'held' AND expires_at <= now()"))
                .isZero();
    }
}

Cómo conectar

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A15, idempotencia de punta a punta

    Las claves, las tres fases, la inbox y los roles son los de A15. Lo nuevo está en lo que se bloquea: A15 tenía una orden por compra y nadie más la quería; aquí cien asientos que muchos quieren a la vez. Si los juntas, la tienda de A15 puede vender boletos con este checkout, y conservar sus reembolsos para lo que no son asientos.

  • Con A00, el laboratorio

    La misma división de A00: la aplicación entra por PgBouncer en modo transaction y Flyway va directo. Aquí se ve qué cuesta ese modo: el mapa en vivo no puede usar LISTEN/NOTIFY, y por eso existe el Pub/Sub de Redis.

  • Con A02, una API que no se rompe

    A02 resolvía la concurrencia con ETag e If-Match, un lock optimista sobre un recurso que casi nadie toca a la vez. Aquí el recurso lo tocan doscientas personas en el mismo segundo, y el lock pesimista con NOWAIT responde antes de que nadie haga trabajo de más.

  • Con A08, un solo líder

    A08 elegía un líder para que un trabajo corriera una sola vez. El barrido de este proyecto no lo necesita: SKIP LOCKED reparte las filas entre los workers, y cada transición comprueba el estado bajo lock, así que dos workers sobre la misma reserva hacen el trabajo una vez.

  • Con A09, colas y pub/sub

    A09 usaba Redis para repartir trabajo; aquí Redis Pub/Sub reparte avisos, y está bien perder uno, porque el navegador vuelve a pedir la foto. La inbox de webhooks, en cambio, no puede perder nada, y por eso vive en PostgreSQL.

  • Con A10, cuando Redis se cae

    Si Redis se cae, las reservas siguen funcionando, porque SeatEvents publica después del commit y un error ahí solo se loguea; el mapa se corrige con la foto. El rate limit, en cambio, falla y la api responde 500: con la compuerta de A10 podrías dejar pasar las reservas sin límite o rechazarlas con 503.
