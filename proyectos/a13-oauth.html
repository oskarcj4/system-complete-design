OAuth 2 y OIDC con un servidor en Workers

La tienda de A12 crece: ahora hay varias aplicaciones y un API aparte, y quieres una sola cuenta para todas. Vas a construir las tres piezas de un SSO con tus propias manos: un servidor de autorización en Cloudflare Workers que emite y firma tokens, un BFF que es el cliente OAuth2 y guarda los tokens donde el navegador no los ve, y un API que valida esos tokens sin guardar sesión. Por el camino implementas Authorization Code con PKCE, tokens ES256 con un JWKS que rota, refresh tokens que rotan y se revocan en familia al detectar un reuso, y el single sign-on de verdad. Cada ataque conocido —robar el código, reinyectar un token, un redirect abierto, reusar un refresh— llega como una prueba que comprueba que la defensa lo rechaza.

La excusa

La tienda de A12 tenía un panel, un dominio y unas pocas personas: la sesión en Redis bastaba. Ahora hay dos aplicaciones de cara al público y un API aparte que las dos consumen, y quieres una sola cuenta para todo: que ana entre una vez y esté dentro en las dos apps, y que el API sepa quién llama y con qué permisos. La respuesta de manual —"usa OAuth"— esconde tres decisiones que la mayoría de los tutoriales se saltan, y que son justo donde se rompe la seguridad:

  • ¿Dónde vive el token? El atajo típico es guardar el access token en el navegador, en localStorage. Ahí lo lee cualquier XSS, y entonces no hay cookie HttpOnly que valga. El token tiene que vivir del lado servidor; el navegador solo debería tener una cookie opaca, como en A12.
  • ¿Qué pasa si interceptan el código? El flujo manda un código de autorización por la URL del navegador, que es terreno manipulable. Sin PKCE, quien intercepte ese código lo canjea por tokens. PKCE ata el canje a un secreto que nunca viajó por la URL.
  • ¿Cómo se revoca? Un JWT sin estado vale hasta que vence; no lo puedes cerrar. La salida es un access token de vida corta —minutos— y un refresh token que sí se controla: rota en cada uso y, si se reutiliza, se revoca su familia entera.

Casi nadie monta su propio servidor de autorización, y con razón: en producción usas uno probado. Pero construir uno pequeño, entero y a mano es la única forma de ver qué hace cada parámetro y por qué cada defensa está donde está. Así que este proyecto arma las tres piezas: un servidor de autorización en Cloudflare Workers con D1 —un IdP local, sin cuentas externas, con usuarios sembrados—; un BFF con Spring Cloud Gateway que es el cliente OAuth2 y guarda los tokens donde el navegador no llega; y un API resource server de Spring que valida el token sin guardar nada. Y, como en A12, trae las requests que un atacante haría —convertidas en pruebas— para comprobar que cada capa las rechaza.

En producción real

En serio no escribes tu propio servidor de autorización: usas uno probado —Keycloak, Auth0, Entra ID, Cognito— y te ahorras años de aristas de seguridad. Lo que no cambia es el papel del cliente (el BFF) y del resource server (el API): esos sí los escribes tú, y son casi idénticos contra cualquier proveedor, porque hablan los mismos estándares. Construir aquí el servidor completo es para ver por dentro lo que el proveedor te da hecho. Las contraseñas de los usuarios sembrados y el secreto del cliente son solo de laboratorio; en producción el alta de usuarios y los secretos no nacen de una variable de entorno.

Trade-off

El servidor de autorización en Workers, no otro Spring Boot. Podría ser un tercer servicio Java con Spring Authorization Server, que es excelente. Se eligió Workers por tres razones didácticas: obliga a escribir la criptografía con WebCrypto y a ver cada pieza (PBKDF2, AES-GCM, ES256) sin que un framework la esconda; D1 es SQLite, así que el esquema de claves, códigos y tokens se lee de un vistazo; y deja claro que el cliente (BFF) y el resource server (API) hablan estándares, no un dialecto de un proveedor: funcionan igual contra este Worker que contra Keycloak. El costo es mantener dos toolchains —npm y Maven— y una criptografía más manual de lo que harías en producción.

Para que el navegador y los dos procesos Java confíen en el certificado del laboratorio, agrégalo a tu almacén de confianza. El BFF y el API descubren el JWKS por HTTPS contra sso.localhost, así que la JVM tiene que confiar en esa CA: importa el rootCA.pem de mkcert a un truststore y arranca con él, o al almacén por defecto de tu JDK. Y para que sso.localhost y app.localhost resuelvan a tu máquina, en muchos sistemas *.localhost ya apunta a 127.0.0.1; si no, agrégalos a tu archivo de hosts.

events {}

http {
  # Un solo puerto, 8443, con dos nombres. Nginx separa por server_name (SNI) y termina el TLS. Los
  # tres procesos de atras hablan en claro: el AS (wrangler) en 8787, el BFF en 8080, y el API ni
  # siquiera se expone (lo llama el BFF por dentro).

  # sso.localhost -> el servidor de autorizacion (Worker en wrangler dev). El AS arma sus URLs
  # publicas a partir de su variable ISSUER, asi que no necesita saber que va detras de TLS.
  server {
    listen 8443 ssl;
    server_name sso.localhost;

    ssl_certificate     /etc/nginx/certs/localhost.pem;
    ssl_certificate_key /etc/nginx/certs/localhost-key.pem;

    location / {
      proxy_pass http://host.docker.internal:8787;
      proxy_set_header Host $host;
    }
  }

  # app.localhost -> el BFF. Aqui si viajan las cabeceras X-Forwarded-*, porque Spring reconstruye
  # con ellas la redirect_uri publica (https://app.localhost:8443/...). Sin ellas, saldria con
  # http y el puerto interno, y el AS rechazaria la redirect por no coincidir.
  server {
    listen 8443 ssl;
    server_name app.localhost;

    ssl_certificate     /etc/nginx/certs/localhost.pem;
    ssl_certificate_key /etc/nginx/certs/localhost-key.pem;

    location / {
      proxy_pass http://host.docker.internal:8080;
      proxy_set_header Host              $host;
      proxy_set_header X-Real-IP         $remote_addr;
      proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto https;
      proxy_set_header X-Forwarded-Host  $host;
      proxy_set_header X-Forwarded-Port  8443;
    }
  }
}

La decisión
Nginx como único punto TLS, con los dos nombres en el puerto 8443 separados por server_name. El servidor de autorización arma sus URLs públicas a partir de su variable ISSUER, así que no necesita saber que va detrás de TLS; el BFF sí, y por eso recibe los X-Forwarded-*.
Lo que descartas
Exponer cada proceso con su propio TLS. Multiplicaría certificados y haría que los redirect_uri dependieran del puerto de cada servicio. Un solo frente es más parecido a producción y más fácil de razonar.
Qué puede salir mal
Si la JVM no confía en la CA del laboratorio, el descubrimiento del JWKS por HTTPS falla con un error de handshake al arrancar el BFF o el API, no al usarlos. Importar el rootCA.pem lo resuelve.

Paso a paso

Once pasos, de adentro hacia afuera. Primero el servidor de autorización entero —esqueleto, claves, usuarios, los dos endpoints del flujo, el refresh y OIDC—; después el BFF que lo consume y el API que valida; y al final Nginx, la rotación de claves y los ataques. Paso 1. El servidor de autorización: esqueleto, D1 y criptografía

El servidor arranca como un Worker de Hono con una base D1. El esquema son seis tablas, y la regla es la misma de A11 y A12: nada que sirva como credencial se guarda en claro. Las contraseñas, con PBKDF2; los tokens y las cookies, como su hash SHA-256; las claves privadas de firma, cifradas con una clave maestra (la KEK) que solo existe como secreto del Worker.

La criptografía va toda sobre WebCrypto, que el runtime de Workers trae: no hay bcrypt ni librerías de azar. crypto.ts reúne las primitivas —base64url, tokens aleatorios, SHA-256, PBKDF2 para contraseñas, comparación en tiempo constante y el envelope AES-GCM para las claves privadas—; es el corazón, y lo viste a fondo en M36.

-- Esquema del servidor de autorizacion. D1 es SQLite, asi que los tipos son los de SQLite
-- (TEXT, INTEGER) y los booleanos se guardan como 0 o 1. Todo lo que caduca lleva una marca de
-- tiempo en segundos Unix, y lo que es un secreto se guarda como hash o cifrado, nunca en claro.

-- Los usuarios del IdP local. La contrasena se guarda con PBKDF2-HMAC-SHA256: hash, sal e
-- iteraciones por separado, como en M36. 'scopes' es lo maximo que este usuario puede pedir.
CREATE TABLE users (
  id          TEXT PRIMARY KEY,              -- uuid
  username    TEXT NOT NULL UNIQUE,
  name        TEXT NOT NULL,
  pw_hash     TEXT NOT NULL,                 -- base64url del hash PBKDF2
  pw_salt     TEXT NOT NULL,                 -- base64url de 16 bytes
  pw_iter     INTEGER NOT NULL,              -- iteraciones de PBKDF2
  scopes      TEXT NOT NULL DEFAULT '',      -- scopes permitidos, separados por espacio
  enabled     INTEGER NOT NULL DEFAULT 1,
  created_at  INTEGER NOT NULL
);

-- Los clientes registrados. El BFF es confidencial (tiene secreto, guardado con hash) y ademas
-- usa PKCE. Las redirect_uri se comparan por igualdad exacta, nunca por prefijo.
CREATE TABLE clients (
  client_id            TEXT PRIMARY KEY,
  name                 TEXT NOT NULL,
  confidential         INTEGER NOT NULL DEFAULT 1,
  secret_hash          TEXT,                 -- PBKDF2 del secreto; NULL en un cliente publico
  secret_salt          TEXT,
  secret_iter          INTEGER,
  redirect_uris        TEXT NOT NULL,        -- JSON: lista de URIs exactas
  post_logout_uris     TEXT NOT NULL DEFAULT '[]',
  allowed_scopes       TEXT NOT NULL DEFAULT '',
  require_pkce         INTEGER NOT NULL DEFAULT 1,
  created_at           INTEGER NOT NULL
);

-- Las claves de firma ES256. La privada se guarda envuelta (AES-GCM con la KEK del Worker): el
-- byte de iv va delante del texto cifrado, todo en base64. La publica, en claro, para el JWKS.
-- 'status': active firma; next ya esta publicada y aun no firma; retiring solo verifica.
CREATE TABLE signing_keys (
  kid                  TEXT PRIMARY KEY,
  public_jwk           TEXT NOT NULL,        -- JSON de la JWK publica (con kid, alg, use)
  private_jwk_wrapped  TEXT NOT NULL,        -- base64(iv (12 bytes) || AES-GCM(JWK privada))
  status               TEXT NOT NULL CHECK (status IN ('active','next','retiring')),
  created_at           INTEGER NOT NULL
);

-- La sesion del AS. Es lo que hace el SSO: una vez iniciada, las siguientes apps no vuelven a
-- pedir contrasena. La cookie __Host-AS_SESSION lleva solo el id (hash); el estado vive aqui.
CREATE TABLE as_sessions (
  id          TEXT PRIMARY KEY,              -- base64url de SHA-256 del valor de la cookie
  user_id     TEXT NOT NULL,
  auth_time   INTEGER NOT NULL,             -- cuando se autentico de verdad (para max_age/auth_time)
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- El codigo de autorizacion: de un solo uso y de vida corta. Se guarda su hash, nunca el valor.
-- Lleva el PKCE que presento el cliente; /token exige el verifier que corresponde.
CREATE TABLE authorization_codes (
  code_hash             TEXT PRIMARY KEY,     -- SHA-256 del codigo
  client_id             TEXT NOT NULL,
  user_id               TEXT NOT NULL,
  redirect_uri          TEXT NOT NULL,
  scope                 TEXT NOT NULL,
  nonce                 TEXT,
  code_challenge        TEXT NOT NULL,
  code_challenge_method TEXT NOT NULL,       -- solo S256
  auth_time             INTEGER NOT NULL,
  expires_at            INTEGER NOT NULL,
  consumed_at           INTEGER               -- se marca al canjearlo; un segundo uso es un ataque
);

-- Los refresh tokens, que rotan. Cada uno se guarda por su hash, con una familia. Al canjear uno
-- se marca consumed_at y se crea el siguiente (replaced_by). Si llega uno ya consumido, es reuso:
-- se revoca toda la familia. 'revoked' corta la familia entera de una.
CREATE TABLE refresh_tokens (
  token_hash   TEXT PRIMARY KEY,             -- SHA-256 del token opaco
  family_id    TEXT NOT NULL,
  client_id    TEXT NOT NULL,
  user_id      TEXT NOT NULL,
  scope        TEXT NOT NULL,
  issued_at    INTEGER NOT NULL,
  expires_at   INTEGER NOT NULL,
  consumed_at  INTEGER,
  replaced_by  TEXT,                          -- token_hash del siguiente de la familia
  revoked      INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_refresh_family ON refresh_tokens(family_id);
CREATE INDEX idx_codes_expires ON authorization_codes(expires_at);
CREATE INDEX idx_sessions_expires ON as_sessions(expires_at);

// Primitivas de criptografia, todas sobre WebCrypto (crypto.subtle), que el runtime de Workers trae.
// No hay librerias de hash de contrasenas ni de random aqui: lo que hace falta lo da el navegador
// de serie. La idea de cada pieza esta en M36.

const enc = new TextEncoder();

// base64url sin relleno, el formato de JOSE y de todo lo que viaja en una URL.
export function b64url(bytes: ArrayBuffer | Uint8Array): string {
  const b = bytes instanceof Uint8Array ? bytes : new Uint8Array(bytes);
  let s = "";
  for (const byte of b) s += String.fromCharCode(byte);
  return btoa(s).replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}

export function b64urlDecode(s: string): Uint8Array {
  const pad = s.length % 4 === 0 ? "" : "=".repeat(4 - (s.length % 4));
  const b = atob(s.replace(/-/g, "+").replace(/_/g, "/") + pad);
  const out = new Uint8Array(b.length);
  for (let i = 0; i < b.length; i++) out[i] = b.charCodeAt(i);
  return out;
}

// Un token opaco: 32 bytes de azar, en base64url. Es lo que se entrega como refresh token, como
// codigo de autorizacion y como valor de la cookie de sesion. Nunca se guarda tal cual.
export function randomToken(bytes = 32): string {
  return b64url(crypto.getRandomValues(new Uint8Array(bytes)));
}

export function randomId(): string {
  return crypto.randomUUID();
}

// SHA-256 en base64url. Con esto se guardan los tokens: en la base vive el hash, no el token, asi
// que quien lea la base no puede usar lo que ve. Comparar hashes es comparar cadenas de largo fijo.
export async function sha256(input: string): Promise<string> {
  const digest = await crypto.subtle.digest("SHA-256", enc.encode(input));
  return b64url(digest);
}

// --- Contrasenas: PBKDF2-HMAC-SHA256 ---
// bcrypt y scrypt no estan en WebCrypto; PBKDF2 si, y con suficientes iteraciones cumple. Guardamos
// hash, sal e iteraciones por separado (pwHash). Verificar rehace el calculo y compara en tiempo
// constante. En produccion de verdad se preferiria Argon2id (ver M36); aqui PBKDF2 por portabilidad.
export interface PwHash {
  hash: string;
  salt: string;
  iter: number;
}

export async function hashPassword(password: string, iter = 210000): Promise<PwHash> {
  const salt = crypto.getRandomValues(new Uint8Array(16));
  const hash = await pbkdf2(password, salt, iter);
  return { hash: b64url(hash), salt: b64url(salt), iter };
}

export async function verifyPassword(password: string, stored: PwHash): Promise<boolean> {
  const expected = b64urlDecode(stored.hash);
  const actual = await pbkdf2(password, b64urlDecode(stored.salt), stored.iter);
  return timingSafeEqual(new Uint8Array(actual), expected);
}

async function pbkdf2(password: string, salt: Uint8Array, iterations: number): Promise<ArrayBuffer> {
  const key = await crypto.subtle.importKey("raw", enc.encode(password), "PBKDF2", false, ["deriveBits"]);
  return crypto.subtle.deriveBits(
    { name: "PBKDF2", hash: "SHA-256", salt, iterations },
    key,
    256,
  );
}

// Comparacion en tiempo constante: no corta en la primera diferencia, para no filtrar cuanto
// coincide por el tiempo que tarda. La misma idea que MessageDigest.isEqual de A11.
export function timingSafeEqual(a: Uint8Array, b: Uint8Array): boolean {
  if (a.length !== b.length) return false;
  let diff = 0;
  for (let i = 0; i < a.length; i++) diff |= (a[i] as number) ^ (b[i] as number);
  return diff === 0;
}

// --- Envolver claves privadas: AES-GCM con la KEK del Worker ---
// Las claves privadas de firma viven en D1, pero cifradas con una clave maestra (KEK) que solo
// existe como secreto del Worker. Quien lea la base no tiene la KEK, asi que no puede firmar.
// Es envelope encryption, como en M10: el iv de 12 bytes va delante del texto cifrado.
async function kekKey(kekBase64: string): Promise<CryptoKey> {
  const raw = b64urlDecode(kekBase64.replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, ""));
  return crypto.subtle.importKey("raw", raw, "AES-GCM", false, ["encrypt", "decrypt"]);
}

export async function wrap(plaintext: string, kekBase64: string): Promise<string> {
  const key = await kekKey(kekBase64);
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const ct = await crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, enc.encode(plaintext));
  const out = new Uint8Array(iv.length + ct.byteLength);
  out.set(iv, 0);
  out.set(new Uint8Array(ct), iv.length);
  return b64url(out);
}

export async function unwrap(wrapped: string, kekBase64: string): Promise<string> {
  const key = await kekKey(kekBase64);
  const all = b64urlDecode(wrapped);
  const iv = all.slice(0, 12);
  const ct = all.slice(12);
  const pt = await crypto.subtle.decrypt({ name: "AES-GCM", iv }, key, ct);
  return new TextDecoder().decode(pt);
}

La decisión
PBKDF2-HMAC-SHA256 para contraseñas y AES-GCM para envolver las claves privadas, porque es lo que WebCrypto da sin dependencias. Guardar el hash, nunca el valor, para tokens, cookies y códigos.
Lo que descartas
Argon2id, que sería mejor para contraseñas pero no está en WebCrypto; en producción de verdad lo preferirías (M36). Y guardar las claves privadas en claro en la base: quien la leyera podría firmar tokens a nombre del servidor.
Qué puede salir mal
Si la KEK_BASE64 cambia o se pierde, las claves privadas envueltas ya no se pueden descifrar y el servidor no puede firmar: hay que sembrar claves nuevas. La KEK es el secreto que protege a todos los demás.

Paso 2. Las claves ES256 y el JWKS

El servidor firma los tokens con ES256 —ECDSA sobre P-256—, no con un secreto compartido. La diferencia importa: con firma asimétrica, el resource server verifica con la clave pública y nunca necesita un secreto; si ese secreto se filtrara, cualquiera firmaría tokens. El kid en la cabecera de cada token dice con qué clave se firmó, para poder tener varias a la vez y rotarlas.

keys.ts genera el par con jose, deriva el kid del thumbprint de la clave (RFC 7638), guarda la privada envuelta y la pública en claro, y arma el JWKS con las tres claves. Firmar un access token o un id_token es poner el kid en la cabecera y llamar a SignJWT.

Ver keys.ts 
// Las claves de firma ES256 y su rotacion. Firmar con jose; guardar la privada envuelta con la KEK.
// El Spring resource server y el BFF solo necesitan la parte publica, que sirve el endpoint JWKS.
import * as jose from "jose";
import type { Env } from "./env.js";
import { now } from "./env.js";
import { wrap, unwrap } from "./crypto.js";

const ALG = "ES256";

export interface LoadedKey {
  kid: string;
  privateKey: CryptoKey;
}

// Genera un par ES256 nuevo y lo devuelve como dos JWK (publica y privada) con un kid derivado del
// thumbprint RFC 7638: el mismo par siempre da el mismo kid, y el kid no revela nada de la clave.
export async function generateKeyJwks(): Promise<{ kid: string; publicJwk: jose.JWK; privateJwk: jose.JWK }> {
  const { publicKey, privateKey } = await jose.generateKeyPair(ALG, { extractable: true });
  const publicJwk = await jose.exportJWK(publicKey);
  const privateJwk = await jose.exportJWK(privateKey);
  const kid = await jose.calculateJwkThumbprint(publicJwk);
  publicJwk.kid = kid;
  publicJwk.alg = ALG;
  publicJwk.use = "sig";
  return { kid, publicJwk, privateJwk };
}

// Guarda una clave con su estado. La privada va cifrada; la publica, en claro (es la que se publica).
export async function storeKey(
  env: Env,
  key: { kid: string; publicJwk: jose.JWK; privateJwk: jose.JWK },
  status: "active" | "next" | "retiring",
): Promise<void> {
  const wrapped = await wrap(JSON.stringify(key.privateJwk), env.KEK_BASE64);
  await env.DB.prepare(
    "INSERT INTO signing_keys (kid, public_jwk, private_jwk_wrapped, status, created_at) VALUES (?, ?, ?, ?, ?)",
  )
    .bind(key.kid, JSON.stringify(key.publicJwk), wrapped, status, now())
    .run();
}

// La clave que firma ahora. Desenvuelve la privada con la KEK y la importa para que jose la use.
export async function activeKey(env: Env): Promise<LoadedKey> {
  const row = await env.DB.prepare(
    "SELECT kid, private_jwk_wrapped FROM signing_keys WHERE status = 'active' ORDER BY created_at DESC LIMIT 1",
  ).first<{ kid: string; private_jwk_wrapped: string }>();
  if (!row) throw new Error("no hay clave activa: corre el sembrado");
  const privateJwk = JSON.parse(await unwrap(row.private_jwk_wrapped, env.KEK_BASE64)) as jose.JWK;
  const privateKey = (await jose.importJWK(privateJwk, ALG)) as CryptoKey;
  return { kid: row.kid, privateKey };
}

// El JWKS publico: todas las claves que podrian haber firmado un token aun valido (active, next y
// retiring). 'next' ya aparece aqui antes de empezar a firmar, para que los verificadores la tengan
// cacheada cuando llegue su turno. Nunca sale la parte privada.
export async function publicJwks(env: Env): Promise<{ keys: jose.JWK[] }> {
  const rows = await env.DB.prepare("SELECT public_jwk FROM signing_keys").all<{ public_jwk: string }>();
  return { keys: rows.results.map((r) => JSON.parse(r.public_jwk) as jose.JWK) };
}

// Rota las claves: la 'next' pasa a 'active', la 'active' a 'retiring', se crea una 'next' nueva y
// se borra la 'retiring' anterior. El solapamiento es lo que evita cortar los tokens ya emitidos:
// una retiring aun verifica hasta que todos sus tokens vencen. Lo dispara el reader a mano (paso 11).
export async function rotateKeys(env: Env): Promise<{ newActive: string; newNext: string }> {
  const oldRetiring = await env.DB.prepare("SELECT kid FROM signing_keys WHERE status = 'retiring'").all<{ kid: string }>();
  const active = await env.DB.prepare("SELECT kid FROM signing_keys WHERE status = 'active' LIMIT 1").first<{ kid: string }>();
  const next = await env.DB.prepare("SELECT kid FROM signing_keys WHERE status = 'next' LIMIT 1").first<{ kid: string }>();
  if (!active || !next) throw new Error("faltan claves active o next");

  const fresh = await generateKeyJwks();
  const statements = [
    ...oldRetiring.results.map((r) => env.DB.prepare("DELETE FROM signing_keys WHERE kid = ?").bind(r.kid)),
    env.DB.prepare("UPDATE signing_keys SET status = 'retiring' WHERE kid = ?").bind(active.kid),
    env.DB.prepare("UPDATE signing_keys SET status = 'active' WHERE kid = ?").bind(next.kid),
    env.DB.prepare("INSERT INTO signing_keys (kid, public_jwk, private_jwk_wrapped, status, created_at) VALUES (?, ?, ?, 'next', ?)")
      .bind(fresh.kid, JSON.stringify(fresh.publicJwk), await wrap(JSON.stringify(fresh.privateJwk), env.KEK_BASE64), now()),
  ];
  await env.DB.batch(statements);
  return { newActive: next.kid, newNext: fresh.kid };
}

// Firma un access token: JWT ES256 con el kid en la cabecera, para el resource server (aud = api).
export async function signAccessToken(
  env: Env,
  claims: { sub: string; scope: string; client_id: string; username: string },
  ttl: number,
): Promise<string> {
  const key = await activeKey(env);
  return new jose.SignJWT({ scope: claims.scope, client_id: claims.client_id, username: claims.username })
    .setProtectedHeader({ alg: ALG, kid: key.kid, typ: "at+jwt" })
    .setIssuer(env.ISSUER)
    .setSubject(claims.sub)
    .setAudience("sso-api")
    .setIssuedAt()
    .setExpirationTime(now() + ttl)
    .setJti(crypto.randomUUID())
    .sign(key.privateKey);
}

// Firma un id_token: para el cliente (aud = client_id), con nonce y auth_time, como pide OIDC.
export async function signIdToken(
  env: Env,
  claims: { sub: string; aud: string; nonce?: string; auth_time: number; name: string; username: string },
  ttl: number,
): Promise<string> {
  const key = await activeKey(env);
  const jwt = new jose.SignJWT({ name: claims.name, preferred_username: claims.username, auth_time: claims.auth_time, ...(claims.nonce ? { nonce: claims.nonce } : {}) })
    .setProtectedHeader({ alg: ALG, kid: key.kid, typ: "JWT" })
    .setIssuer(env.ISSUER)
    .setSubject(claims.sub)
    .setAudience(claims.aud)
    .setIssuedAt()
    .setExpirationTime(now() + ttl);
  return jwt.sign(key.privateKey);
}
La decisión
ES256 y un JWKS público, para que el resource server verifique sin secretos. Tres claves con solapamiento, para rotar sin cortar sesiones.
Lo que descartas
HS256 con un secreto compartido entre el servidor y el API: más simple, pero el API tendría un secreto capaz de firmar, no solo de verificar. Y una sola clave sin kid: rotarla invalidaría de golpe todos los tokens vivos.
Qué puede salir mal
Si borras la clave retiring antes de que venzan sus tokens, esos tokens dejan de verificar de golpe. El solapamiento existe justo para evitarlo: se borra una rotación después, cuando ya nadie la usa.

Paso 3. El IdP local: usuarios, clientes y el sembrado

Para no depender de un proveedor externo, el servidor es su propio IdP: guarda usuarios y clientes. Los usuarios son ana, beto y carla, cada uno con sus scopes —ana puede leer y escribir productos, beto solo leer, carla ni eso—. El cliente es el BFF: confidencial (tiene secreto), con su redirect_uri registrada por igualdad exacta y PKCE obligatorio.

Workers no tiene un "al arrancar" fiable, así que el sembrado es un POST /internal/seed idempotente: crea las claves si no hay, el cliente del BFF y los usuarios, y no duplica nada si se corre dos veces. Le pasas el mismo BFF_CLIENT_SECRET que pusiste en el .env.

// Verifica usuario y contrasena. Devuelve el usuario si todo cuadra; null si no existe, esta
// deshabilitado o la contrasena no coincide. El mismo null para los tres casos: no decimos cual.
export async function login(env: Env, username: string, password: string): Promise<User | null> {
  const row = await env.DB.prepare(
    "SELECT id, username, name, scopes, enabled, pw_hash, pw_salt, pw_iter FROM users WHERE username = ?",
  )
    .bind(username)
    .first<UserRow>();
  if (!row || row.enabled !== 1) {
    // Aun sin usuario, gastamos un PBKDF2 para que el tiempo de respuesta no delate si existe.
    await verifyPassword(password, { hash: "AAAA", salt: "AAAA", iter: 210000 }).catch(() => false);
    return null;
  }
  const ok = await verifyPassword(password, { hash: row.pw_hash, salt: row.pw_salt, iter: row.pw_iter });
  if (!ok) return null;
  return { id: row.id, username: row.username, name: row.name, scopes: row.scopes, enabled: row.enabled };
}

    return c.json({ error: "SEED_PASSWORD vacia o menor de 12 caracteres" }, 400);
  }
  const body = (await c.req.parseBody().catch(() => ({}))) as Record<string, string>;
  const report: Record<string, unknown> = { keys: "ya existian", bff: "ya existia", users: [] as string[] };

  // Claves de firma: si no hay ninguna, crear active y next.
  const keyCount = await c.env.DB.prepare("SELECT COUNT(*) AS n FROM signing_keys").first<{ n: number }>();
  if ((keyCount?.n ?? 0) === 0) {

  if (!existing) {

    const h = await hashPassword(secret);
    await c.env.DB.prepare(
      `INSERT INTO clients (client_id, name, confidential, secret_hash, secret_salt, secret_iter,
         redirect_uris, post_logout_uris, allowed_scopes, require_pkce, created_at)
       VALUES ('bff', 'Panel de la tienda', 1, ?, ?, ?, ?, ?, ?, 1, ?)`,
    )
      .bind(
        h.hash,
        h.salt,
        h.iter,
        JSON.stringify(["https://app.localhost:8443/login/oauth2/code/sso"]),
        JSON.stringify(["https://app.localhost:8443/"]),
        "openid profile productos.read productos.write",
        now(),
      )
      .run();
    report.bff = body.bff_secret ? "creado (secreto propio)" : `creado (guarda este secreto: ${secret})`;
  }

  // Usuarios. Cada uno con su hash PBKDF2 de la SEED_PASSWORD. No se recrean si ya existen.
  const created: string[] = [];
  for (const u of USERS) {
    const there = await c.env.DB.prepare("SELECT 1 AS one FROM users WHERE username = ?").bind(u.username).first();

      .bind(randomId(), u.username, u.name, h.hash, h.salt, h.iter, u.scopes, now())
      .run();

  }
  report.users = created.length ? created : "ya existian";
  return c.json(report);
}

Paso 4. /authorize, el login y PKCE

El /authorize es el front-channel: lo que pasa por el navegador. Valida al cliente y la redirect_uri antes de confiar en nada más —si cualquiera falla, no se redirige a ningún lado—; luego mira si hay sesión del SSO. Si no la hay, pinta el login; si la hay, emite el código y vuelve al cliente. El código guarda el code_challenge de PKCE y el nonce.

El login del IdP es una página HTML que el propio Worker dibuja, con su CSP que prohíbe scripts. Protege el POST con un csrf de un solo uso (doble envío contra una cookie) y valida que el return_to sea una URL de /authorize de este mismo servidor, para que el login no se pueda usar como redirector abierto.

// /authorize ya lo encuentra autenticado y no vuelve a pedir contrasena. La cookie __Host-AS_SESSION

import { now } from "./env.js";
import { randomToken, sha256 } from "./crypto.js";

  user_id: string;

  expires_at: number;
}

// Crea la sesion y devuelve el valor que va en la cookie (el que el navegador guardara). En la base
// solo entra su hash.
export async function createSession(env: Env, userId: string, ttl: number): Promise<string> {
  const value = randomToken();
  const id = await sha256(value);
  const t = now();
  await env.DB.prepare(
    "INSERT INTO as_sessions (id, user_id, auth_time, created_at, expires_at) VALUES (?, ?, ?, ?, ?)",
  )
    .bind(id, userId, t, t, t + ttl)
    .run();
  return value;
}

export async function getSession(env: Env, cookieValue: string | undefined): Promise<Session | null> {
  if (!cookieValue) return null;
  const id = await sha256(cookieValue);
  const row = await env.DB.prepare(
    "SELECT id, user_id, auth_time, expires_at FROM as_sessions WHERE id = ?",
  )
    .bind(id)
    .first<Session>();
  if (!row) return null;
  if (row.expires_at <= now()) {
    await env.DB.prepare("DELETE FROM as_sessions WHERE id = ?").bind(id).run();
    return null;
  }
  return row;
}

export async function destroySession(env: Env, cookieValue: string | undefined): Promise<void> {
  if (!cookieValue) return;
  const id = await sha256(cookieValue);
  await env.DB.prepare("DELETE FROM as_sessions WHERE id = ?").bind(id).run();
}

// El front-channel: /authorize y /login. Aqui es donde el usuario ve algo (el login), y donde se
// decide si ya tiene sesion en el AS (SSO) o si hay que pedirle la contrasena. El resultado de todo
// esto es un codigo de autorizacion que vuelve al cliente por la redirect_uri.
import type { Context } from "hono";
import { getCookie } from "hono/cookie";
import type { Env } from "./env.js";
import { config, now } from "./env.js";
import { getClient, redirectAllowed, clientScopesAllowed } from "./clients.js";
import { login, grantableScopes, getUserById } from "./users.js";
import { getSession, createSession, sessionCookie, SESSION_COOKIE } from "./sessions.js";
import { issueCode } from "./codes.js";
import { redirectError } from "./oidc.js";
import { loginPage, errorPage } from "./pages.js";
import { randomToken, sha256, timingSafeEqual } from "./crypto.js";

const LOGIN_CSRF = "__Host-AS_LOGIN_CSRF";

// GET /authorize. Valida al cliente y la redirect_uri ANTES de confiar en nada mas: si cualquiera
// falla, no se redirige a ningun lado (seria mandar el error, o peor, a un sitio no verificado), se
// muestra una pagina. Una vez validados, los errores si vuelven al cliente, como pide OAuth.
export async function authorize(c: Context<{ Bindings: Env }>): Promise<Response> {
  const q = c.req.query();
  const client = q.client_id ? await getClient(c.env, q.client_id) : null;
  if (!client) return c.html(errorPage("Cliente desconocido", "El client_id no esta registrado."), 400);
  if (!q.redirect_uri || !redirectAllowed(client, q.redirect_uri)) {
    return c.html(errorPage("redirect_uri invalida", "No coincide, de forma exacta, con ninguna registrada."), 400);
  }
  const redirectUri = q.redirect_uri;
  const state = q.state;

  if (q.response_type !== "code") return redirectError(redirectUri, "unsupported_response_type", "Solo se admite code.", state);
  if (!q.code_challenge || q.code_challenge_method !== "S256") {
    return redirectError(redirectUri, "invalid_request", "Falta PKCE S256 (code_challenge).", state);
  }

  const requested = (q.scope ?? "").split(/\s+/).filter(Boolean);
  if (!requested.includes("openid")) return redirectError(redirectUri, "invalid_scope", "Falta el scope openid.", state);

  // La sesion del AS. Si existe y no hay que forzar login, es SSO: no se pide contrasena.
  const session = await getSession(c.env, getCookie(c, SESSION_COOKIE));
  const cfg = config(c.env);
  const forceLogin = q.prompt === "login" || (q.max_age != null && session != null && now() - session.auth_time > Number(q.max_age));

  if (!session || forceLogin) {
    // Sin sesion: pintar el login. El return_to es esta misma URL de /authorize, para volver aqui
    // ya autenticado. Un csrf de un solo uso va en una cookie y en el form.
    const csrf = randomToken();
    // El return_to se arma desde ISSUER (la URL publica), no desde c.req.url: tras nginx, la url
    // interna es http://...:8787 y mandaria al navegador al esquema y puerto equivocados.
    const returnTo = `${c.env.ISSUER}/authorize${new URL(c.req.url).search}`;
    c.header("Set-Cookie", `${LOGIN_CSRF}=${await sha256(csrf)}; Path=/; Max-Age=600; HttpOnly; Secure; SameSite=Lax`);
    return c.html(loginPage({ returnTo, csrf, app: client.name }));
  }

  // Con sesion: emitir el codigo y volver al cliente. El scope final es lo que coinciden las tres
  // listas: lo pedido, lo que el cliente puede, y lo que el usuario tiene. El codigo guarda el PKCE.
  const user = await getUserById(c.env, session.user_id);
  if (!user || user.enabled !== 1) {
    c.header("Set-Cookie", `${SESSION_COOKIE}=; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax`);
    return redirectError(redirectUri, "access_denied", "La cuenta ya no esta activa.", state);
  }
  const granted = grantableScopes(user, clientScopesAllowed(client, requested));
  const code = await issueCode(
    c.env,
    {
      client_id: client.client_id,
      user_id: session.user_id,
      redirect_uri: redirectUri,
      scope: granted.join(" "),
      nonce: q.nonce ?? null,
      code_challenge: q.code_challenge,
      code_challenge_method: "S256",
      auth_time: session.auth_time,
    },
    cfg.codeTtl,
  );
  const u = new URL(redirectUri);
  u.searchParams.set("code", code);
  if (state) u.searchParams.set("state", state);
  return c.redirect(u.toString(), 302);
}

// POST /login. Valida el csrf (doble envio contra la cookie) y que el return_to sea una URL de
// /authorize de ESTE emisor, nunca otra: asi el login no se puede usar como redirector abierto.
export async function doLogin(c: Context<{ Bindings: Env }>): Promise<Response> {
  const body = await c.req.parseBody();
  const csrf = String(body.csrf ?? "");
  const returnTo = String(body.return_to ?? "");
  const cookieCsrf = getCookie(c, LOGIN_CSRF) ?? "";

  const csrfOk = cookieCsrf !== "" && timingSafeEqual(new TextEncoder().encode(await sha256(csrf)), new TextEncoder().encode(cookieCsrf));
  if (!csrfOk) return c.html(errorPage("Sesion de login expirada", "Vuelve a la aplicacion e intenta de nuevo."), 400);

  const authorizePrefix = `${c.env.ISSUER}/authorize`;
  if (!returnTo.startsWith(authorizePrefix)) {
    return c.html(errorPage("Destino invalido", "El login solo vuelve a una peticion de autorizacion."), 400);
  }

  const user = await login(c.env, String(body.username ?? ""), String(body.password ?? ""));
  if (!user) {
    // Reintento: nuevo csrf, mismo return_to, aviso de error.
    const csrfNew = randomToken();
    c.header("Set-Cookie", `${LOGIN_CSRF}=${await sha256(csrfNew)}; Path=/; Max-Age=600; HttpOnly; Secure; SameSite=Lax`);
    return c.html(loginPage({ returnTo, csrf: csrfNew, error: true }), 401);
  }

  // Éxito: crear la sesion del AS, limpiar el csrf y volver a /authorize, que ahora vera la sesion.
  const value = await createSession(c.env, user.id, config(c.env).sessionTtl);
  c.header("Set-Cookie", sessionCookie(value, config(c.env).sessionTtl));
  c.header("Set-Cookie", `${LOGIN_CSRF}=; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax`, { append: true });
  return c.redirect(returnTo, 302);
}
La decisión
PKCE S256 obligatorio para todos los clientes, incluido el confidencial. El código es de un solo uso y de vida corta (60 s). La cookie de sesión del SSO lleva los mismos atributos blindados de A12: __Host-, HttpOnly, Secure, SameSite=Lax.
Lo que descartas
El flujo implícito, que devolvía el token directo por la URL —hoy desaconsejado— y PKCE plain, que no protege nada. Y confiar en la redirect_uri para reportar un error cuando aún no se validó: se muestra una página en su lugar.
Qué puede salir mal
Si construyeras el return_to a partir de la URL interna que ve el Worker tras Nginx, saldría con http y el puerto interno, y el navegador iría al sitio equivocado. Se arma desde ISSUER, la URL pública.

Paso 5. /token: canjear el código con PKCE

El /token es el back-channel: habla el cliente, de servidor a servidor, sin navegador. Autentica al cliente (el BFF, confidencial, con Basic), canjea el código una sola vez, comprueba que sea de ese cliente y esa redirect_uri, verifica el PKCE y, si todo cuadra, emite el access token, el id_token y el primer refresh.

El canje del código es atómico: el UPDATE ... WHERE consumed_at IS NULL con RETURNING marca y lee en una sola sentencia, así que dos /token a la vez no lo usan dos veces. Si llega un código ya consumido, se niega con invalid_grant.

Ver codes.ts y token.ts 
// El codigo de autorizacion: de un solo uso y de vida corta (60 s). Se guarda su hash. Al canjearlo
// se marca consumed_at en la misma sentencia que lo lee, para que dos /token a la vez no lo usen dos
// veces. El PKCE que presento el cliente viaja con el codigo; /token exige el verifier que calza.
import type { Env } from "./env.js";
import { now } from "./env.js";
import { randomToken, sha256, b64url } from "./crypto.js";

export interface CodeData {
  client_id: string;
  user_id: string;
  redirect_uri: string;
  scope: string;
  nonce: string | null;
  code_challenge: string;
  code_challenge_method: string;
  auth_time: number;
}

export async function issueCode(env: Env, data: CodeData, ttl: number): Promise<string> {
  const code = randomToken();
  await env.DB.prepare(
    `INSERT INTO authorization_codes
       (code_hash, client_id, user_id, redirect_uri, scope, nonce, code_challenge, code_challenge_method, auth_time, expires_at)
     VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)`,
  )
    .bind(
      await sha256(code),
      data.client_id,
      data.user_id,
      data.redirect_uri,
      data.scope,
      data.nonce,
      data.code_challenge,
      data.code_challenge_method,
      data.auth_time,
      now() + ttl,
    )
    .run();
  return code;
}

// Canjea el codigo una sola vez. El UPDATE ... WHERE consumed_at IS NULL con RETURNING es atomico:
// el primero en llegar lo marca y recibe la fila; un segundo intento no actualiza nada y recibe
// null. Devuelve 'reused' si el codigo existia pero ya estaba consumido, para poder reaccionar.
export async function consumeCode(
  env: Env,
  code: string,
): Promise<{ status: "ok"; data: CodeData & { expires_at: number } } | { status: "reused" } | { status: "unknown" }> {
  const hash = await sha256(code);
  const row = await env.DB.prepare(
    `UPDATE authorization_codes SET consumed_at = ?
       WHERE code_hash = ? AND consumed_at IS NULL
       RETURNING client_id, user_id, redirect_uri, scope, nonce, code_challenge, code_challenge_method, auth_time, expires_at`,
  )
    .bind(now(), hash)
    .first<CodeData & { expires_at: number }>();
  if (row) return { status: "ok", data: row };

  const exists = await env.DB.prepare("SELECT 1 AS one FROM authorization_codes WHERE code_hash = ?").bind(hash).first();
  return exists ? { status: "reused" } : { status: "unknown" };
}

// Verifica el PKCE S256: SHA-256 del verifier, en base64url, tiene que igualar al challenge guardado.
export async function pkceMatches(verifier: string, challenge: string): Promise<boolean> {
  const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
  return b64url(digest) === challenge;
}
// El back-channel: /token y /revoke. Aqui no hay navegador; habla el cliente (el BFF) de servidor a
// servidor. /token cambia un codigo por tokens, o rota un refresh. Cada paso valida algo: el cliente,
// el PKCE, que el codigo sea de un solo uso, que el refresh no sea un reuso.
import type { Context } from "hono";
import type { Env } from "./env.js";
import { config, now } from "./env.js";
import { getClient, verifyClientSecret, type Client } from "./clients.js";
import { getUserById } from "./users.js";
import { consumeCode, pkceMatches } from "./codes.js";
import { issueRefresh, rotateRefresh, revokeByToken } from "./refresh.js";
import { signAccessToken, signIdToken } from "./keys.js";
import { tokenError } from "./oidc.js";

// Autentica al cliente: Basic en la cabecera (cliente confidencial, como el BFF) o client_id en el
// cuerpo (cliente publico, que se apoya solo en PKCE). Devuelve el cliente o null.
async function authenticateClient(c: Context<{ Bindings: Env }>, body: Record<string, string>): Promise<Client | "bad" | null> {
  const auth = c.req.header("Authorization");
  if (auth?.startsWith("Basic ")) {
    const [id, secret] = atob(auth.slice(6)).split(":", 2);
    const client = id ? await getClient(c.env, id) : null;
    if (!client) return null;
    if (!(await verifyClientSecret(client, secret ?? ""))) return "bad";
    return client;
  }
  const client = body.client_id ? await getClient(c.env, body.client_id) : null;
  if (!client) return null;
  // Un cliente confidencial no puede autenticarse sin secreto.
  if (client.confidential === 1) return "bad";
  return client;
}

export async function token(c: Context<{ Bindings: Env }>): Promise<Response> {
  const raw = await c.req.parseBody();
  const body: Record<string, string> = {};
  for (const [k, v] of Object.entries(raw)) body[k] = String(v);

  const client = await authenticateClient(c, body);
  if (client === null) return tokenError("invalid_client", "Cliente desconocido.");
  if (client === "bad") return tokenError("invalid_client", "Autenticacion de cliente invalida.");

  if (body.grant_type === "authorization_code") return authCodeGrant(c, client, body);
  if (body.grant_type === "refresh_token") return refreshGrant(c, client, body);
  return tokenError("unsupported_grant_type", "Solo authorization_code y refresh_token.");
}

async function authCodeGrant(c: Context<{ Bindings: Env }>, client: Client, body: Record<string, string>): Promise<Response> {
  if (!body.code || !body.redirect_uri || !body.code_verifier) {
    return tokenError("invalid_request", "Faltan code, redirect_uri o code_verifier.");
  }
  const result = await consumeCode(c.env, body.code);
  if (result.status === "unknown") return tokenError("invalid_grant", "El codigo no existe.");
  // Reuso del codigo: ya se canjeo una vez. Es senal de robo; se niega.
  if (result.status === "reused") return tokenError("invalid_grant", "El codigo ya se uso.");

  const code = result.data;
  if (code.client_id !== client.client_id) return tokenError("invalid_grant", "El codigo es de otro cliente.");
  if (code.redirect_uri !== body.redirect_uri) return tokenError("invalid_grant", "La redirect_uri no coincide.");
  if (code.expires_at <= now()) return tokenError("invalid_grant", "El codigo expiro.");
  if (!(await pkceMatches(body.code_verifier, code.code_challenge))) {
    return tokenError("invalid_grant", "El code_verifier no corresponde al challenge.");
  }

  const user = await getUserById(c.env, code.user_id);
  if (!user || user.enabled !== 1) return tokenError("invalid_grant", "La cuenta no esta activa.");

  return issueTokens(c, {
    client,
    sub: user.id,
    username: user.username,
    name: user.name,
    scope: code.scope,
    nonce: code.nonce,
    auth_time: code.auth_time,
    withIdToken: code.scope.split(" ").includes("openid"),
  });
}

async function refreshGrant(c: Context<{ Bindings: Env }>, client: Client, body: Record<string, string>): Promise<Response> {
  if (!body.refresh_token) return tokenError("invalid_request", "Falta refresh_token.");
  const rotated = await rotateRefresh(c.env, body.refresh_token, config(c.env).refreshTtl);
  if (rotated.status === "unknown") return tokenError("invalid_grant", "Refresh desconocido.");
  if (rotated.status === "expired") return tokenError("invalid_grant", "Refresh expirado.");
  // Reuso: la familia ya se revoco. Quien tenga cualquier token de esa familia queda fuera.
  if (rotated.status === "reuse") return tokenError("invalid_grant", "Refresh reutilizado: la sesion se cerro por seguridad.");
  if (rotated.data.client_id !== client.client_id) return tokenError("invalid_grant", "El refresh es de otro cliente.");

  const user = await getUserById(c.env, rotated.data.user_id);
  if (!user || user.enabled !== 1) return tokenError("invalid_grant", "La cuenta no esta activa.");

  return issueTokens(c, {
    client,
    sub: user.id,
    username: user.username,
    name: user.name,
    scope: rotated.data.scope,
    nonce: null,
    auth_time: now(),
    withIdToken: false,
    refreshOverride: rotated.token,
  });
}

// Arma la respuesta de /token: access token siempre, id_token si hay openid, y un refresh (el nuevo
// de la rotacion, o uno nuevo de familia en el intercambio del codigo).
async function issueTokens(
  c: Context<{ Bindings: Env }>,
  p: {
    client: Client;
    sub: string;
    username: string;
    name: string;
    scope: string;
    nonce: string | null;
    auth_time: number;
    withIdToken: boolean;
    refreshOverride?: string;
  },
): Promise<Response> {
  const cfg = config(c.env);
  const access = await signAccessToken(c.env, { sub: p.sub, scope: p.scope, client_id: p.client.client_id, username: p.username }, cfg.accessTtl);
  const refresh =
    p.refreshOverride ?? (await issueRefresh(c.env, { client_id: p.client.client_id, user_id: p.sub, scope: p.scope }, cfg.refreshTtl));

  const out: Record<string, unknown> = {
    access_token: access,
    token_type: "Bearer",
    expires_in: cfg.accessTtl,
    refresh_token: refresh,
    scope: p.scope,
  };
  if (p.withIdToken) {
    out.id_token = await signIdToken(
      c.env,
      { sub: p.sub, aud: p.client.client_id, nonce: p.nonce ?? undefined, auth_time: p.auth_time, name: p.name, username: p.username },
      cfg.accessTtl,
    );
  }
  return new Response(JSON.stringify(out), { headers: { "Content-Type": "application/json", "Cache-Control": "no-store" } });
}

// POST /revoke: revoca un refresh y toda su familia. Solo el cliente que lo tiene puede revocarlo.
export async function revoke(c: Context<{ Bindings: Env }>): Promise<Response> {
  const raw = await c.req.parseBody();
  const body: Record<string, string> = {};
  for (const [k, v] of Object.entries(raw)) body[k] = String(v);
  const client = await authenticateClient(c, body);
  if (client === null || client === "bad") return tokenError("invalid_client", "Cliente invalido.");
  if (body.token) await revokeByToken(c.env, body.token);
  // El revoke siempre responde 200, exista el token o no, para no filtrar cuales existen.
  return new Response(null, { status: 200, headers: { "Cache-Control": "no-store" } });
}
La decisión
El access token es un JWT firmado y autovalidable, de vida corta. El PKCE se verifica rehaciendo el hash del verifier y comparándolo con el challenge guardado. El código se consume una sola vez, de forma atómica.
Lo que descartas
Un access token opaco que el API tuviera que consultar por red en cada request (introspección): más control, pero una ida al servidor por llamada. Para un access de 5 min, el JWT autovalidable gana.
Qué puede salir mal
Sin el consumo atómico, dos canjes simultáneos del mismo código podrían emitir dos juegos de tokens. El RETURNING condicionado lo cierra: el segundo no actualiza ninguna fila.

Paso 6. Refresh rotatorio y detección de reuso

El access token dura 5 minutos; el refresh es lo que permite renovarlo sin volver a entrar. Pero un refresh robado sería tan peligroso como una contraseña si valiera para siempre. La defensa es la rotación: cada canje entrega uno nuevo de la misma familia y marca el viejo como consumido. Si llega de nuevo uno ya consumido, es señal de robo —lo usó el legítimo y el ladrón, o al revés— y se revoca la familia entera.

Ver refresh.ts 
// Los refresh tokens, que rotan: cada canje invalida el anterior y entrega uno nuevo de la misma
// familia. Si llega uno ya consumido, es reuso (alguien lo robo y lo uso, o lo usa el legitimo
// despues del ladron): se revoca la familia entera. Asi un refresh robado sirve, como mucho, una vez.
import type { Env } from "./env.js";
import { now } from "./env.js";
import { randomToken, sha256, randomId } from "./crypto.js";

export interface RefreshData {
  family_id: string;
  client_id: string;
  user_id: string;
  scope: string;
}

// Emite el primer refresh de una familia nueva (tras el intercambio del codigo).
export async function issueRefresh(env: Env, data: Omit<RefreshData, "family_id">, ttl: number): Promise<string> {
  return insertRefresh(env, { ...data, family_id: randomId() }, ttl);
}

async function insertRefresh(env: Env, data: RefreshData, ttl: number): Promise<string> {
  const token = randomToken();
  await env.DB.prepare(
    `INSERT INTO refresh_tokens (token_hash, family_id, client_id, user_id, scope, issued_at, expires_at)
     VALUES (?, ?, ?, ?, ?, ?, ?)`,
  )
    .bind(await sha256(token), data.family_id, data.client_id, data.user_id, data.scope, now(), now() + ttl)
    .run();
  return token;
}

export type RotateResult =
  | { status: "ok"; token: string; data: RefreshData }
  | { status: "reuse" } // ya consumido o revocado: la familia se revoca
  | { status: "expired" }
  | { status: "unknown" };

// Rota un refresh: valida, marca el viejo como consumido, emite el nuevo y los enlaza. Si el que
// llega ya estaba consumido o la familia esta revocada, revoca toda la familia y niega.
export async function rotateRefresh(env: Env, presented: string, ttl: number): Promise<RotateResult> {
  const hash = await sha256(presented);
  const row = await env.DB.prepare(
    "SELECT family_id, client_id, user_id, scope, expires_at, consumed_at, revoked FROM refresh_tokens WHERE token_hash = ?",
  )
    .bind(hash)
    .first<RefreshData & { expires_at: number; consumed_at: number | null; revoked: number }>();

  if (!row) return { status: "unknown" };

  // Reuso: el token ya se canjeo, o su familia fue revocada. Cortar la familia entera.
  if (row.consumed_at !== null || row.revoked === 1) {
    await revokeFamily(env, row.family_id);
    return { status: "reuse" };
  }
  if (row.expires_at <= now()) return { status: "expired" };

  const next = randomToken();
  const nextHash = await sha256(next);
  await env.DB.batch([
    env.DB.prepare("UPDATE refresh_tokens SET consumed_at = ?, replaced_by = ? WHERE token_hash = ?").bind(now(), nextHash, hash),
    env.DB.prepare(
      "INSERT INTO refresh_tokens (token_hash, family_id, client_id, user_id, scope, issued_at, expires_at) VALUES (?, ?, ?, ?, ?, ?, ?)",
    ).bind(nextHash, row.family_id, row.client_id, row.user_id, row.scope, now(), now() + ttl),
  ]);
  return { status: "ok", token: next, data: { family_id: row.family_id, client_id: row.client_id, user_id: row.user_id, scope: row.scope } };
}

export async function revokeFamily(env: Env, familyId: string): Promise<void> {
  await env.DB.prepare("UPDATE refresh_tokens SET revoked = 1 WHERE family_id = ?").bind(familyId).run();
}

// Revoca por token presentado (el endpoint /revoke). Revoca su familia, no solo ese token.
export async function revokeByToken(env: Env, presented: string): Promise<void> {
  const row = await env.DB.prepare("SELECT family_id FROM refresh_tokens WHERE token_hash = ?")
    .bind(await sha256(presented))
    .first<{ family_id: string }>();
  if (row) await revokeFamily(env, row.family_id);
}
La decisión
Refresh de un solo uso que rota en cada canje, agrupado en familias por un family_id. Un reuso revoca toda la familia. Es la recomendación de OAuth 2.1 para clientes que guardan refresh tokens.
Lo que descartas
Un refresh de larga vida que no rota: más simple, pero una copia robada vale hasta que venza, catorce días, sin que nadie se entere. Con rotación, el segundo uso delata el robo.
Qué puede salir mal
Si el cliente pierde la respuesta de una rotación (un corte de red justo después de que el servidor rotó), reintentará con el viejo y disparará la revocación de su propia familia. Es el precio de la detección; en la práctica, el cliente vuelve a entrar.

Paso 7. OIDC: descubrimiento, /userinfo y /logout

Hasta aquí es OAuth 2 (autorización). OIDC añade la capa de identidad: el id_token, que le dice al cliente quién entró, y dos endpoints. El de descubrimiento, /.well-known/openid-configuration, es lo que deja que el BFF y el API se autoconfiguren con solo el issuer. El /userinfo devuelve claims del usuario según el scope. El /logout cierra la sesión del SSO y, validando la post_logout_redirect_uri contra el cliente, vuelve a la app.

Ver oidc.ts, userinfo.ts y index.ts 
// Piezas comunes de OIDC: el documento de descubrimiento y la forma de los errores de OAuth.
import type { Env } from "./env.js";

// El documento que un cliente lee de /.well-known/openid-configuration para autoconfigurarse:
// donde esta cada endpoint, que algoritmos se firman y que scopes se ofrecen. Spring lo usa para
// no cablear URLs a mano (issuer-uri).
export function discovery(env: Env): Record<string, unknown> {
  const i = env.ISSUER;
  return {
    issuer: i,
    authorization_endpoint: `${i}/authorize`,
    token_endpoint: `${i}/token`,
    userinfo_endpoint: `${i}/userinfo`,
    jwks_uri: `${i}/jwks`,
    end_session_endpoint: `${i}/logout`,
    revocation_endpoint: `${i}/revoke`,
    response_types_supported: ["code"],
    grant_types_supported: ["authorization_code", "refresh_token"],
    code_challenge_methods_supported: ["S256"],
    token_endpoint_auth_methods_supported: ["client_secret_basic", "none"],
    id_token_signing_alg_values_supported: ["ES256"],
    subject_types_supported: ["public"],
    scopes_supported: ["openid", "profile", "productos.read", "productos.write"],
  };
}

export function scopeArray(scope: string | undefined | null): string[] {
  return (scope ?? "").split(/\s+/).filter(Boolean);
}

// Un error de OAuth en /token: JSON con error y error_description, y el status que corresponde.
// invalid_client va con 401; el resto, con 400. No-store para que nada de esto quede en cache.
export function tokenError(error: string, description: string, status = 400): Response {
  return new Response(JSON.stringify({ error, error_description: description }), {
    status: error === "invalid_client" ? 401 : status,
    headers: { "Content-Type": "application/json", "Cache-Control": "no-store" },
  });
}

// Un error en /authorize cuando SI se puede confiar en la redirect_uri (cliente y uri validados):
// se devuelve al cliente con los parametros de error, como pide el protocolo, conservando el state.
export function redirectError(redirectUri: string, error: string, description: string, state?: string): Response {
  const u = new URL(redirectUri);
  u.searchParams.set("error", error);
  u.searchParams.set("error_description", description);
  if (state) u.searchParams.set("state", state);
  return Response.redirect(u.toString(), 302);
}

// segun el scope. logout cierra la sesion del AS (el SSO) y, si el cliente lo pide con una uri
// registrada, vuelve a la app.
import type { Context } from "hono";
import { getCookie } from "hono/cookie";
import * as jose from "jose";
import type { Env } from "./env.js";
import { getUserById } from "./users.js";
import { publicJwks } from "./keys.js";
import { getSession, destroySession, clearSessionCookie, SESSION_COOKIE } from "./sessions.js";
import { getClient, postLogoutAllowed } from "./clients.js";
import { errorPage } from "./pages.js";

// GET /userinfo. Verifica la firma del access token con las claves publicas del propio AS (las
// mismas del JWKS), el emisor y el vencimiento. Devuelve claims filtrados por el scope del token.
export async function userinfo(c: Context<{ Bindings: Env }>): Promise<Response> {
  const auth = c.req.header("Authorization");
  if (!auth?.startsWith("Bearer ")) {
    return new Response(JSON.stringify({ error: "invalid_token" }), {
      status: 401,
      headers: { "WWW-Authenticate": "Bearer", "Content-Type": "application/json" },
    });
  }
  const jwks = jose.createLocalJWKSet(await publicJwks(c.env));
  let payload: jose.JWTPayload;
  try {
    ({ payload } = await jose.jwtVerify(auth.slice(7), jwks, { issuer: c.env.ISSUER }));
  } catch {
    return new Response(JSON.stringify({ error: "invalid_token" }), {
      status: 401,
      headers: { "WWW-Authenticate": 'Bearer error="invalid_token"', "Content-Type": "application/json" },
    });
  }

  const user = await getUserById(c.env, String(payload.sub));
  if (!user) return new Response(JSON.stringify({ error: "invalid_token" }), { status: 401, headers: { "Content-Type": "application/json" } });

  const scopes = String(payload.scope ?? "").split(" ");
  const claims: Record<string, unknown> = { sub: user.id };
  if (scopes.includes("profile")) {
    claims.name = user.name;
    claims.preferred_username = user.username;
  }
  return new Response(JSON.stringify(claims), { headers: { "Content-Type": "application/json", "Cache-Control": "no-store" } });
}

// GET /logout (RP-initiated logout de OIDC). Cierra la sesion del AS. El cliente que se identifica
// con el id_token_hint; de su claim aud sale el client_id, y contra ESE cliente se valida la
// post_logout_redirect_uri. Solo si la uri esta registrada se redirige; validarla evita un
// redirector abierto. Si algo no cuadra, se muestra una pagina de "sesion cerrada" sin redirigir.
export async function logout(c: Context<{ Bindings: Env }>): Promise<Response> {
  await destroySession(c.env, getCookie(c, SESSION_COOKIE));
  c.header("Set-Cookie", clearSessionCookie());

  const target = c.req.query("post_logout_redirect_uri");
  const hint = c.req.query("id_token_hint");
  if (target && hint) {
    const clientId = await clientFromIdToken(c, hint);
    if (clientId) {
      const client = await getClient(c.env, clientId);
      if (client && postLogoutAllowed(client, target)) {
        const u = new URL(target);
        const state = c.req.query("state");
        if (state) u.searchParams.set("state", state);
        return c.redirect(u.toString(), 302);
      }
    }
  }
  return c.html(errorPage("Sesion cerrada", "Cerraste la sesion unica. Cierra las pestanas para terminar."));
}

// Verifica el id_token_hint con las claves del AS y devuelve su aud (el client_id). Tolera que este
// vencido: el logout suele llegar despues de que el token expire, y aqui solo sirve para identificar
// al cliente, no como credencial. Si la firma no es nuestra, devuelve null y no se redirige.
async function clientFromIdToken(c: Context<{ Bindings: Env }>, idToken: string): Promise<string | null> {
  try {
    const jwks = jose.createLocalJWKSet(await publicJwks(c.env));
    const { payload } = await jose.jwtVerify(idToken, jwks, { issuer: c.env.ISSUER, clockTolerance: Number.MAX_SAFE_INTEGER });
    return typeof payload.aud === "string" ? payload.aud : Array.isArray(payload.aud) ? (payload.aud[0] ?? null) : null;
  } catch {
    return null;
  }
}

// Por si acaso: lee la sesion para una pagina de estado (no se usa en el flujo, util en pruebas).
export async function whoami(c: Context<{ Bindings: Env }>): Promise<Response> {
  const session = await getSession(c.env, getCookie(c, SESSION_COOKIE));
  if (!session) return new Response(JSON.stringify({ authenticated: false }), { headers: { "Content-Type": "application/json" } });
  const user = await getUserById(c.env, session.user_id);
  return new Response(JSON.stringify({ authenticated: true, username: user?.username, auth_time: session.auth_time }), {
    headers: { "Content-Type": "application/json", "Cache-Control": "no-store" },
  });
}

La decisión
El descubrimiento como contrato: el cliente y el resource server solo necesitan el issuer, y de ahí sacan todo lo demás. El /logout identifica al cliente por el id_token_hint y valida la uri de retorno.
Lo que descartas
Cablear a mano las URLs de cada endpoint en el cliente. Funcionaría, pero rompería el día que el servidor mueva un endpoint o rote la configuración; el descubrimiento lo hace solo.
Qué puede salir mal
Si el issuer del documento no coincide, carácter por carácter, con el que el cliente y el API tienen configurado, la validación del iss de cada token fallará. Tiene que ser idéntico en los tres.

Paso 8. El BFF: cliente OAuth2 con sesión en Redis

El servidor ya emite tokens. Ahora el cliente. El BFF es una app Spring con oauth2Login: cuando una request sin sesión llega, Spring la manda al /authorize, hace todo el baile del código y guarda los tokens en la sesión —que vive en Redis, como en A12—. El navegador se lleva solo una cookie de sesión del BFF, opaca y HttpOnly.

Hay un detalle que casi todos los tutoriales omiten: Spring no manda PKCE para un cliente confidencial por defecto. Como el servidor lo exige a todos, hay que forzarlo con un resolver que añada el code_challenge. El logout encadena: cierra la sesión del BFF y redirige al /logout del servidor para cerrar también el SSO.

package lab.sso.bff;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.oauth2.client.oidc.web.logout.OidcClientInitiatedLogoutSuccessHandler;
import org.springframework.security.oauth2.client.registration.ClientRegistrationRepository;
import org.springframework.security.oauth2.client.web.DefaultOAuth2AuthorizationRequestResolver;
import org.springframework.security.oauth2.client.web.OAuth2AuthorizationRequestCustomizers;
import org.springframework.security.oauth2.client.web.OAuth2AuthorizationRequestResolver;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.www.BasicAuthenticationFilter;
import org.springframework.security.web.csrf.CookieCsrfTokenRepository;

/**
 * Seguridad del BFF. Tres decisiones viven aqui:
 *  1. oauth2Login: el BFF es un cliente OIDC. El usuario que no tiene sesion se manda al AS.
 *  2. CSRF con cookie legible por la SPA (patron XOR/BREACH de Spring), porque el BFF mantiene
 *     sesion con cookie y las peticiones que mutan necesitan el token anti-CSRF (leccion de A12).
 *  3. logout encadenado: cerrar la sesion del BFF y, ademas, la sesion unica del AS (RP-initiated).
 */
@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http, ClientRegistrationRepository clients) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                // Lo estatico y el endpoint que la SPA usa para saber si hay login son abiertos.
                // /bff/me vive fuera de /api a proposito: /api/** lo captura el gateway y lo releva.
                .requestMatchers("/", "/index.html", "/assets/**", "/favicon.ico", "/bff/me").permitAll()
                // Todo lo demas, incluido /api/**, exige sesion. Sin sesion, el gateway no relevaria token.
                .anyRequest().authenticated())
            .oauth2Login(oauth -> oauth
                // Forzar PKCE aunque el cliente sea confidencial: el AS lo exige a todos.
                .authorizationEndpoint(a -> a.authorizationRequestResolver(pkceResolver(clients)))
                // Tras el login, volver a la raiz; la SPA ya arranca autenticada.
                .defaultSuccessUrl("/", true))
            .logout(logout -> logout
                .logoutUrl("/logout")
                .logoutSuccessHandler(oidcLogoutSuccessHandler(clients)))
            // CSRF: cookie XSRF-TOKEN legible por JavaScript + manejo XOR contra BREACH.
            .csrf(csrf -> csrf
                .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
                .csrfTokenRequestHandler(new SpaCsrfTokenRequestHandler()))
            .addFilterAfter(new CsrfCookieFilter(), BasicAuthenticationFilter.class);
        return http.build();
    }

    // El resolver que anade code_challenge/code_verifier (PKCE S256) a la peticion de autorizacion.
    private OAuth2AuthorizationRequestResolver pkceResolver(ClientRegistrationRepository clients) {
        var resolver = new DefaultOAuth2AuthorizationRequestResolver(clients, "/oauth2/authorization");
        resolver.setAuthorizationRequestCustomizer(OAuth2AuthorizationRequestCustomizers.withPkce());
        return resolver;
    }

    // Al cerrar sesion en el BFF, redirige tambien al end_session_endpoint del AS para cerrar el SSO.
    // Tras cerrar alli, el AS devuelve a la raiz del BFF (post_logout_redirect_uri registrada).
    private OidcClientInitiatedLogoutSuccessHandler oidcLogoutSuccessHandler(ClientRegistrationRepository clients) {
        var handler = new OidcClientInitiatedLogoutSuccessHandler(clients);
        handler.setPostLogoutRedirectUri("{baseUrl}/");
        return handler;
    }
}

La decisión
El patrón BFF: el cliente es una app de servidor que guarda los tokens y expone al navegador solo una cookie de sesión. El navegador nunca ve un token.
Lo que descartas
Una SPA que sea ella misma el cliente OAuth y guarde el token en localStorage. Es común, pero pone el token en el terreno más hostil: un XSS lo roba y no hay HttpOnly que ayude.
Qué puede salir mal
Si no fuerzas PKCE para el cliente confidencial, el servidor rechazará /authorize con invalid_request por falta de code_challenge. El resolver con withPkce() lo arregla.

Paso 9. El gateway, TokenRelay y la SPA

El BFF también es la puerta al API. Su gateway define una ruta —/api/** va al resource server— y el filtro TokenRelay toma el access token de la sesión y lo pone en Authorization: Bearer hacia el API. El navegador llama a /api/... con su cookie; el BFF traduce esa cookie en un Bearer. El token solo existe en el tramo servidor a servidor.

La SPA es una página estática que el BFF sirve. Llama a /bff/me para saber si hay sesión y a /api/productos para los datos; en las escrituras manda el token CSRF que el BFF pone en una cookie legible, con el patrón XOR de Spring que viste en A12. Un detalle: /bff/me vive fuera de /api a propósito, porque todo /api/** lo captura el gateway y lo releva.

    public void handle(HttpServletRequest request, HttpServletResponse response, Supplier<CsrfToken> csrfToken) {
        this.xor.handle(request, response, csrfToken);
    }

    @Override
    public String resolveCsrfTokenValue(HttpServletRequest request, CsrfToken csrfToken) {
        // Si viene por cabecera (la SPA), leer en claro; si viene como parametro de form, usar XOR.
        String headerValue = request.getHeader(csrfToken.getHeaderName());
        return StringUtils.hasText(headerValue) ? this.plain.resolveCsrfTokenValue(request, csrfToken)
                                                 : this.xor.resolveCsrfTokenValue(request, csrfToken);
    }

import java.util.List;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.oauth2.core.DelegatingOAuth2TokenValidator;
import org.springframework.security.oauth2.core.OAuth2Error;
import org.springframework.security.oauth2.core.OAuth2TokenValidator;
import org.springframework.security.oauth2.core.OAuth2TokenValidatorResult;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.jwt.JwtDecoders;
import org.springframework.security.oauth2.jwt.JwtValidators;
import org.springframework.security.oauth2.jwt.NimbusJwtDecoder;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationConverter;
import org.springframework.security.oauth2.server.resource.authentication.JwtGrantedAuthoritiesConverter;
import org.springframework.security.web.SecurityFilterChain;

/**
 * El resource server. No tiene sesion ni cookies: cada peticion trae un Bearer JWT que el BFF relevo.
 * Aqui se decide tres cosas:
 *  1. De donde salen las claves para verificar la firma: el JWKS del AS (via issuer-uri, descubierto).
 *  2. Que el token sea para este API (claim aud = sso-api) y del emisor correcto.
 *  3. Que cada endpoint exija el scope que le toca (productos.read para leer, productos.write para crear).
 */
@Configuration
public class ResourceServerConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http, NimbusJwtDecoder jwtDecoder) throws Exception {
        http
            // Sin estado: no se crea sesion. El JWT es la unica credencial.
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable()) // no hay cookies que proteger; la autorizacion es por token
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.GET, "/api/productos/**").hasAuthority("SCOPE_productos.read")
                .requestMatchers(HttpMethod.POST, "/api/productos/**").hasAuthority("SCOPE_productos.write")
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth -> oauth
                .jwt(jwt -> jwt.decoder(jwtDecoder).jwtAuthenticationConverter(scopeConverter())));
        return http.build();
    }

    // Construye el decoder a partir del issuer (descubre el jwks_uri solo) y le suma dos validaciones
    // encima de las de serie (firma, exp, iss): que el emisor sea el esperado y que aud contenga sso-api.
    @Bean
    NimbusJwtDecoder jwtDecoder(@Value("${sso.issuer}") String issuer) {
        NimbusJwtDecoder decoder = (NimbusJwtDecoder) JwtDecoders.fromIssuerLocation(issuer);
        OAuth2TokenValidator<Jwt> withAudience =
            new DelegatingOAuth2TokenValidator<>(JwtValidators.createDefaultWithIssuer(issuer), new AudienceValidator("sso-api"));
        decoder.setJwtValidator(withAudience);
        return decoder;
    }

    // El claim 'scope' (cadena separada por espacios) se mapea a autoridades SCOPE_*. Es lo que leen
    // los hasAuthority de arriba. El default de Spring ya hace esto; se deja explicito para que se vea.
    private JwtAuthenticationConverter scopeConverter() {
        JwtGrantedAuthoritiesConverter authorities = new JwtGrantedAuthoritiesConverter();
        authorities.setAuthorityPrefix("SCOPE_");
        authorities.setAuthoritiesClaimName("scope");
        JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(authorities);
        return converter;
    }

    // Rechaza un token cuya audiencia no incluya este API. Sin esto, un token emitido para otro
    // recurso (otra aud) tambien pasaria: el aud es lo que ata el token a SU destinatario.
    record AudienceValidator(String audience) implements OAuth2TokenValidator<Jwt> {
        @Override
        public OAuth2TokenValidatorResult validate(Jwt token) {
            List<String> aud = token.getAudience();
            if (aud != null && aud.contains(audience)) {
                return OAuth2TokenValidatorResult.success();
            }
            return OAuth2TokenValidatorResult.failure(
                new OAuth2Error("invalid_token", "Falta la audiencia " + audience, null));
        }
    }
}

Paso 11. El SSO, la rotación y el cierre encadenado

Con todo arriba, el single sign-on ya funciona: ana entra una vez y, cuando abre una segunda aplicación que use el mismo servidor, no vuelve a escribir la contraseña. El servidor encuentra su sesión por la cookie y emite un código nuevo sin mostrar login.

Rotar las claves es un POST de administración; el solapamiento hace que ningún token vivo se corte. Y el cierre de sesión encadena los dos lados: la SPA hace POST /logout al BFF, que borra su sesión y redirige al /logout del servidor para cerrar el SSO.

curl -s -X POST http://127.0.0.1:8787/internal/rotate-keys | jq
curl -s http://127.0.0.1:8787/jwks | jq '.keys | length'   # sigue habiendo varias claves
La decisión
El SSO nace de una sola sesión en el servidor, no en cada app. Cerrar sesión cierra las dos: el BFF y el SSO. La rotación de claves es una operación aparte, con solapamiento.
Lo que descartas
Un logout que solo cierre el BFF: la ilusión de haber salido, con el SSO aún abierto. Y rotar sin solapar, que cortaría todas las sesiones a la vez.
Qué puede salir mal
El single logout completo —cerrar a la vez todas las apps donde entraste— es más difícil que esto y tiene varios estándares en competencia. Aquí cerramos el SSO y la app que inició; las otras caen en su próxima renovación.

import { randomToken } from "../src/crypto.js";

// Las pruebas son fixtures defensivos: cada una manda un ataque conocido y verifica que el AS lo
// RECHAZA. No se demuestra como robar nada; se demuestra que la defensa responde.

const ISSUER = "https://sso.localhost:8443";
const REDIRECT = "https://app.localhost:8443/login/oauth2/code/sso";
const BFF_SECRET = "test-bff-secret-0123456789";

// PKCE S256: challenge = base64url(SHA-256(verifier)).
async function pkce(): Promise<{ verifier: string; challenge: string }> {
  const verifier = randomToken(32);
  const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
  const challenge = btoa(String.fromCharCode(...new Uint8Array(digest)))
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
  return { verifier, challenge };
}

function basicAuth(): string {
  return "Basic " + btoa(`bff:${BFF_SECRET}`);
}

async function anaId(): Promise<string> {
  const row = await env.DB.prepare("SELECT id FROM users WHERE username = 'ana'").first<{ id: string }>();
  return row!.id;
}

// Obtiene un codigo de autorizacion saltandose el login: se crea la sesion directamente y se llama a
// /authorize con su cookie. Asi las pruebas se centran en el back-channel.
async function getCode(challenge: string): Promise<string> {
  const session = await createSession(env, await anaId(), 28800);
  const url = new URL(`${ISSUER}/authorize`);
  url.search = new URLSearchParams({
    response_type: "code",
    client_id: "bff",
    redirect_uri: REDIRECT,
    scope: "openid profile productos.read productos.write",
    state: "xyz",
    code_challenge: challenge,
    code_challenge_method: "S256",
    nonce: "n-1",
  }).toString();
  const res = await SELF.fetch(url, { headers: { Cookie: `__Host-AS_SESSION=${session}` }, redirect: "manual" });
  expect(res.status).toBe(302);
  return new URL(res.headers.get("Location")!).searchParams.get("code")!;
}

async function exchange(code: string, verifier: string): Promise<Response> {
  return SELF.fetch(`${ISSUER}/token`, {
    method: "POST",
    headers: { Authorization: basicAuth(), "Content-Type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({ grant_type: "authorization_code", code, redirect_uri: REDIRECT, code_verifier: verifier }),
  });
}

async function refresh(token: string): Promise<Response> {
  return SELF.fetch(`${ISSUER}/token`, {
    method: "POST",
    headers: { Authorization: basicAuth(), "Content-Type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({ grant_type: "refresh_token", refresh_token: token }),
  });
}

    expect(res.status).toBe(200);
    const body = await res.json<{ access_token: string; refresh_token: string; id_token: string; scope: string }>();
    expect(body.access_token).toBeTruthy();

  it("rechaza un code_verifier que no corresponde al challenge", async () => {

describe("Rotacion de refresh con deteccion de reuso", () => {
  it("rota el refresh y revoca la familia si se reutiliza el viejo", async () => {
    const { verifier, challenge } = await pkce();
    const first = await (await exchange(await getCode(challenge), verifier)).json<{ refresh_token: string }>();

    // Rotacion normal: el viejo se canjea, sale uno nuevo.
    const rotated = await refresh(first.refresh_token);
    expect(rotated.status).toBe(200);
    const second = await rotated.json<{ refresh_token: string }>();

    // Reuso del viejo: es senal de robo. Se niega Y se revoca la familia.
    const reuse = await refresh(first.refresh_token);
    expect(reuse.status).toBe(400);
    expect((await reuse.json<{ error: string }>()).error).toBe("invalid_grant");

    // Tras la revocacion, ni el token nuevo sirve: la familia entera quedo fuera.
    const after = await refresh(second.refresh_token);
    expect(after.status).toBe(400);
  });

El flujo, en DevTools

Entra como ana con la pestaña Network abierta y "Preserve log" encendido. Verás la cadena de redirecciones de la figura A13.3: tu clic va al BFF, de ahí un 302 al /authorize del servidor con el code_challenge en la URL, el login, un 302 de vuelta con ?code=, y el callback del BFF. Fíjate en que el code_verifier no aparece en ninguna URL: solo viaja en el /token, que es una llamada de servidor, invisible aquí.

El navegador no tiene el token

Con la sesión abierta, mira en DevTools, Application, las cookies de app.localhost: hay una cookie de sesión del BFF, HttpOnly, y nada más. En la consola, localStorage y sessionStorage están vacíos de tokens. Ahora mira la request a /api/productos en Network: no lleva Authorization desde el navegador —va la cookie—. El Bearer lo pone el BFF, en un tramo que no ves.

El scope manda, no la interfaz

Entra como ana (tiene productos.write) y agrega un producto: funciona. Cierra sesión y entra como beto (solo productos.read). El catálogo se ve, pero al intentar agregar un producto el API responde 403, y la SPA lo dice. La interfaz no cambió entre un usuario y otro: quien decide es el scope dentro del token, en el resource server.

El código robado no sirve

En el 302 de vuelta del servidor, copia el valor de ?code= antes de que el BFF lo canjee. Intenta canjearlo tú con curl, sin el code_verifier correcto:

curl -s -X POST http://127.0.0.1:8787/token \
  -u "bff:$BFF_CLIENT_SECRET" \
  -d grant_type=authorization_code -d code=EL_CODIGO \
  -d redirect_uri=https://app.localhost:8443/login/oauth2/code/sso \
  -d code_verifier=inventado | jq

La respuesta es invalid_grant: sin el verifier que el BFF generó y nunca mandó por la URL, el código no vale. Y si el BFF ya lo canjeó, el tuyo da invalid_grant igual, porque es de un solo uso.

El redirect abierto, cerrado

Pide un /authorize con una redirect_uri que no sea la registrada, por ejemplo con un host pegado:

curl -si "http://127.0.0.1:8787/authorize?response_type=code&client_id=bff&redirect_uri=https://app.localhost.evil.com/x&scope=openid&code_challenge=x&code_challenge_method=S256" | head -5

El servidor responde con una página de error y 400, no con una redirección: nunca manda el código —ni el error— a una uri que no validó. Es la figura A13.10.

El refresh robado, revocado

La prueba flow.test.ts ya lo demuestra, pero puedes verlo a mano: canjea un refresh dos veces. El primer canje rota y da uno nuevo; el segundo, con el mismo token viejo, da invalid_grant y, a partir de ahí, el token nuevo tampoco sirve: la familia quedó revocada y ana tiene que entrar de nuevo. Es la figura A13.8.

El cierre encadenado

Con la sesión abierta, pulsa "Salir". Vuelves a la pantalla de entrar. Ahora abre de nuevo https://app.localhost:8443: te pide entrar otra vez —no te deja pasar directo—, porque el logout cerró también la sesión del SSO, no solo la del BFF. Si solo se hubiera cerrado el BFF, el servidor te habría reconocido y habrías entrado sin escribir nada.

La diferencia entre las dos credenciales

Para fijar la idea de fondo: la cookie del BFF y el access token del API son dos naturalezas distintas. La cookie es una referencia opaca que se valida buscándola en Redis y se revoca borrándola al instante; el token es autovalidable, se verifica con la firma sin consultar a nadie, y por eso dura poco, porque no se puede cerrar antes de su exp.

Cómo conectar

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A01, detrás de Nginx

    El Nginx que termina TLS y pasa los X-Forwarded-* es el de A01. Aquí reparte por server_name entre dos nombres, sso.localhost y app.localhost, y es lo que hace posibles las cookies Secure y el descubrimiento por HTTPS.

  • Con A03 y A10, Redis y fallar cerrado

    Redis vuelve como almacén de la sesión del BFF, igual que en A12. Y la idea de fail-closed de A10 aparece en el servidor: un código o un refresh dudoso se niega, no se concede "por si acaso".

  • Con A11, las URLs firmadas

    A11 firmaba URLs con HMAC para dar acceso temporal a un archivo. Aquí la firma es asimétrica (ES256) y lo que se firma es la identidad y los permisos; la misma idea —un dato que se valida por su firma, no por una consulta— aplicada a los tokens.

  • Con A12, la sesión y la cookie que ya blindabas

    A12 puso la sesión en Redis y blindó la cookie con __Host-, SameSite y el token CSRF. El BFF reusa todo eso tal cual; la novedad es que, detrás de esa cookie, ahora hay tokens hacia otros servicios. A12 era el mundo de un dominio; A13 es el de varios.
