La excusa

El sistema de prácticas ya hace casi todo bien por separado: cada request valida, autoriza (WEB06) y escribe con consultas preparadas (WEB07). Lo que no está probado es qué pasa cuando dos requests tocan la misma fila en el mismo instante. Es una condición de carrera de negocio (83.6): ninguna request hace nada mal, y aun así la regla del negocio se rompe, porque las dos leen el mismo estado antes de que cualquiera lo cambie.

Leyendo models/postulaciones.php, la re-auditoría encuentra una cosa ya resuelta y tres que no:

  • H1. Un cambio de estado se decide con lo que se leyó antes. changeState lee el estado, compara en PHP y después escribe. Dos reclutadores (o dos pestañas, o un doble clic) que confirman a la vez leen los dos pendiente y escriben los dos: el estudiante recibe "aceptada" y "rechazada", y el historial dice dos veces que antes estaba pendiente.
  • H2. Una postulación retirada se puede aceptar. El retiro (delete) ya es un UPDATE condicional (AND estado_postulacion = 'pendiente'), pero el cambio de estado no mira si la fila sigue activa: si el estudiante la retira entre la lectura y la escritura del reclutador, queda retirada y aceptada, y le llega "¡Postulación aceptada!" por algo que ya no existe.
  • H3. Una reactivación entra tantas veces como se pida. Volver a postularse a una oferta retirada reactiva la fila vieja con un UPDATE … WHERE id = ?. Diez requests a la vez dan diez respuestas de éxito, diez avisos al reclutador y diez CVs subidos, de los que solo queda el último.

  1. Entra con estudiante, estudiante2 y reclutador, y busca la postulación de WEB08.

# Manda todos los pedidos a la vez con una sola llamada a curl y devuelve los códigos HTTP
function EnParalelo([object[]]$Pedidos) {
    $a = @('--parallel', '--parallel-immediate', '--parallel-max', '100')
    for ($i = 0; $i -lt $Pedidos.Count; $i++) {
        $p = $Pedidos[$i]
        if ($i -gt 0) { $a += '--next' }
        $a += @('-s', '-o', 'NUL', '-w', '%{http_code}\n', '-X', $p.Metodo,
                '-b', "lab\jar-$($p.Quien).txt", '-H', "X-CSRF-Token: $($token[$p.Quien])")
        if ($p.Json) {
            $f = "lab\carrera-$i.json"
            [IO.File]::WriteAllText((Join-Path $PWD $f), $p.Json)
            $a += @('-H', 'Content-Type: application/json', '--data-binary', "@$f")
        }
        foreach ($c in @($p.Form)) { if ($c) { $a += @('-F', $c) } }
        $a += "$Base/$($p.Ruta)"
    }
    @(& curl.exe @a | Where-Object { $_ })
}

PowerShell de por medio

EnParalelo arma una sola llamada a curl.exe: --parallel y --parallel-immediate valen para todas las transferencias, y cada --next empieza una nueva con sus propias opciones (su cookie, su token, su cuerpo). -w '%{http_code}\n' imprime el código de cada una al terminar, en el orden en que terminan. Los cuerpos JSON van por archivo por lo mismo que en WEB06: Windows PowerShell 5 quita las comillas de un argumento con JSON.

Ensanchar la ventana

Entre el SELECT y el UPDATE de changeState pasan microsegundos: diez requests a la vez pueden caer en esa ventana o no, según tu máquina. Para que la carrera se vea siempre, la guía la ensancha a propósito con una pausa de 300 ms en los dos lugares donde se decide con lo leído. Es una línea de laboratorio: se pone ahora, se deja puesta mientras arreglas (así compruebas el arreglo con la ventana abierta) y se borra al final.

Errores típicos

  • curl: option --parallel-immediate: is unknown: el curl.exe que encuentra PowerShell es anterior a 7.68 (a veces el de Git). Usa C:\Windows\System32\curl.exe o actualízalo.
  • La carrera 3 o la 4 dan todo 404: la oferta ya cerró o dejó de estar activa. Abre otra oferta con el reclutador, postúlate a ella como en WEB08 y vuelve a correr.
  • Todo da 403 Origen no permitido: ORIGENES_PERMITIDOS no se cargó; curl no manda Origin ni Sec-Fetch-Site, y requireOrigenConfiable de WEB03 lo deja pasar solo si el archivo de secretos está bien.
  • Los mensajes del script salen con letras raras en Windows PowerShell 5: es la codificación del archivo, no un error. Guárdalo como UTF-8 con BOM o córrelo con pwsh.

Paso a paso

Paso 1. La regla del cambio de estado, en una función pura

Antes de tocar la base, la regla: qué cambios se permiten. Hoy changeState solo rechaza el mismo estado. Faltan dos cosas que el paso 3 necesita:

  • El estado que vio quien confirma. Con un lock, la segunda request lee el estado nuevo, pero el reclutador que la mandó estaba mirando el viejo: aceptar o rechazar sobre algo que no vio es la carrera de H1 por otro camino. El frontend manda desde, y si no coincide con lo que hay, 409.
  • No volver a pendiente. pendiente es el único estado en el que el estudiante puede editar sus documentos (buscarEditable) o retirarse (delete). Volver ahí reabriría las dos cosas después de una revisión. La interfaz nunca lo ofrece; la regla lo hace cumplir.
<?php

declare(strict_types=1);

/**
 * Reglas de negocio del cambio de estado de una postulación (WEB10).
 *
 * Funciones puras: no tocan la base ni la sesión, así se prueban sin servidor.
 * El modelo las llama con el estado que leyó bajo SELECT ... FOR UPDATE, que es
 * el estado real en ese momento y nadie lo puede cambiar hasta el commit.
 */

const ESTADOS_POSTULACION = ['pendiente', 'en_revision', 'aceptada', 'rechazada'];

/**
 * Qué impide pasar una postulación de $actual a $nuevo, si algo lo impide.
 *
 * @param string $actual el estado de la fila, leído bajo el lock
 * @param string $desde  el estado que vio quien pide el cambio (lo manda el frontend)
 * @param string $nuevo  el estado pedido
 * @return array{0:int,1:string}|null [código HTTP, mensaje], o null si se puede
 */
function problemaCambioEstado(string $actual, string $desde, string $nuevo): ?array
{
    if (!in_array($nuevo, ESTADOS_POSTULACION, true)) {
        return [400, 'El estado no es valido'];
    }
    if (!in_array($desde, ESTADOS_POSTULACION, true)) {
        return [400, 'Falta el estado que tenía la postulación cuando la viste'];
    }
    # Otra persona (u otra pestaña) la cambió entre que la viste y que confirmaste
    if ($desde !== $actual) {
        return [409, 'La postulación cambió mientras la revisabas: ahora está ' . str_replace('_', ' ', $actual) . '. Recarga la lista.'];
    }
    if ($nuevo === $actual) {
        return [409, 'La postulación ya tiene ese estado'];
    }
    # Pendiente es el único estado en el que el estudiante puede editarla o retirarla
    if ($nuevo === 'pendiente') {
        return [409, 'Una postulación revisada no vuelve a pendiente'];
    }
    return null;
}

WHERE id = ? AND estado = 0 y mirar rowCount().
Lo que descartas
Volver a leer la fila justo antes del UPDATE: achica la ventana pero no la cierra, porque entre esa lectura y la escritura cabe otra request. O un SELECT … FOR UPDATE en validarAlta: funciona, pero el lock quedaría tomado mientras se suben los archivos, y otra request del mismo estudiante esperaría a que termine de subir.
Qué puede salir mal
rowCount() en MariaDB cuenta las filas cambiadas, no las encontradas: un UPDATE que deja todo igual da 0. Aquí no pasa, porque estado va de 0 a 1 siempre. Si copias el patrón a un UPDATE que puede no cambiar nada, compara con SELECT ROW_COUNT() o ajusta PDO::MYSQL_ATTR_FOUND_ROWS.

Paso 3. El cambio de estado, en una transacción con la fila bloqueada

El cambio de estado no cabe en un WHERE: necesita el estado anterior para el historial, el estudiante para el aviso, y escribe en tres tablas. Así que lee, decide y escribe dentro de una transacción, con la lectura bloqueando la fila:

  1. Lo que no depende de la fila, fuera de la transacción: el id y que quien actualiza siga activo.
  2. BEGIN y SELECT … FOR UPDATE: el estado real ahora, con la fila bloqueada hasta el COMMIT. Si no está activa (el estudiante la retiró), 404.
  3. problemaCambioEstado del paso 1, con lo que se leyó y lo que vio el reclutador.
  4. UPDATE, historial y aviso, y COMMIT. Cualquier corte antes deshace todo con cortar.

Es un lock pesimista: se bloquea antes de decidir, porque se espera que choquen. Un SELECT común dentro de una transacción no alcanza. En InnoDB, con el nivel de aislamiento por defecto (REPEATABLE READ), una lectura sin lock lee una foto consistente de MVCC y no espera a nadie; una lectura con FOR UPDATE lee la última versión confirmada y bloquea la fila Documentado. La falla 1 lo muestra.

    /** Deshace la transacción abierta, si hay una, y responde con el error. */
    private function cortar(string $mensaje, int $httpCode): never {
        if ($this->connection->inTransaction()) {
            $this->connection->rollBack();
        }
        $this->response->error($mensaje, -1, $httpCode);
    }

    # Cambiar estado y dejar registro en historial_estado_postulacion
    # WEB10: leer, decidir y escribir dentro de una transacción, con la fila bloqueada
    public function changeState(array $arrayData){
        $id                 = (int)($arrayData["id"] ?? 0);
        $estado_postulacion = trim($arrayData["estado_postulacion"] ?? '');
        $desde              = trim($arrayData["desde"] ?? '');
        $comentario         = trim($arrayData["comentario"] ?? '');
        $actualizado_por    = (int)($arrayData["actualizado_por"] ?? 0);

        if ($id <= 0) {
            $this->response->error("El ID es invalido", -1, 400);
        }

        if ($actualizado_por <= 0) {
            $this->response->error("El usuario que actualiza es obligatorio", -1, 400);
        }

        try {
            $stmt = $this->connection->prepare("SELECT id FROM usuarios WHERE id = ? AND estado = 1 AND estado_cuenta = 'activo'");
            $stmt->execute([$actualizado_por]);
            if (!$stmt->fetch(PDO::FETCH_ASSOC)) {
                $this->response->error("El usuario que actualiza no existe o no está activo", -1, 404);
            }

            $this->connection->beginTransaction();

            # FOR UPDATE: bloquea la fila hasta el commit. Otro cambio de estado, el retiro
            # del estudiante o una edición esperan aquí, y después leen lo que quedó.
            $stmt = $this->connection->prepare("SELECT estado_postulacion, estudiante_id, oportunidad_id
                                                FROM postulaciones
                                                WHERE id = ? AND estado = 1
                                                FOR UPDATE");
            $stmt->execute([$id]);
            $postulacion = $stmt->fetch(PDO::FETCH_ASSOC);

            if (!$postulacion) {
                $this->cortar("Postulación no encontrada", 404);
            }

            $problema = problemaCambioEstado($postulacion['estado_postulacion'], $desde, $estado_postulacion);
            if ($problema !== null) {
                $this->cortar($problema[1], $problema[0]);
            }

            $stmt = $this->connection->prepare("UPDATE postulaciones SET estado_postulacion = ? WHERE id = ?");
            $stmt->execute([$estado_postulacion, $id]);

            $query = "INSERT INTO historial_estado_postulacion (postulacion_id, estado_anterior, estado_nuevo, comentario, actualizado_por)
                      VALUES (?, ?, ?, ?, ?)";
            $stmt = $this->connection->prepare($query);
            $stmt->execute([$id, $postulacion['estado_postulacion'], $estado_postulacion, $comentario !== '' ? $comentario : null, $actualizado_por]);

            # El título se lee aparte: un FOR UPDATE con JOIN bloquearía también la oferta
            $stmt = $this->connection->prepare("SELECT titulo FROM oportunidades WHERE id = ?");
            $stmt->execute([(int)$postulacion['oportunidad_id']]);
            $titulo_oferta = (string)$stmt->fetchColumn();

            # Notificación al estudiante, en la misma transacción: si algo falla, no se avisa nada
            $titulo = $estado_postulacion === 'aceptada' ? "🎉 ¡Postulación Aceptada!" : "Actualización de tu postulación";
            $mensaje = $comentario !== ''
                ? $comentario
                : "Tu postulación para \"{$titulo_oferta}\" cambió a: " . str_replace('_', ' ', $estado_postulacion) . ".";
            crearNotificacion($this->connection, (int)$postulacion['estudiante_id'], $titulo, $mensaje,
                "#/oferta/" . (int)$postulacion['oportunidad_id']);

            $this->connection->commit();

            $this->response->success("Estado de la postulación actualizado");
        } catch (PDOException $e) {
            if ($this->connection->inTransaction()) {
                $this->connection->rollBack();
            }
            Response::error("Error", -1, 500);
            //Response::debugError($e);
        }
    }

Arriba del archivo, junto a los otros require_once:

require_once __DIR__ . "/../core/reglas-postulacion.php";

Con la pausa puesta, ponla después del fetch del SELECT … FOR UPDATE, que es la lectura nueva. Ahora la pausa pasa con la fila bloqueada: las otras requests esperan detrás, y la carrera 1 tarda unos 300 ms por request (la cuenta: 10 requests en fila, unos 3 segundos en total).

La decisión
SELECT … FOR UPDATE sobre postulaciones solo, y el título de la oferta en otra consulta.
Lo que descartas
Un FOR UPDATE con el JOIN a oportunidades, como estaba la lectura: bloquearía también la fila de la oferta, y dos cambios de estado de postulaciones distintas a la misma oferta se esperarían entre sí sin motivo. O LOCK TABLES: frena todas las postulaciones de todos.
Qué puede salir mal
Una request que se queda con el lock (un aviso que tarda, una pausa olvidada): las demás esperan hasta innodb_lock_wait_timeout, 50 segundos por defecto Documentado, y después reciben un error que aquí sale como 500. Por eso dentro de la transacción solo va lo que toca la base.

Fallas provocadas

Las tres con la pausa puesta otra vez después del fetch del FOR UPDATE y al principio de la reactivación, para que la ventana no dependa de la suerte.

Falla 1. Una transacción sin lock. Borra solo las palabras FOR UPDATE del SELECT de changeState, y deja el beginTransaction y el commit. Corre lab\web10.ps1 -Carrera estado. El diseño espera MAL en las tres líneas: cada request lee pendiente en su propia foto consistente, ninguna espera a nadie, y la regla de desde deja pasar a todas porque todas vieron lo mismo que leyeron. Es la diferencia de el paso 3: la transacción hace que todo se confirme o se deshaga junto, el lock hace que nadie lea en el medio. Vuelve a poner FOR UPDATE.

Falla 2. Una reactivación sin condición. En registrar, cambia WHERE id = ? AND estado = 0 por WHERE id = ? y corre lab\web10.ps1 -Carrera reactivar. El diseño espera varios 200 y varios avisos, como antes del arreglo: el rowCount() sigue ahí, pero sin la condición siempre cambia una fila. Vuelve la condición.

Falla 3. Sin mirar lo que vio el reclutador. En problemaCambioEstado, cambia if ($desde !== $actual) { por if (false) {. La prueba pura da tres FALLA: "la vio pendiente, ya está aceptada: 409", "el 409 dice el estado de ahora" y "dos cambios desde pendiente, en serie: 200 y 409". La carrera 1 también da MAL, pero distinto que en la falla 1: ahora las requests entran de a una, y el historial queda coherente (cada fila con el estado anterior de verdad), pero entra más de un cambio y el estudiante recibe más de un aviso. Vuelve la línea.

FallaLo que viste
1. Sin FOR UPDATE: códigos, historial y avisos 
2. Sin AND estado = 0: códigos y avisos 
3. Sin desde: la prueba, y el historial de la carrera 1

Limitaciones

  • Los archivos de la request que pierde quedan huérfanos. El alta valida, sube los archivos y recién después escribe: la que recibe 409 ya subió su CV. Cada corrida de las carreras 3 y 4 deja hasta 2 (N − 1) PDFs sin dueño (la cuenta: N − 1 perdedoras en cada una). Ya está anotado en docs/SUBIDA_ARCHIVOS.md, sección 9; el arreglo es borrar el archivo en el 409 o barrer los que ninguna fila nombra.
  • La oferta no se bloquea. validarAlta lee si la oferta sigue activa sin lock: una oferta que se cierra en el mismo instante puede recibir una última postulación. Para esta aplicación es aceptable; si no lo fuera, el alta tomaría un FOR UPDATE de la oferta, o el cierre se haría con un UPDATE condicional que las postulaciones respeten.
  • No hay cupos. El esquema no tiene un límite de plazas por oferta. Si se agrega, aceptar consume el cupo con el UPDATE … WHERE cupos > 0 de 83.6, dentro de la misma transacción del paso 3.
  • La lista del reclutador queda vieja. Después de un 409, la pantalla sigue mostrando el estado anterior hasta que recarga: el mensaje lo pide, pero no recarga sola.
  • Una carrera que no se provocó no se probó. El script cubre las cuatro de la re-auditoría. Cualquier otro "leer, decidir en PHP y escribir" (las solicitudes de publicación, el cambio de contraseña) tiene la misma forma, y se busca igual: un SELECT seguido de un if y de un UPDATE sin la condición en el WHERE.
  • Costo. Un lock de fila durante una transacción de cuatro sentencias. Dos cambios de estado a la misma postulación esperan uno detrás del otro; a postulaciones distintas, no.
  • Nada se ejecutó contra tu sistema al escribir esta guía. La prueba pura se corrió sobre copias; lo que muestran las carreras sale de leer el código, y las tablas son tuyas.
