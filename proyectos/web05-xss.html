XSS en el feed de oportunidades

Tu frontend escapa bien el texto. Lo que queda abierto son las URL que vienen de la base y una puerta, dangerouslySetInnerHTML, que nadie cerró con llave.

Al terminar podrás

  • Ubicar, en tu frontend de React y en tu API, cada lugar donde un texto escrito por otra persona termina en pantalla, y decir qué lo neutraliza hoy.
  • Probar con un payload mínimo que React escapa el texto y que la API, abierta como documento, ya no interpreta HTML (lo que cerró WEB01).
  • Cerrar el sumidero que queda, las URL guardadas en la base que llegan a un href o un src, con una función de diez líneas probada con node --test.
  • Dejar dos reglas de oxlint que rompen el lint si alguien vuelve a abrir la puerta, y saber qué se lleva un XSS aunque la cookie sea HttpOnly.

La excusa

El feed muestra textos que escribió otra persona: el título y la descripción de una oferta (los escribe un reclutador), el mensaje de presentación de una postulación (un estudiante), un aviso masivo (un administrador), y los enlaces a los documentos que cada uno subió. Si alguno de esos textos llega al navegador como código y no como texto, es un XSS almacenado: lo escribe una persona una vez y se ejecuta en el navegador de todas las que lo vean.

Leído el código, tu sistema está mejor de lo que suele estar uno de este tamaño. Esta guía lo comprueba con tus propias manos, cierra lo que queda y deja una alarma para el día que alguien quiera "darle formato a la descripción". Hay cuatro caminos de un dato a la pantalla:

Lo que está en juego: un script que corre en el origen del frontend no necesita robar la cookie. La cookie es HttpOnly y no la puede leer, pero tampoco le hace falta: apiFetch ya la manda sola y agrega el token CSRF que tiene en memoria. Para tu API, ese script es la persona.

Paso a paso

Paso 1. El payload mínimo, antes de tocar nada

Primero se mira, después se cambia. Como reclutador, edita la oferta y pon esto en la descripción:

Práctica de backend. <img src=x onerror="console.log('xss', document.domain)">

Es el payload más chico que delata un XSS: una imagen que no carga y un console.log. No roba nada y no sale de tu máquina. Ahora, como estudiante, abre el feed y el detalle de la oferta con DevTools abierto en Console:

  • Lo que espera el diseño: la descripción se ve con la etiqueta escrita, <img src=x …>, como texto, y Console no muestra xss. En Elements, el <p> tiene un nodo de texto, no un <img>.
  • Por qué: {oportunidad.descripcion} en JSX termina en un nodo de texto (textContent, no innerHTML). Es el escape del contexto "texto de HTML", y React lo hace siempre Documentado.

Después, en la misma sesión, abre la API como si fuera una página: http://localhost/SistemaControlPracticas/api/endpoints/oportunidades.php. El navegador tiene que mostrar el JSON como texto, sin ejecutar nada. Antes de WEB01, PHP respondía text/html, el navegador armaba el <img> y el console.log corría en el origen de Apache: era el hallazgo 5 de la auditoría. Lo vuelves a provocar en la falla 3.

La decisión
Probar con un payload que solo escribe en Console, sobre tu propia oferta, en tu laboratorio.
Lo que descartas
Payloads de listas públicas con evasión de filtros: no aportan nada contra React (que no filtra, escapa) y la regla de esta parte es payload mínimo y solo contra tu laboratorio.
Qué puede salir mal
Pegar el payload en un campo que el frontend recorta o valida (el título tiene largo máximo). Si el formulario lo rechaza, la prueba no dice nada de React: usa la descripción, que es texto largo.

Paso 2. enlaceSeguro()

El único sumidero que queda abierto es el de las URL: un href o un src con un valor que viene de la base. React 19 cambia un javascript: en esos atributos por una URL que lanza un error Documentado, pero no hace nada con data:, y no protege los otros sumideros de URL (window.open, location.href). La regla que sirve en cualquier versión y en cualquier sumidero es una lista permitida de esquemas:

  1. Si no es un texto con algo adentro, no hay enlace.
  2. Se interpreta con el mismo parser que usa el navegador, new URL(). Si no es una URL absoluta, no hay enlace.
  3. Si el esquema es http: o https:, se devuelve la URL ya normalizada. Cualquier otro, no hay enlace.
// Una URL que viene de datos (la base, la API, la ruta) solo llega a un href o un src
// si es absoluta y su esquema es http o https. Todo lo demás (javascript:, data:,
// vbscript:, una ruta relativa, algo mal formado) devuelve null y el enlace queda sin destino.
const ESQUEMAS_PERMITIDOS = new Set(["http:", "https:"]);

export function enlaceSeguro(valor) {
  if (typeof valor !== "string" || valor.trim() === "") return null;
  let url;
  try {
    url = new URL(valor.trim());
  } catch {
    return null;
  }
  return ESQUEMAS_PERMITIDOS.has(url.protocol) ? url.href : null;
}

Usar new URL() y no una expresión regular es la decisión importante. El navegador limpia la URL antes de decidir el esquema: quita espacios del principio, borra tabulaciones y saltos de línea de adentro, y pasa el esquema a minúsculas. Por eso "java\tscript:…" y " JavaScript:…" son un javascript: para el navegador, y una regex que busca ^javascript: los deja pasar. Con new URL(), tu función ve exactamente lo que va a ver el navegador. La prueba del paso 5 trae esos casos.

La decisión
Una lista permitida de dos esquemas, comprobada con el parser del navegador, y null si no pasa.
Lo que descartas
Una lista prohibida (javascript:, data:): siempre falta uno. Y comparar el prefijo de la URL contra el almacenamiento, como hace esUrlPermitida en PHP: sería más estricto, pero obliga al frontend a conocer STORAGE_PUBLIC_URL, que cambia entre local y S3. La API ya hace esa comprobación al guardar; el frontend solo necesita que ninguna URL ejecute código.
Qué puede salir mal
Usarla en un enlace relativo de la propia app (#/oferta/3): devuelve null y el enlace muere. Es para URL que vienen de datos; las rutas internas usan irA(), que siempre arma un #/….

Es el hallazgo 5 de la auditoría de octubre. nosniff no ayuda aquí: le impide al navegador cambiar el tipo, y text/html ya es el tipo. La fila de Content-Type del script da MAL. Descomenta la línea.

Limitaciones

  • Esto es una capa. Si a pesar de todo corre un script en el frontend, la segunda capa es la CSP, que le impide al navegador ejecutar lo que no viene de tu bundle. Es WEB09, y M78 la explica.
  • Los PDF en el iframe. La vista previa de PostulantesVentana carga el PDF del postulante. El visor de PDF del navegador corre aparte de la página, pero un PDF que no es PDF es otra historia: el tipo real del archivo se comprueba al subirlo, en WEB08.
  • Las dependencias del frontend. Un paquete de node_modules con código malicioso corre en el mismo origen y nada de esta guía lo frena. Eso es cadena de suministro.
  • El patrón del script reconoce una forma. Un sumidero escrito de otra manera (window.open(p.cv_url), una variable con otro nombre) no lo cuenta. La regla es de equipo: toda URL que viene de datos pasa por enlaceSeguro.
  • Sin costo medible. Diez llamadas a new URL() por pantalla no se notan; no hay nada que medir.
  • Nada se ejecutó al escribir esta guía. Lo que espera Console y lo que muestra Elements sale de leer el código y la documentación de React; la tabla de las fallas es tuya.

Cómo conectar

Esta guía funciona sola. Si quieres juntarla con otras:

  • Con WEB01, lo que no debe verse

    La falla 3 deshace un pedazo de WEB01 y muestra por qué el Content-Type va en Response::json y no en cada endpoint.

  • Con WEB03 y WEB04

    Las dos dejaron dicho que un XSS en un origen permitido lo cambia todo. La figura WEB05.2 es esa frase dibujada: el script pasa el Origin de WEB03 y lee las respuestas que CORS de WEB04 le permite leer al frontend.

  • Con WEB02, la sesión

    La cookie HttpOnly de WEB02 es la razón por la que el script no se la lleva; la versión de sesión es lo que permite cortarlo después, cerrando todas las sesiones de la víctima.

  • Con M77, XSS y el DOM

    Los contextos de salida están en M77; esta guía usa dos, texto de HTML (lo hace React) y URL (lo hace enlaceSeguro), y deja el de HTML crudo cerrado con lint.
