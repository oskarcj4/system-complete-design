La excusa

Las reglas de SEC00 a SEC06 buscan ataques que ya conoces: una fuerza bruta, un escaneo, una shell. Quien ya entró con una clave robada no hace nada de eso: mira tablas, lee archivos de configuración y prueba lo que encuentra. Para eso no hay umbral que valga.

Un señuelo invierte el problema. Es algo que nadie legítimo usa, así que cualquier uso es un ataque, como la cuenta señuelo de M38 o los señuelos que propone M59 para Tienda Norte: una llave falsa en la configuración y una fila trampa en la tabla de clientes. Esta guía planta cuatro, cada uno con su alerta, su prueba y su emulación.

Las fronteras. Nada sale de tu máquina. Los señuelos no tienen valor real: el token no abre nada, la cuenta no tiene clave que funcione, las tarjetas son números de prueba conocidos y las llaves de AWS son texto al azar. Las emulaciones solo apuntan a 127.0.0.1 y a tu servidor.

Qué es un señuelo

Analogía

Un billete marcado en la caja de un banco. Ningún cajero lo entrega, así que si aparece afuera, alguien lo sacó. No hace falta vigilar cada billete: alcanza con saber cuáles son los marcados.

Dos cosas lo arruinan: que se note (un nombre como trampa, una respuesta distinta, un comentario) y que lo toque alguien del equipo sin saberlo. La primera se cuida al plantarlo; la segunda, con el inventario del paso 7.

Los endpoints

Los de SEC00. Cambia uno por dentro, sin cambiar lo que responde:

GET /api/pedidos/{id}

Con el token señuelo en Authorization, escribe el evento senuelo_token y responde igual que con cualquier token desconocido.

Códigos de respuesta

  • 200Un pedido propio, con un token de sesión válido.
  • 401Token desconocido: un token que no existe, o el señuelo.
  • 404No existe: un pedido ajeno o inexistente.

Dependencias

Ninguna nueva. La API sigue con las de SEC00, PostgreSQL 18 escribe su log en JSON con log_destination = jsonlog Documentado, auditd es el de SEC06 y las pruebas, las de SEC05.

INSERT INTO usuarios (usuario, sal, hash)
VALUES ('admin_respaldo', md5(random()::text), encode(sha256(random()::text::bytea), 'hex'))

  1. La sal y el hash son al azar: md5 de un número aleatorio da 32 caracteres hexadecimales, como una sal real, y sha256 da 64, como un hash de scrypt. Ninguna clave da ese hash, así que la cuenta nunca entra. ON CONFLICT deja correr el archivo dos veces sin error.

def conectar():
    return psycopg.connect(DSN, autocommit=True)


def ip_de(request: Request) -> str:
    return request.headers.get("x-real-ip", "desconocida")
  1. La única línea nueva de este bloque. Sin la variable, SENUELO queda vacío y la API funciona igual que en SEC00.

class Credenciales(BaseModel):
    usuario: str
    clave: str


def clave_correcta(clave: str, sal: str, esperado: str) -> bool:
    calculado = hashlib.scrypt(clave.encode(), salt=bytes.fromhex(sal), n=2**14, r=8, p=1, dklen=32)
    return hmac.compare_digest(calculado.hex(), esperado)


@app.post("/api/login")
def login(datos: Credenciales, request: Request):
    with conectar() as db:
        fila = db.execute("SELECT id, sal, hash FROM usuarios WHERE usuario = %s", (datos.usuario,)).fetchone()
    if fila is None or not clave_correcta(datos.clave, fila[1], fila[2]):
        evento("login_fallido", usuario=datos.usuario, ip=ip_de(request))
        raise HTTPException(401, "Usuario o clave incorrectos")
    token = secrets.token_urlsafe(32)
    SESIONES[token] = (fila[0], datos.usuario)
    evento("login_ok", usuario=datos.usuario, ip=ip_de(request))
    return {"token": token}
  1. Igual que en SEC00. Un intento con admin_respaldo termina en login_fallido, porque ninguna clave da su hash: la cuenta del paso 1 no necesita código.

        raise HTTPException(401, "Token desconocido")
    quien = SESIONES.get(token)
    if quien is None:

Errores típicos

  • El contenedor api no arranca: required variable TIENDA_SENUELO_TOKEN is missing a value: Falta la línea en .env. Es a propósito: sin ella, el señuelo no funcionaría y nadie se daría cuenta.

En palabras, antes del código

-- (1)
CREATE OR REPLACE FUNCTION registrar_acceso_pci(objeto text) RETURNS boolean
LANGUAGE plpgsql VOLATILE AS $$
BEGIN
  RAISE LOG 'SENUELO tocado: % por % desde % (%)',
    objeto, session_user, coalesce(inet_client_addr()::text, 'local'), current_setting('application_name');
  RETURN true;
END
$$;

-- (2)
CREATE OR REPLACE VIEW clientes_tarjetas AS
SELECT * FROM (VALUES
    (1, 'Marta Ríos', '4111 1111 1111 1111', '09/27'),
    (2, 'Jorge Paz',  '5500 0000 0000 0004', '03/28'),
    (3, 'Lucía Vera', '3400 000000 00009',   '11/26')
) AS t (id, titular, tarjeta, vence)
-- (3)
WHERE registrar_acceso_pci('clientes_tarjetas');
  1. RAISE LOG escribe en el log del servidor con nivel LOG, que el servidor guarda con la configuración por defecto y que no se le manda al cliente Documentado. VOLATILE obliga a PostgreSQL a llamarla de nuevo para cada fila. El nombre parece de cumplimiento normativo, no de trampa.
  2. Las filas son valores fijos, no una tabla: no hay una tabla debajo que alguien pueda leer sin pasar por la vista, ni siquiera un superusuario. Los números son tarjetas de prueba conocidas, que no cobran nada.
  3. La condición llama a la función, que devuelve true: las tres filas salen, y el log queda escrito.

Limitaciones

  • Quien lee la configuración lo sabe. La excepción de gitleaks.toml nombra el archivo, la definición de la vista muestra la función y .env tiene el token. Un atacante cuidadoso que lea todo puede esquivar los señuelos.
  • El volcado no avisa. pg_dump no consulta la vista (falla 3). La cuenta señuelo cubre ese caso solo si alguien la prueba después.
  • El token solo avisa donde se usa. En el laboratorio la API escucha en 127.0.0.1: solo tú puedes usarlo. Si el repositorio es público (SEC02 lo pide), el token está a la vista de cualquiera, pero no abre nada.
  • El archivo avisa con root. Quien tiene root puede borrar la regla de auditd antes de leer. La vigilancia de /etc/audit/ de SEC06 lo anota, pero no lo impide.
  • Las cuatro reglas no dicen quién. Dicen desde qué IP o con qué auid. Llegar a una persona es trabajo del incidente, como en SEC06.

Costo y tiempo, con la cuenta a mano

No hay costo nuevo. El log JSON de PostgreSQL crece con cada mensaje del servidor; supuesto: con los checkpoint y arranques de un laboratorio, unas decenas de líneas por día. El costo real es de personas: cada alerta de un señuelo pide una respuesta, y la tabla del paso 7 dice cuántas fueron de verdad. Si en una semana fueron cero de verdad y una tuya, el costo es una pregunta al equipo.

Qué cambia en producción

  • Llaves de nube reales sin permisos, que avisan desde el proveedor cuando alguien las usa (servicios como Canarytokens las ofrecen para AWS Documentado).
  • Señuelos en el directorio de la empresa, como la cuenta con SPN de M38.
  • El inventario en el gestor de secretos del equipo de seguridad, con dueños y fechas de rotación.
  • Un playbook por señuelo, con la contención que le toca, y el triaje que en SEC08 hace un agente.
