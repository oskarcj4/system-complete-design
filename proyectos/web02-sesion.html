Sesión y login seguros

Una cookie firmada no se puede revocar: el servidor no guarda nada. Se le agrega una versión que la base controla, y al login, un límite de intentos y un tiempo parejo.

Al terminar podrás

  • Explicar por qué una cookie firmada sin estado no se puede revocar, y agregarle una versión que la base controla.
  • Cerrar todas las demás sesiones de una persona cuando cambia su contraseña, sin sacar a la pestaña que la cambió.
  • Limitar los intentos de login por cuenta y por IP en una ventana de 15 minutos, con un 429 y Retry-After.
  • Hacer que el login tarde lo mismo exista o no la cuenta, y comparar la IP de la cookie entera, no por prefijo.

La excusa

Una estudiante entra al sistema desde una computadora del laboratorio de la facultad y se olvida de cerrar la sesión. Al día siguiente se da cuenta y cambia la contraseña desde su casa. Con el código de hoy, la sesión del laboratorio sigue abierta hasta que vence la cookie: la cookie es base64(json)|hmac, el servidor no guarda nada y no tiene cómo saber que esa copia ya no debería valer. Cambiar la contraseña no cambia la firma.

Mientras tanto, alguien prueba contraseñas contra login.php. No hay límite: puede intentar todas las que quiera. Y aunque el mensaje de error es el mismo para un usuario que no existe y para una contraseña incorrecta, la respuesta llega antes cuando el usuario no existe, porque password_verify solo corre si la base devolvió una fila. Esta guía cierra los cuatro hallazgos de sesión de la re-auditoría (C, D y E en WEB00).

El viaje, por adelantado

Los endpoints

El frontend no cambia: apiFetch ya guarda cualquier csrfToken que venga en data, así que la respuesta del cambio de contraseña le actualiza el token sin tocar CambiarPasswordForm.jsx. Lo que sí pasa una vez: al aplicar la guía, todas las cookies emitidas antes dejan de valer, porque no traen versión. Cada persona vuelve a entrar una vez.

Qué necesitas

El laboratorio de WEB00 y la respuesta central de WEB01 (Response::serverError y Env::exigir). Si no hiciste WEB01, cambia cada Response::serverError($e) de esta guía por el Response::error("Error", -1, 500) de siempre y quita la línea de exigirHash. No se instala nada.

La infraestructura

Una migración agrega la columna de la versión y la tabla de intentos. Sigue el formato de las que ya están en database/migrations/, con la reversa comentada al final.

-- Fecha: 2026-11-09
--
--   - usuarios.version_sesion: sube al cambiar la contraseña. Una cookie con otra
--     versión deja de valer, aunque su firma sea correcta.
--   - intentos_login: un renglón por intento fallido, por cuenta y por IP.

    ADD COLUMN version_sesion INT UNSIGNED NOT NULL DEFAULT 1

    INDEX idx_intentos_clave_fecha (clave, creado)

Y una variable nueva en el .env (en C:\xampp\secretos\practicas.env si hiciste WEB01): un hash de bcrypt de una contraseña que nadie conoce, para el paso 4. Genéralo con PHP y pega la salida:

C:\xampp\php\php.exe -r "echo password_hash(bin2hex(random_bytes(16)), PASSWORD_DEFAULT), PHP_EOL;"
# Hash de relleno para el login (paso 4 de WEB02). Mismo costo que los de usuarios.password_hash.
LOGIN_HASH_RELLENO=$2y$10$...los 53 caracteres que imprimió el comando...
La decisión
Guardar la versión en la fila del usuario, que ya se lee en cada request, y los intentos en una tabla propia con un índice por clave y fecha.
Lo que descartas
Pasar a sesiones del lado del servidor (una tabla sesiones con un id aleatorio en la cookie): es la solución más flexible, porque permite cerrar una sesión concreta, pero cambia el formato de la cookie y todo checkAuth. Con la versión, la cookie sigue igual y se gana lo que pidió la re-auditoría: que cambiar la contraseña corte las demás. Tampoco se usa Redis para los intentos: el sistema no lo tiene y MariaDB alcanza para este volumen.
Qué puede salir mal
Que el hash de relleno tenga otro costo que los de la base. En PHP 8.3, PASSWORD_DEFAULT es bcrypt con costo 10, y los hashes de seed.sql empiezan con $2y$10$: el de relleno tiene que empezar igual. PHP 8.4 subió el costo por defecto a 12 Documentado; si actualizas, los hashes nuevos y el relleno tienen que seguir coincidiendo.

Paso a paso

Paso 1. La cookie, en un solo lugar

Hoy las opciones de setcookie se repiten en login() y en logout(), y el paso 5 necesita una tercera copia. Un archivo nuevo las junta, y de paso arma el payload con la versión.

  1. opcionesCookie devuelve las opciones de siempre, leídas del .env.
  2. emitirSesion arma el payload con los datos del usuario, la versión, el vencimiento y la IP, lo firma y lo envía.
  3. También deja la cookie nueva en $_COOKIE, porque csrfToken() se calcula sobre ella en la misma request.
  4. mismaIp compara la IP guardada con la actual, entera.
<?php

declare(strict_types=1);

/** Opciones de la cookie de sesión: las usan el login, el cambio de contraseña y el logout. */
function opcionesCookie(int $expira): array
{
    return [
        'expires'  => $expira,
        'path'     => '/',
        'domain'   => COOKIE_DOMAIN,
        'secure'   => filter_var(COOKIE_SECURE, FILTER_VALIDATE_BOOLEAN),
        'httponly' => filter_var(COOKIE_HTTPONLY, FILTER_VALIDATE_BOOLEAN),
        'samesite' => COOKIE_SAMESITE,
    ];
}

/**
 * Firma y envía la cookie. $usuario trae id, username, name, institucion_id, roles e isAdmin;
 * $version es usuarios.version_sesion en este momento.
 */
function emitirSesion(array $usuario, int $version): array
{
    $payload = [
        'id'             => (int)$usuario['id'],
        'username'       => (string)$usuario['username'],
        'name'           => (string)$usuario['name'],
        'institucion_id' => $usuario['institucion_id'],
        'roles'          => (string)$usuario['roles'],
        'isAdmin'        => (bool)$usuario['isAdmin'],
        'v'              => $version,
        'exp'            => time() + (int)COOKIE_LIFETIME,
        'ip'             => (string)($_SERVER['REMOTE_ADDR'] ?? ''),
    ];
    $json  = json_encode($payload, JSON_UNESCAPED_UNICODE | JSON_THROW_ON_ERROR);
    $valor = base64_encode($json) . '|' . hash_hmac('sha256', $json, COOKIE_KEY);

    setcookie(COOKIE_NAME, $valor, opcionesCookie($payload['exp']));
    $_COOKIE[COOKIE_NAME] = $valor;   # csrfToken() se calcula sobre la cookie nueva
    return $payload;
}

function borrarSesion(): void
{
    setcookie(COOKIE_NAME, '', opcionesCookie(time() - 3600));
    unset($_COOKIE[COOKIE_NAME]);
}

/** La IP de la cookie tiene que ser exactamente la de la request, no un prefijo. */
function mismaIp(string $guardada, string $actual): bool
{
    return $guardada !== '' && hash_equals($guardada, $actual);
}

PHP de por medio

El archivo solo define funciones: no corre nada al incluirlo, y por eso la prueba del final puede cargarlo sin base ni .env. Las constantes como COOKIE_KEY se leen recién cuando se llama a la función. hash_equals compara dos textos en tiempo constante; aquí no hace falta por el tiempo (la IP no es secreta), pero deja la comparación en una sola forma para todo el archivo.

La decisión
Un solo lugar arma, firma y envía la cookie; el formato base64(json)|hmac no cambia, así que checkAuth sigue leyendo lo mismo más un campo v.
Lo que descartas
Copiar el setcookie a usuarios.php para el cambio de contraseña: sería la tercera copia, y la primera que se desincroniza cuando alguien cambie SameSite en el .env.
Qué puede salir mal
Llamar a emitirSesion después de haber escrito algo en la salida: setcookie falla con Cannot modify header information - headers already sent y el cambio de contraseña queda hecho sin cookie nueva. En los endpoints de este repositorio nada imprime antes de Response; si agregas un echo de depuración, ese es el síntoma.

Paso 2. La IP entera y la versión

Dos cambios en la lectura de la cookie. El primero está en checkAuth: la comparación de hoy es strpos($_SERVER['REMOTE_ADDR'], $data['ip']) !== 0, que acepta cualquier IP que empiece igual. Una cookie emitida para 127.0.0.1 vale desde 127.0.0.10, y una con ip vacía vale desde cualquier lado, porque en PHP 8 strpos con una aguja vacía devuelve 0. Reemplaza el bloque de la IP al final de checkAuth:

<?php

declare(strict_types=1);

require_once __DIR__ . '/sesion.php';

# ... checkAuth() igual hasta las validaciones de tiempo ...

    # La cookie vale solo desde la IP exacta que la recibió
    if (!isset($data['ip']) || !mismaIp((string)$data['ip'], (string)($_SERVER['REMOTE_ADDR'] ?? ''))) {
        return null;
    }

    # Sin versión: es una cookie emitida antes de esta guía, y hay que volver a entrar
    if (!isset($data['v']) || !is_int($data['v'])) {
        return null;
    }

    return $data;
}

El segundo está en refrescarAuthDesdeBD, que ya lee la fila del usuario en cada request: ahora también trae version_sesion y la compara con la de la cookie.

function refrescarAuthDesdeBD(array $data): array
{
    $stmt = Connection::load()->prepare("SELECT u.estado_cuenta, u.version_sesion,
                                                (SELECT GROUP_CONCAT(ar.id_rol ORDER BY ar.id_rol)
                                                   FROM asignaciones_roles ar
                                                  WHERE ar.id_usuario = u.id AND ar.estado = 1) AS roles
                                           FROM usuarios u WHERE u.id = ? AND u.estado = 1");
    $stmt->execute([(int)($data['id'] ?? 0)]);
    $fila = $stmt->fetch(PDO::FETCH_ASSOC);

    # Cuenta suspendida, borrada o con una versión de sesión más nueva que la de la cookie
    if (!$fila || $fila['estado_cuenta'] !== 'activo'
        || (int)$fila['version_sesion'] !== (int)($data['v'] ?? -1)) {
        Response::error("Tu sesión ya no es válida. Vuelve a iniciar sesión.", -2);
    }

    $roles = $fila['roles'] !== null ? array_map('intval', explode(',', (string)$fila['roles'])) : [];
    $data['roles']   = implode(',', $roles);
    $data['isAdmin'] = in_array(2, $roles, true);
    return $data;
}
La decisión
Comparar la IP entera y la versión en los dos lugares donde ya se valida la cookie: la firma y la fecha en checkAuth, el estado de la cuenta en refrescarAuthDesdeBD.
Lo que descartas
Quitar el ligado a la IP, que es lo que hacen muchos sistemas porque un teléfono cambia de IP al pasar de wifi a datos. Es razonable, pero el repositorio ya lo decidió así y la guía no cambia esa decisión, solo arregla la comparación. Si lo quitas, la versión de sesión sigue protegiéndote al cambiar la contraseña.
Qué puede salir mal
Que localhost resuelva a veces a 127.0.0.1 y a veces a ::1: con la comparación exacta, la cookie emitida por IPv4 no vale por IPv6 y la sesión "se cae sola". Lo provocas en la falla 3. Detrás del proxy de Vite la IP es siempre la de la conexión del proxy, así que en el laboratorio no pasa.

Paso 3. El límite de intentos

La clase lleva la cuenta en intentos_login. Cada fallo deja dos renglones, uno con la clave de la cuenta y otro con la de la IP; un login correcto borra los de la cuenta.

<?php

declare(strict_types=1);

/**
 * Intentos de login fallidos en una ventana deslizante, por cuenta y por IP.
 * Un login correcto borra los fallos de la cuenta; los de la IP se quedan hasta salir de la ventana.
 */
final class LoginThrottle
{
    private const VENTANA_MIN = 15;
    private const MAX_POR_CUENTA = 5;
    private const MAX_POR_IP = 20;

    /** @return array{cuenta: string, ip: string} */
    public static function claves(string $identificador, string $ip): array
    {
        return [
            'cuenta' => 'cuenta:' . mb_strtolower(trim($identificador)),
            'ip'     => 'ip:' . $ip,
        ];
    }

    public static function bloqueado(PDO $db, array $claves): bool
    {
        $stmt = $db->prepare(
            "SELECT clave, COUNT(*) FROM intentos_login
              WHERE clave IN (?, ?) AND creado > NOW() - INTERVAL " . self::VENTANA_MIN . " MINUTE
              GROUP BY clave"
        );
        $stmt->execute([$claves['cuenta'], $claves['ip']]);
        $n = $stmt->fetchAll(PDO::FETCH_KEY_PAIR);
        return (int)($n[$claves['cuenta']] ?? 0) >= self::MAX_POR_CUENTA
            || (int)($n[$claves['ip']] ?? 0) >= self::MAX_POR_IP;
    }

    public static function registrarFallo(PDO $db, array $claves): void
    {
        $db->prepare("INSERT INTO intentos_login (clave) VALUES (?), (?)")
           ->execute([$claves['cuenta'], $claves['ip']]);
        if (random_int(1, 100) === 1) {   # de vez en cuando, borra lo que tiene más de un día
            $db->exec("DELETE FROM intentos_login WHERE creado < NOW() - INTERVAL 1 DAY");
        }
    }

    public static function limpiarCuenta(PDO $db, array $claves): void
    {
        $db->prepare("DELETE FROM intentos_login WHERE clave = ?")->execute([$claves['cuenta']]);
    }

    public static function segundosDeEspera(): int
    {
        return self::VENTANA_MIN * 60;
    }
}

PHP de por medio

PDO::FETCH_KEY_PAIR convierte un resultado de dos columnas en un arreglo clave => valor: aquí, ['cuenta:estudiante' => 5, 'ip:127.0.0.1' => 7]. Si una clave no tuvo fallos, no aparece, y por eso el ?? 0. Concatenar self::VENTANA_MIN en el SQL es seguro porque es una constante entera del código, no un dato de la request; el resto va como parámetro.

La decisión
Dos contadores: 5 fallos por cuenta frenan a quien insiste con una persona; 20 por IP frenan a quien prueba una contraseña común contra muchas cuentas (password spraying, que M59 detecta del otro lado). La cuenta se normaliza a minúsculas y sin espacios, que es como la compara MariaDB con utf8mb4_unicode_ci.
Lo que descartas
Bloquear la cuenta hasta que un administrador la desbloquee: convierte el límite en una forma barata de dejar sin acceso a cualquiera cuyo usuario conozcas. Con una ventana de 15 minutos, el bloqueo se levanta solo. Tampoco se usa un CAPTCHA: agrega un servicio externo y el problema aquí es de volumen, no de bots sofisticados.
Qué puede salir mal
Que el contador lo lea y lo escriba una request a la vez, sin transacción: dos intentos que llegan en el mismo instante pueden pasar los dos con 4 fallos registrados y terminar en 6. Para un límite de login, uno de más no cambia nada; las carreras que sí importan son el tema de WEB10. Y que detrás de un proxy todas las requests lleguen con la IP del proxy: el contador por IP bloquearía a todos juntos. Lo ves en Limitaciones.

Paso 4. El login: límite y mismo tiempo

La función login() de api/models/login.php queda así, entera. Lo que cambia está marcado con un comentario; la consulta suma u.version_sesion.

    public function login(array $arrayData) {
        $identificador = trim($arrayData["identificador"] ?? '');
        $contrasena    = $arrayData["contrasena"] ?? '';

        if (mb_strlen($identificador) < 3 || mb_strlen($identificador) > 150) {
            $this->response->error("El identificador de usuario no es valido", -1, 400);
        }
        if (strlen($contrasena) < 8) {
            $this->response->error("La contraseña debe tener al menos 8 caracteres", -1, 400);
        }

        # Nuevo: antes de tocar la contraseña, ¿esta cuenta o esta IP ya fallaron demasiado?
        $claves = LoginThrottle::claves($identificador, (string)($_SERVER['REMOTE_ADDR'] ?? ''));
        if (LoginThrottle::bloqueado($this->connection, $claves)) {
            header('Retry-After: ' . LoginThrottle::segundosDeEspera());
            $this->response->error("Demasiados intentos. Espera unos minutos e inténtalo de nuevo.", -1, 429);
        }

        $columna = filter_var($identificador, FILTER_VALIDATE_EMAIL) ? 'u.email' : 'u.username';

        try {
            $query = "SELECT u.id, u.username, u.nombre, u.apellido, u.password_hash, u.institucion_id,
                             u.autorizado_publicar, u.version_sesion,
                             (SELECT GROUP_CONCAT(ar.id_rol ORDER BY ar.id_rol)
                                FROM asignaciones_roles ar
                               WHERE ar.id_usuario = u.id AND ar.estado = 1) AS roles
                      FROM usuarios u
                      WHERE $columna = ? AND u.estado = 1 AND u.estado_cuenta = 'activo'";
            $stmt = $this->connection->prepare($query);
            $stmt->execute([$identificador]);
            $result = $stmt->fetch(PDO::FETCH_ASSOC);

            # Nuevo: password_verify corre siempre, exista o no la cuenta
            $hash     = $result ? $result['password_hash'] : (string)LOGIN_HASH_RELLENO;
            $coincide = password_verify($contrasena, $hash) && $result !== false;

            if (!$coincide) {
                LoginThrottle::registrarFallo($this->connection, $claves);
                $this->response->error("La contraseña y el usuario no coinciden", -1, 401);
            }
            LoginThrottle::limpiarCuenta($this->connection, $claves);

            $roles = $result['roles'] !== null
                ? array_map('intval', explode(',', $result['roles']))
                : [];

            # Nuevo: la cookie la arma sesion.php, con la versión de sesión de la fila
            $payload = emitirSesion([
                'id'             => $result['id'],
                'username'       => $result['username'],
                'name'           => $result['nombre'] . ' ' . $result['apellido'],
                'institucion_id' => $result['institucion_id'],
                'roles'          => implode(',', $roles),
                'isAdmin'        => in_array(self::ROL_ADMIN, $roles, true),
            ], (int)$result['version_sesion']);

            $this->response->success([
                'id'        => $payload['id'],
                'username'  => $payload['username'],
                'name'      => $payload['name'],
                'roles'     => $payload['roles'],
                'isAdmin'   => $payload['isAdmin'],
                'institucion_id' => $payload['institucion_id'],
                'autorizado_publicar' => (int)$result['autorizado_publicar'],
                'csrfToken' => csrfToken()
            ], "Logueado exitosamente");
        } catch (PDOException $e) {
            Response::serverError($e);
        }
    }

    # Cierra sesión en este navegador: borra la cookie
    public function logout() {
        borrarSesion();
        $this->response->success([], "Sesión cerrada");
    }

Tres líneas más para que todo esté cargado. En api/endpoints/login.php, junto a los otros require_once:

    public static function exigirHash(string $clave): void
    {
        if (password_get_info((string)self::get($clave, ''))['algo'] === null) {
            self::fallar("$clave no es un hash de password_hash()");
        }

La decisión
Verificar siempre contra un hash, real o de relleno, y comprobar el límite antes de esa verificación, para que un bloqueado no cueste un bcrypt.
Lo que descartas
Un usleep aleatorio en el camino corto: el ruido se promedia con suficientes intentos y la diferencia vuelve a aparecer. Tampoco sirve calcular password_hash en cada request para la cuenta inexistente: costaría un bcrypt de más y el tiempo seguiría distinto (hash más verificación contra solo verificación).
Qué puede salir mal
Que alguien "simplifique" la condición a $result && password_verify(...): PHP corta en el primer falso y la verificación deja de correr para las cuentas inexistentes. El orden de la línea es la defensa. Y que LOGIN_HASH_RELLENO quede sin definir: exigirHash no deja arrancar, que es preferible a un login que filtra cuentas en silencio.

Paso 5. Cambiar la contraseña cierra las demás

El final de changePassword en api/models/usuarios.php sube la versión en el mismo UPDATE que cambia el hash, y le da a esta pestaña una cookie nueva. La función recibe un parámetro más, la sesión actual, para armar esa cookie.

    public function changePassword(array $arrayData, array $sesion) {
        # ... las validaciones y la verificación de password_actual quedan igual ...

        $newPasswordHash = password_hash($password_nueva, PASSWORD_DEFAULT);
        try {
            # La contraseña y la versión cambian juntas: toda cookie anterior deja de valer
            $stmt = $this->connection->prepare(
                "UPDATE usuarios SET password_hash = ?, version_sesion = version_sesion + 1 WHERE id = ?"
            );
            $stmt->execute([$newPasswordHash, $id]);

            $stmt = $this->connection->prepare("SELECT version_sesion FROM usuarios WHERE id = ?");
            $stmt->execute([$id]);
            $version = (int)$stmt->fetchColumn();
        } catch (PDOException $e) {
            Response::serverError($e);
        }

        # Esta pestaña sigue dentro con una cookie nueva; el resto de las sesiones queda fuera
        emitirSesion($sesion, $version);
        $this->response->success(['csrfToken' => csrfToken()], "La contraseña se cambio correctamente!");
    }
$auth = requireAuth([1,2,3]);
$data = readJsonInput("PUT");
$connection = new Connection();
$response = new Response();

try {
  $cambioContrasena = new Usuarios($connection, $response);
  $cambioContrasena->changePassword([
                'id'                          => (string)$auth['id'], # sale de la sesion, no del cuerpo
                'password_actual'             => inputString($data, 'password_actual'),
                'password_nueva'              => inputString($data, 'password_nueva'),
                'password_nueva_confirmacion' => inputString($data, 'password_nueva_confirmacion')
            ], $auth);

catch (Exception $e) {
  Response::serverError($e);
}
La decisión
Subir la versión en el mismo UPDATE que el hash, para que no exista un momento con la contraseña nueva y las sesiones viejas vivas; y reemitir la cookie de quien hizo el cambio, para no sacarlo.
Lo que descartas
Cerrar también la sesión actual y mandarlo al login: es más simple y algunos sistemas lo hacen, pero para quien acaba de escribir su contraseña nueva es un paso de más sin ganancia. Tampoco se agrega un "cerrar todas mis sesiones" sin cambiar la contraseña; con esta columna es un UPDATE de una línea, y queda como ejercicio en Limitaciones.
Qué puede salir mal
Que el frontend se quede con el csrfToken viejo: el token es el HMAC de la cookie, y la cookie cambió. No pasa porque apiFetch guarda el csrfToken de cualquier respuesta; si un día cambias eso, la siguiente escritura de esa pestaña da 403. Y que la cuenta del administrador no tenga roles 1, 2 o 3 en requireAuth([1,2,3]): no es tu caso, porque isAdmin pasa siempre.

Fallas provocadas

Falla 1. Sin la versión. En refrescarAuthDesdeBD, comenta la línea || (int)$fila['version_sesion'] !== … y repite el bloque 4 del script. Ahora la otra sesión responde 200 después del cambio: la cookie del laboratorio sigue entrando. Esa es la situación de la excusa. Descomenta la línea.

Falla 2. El atajo de la condición. Cambia la línea de $coincide por $coincide = $result !== false && password_verify($contrasena, $hash); y repite el bloque 1. Anota los dos promedios: con este orden, la cuenta que no existe deja de pagar el bcrypt. La diferencia entre los dos números es lo que un atacante mide para saber qué usuarios existen. Vuelve al orden original.

Falla 3. IPv4 contra IPv6. Entra con curl.exe -4 y pide la sesión con curl.exe -6, con el mismo archivo de cookies. La segunda request tiene que dar 401, porque llega desde ::1 y la cookie dice 127.0.0.1. Si curl responde Failed to connect, tu Apache no escucha en IPv6 y la falla no aplica.

curl.exe -6 -s -o NUL -w "%{http_code}`n" -b lab\ip.txt http://localhost/SistemaControlPracticas/api/endpoints/login.php

Limitaciones

  • No se cierra una sesión concreta. La versión es por usuario: corta todas o ninguna. Para "cerrar la sesión del laboratorio" sin tocar la de casa hacen falta sesiones del lado del servidor, con un id por dispositivo. Un botón "cerrar todas mis sesiones" sí sale con lo que hay: UPDATE usuarios SET version_sesion = version_sesion + 1 WHERE id = ? y emitirSesion, como en el paso 5.
  • El logout no revoca. DELETE login.php borra la cookie del navegador, pero una copia robada antes sigue valiendo hasta exp. Si quieres que el logout también corte las copias, súbele la versión (y cerrará todas las sesiones de esa persona).
  • La IP detrás de un proxy. Si pones Nginx o Cloudflare delante, REMOTE_ADDR pasa a ser la del proxy: el ligado a la IP deja de significar algo y el contador por IP junta a todos. La IP real viene en una cabecera (X-Forwarded-For) que solo vale si la escribe tu proxy, nunca leída directa del cliente.
  • El costo. Cada fallo suma dos INSERT y cada login, un SELECT con COUNT sobre un índice. Para el volumen de un sistema de prácticas es despreciable; la tabla se purga sola de lo que tiene más de un día, en promedio una vez cada 100 fallos.
  • Nada se ejecutó al escribir esta guía. Los códigos esperados salen de leer el código. Los tiempos del bloque 1 son tuyos y la guía no los anticipa.

Cómo conectar

Esta guía funciona sola. Si quieres juntarla con otras:

  • Con WEB00 y WEB01

    El script usa el laboratorio de WEB00 y depende de que los errores salgan con su código HTTP real (WEB01): un 429 que saliera como 200 no lo vería %{http_code}.

  • Con M81, autenticación y sesiones

    La versión de sesión es la forma mínima de revocar un token sin estado; las alternativas (sesiones en servidor, listas de revocación, tokens cortos con refresh) están en M81.

  • Con M74, cookies

    opcionesCookie junta los atributos que M74 explica uno por uno: HttpOnly, Secure, SameSite y el dominio.

  • Con A12, sesiones en Java

    A12 resuelve lo mismo con sesiones en Redis: ahí revocar es borrar una clave. Compara qué se gana y qué se paga con cada forma.
