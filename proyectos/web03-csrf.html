CSRF

La cookie SameSite y el token ya están. Falta la capa que mira de dónde viene la request, y cerrar un Content-Type que deja pasar JSON como texto plano.

Estado
Sin empezar

Al terminar podrás

  • Ubicar las cuatro capas contra CSRF del sistema (SameSite, Fetch Metadata, Origin y el token) y decir qué frena cada una y qué deja pasar.
  • Agregar una comprobación de Sec-Fetch-Site y Origin contra una lista exacta de orígenes, antes de la sesión y del token.
  • Cerrar el hueco del Content-Type: text/plain; application/json pasa hoy la validación y no dispara un preflight.
  • Probar cada capa por separado con una matriz de curl y desde dos sitios atacantes: uno de otro sitio y uno del mismo sitio.

La excusa

El sistema ya tiene dos defensas contra CSRF: la cookie sale con SameSite=Strict y toda escritura exige el X-CSRF-Token, que es el HMAC de la cookie. Las dos funcionan. El problema es que cada una tiene un hueco conocido y hoy no hay nada detrás de ellas.

  • SameSite mira el sitio, no el origen. Una página en http://localhost:8081, o en cualquier subdominio del mismo dominio registrable, es del mismo sitio que la API: la cookie viaja. Lo explica M76.
  • El token depende de que nadie lo lea. Un XSS en el frontend lo lee de la memoria de apiFetch. Contra eso no hay defensa de CSRF que alcance (es WEB05), pero sí conviene que el token no sea lo único.
  • La validación del JSON es un stripos. readJsonInput acepta cualquier Content-Type que contenga application/json, y text/plain; application/json lo contiene. Para el navegador ese tipo es text/plain con un parámetro raro: no pide preflight.

Esta guía agrega la capa que falta (de dónde viene la request, dicho por el propio navegador) y cierra el Content-Type. Es el hallazgo H de la re-auditoría.

Qué necesitas

El laboratorio de WEB00, con atacante.test andando. Esta guía suma un segundo sitio atacante en el puerto 8081. Si hiciste WEB01, los rechazos salen con su código HTTP real; si no, salen con 200 y el script del final lo marca. No se instala nada.

La infraestructura

El vecino del mismo sitio

Un tercer host virtual, en otro puerto de localhost, que sirve la misma carpeta del atacante. Agrégalo al final de httpd-vhosts.conf, después de los dos de WEB00:

Listen 8081

<VirtualHost *:8081>
    ServerName localhost
    DocumentRoot "C:/xampp/htdocs/atacante"
    <Directory "C:/xampp/htdocs/atacante">
        Require local
    </Directory>
</VirtualHost>

Revisa la sintaxis con C:\xampp\apache\bin\httpd.exe -t (tiene que decir Syntax OK) y reinicia Apache desde el panel. http://localhost:8081/ tiene que mostrar la página de WEB00.

La decisión
Un puerto distinto en el mismo host: es otro origen pero el mismo sitio, que es exactamente el caso que SameSite no cubre.
Lo que descartas
Un subdominio como evil.localhost: también es el mismo sitio en la mayoría de los navegadores, pero cómo se trata localhost como dominio registrable varía, y el puerto deja la prueba sin ambigüedad. En un sistema real, el vecino es blog.tu-dominio.com con un plugin vulnerable.
Qué puede salir mal
Que otro programa use el 8081 y Apache no arranque: netstat -ano | findstr :8081 lo dice, y cualquier otro puerto libre sirve igual. Require local deja la página solo para tu máquina.

Los orígenes permitidos, en el .env

# Orígenes que pueden escribir en la API (WEB03) y leerla desde otro origen (WEB04).
# Exactos: esquema, host y puerto, sin barra al final, separados por coma.
ORIGENES_PERMITIDOS=http://localhost:5173,http://localhost

http://localhost:5173 es el frontend en desarrollo: el proxy de Vite reescribe el Host (changeOrigin: true), pero no el Origin, que sigue siendo el de la página. http://localhost es el frontend compilado servido por Apache. Y en configuration.php, la variable se suma a la lista que no puede faltar:

Env::exigir(['COOKIE_NAME', 'COOKIE_KEY', 'DATABASE', 'HOST_DB', 'LOGIN_HASH_RELLENO', 'ORIGENES_PERMITIDOS']);

Paso a paso

Paso 1. De dónde viene la request

Un archivo nuevo con dos partes: la lista de orígenes, que WEB04 también usa para CORS, y la comprobación para las requests que escriben.

  1. origenesPermitidos lee la lista del .env una vez por request.
  2. esOrigenPermitido compara el origen exacto contra la lista: nada de prefijos, sufijos ni expresiones regulares.
  3. requireOrigenConfiable rechaza si el navegador dice cross-site, si hay un Origin fuera de la lista, o si dice same-site sin un Origin permitido.
  4. Si no hay ninguna de las dos cabeceras, no es un navegador: deja la decisión al token.
<?php

declare(strict_types=1);

require_once __DIR__ . '/response.php';

/** Los orígenes del .env, exactos. Los usan la defensa CSRF (WEB03) y CORS (WEB04). */
function origenesPermitidos(): array
{
    static $lista = null;
    if ($lista === null) {
        $lista = array_values(array_filter(array_map('trim',
            explode(',', (string)Env::get('ORIGENES_PERMITIDOS', '')))));
    }
    return $lista;
}

/** Igualdad exacta: "http://localhost:5173.atacante.test" no es "http://localhost:5173". */
function esOrigenPermitido(string $origen, ?array $lista = null): bool
{
    return $origen !== 'null' && in_array($origen, $lista ?? origenesPermitidos(), true);
}

/** Para las requests que escriben: corta lo que el navegador dice que viene de otro lado. */
function requireOrigenConfiable(): void
{
    $sitio  = strtolower((string)($_SERVER['HTTP_SEC_FETCH_SITE'] ?? ''));
    $origen = isset($_SERVER['HTTP_ORIGIN']) ? (string)$_SERVER['HTTP_ORIGIN'] : null;

    if ($sitio === 'cross-site') {
        rechazarOrigen('Sec-Fetch-Site: cross-site, Origin: ' . ($origen ?? '(sin Origin)'));
    }
    if ($origen !== null && !esOrigenPermitido($origen)) {
        rechazarOrigen("Origin no permitido: $origen");
    }
    if ($sitio === 'same-site' && $origen === null) {
        rechazarOrigen('Sec-Fetch-Site: same-site sin Origin');
    }
    # Sin Sec-Fetch-Site ni Origin: no es un navegador. Decide el token.
}

function rechazarOrigen(string $motivo): never
{
    error_log('[csrf] ' . $motivo . ' -> ' . ($_SERVER['REQUEST_METHOD'] ?? '') . ' ' . ($_SERVER['REQUEST_URI'] ?? ''));
    Response::json(-1, 'Origen no permitido', [], 403);
}

PHP de por medio

static $lista dentro de una función guarda el valor entre llamadas de la misma request, así que el .env se parte una sola vez. El segundo parámetro de esOrigenPermitido existe para la prueba de WEB04, que le pasa una lista sin leer ningún .env. Las cabeceras de la request llegan en $_SERVER con el prefijo HTTP_, en mayúsculas y con guiones bajos: Sec-Fetch-Site es HTTP_SEC_FETCH_SITE.

La decisión
Fetch Metadata y Origin juntos, con la lista exacta del .env: Sec-Fetch-Site corta todo lo de otro sitio sin necesitar la lista, y Origin distingue al vecino del mismo sitio, que Sec-Fetch-Site solo marca como same-site.
Lo que descartas
Mirar el Referer: es el respaldo cuando falta Origin, pero lo recortan las políticas de Referrer-Policy y algunos proxies, y los navegadores actuales mandan Origin en toda request que no es GET ni HEAD. Tampoco se rechazan las requests sin cabeceras: dejarías fuera a curl, a los scripts del laboratorio y a cualquier integración, que no son vulnerables a CSRF porque no tienen una cookie ajena.
Qué puede salir mal
Escribir el origen con barra al final en el .env (http://localhost:5173/): el navegador nunca la manda y el frontend recibe 403 en toda escritura. Y que el frontend compilado se sirva desde otro host o puerto que no está en la lista: el síntoma es el mismo y el registro dice [csrf] Origin no permitido: … con el origen real.

Paso 2. La capa, en el orden de M76

En requireAuth, la comprobación va antes de leer la sesión, para las mismas requests que ya exigen el token. Es el orden que propone M76: del control más barato al más caro.

require_once __DIR__ . "/origen.php";

function requireAuth(int|array $roles = [])
{
    $method = strtoupper((string)($_SERVER['REQUEST_METHOD'] ?? 'GET'));
    $escribe = !in_array($method, ['GET', 'HEAD', 'OPTIONS'], true);

    # 1. De dónde viene: barato, sin estado y sin base
    if ($escribe) {
        requireOrigenConfiable();
    }

    # 2. La sesión
    $data = checkAuth();
    if ($data === null) {
        Response::error("Usuario no autenticado", -2);
    }
    $data = refrescarAuthDesdeBD($data);
    AuditLog::setUser($data);

    # 3. El token, atado a esa sesión
    if ($escribe) {
        requireCsrfToken();
    }

    # ... la comprobación de roles sigue igual ...

Fíjate en un cambio de paso: QUERY ya no está en la lista de métodos que no escriben. Hoy requireAuth lo exime del token, pero ningún endpoint lo atiende (no hay un case 'QUERY') y el frontend no lo manda. Una excepción que nadie usa es una puerta que alguien abre sin saberlo: si algún día un endpoint implementa QUERY, pasa por las dos capas como cualquier método que lleva cuerpo.

La decisión
La misma condición ($escribe) para el origen y para el token, en ese orden, en el único lugar por donde pasan todos los endpoints con sesión.
Lo que descartas
Poner la comprobación en el .htaccess con RewriteCond %{HTTP:Origin}: funciona para el caso simple, pero la lista viviría en dos lugares y Apache no sabe qué método escribe en tu API.
Qué puede salir mal
Que algún endpoint que escribe no llame a requireAuth. En este repositorio el único es POST login.php, y por eso tiene su propio paso. Si sumas un endpoint público que escribe (un formulario de contacto), necesita su propia llamada a requireOrigenConfiable.

Paso 3. El login también

El login no pasa por requireAuth, porque todavía no hay sesión. Un login CSRF no roba nada: mete a la víctima en una cuenta del atacante, y lo que ella escriba (su CV, sus datos) queda en esa cuenta. En api/endpoints/login.php, la comprobación va antes de leer el cuerpo:

require_once __DIR__ . "/../core/origen.php";

# ... los header() de CORS y el bloque de OPTIONS siguen igual (WEB04 los cambia) ...

$connection = Connection::load();
$response   = new Response();
$method     = $_SERVER["REQUEST_METHOD"];

# POST y DELETE escriben: primero de dónde vienen, después el cuerpo
if ($method !== 'GET') {
    requireOrigenConfiable();
}
$data = readJsonInput($method);
La decisión
La misma función, antes de readJsonInput, para que una request de otro origen ni siquiera llegue a contar como intento fallido en el límite de WEB02.
Lo que descartas
Exigir un token CSRF en el login, que es la recomendación clásica: requiere un token previo a la sesión (en una cookie aparte o en un GET anterior), y con el Origin exacto y el Content-Type del paso 4, el login ya no se puede disparar desde otro sitio.
Qué puede salir mal
Que el frontend haga el login desde un origen que no está en la lista: nadie puede entrar, y el mensaje es Origen no permitido, no un error de contraseña. Si te pasa, mira el registro.

Paso 4. El Content-Type, entero

El navegador solo manda sin preflight tres tipos: application/x-www-form-urlencoded, multipart/form-data y text/plain. Para decidirlo lee el tipo sin sus parámetros, así que text/plain; application/json es text/plain y sale sin preguntar Documentado. readJsonInput hace lo contrario: busca application/json en cualquier parte del texto. Reemplaza las dos líneas del principio:

    # El tipo sin parámetros: "application/json; charset=utf-8" -> "application/json"
    $contentType = strtolower(trim(explode(';', (string)($_SERVER["CONTENT_TYPE"] ?? ''), 2)[0]));
    if ($contentType !== 'application/json') {
        Response::error("Petición inválida: se esperaba Content-Type application/json.", -1, httpCode: 415);
    }
La decisión
Comparar el tipo base exacto, como lo hace el navegador, y responder 415 (Unsupported Media Type), que es el código para eso.
Lo que descartas
str_starts_with($ct, 'application/json'), que propone M76: cierra el truco de text/plain, pero acepta application/jsonx. Es inofensivo, porque ese tipo sí pide preflight, pero la comparación exacta no deja nada para pensar.
Qué puede salir mal
Que algún cliente mande application/json con mayúsculas o espacios (Application/JSON): el strtolower y el trim lo cubren. Lo que deja de funcionar es lo que nunca debió: un cliente que mandaba JSON como text/plain. El frontend no lo hace: apiFetch pone application/json.

Paso 5. La página del atacante

Tres intentos, en la misma página, que se sirve desde los dos sitios atacantes. Ninguno lleva un payload: el primero es un formulario común, el segundo es el truco del Content-Type con una contraseña incorrecta, y el tercero es un formulario multipart a un endpoint con sesión.

Antes de aplicar los pasos 1 a 4, entra al frontend como estudiante en otra pestaña y abre la página desde los dos sitios: http://atacante.test/web03.html y http://localhost:8081/web03.html. Después, aplica los pasos y repite. Anota todo en la tabla de el navegador.

Errores típicos

  • El botón 2 no aparece en Network. Algunas extensiones bloquean fetch en modo no-cors: prueba en una ventana sin extensiones.
  • El iframe dice que la página rechazó la conexión. Es el iframe, no la API: la respuesta JSON puede verse o no según el navegador. El dato que importa está en Network.
  • localhost:8081 no responde. Falta el Listen 8081 o Apache no se reinició; httpd.exe -t y el panel de XAMPP lo dicen.
La decisión
Una sola página con los tres casos, servida desde un sitio distinto y desde el mismo sitio, para que la diferencia la ponga solo SameSite.
Lo que descartas
Un ataque que cambie algo de verdad (una postulación con datos): no hace falta, porque lo que se prueba es si la request llega al código, y un payload mínimo responde eso sin dejar basura en la base. Tampoco se intenta saltar ninguna defensa: cada intento es el que el diseño de M76 ya describe.
Qué puede salir mal
Leer el resultado del iframe como si fuera la verdad: el formulario 1 desde atacante.test puede mostrar el JSON del error, y eso no significa que el atacante lo pueda leer desde su JavaScript (no puede: el iframe es de otro origen). El dato confiable es el código HTTP en Network.

Cómo comprobar que funciona

La matriz con curl

curl no hace cumplir nada del navegador, pero sí manda las cabeceras que le pidas. Eso sirve para probar el servidor capa por capa: cada fila cambia una sola cabecera. El script usa DELETE login.php, que pasa por requireAuth y no cambia nada en la base (borra la cookie solo en la respuesta, y el script no la guarda).

# Sesión nueva y su token. lab\login.json es el cuerpo del paso 7 de WEB00 (estudiante).
& curl.exe -s -o NUL -c $Jar -H "Content-Type: application/json" --data-binary "@lab\login.json" "$Base/login.php"
$token = (& curl.exe -s -b $Jar "$Base/login.php" | ConvertFrom-Json).data.csrfToken

Fallas provocadas

Falla 1. Solo el token. Comenta la llamada a requireOrigenConfiable() en requireAuth y corre web03.ps1. Las filas 3 a 8 vuelven a dar 200: con un token válido, nada distingue de dónde viene la request. Es la situación de un XSS que robó el token. Descomenta.

Falla 2. Solo el origen. Ahora comenta requireCsrfToken(). La última fila (sin token, con el Origin del frontend) da 200. Las demás siguen en 403. Lo que muestra: el origen solo no alcanza, porque curl puede escribir cualquier Origin; el token es lo que un tercero no puede fabricar. Descomenta.

Falla 3. Una lista mal escrita. Pon ORIGENES_PERMITIDOS=http://localhost:5173/ (con barra) y haz cualquier cambio desde el frontend. Tiene que fallar con Origen no permitido, y el registro tiene que decir [csrf] Origin no permitido: http://localhost:5173. Quita la barra.

Limitaciones

  • Un XSS gana igual. Una página tuya con un script inyectado manda requests desde tu propio origen, con la cookie y con el token. Ninguna capa de esta guía lo frena; lo frenan el escape y la CSP (WEB05 y WEB09).
  • Navegadores viejos. Sec-Fetch-Site llegó a Safari recién en 2023 Documentado. Sin esa cabecera, la capa depende de Origin, que todos los navegadores actuales mandan en las requests que escriben.
  • El token vale lo que vale la cookie. Es el HMAC de la cookie, así que dura lo mismo que ella; con WEB02 cambia cada vez que la cookie se reemite (un login, un cambio de contraseña), pero no rota por request. Un token por request agrega estado en el servidor y no frena nada que estas capas dejen pasar.
  • La lista es estática. Un frontend nuevo (otro puerto, un dominio de producción) hay que agregarlo al .env, y se olvida. El síntoma es claro: 403 y una línea en el registro.
  • Nada se ejecutó al escribir esta guía. Las columnas del navegador son tuyas; los códigos de la matriz salen de leer el código.
