Un servidor seguro: de una VM a una VPC

Una API de notas con cada defensa puesta en una sola VM, y después la misma API separada en capas: primero en VMs con redes aisladas y una IP virtual, después en Kubernetes, donde cada capa escala por su cuenta.

Al terminar podrás

  • Endurecer una VM con Ubuntu 24.04 de punta a punta: SSH solo con llave, nftables con entrada y salida filtradas, fail2ban, auditd, parches automáticos y la API dentro de un sandbox de systemd.
  • Poner delante de la API un borde con TLS, ModSecurity con el OWASP CRS, límites de tasa y solo las rutas públicas, y comprobar cada defensa con un script que la ataca.
  • Darle a la API un rol de PostgreSQL que solo toca filas, y correr las migraciones aparte con el rol dueño.
  • Separar el borde, las apps y la base en VMs con redes aisladas, y mantener el borde con dos máquinas y una IP virtual con keepalived.
  • Llevar el borde y las apps a Kubernetes, con el WAF y el gateway separados, NetworkPolicy entre capas y un HPA por capa.

La excusa

Una API de notas privadas: te registras, inicias sesión y guardas notas que solo tú puedes leer. Es chica a propósito. Lo que importa es todo lo que la rodea: en esta guía la API casi no cambia, y lo que crece son las capas que la protegen y la forma en que se reparten entre máquinas.

Empiezas con todo en una VM, que es como arranca casi todo proyecto: una máquina con Nginx, la aplicación y la base. Con todas las defensas puestas, esa VM ya es difícil de atacar. Pero tiene dos límites que ninguna configuración arregla: si se cae, se cae todo; y si alguien toma Nginx, está en la misma máquina que la base. Por eso, después, la separas: primero en cinco VMs con redes que no se ven entre sí, y después en un clúster de Kubernetes, donde el WAF, el gateway y la API escalan cada uno por su lado.

Lo que esta guía no promete

Un servidor 100 % seguro no existe. Lo que sí existe es un servidor donde cada ataque común choca contra una defensa que lo detiene, donde un error en una capa no abre todas las demás y donde queda registro de lo que pasó. Eso es lo que construyes aquí, y la sección Lo que falta para producción dice lo que queda afuera. Todos los ataques de la guía se hacen contra tu propio laboratorio, en tu máquina, con cargas mínimas, y cada uno termina en la defensa que lo detiene.

La idea que ordena todo es la de M32, 32.9: cada capa detiene una clase de ataque distinta, y ninguna alcanza sola. El firewall no sabe qué es una inyección SQL; el WAF no sabe de quién es una nota; la API no ve un SYN a un puerto que nadie publicó.

El servicio de sesiones es el corazón de la guía. Tiene tres defensas: el token se guarda como hash, la comparación tarda lo mismo exista o no el usuario, y el contador de fallos no se puede saltar con requests en paralelo.

package lab.notas.sesiones;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.util.Base64;
import java.util.Optional;

import lab.notas.NotasProps;

import org.springframework.dao.DuplicateKeyException;
import org.springframework.http.HttpStatus;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.web.ErrorResponseException;

@Service
public class SesionService {

    private static final SecureRandom RANDOM = new SecureRandom();

    private final JdbcClient db;
    private final NotasProps props;
    private final BCryptPasswordEncoder bcrypt;
    private final String hashFalso;

    record Intento(long id, String claveHash, int fallidos) {
    }

    SesionService(JdbcClient db, NotasProps props) {
        this.db = db;
        this.props = props;
        this.bcrypt = new BCryptPasswordEncoder(props.bcryptCosto());
        // Para comparar contra algo cuando el usuario no existe o está bloqueado: misma demora, misma respuesta.
        this.hashFalso = bcrypt.encode("no-existe-" + RANDOM.nextLong());
    }

    public void registrar(String usuario, String clave) {
        try {
            db.sql("INSERT INTO usuarios (usuario, clave_hash) VALUES (:u, :h)")
                    .param("u", usuario).param("h", bcrypt.encode(clave)).update();
        } catch (DuplicateKeyException e) {
            throw new ErrorResponseException(HttpStatus.CONFLICT);
        }
    }

    /** El token de una sesión nueva, o vacío si el usuario no existe, la clave no coincide o la cuenta está bloqueada. */
    public Optional<String> iniciar(String usuario, String clave) {
        // 1. Reservar el intento ANTES de comparar. El UPDATE es atómico: con 50 requests a la vez,
        //    solo max-fallidos consiguen fila; el resto no llega a bcrypt con la clave real.
        Optional<Intento> intento = db.sql("""
                UPDATE usuarios
                   SET fallidos = CASE WHEN bloqueado_hasta < now() THEN 1 ELSE fallidos + 1 END,
                       bloqueado_hasta = CASE WHEN bloqueado_hasta < now() THEN NULL ELSE bloqueado_hasta END
                 WHERE usuario = :u
                   AND (bloqueado_hasta < now() OR (bloqueado_hasta IS NULL AND fallidos < :max))
                RETURNING id, clave_hash, fallidos""")
                .param("u", usuario).param("max", props.maxFallidos())
                .query(Intento.class).optional();

        if (intento.isEmpty()) {
            bcrypt.matches(clave, hashFalso);   // no existe o está bloqueado: la misma demora que un intento real
            return Optional.empty();
        }
        Intento i = intento.get();

        // 2. Comparar fuera de cualquier transacción: bcrypt tarda y no debe tener una fila bloqueada mientras tanto.
        if (!bcrypt.matches(clave, i.claveHash())) {
            if (i.fallidos() >= props.maxFallidos()) {
                db.sql("UPDATE usuarios SET bloqueado_hasta = now() + make_interval(mins => :m) WHERE id = :id")
                        .param("m", props.bloqueoMinutos()).param("id", i.id()).update();
            }
            return Optional.empty();
        }

        // 3. Clave correcta: el contador vuelve a cero y nace la sesión.
        db.sql("UPDATE usuarios SET fallidos = 0 WHERE id = :id").param("id", i.id()).update();
        byte[] crudo = new byte[32];
        RANDOM.nextBytes(crudo);
        String token = Base64.getUrlEncoder().withoutPadding().encodeToString(crudo);
        db.sql("INSERT INTO sesiones (token_hash, usuario_id, vence) VALUES (:h, :id, now() + make_interval(mins => :m))")
                .param("h", sha256(token)).param("id", i.id()).param("m", props.sesionMinutos()).update();
        return Optional.of(token);
    }

    public Optional<Long> usuarioDe(String token) {
        return db.sql("SELECT usuario_id FROM sesiones WHERE token_hash = :h AND vence > now()")
                .param("h", sha256(token)).query(Long.class).optional();
    }

    static byte[] sha256(String s) {
        try {
            return MessageDigest.getInstance("SHA-256").digest(s.getBytes(StandardCharsets.UTF_8));
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}

El UPDATE del paso 1 hace dos cosas en una sentencia: decide si al usuario le queda un intento y lo gasta. Si la cuenta está bloqueada y el bloqueo ya venció, empieza de nuevo con fallidos = 1. Si está bloqueada y no venció, o ya gastó sus cinco intentos, el WHERE no encuentra la fila y el método compara la clave contra un hash falso, para que la respuesta tarde lo mismo que un intento real. La versión ingenua, leer el contador, comparar y escribir, deja pasar más intentos de los que debería cuando llegan juntos; la sección La versión con hilos lo provoca con 50 hilos.

package lab.notas.sesiones;

import java.nio.charset.StandardCharsets;

import jakarta.validation.Valid;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.ErrorResponseException;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api")
class SesionController {

    record Credenciales(
            @NotNull @Pattern(regexp = "[a-z0-9_.-]{3,32}") String usuario,
            @NotNull @Size(min = 12, max = 72) String clave) {
    }

    record Token(String token) {
    }

    private final SesionService sesiones;

    SesionController(SesionService sesiones) {
        this.sesiones = sesiones;
    }

    @PostMapping("/usuarios")
    ResponseEntity<Void> registrar(@Valid @RequestBody Credenciales c) {
        hasta72Bytes(c.clave());
        sesiones.registrar(c.usuario(), c.clave());
        return ResponseEntity.status(HttpStatus.CREATED).build();
    }

    @PostMapping("/sesiones")
    ResponseEntity<Token> iniciar(@Valid @RequestBody Credenciales c) {
        hasta72Bytes(c.clave());
        return sesiones.iniciar(c.usuario(), c.clave())
                .map(t -> ResponseEntity.status(HttpStatus.CREATED).body(new Token(t)))
                .orElseThrow(() -> new ErrorResponseException(HttpStatus.UNAUTHORIZED));
    }

    /** bcrypt solo mira 72 bytes, y 72 caracteres con tildes son más. Sin esto, la librería lanza y responde 500. */
    private static void hasta72Bytes(String clave) {
        if (clave.getBytes(StandardCharsets.UTF_8).length > 72) {
            throw new ErrorResponseException(HttpStatus.BAD_REQUEST);
        }
    }
}
package lab.notas.sesiones;

import java.util.Optional;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;
import org.springframework.web.ErrorResponseException;
import org.springframework.web.servlet.HandlerInterceptor;

/** Toda ruta de /api/notas necesita un token vigente. Deja el id del usuario en la request. */
@Component
public class AuthInterceptor implements HandlerInterceptor {

    public static final String USUARIO = "notas.usuario";

    private final SesionService sesiones;

    AuthInterceptor(SesionService sesiones) {
        this.sesiones = sesiones;
    }

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        String h = req.getHeader("Authorization");
        Optional<Long> usuario = h != null && h.startsWith("Bearer ")
                ? sesiones.usuarioDe(h.substring(7))
                : Optional.empty();
        if (usuario.isEmpty()) {
            res.setHeader("WWW-Authenticate", "Bearer");
            throw new ErrorResponseException(HttpStatus.UNAUTHORIZED);
        }
        req.setAttribute(USUARIO, usuario.get());
        return true;
    }
}

La decisión
Defensas que no dependen de la red: escuchar en localhost, el dueño de la nota en el WHERE (contra BOLA, M10), el token guardado como hash, la misma respuesta para los tres motivos del 401 y el contador que se reserva antes de comparar. Lo que descartas
JWT: un token opaco se revoca borrando la fila, y aquí no hay otro servicio que tenga que validarlo sin preguntarle a la base. Spring Security entero: para un Bearer y un interceptor, es más configuración de la que se puede revisar en una tarde. Y el 403 para la nota ajena, que confirma que el id existe.
Qué puede salir mal
Que la clave tenga más de 72 bytes: bcrypt solo mira los primeros 72, y la librería lanza una excepción con una clave más larga. Por eso el controlador mide bytes y no solo caracteres: 40 eñes pasan un @Size(max = 72) y son 80 bytes. Y que el bloqueo sirva para molestar: cualquiera puede bloquear la cuenta de otro con cinco intentos. Está acotado a 15 minutos y el borde limita los intentos por IP.

Paso 2. La base, con dos roles

La API se conecta con un rol que solo puede leer y escribir filas. Las tablas las crea otro rol, el dueño del esquema, que usan únicamente las migraciones. Si alguien toma la API, puede hacer lo que la API hace, pero no borrar tablas, crear funciones ni leer otras bases.

-- Roles con lo justo. Lo corre el superusuario postgres con:
--   psql -v app_pass=... -v owner_pass=... < db.sql
-- Se puede correr dos veces: lo que ya existe no se vuelve a crear.
SELECT 'CREATE ROLE notas_owner LOGIN'
 WHERE NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'notas_owner') \gexec
SELECT 'CREATE ROLE notas_app LOGIN'
 WHERE NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'notas_app') \gexec
ALTER ROLE notas_owner PASSWORD :'owner_pass';
ALTER ROLE notas_app PASSWORD :'app_pass';

SELECT 'CREATE DATABASE notas OWNER notas_owner'
 WHERE NOT EXISTS (SELECT FROM pg_database WHERE datname = 'notas') \gexec
\c notas

-- Nadie más se conecta a esta base, y nadie crea tablas en public.
REVOKE ALL ON DATABASE notas FROM PUBLIC;
GRANT CONNECT ON DATABASE notas TO notas_app;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

-- El esquema es del dueño. La app puede usarlo, no cambiarlo.
CREATE SCHEMA IF NOT EXISTS notas AUTHORIZATION notas_owner;
GRANT USAGE ON SCHEMA notas TO notas_app;
-- Toda tabla que cree el dueño (las migraciones) le da a la app solo filas: leer, escribir y borrar.
ALTER DEFAULT PRIVILEGES FOR ROLE notas_owner IN SCHEMA notas
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO notas_app;
ALTER DEFAULT PRIVILEGES FOR ROLE notas_owner IN SCHEMA notas
    GRANT USAGE ON SEQUENCES TO notas_app;
ALTER ROLE notas_owner SET search_path = notas;
ALTER ROLE notas_app SET search_path = notas;

Los ALTER DEFAULT PRIVILEGES son la pieza clave: le dicen a PostgreSQL que toda tabla que cree notas_owner en el esquema notas nace con SELECT, INSERT, UPDATE y DELETE para notas_app. Por eso la migración no tiene ningún GRANT, y una tabla nueva no queda olvidada sin permisos ni con permisos de más. M35 explica el modelo de roles y privilegios de PostgreSQL.

Las migraciones corren en un proceso aparte, notas-migrar, que arranca la misma aplicación sin servidor web, aplica Flyway con la clave del dueño y termina. La API arranca después, con otro archivo de entorno que no tiene esa clave.

La decisión
Dos roles: notas_owner, dueño del esquema, y notas_app, que solo toca filas. La clave del dueño está en un archivo que la API no lee.
Lo que descartas
Conectar la API como postgres, que es lo que pasa cuando nadie lo piensa: una inyección SQL pasa a ser un COPY … TO PROGRAM. Y Flyway dentro de la API con el rol dueño, que deja la clave del dueño en el entorno de la API toda su vida.
Qué puede salir mal
Que una migración cree una función o una vista y la app no pueda usarla: los privilegios por defecto de arriba cubren tablas y secuencias, no funciones. Si agregas una, súmale su GRANT EXECUTE en la misma migración.

Los tres nodos tienen que estar Ready, el Job tiene que terminar Complete y los seis pods tienen que estar Running, repartidos entre nodos. Si al aplicar ves un aviso de Pod Security, lee qué campo nombra: es un pod que no cumple restricted.

La decisión
WAF y gateway separados, cada uno con su HPA: el WAF gasta CPU por request inspeccionada, el gateway casi nada, y la API gasta en bcrypt. Tres curvas distintas, tres autoescalados. La API sin token de Kubernetes, con el disco de solo lectura y sin capacidades.
Lo que descartas
Un Ingress con el WAF dentro (ingress-nginx con ModSecurity): es una sola pieza que escala junta, y su soporte de ModSecurity quedó deprecado. Mover la base al clúster: un operador como el de A07 lo hace bien, pero aquí la base es la capa que menos se toca.
Qué puede salir mal
ServiceLB, el balanceador de k3s, hace SNAT: el WAF ve la IP de un nodo, no la del cliente. Por eso el gateway limita por token y el inicio de sesión tiene un límite global, más alto que el por IP de la etapa 1. En una nube, el balanceador administrado conserva la IP del cliente en X-Forwarded-For o con proxy protocol. Y la base: flannel sale con la IP del nodo, así que pg_hba y el firewall de la base listan los tres nodos, no los pods.

 * bcrypt detrás de un bulkhead: como mucho bcryptConcurrentes cálculos a la vez.
 * Una ráfaga de inicios de sesión espera 200 ms por un lugar y, si no lo consigue, recibe 503:
 * la CPU sigue libre para leer y escribir notas.
 */
@Component
public class Bcrypt {

    private final BCryptPasswordEncoder encoder;
    private final Semaphore lugares;

    Bcrypt(NotasProps props) {
        this.encoder = new BCryptPasswordEncoder(props.bcryptCosto());
        this.lugares = new Semaphore(props.bcryptConcurrentes(), true);
    }

    public String hash(String clave) {
        return conLugar(() -> encoder.encode(clave));
    }

    public boolean coincide(String clave, String hash) {
        return conLugar(() -> encoder.matches(clave, hash));
    }

    private <T> T conLugar(java.util.function.Supplier<T> calculo) {
        boolean tengo;
        try {
            tengo = lugares.tryAcquire(200, TimeUnit.MILLISECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new ErrorResponseException(HttpStatus.SERVICE_UNAVAILABLE);
        }
        if (!tengo) {
            var ocupado = new ErrorResponseException(HttpStatus.SERVICE_UNAVAILABLE);
            ocupado.getHeaders().set("Retry-After", "1");
            throw ocupado;
        }
        try {
            return calculo.get();
        } finally {
            lugares.release();
        }
    }
}

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.util.Base64;
import java.util.Optional;

import lab.notas.NotasProps;

import org.springframework.dao.DuplicateKeyException;
import org.springframework.http.HttpStatus;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Service;
import org.springframework.web.ErrorResponseException;

@Service
public class SesionService {

    private static final SecureRandom RANDOM = new SecureRandom();

    private final JdbcClient db;
    private final NotasProps props;
    private final Bcrypt bcrypt;
    private final String hashFalso;

    record Intento(long id, String claveHash, int fallidos) {
    }

    SesionService(JdbcClient db, NotasProps props, Bcrypt bcrypt) {
        this.db = db;
        this.props = props;
        this.bcrypt = bcrypt;
        // Para comparar contra algo cuando el usuario no existe o está bloqueado: misma demora, misma respuesta.
        this.hashFalso = bcrypt.hash("no-existe-" + RANDOM.nextLong());
    }

    public void registrar(String usuario, String clave) {
        try {
            db.sql("INSERT INTO usuarios (usuario, clave_hash) VALUES (:u, :h)")
                    .param("u", usuario).param("h", bcrypt.hash(clave)).update();
        } catch (DuplicateKeyException e) {
            throw new ErrorResponseException(HttpStatus.CONFLICT);
        }
    }

    /** El token de una sesión nueva, o vacío si el usuario no existe, la clave no coincide o la cuenta está bloqueada. */
    public Optional<String> iniciar(String usuario, String clave) {
        // 1. Reservar el intento ANTES de comparar. El UPDATE es atómico: con 50 requests a la vez,
        //    solo max-fallidos consiguen fila; el resto no llega a bcrypt con la clave real.
        Optional<Intento> intento = db.sql("""
                UPDATE usuarios
                   SET fallidos = CASE WHEN bloqueado_hasta < now() THEN 1 ELSE fallidos + 1 END,
                       bloqueado_hasta = CASE WHEN bloqueado_hasta < now() THEN NULL ELSE bloqueado_hasta END
                 WHERE usuario = :u
                   AND (bloqueado_hasta < now() OR (bloqueado_hasta IS NULL AND fallidos < :max))
                RETURNING id, clave_hash, fallidos""")
                .param("u", usuario).param("max", props.maxFallidos())
                .query(Intento.class).optional();

        if (intento.isEmpty()) {
            bcrypt.coincide(clave, hashFalso);   // no existe o está bloqueado: la misma demora que un intento real
            return Optional.empty();
        }
        Intento i = intento.get();

        // 2. Comparar fuera de cualquier transacción, y dentro del bulkhead: si no hay lugar, 503 y el intento
        //    ya reservado cuenta como fallido (quien insiste sin parar no gana intentos gratis).
        if (!bcrypt.coincide(clave, i.claveHash())) {
            if (i.fallidos() >= props.maxFallidos()) {
                db.sql("UPDATE usuarios SET bloqueado_hasta = now() + make_interval(mins => :m) WHERE id = :id")
                        .param("m", props.bloqueoMinutos()).param("id", i.id()).update();
            }
            return Optional.empty();
        }

        // 3. Clave correcta: el contador vuelve a cero y nace la sesión.
        db.sql("UPDATE usuarios SET fallidos = 0 WHERE id = :id").param("id", i.id()).update();
        byte[] crudo = new byte[32];
        RANDOM.nextBytes(crudo);
        String token = Base64.getUrlEncoder().withoutPadding().encodeToString(crudo);
        db.sql("INSERT INTO sesiones (token_hash, usuario_id, vence) VALUES (:h, :id, now() + make_interval(mins => :m))")
                .param("h", sha256(token)).param("id", i.id()).param("m", props.sesionMinutos()).update();
        return Optional.of(token);
    }

    public Optional<Long> usuarioDe(String token) {
        return db.sql("SELECT usuario_id FROM sesiones WHERE token_hash = :h AND vence > now()")
                .param("h", sha256(token)).query(Long.class).optional();
    }

    static byte[] sha256(String s) {
        try {
            return MessageDigest.getInstance("SHA-256").digest(s.getBytes(StandardCharsets.UTF_8));
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
