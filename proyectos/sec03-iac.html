La excusa

Tienda Norte corre en tu máquina desde SEC00. El paso siguiente es una nube: un bucket para las fotos de los productos, una base PostgreSQL administrada, la red que separa la API de la base y un permiso de IAM para que la API lea y escriba fotos. Cada una de esas piezas tiene su error clásico: el bucket que queda público, el puerto 22 abierto a internet, la base con IP pública, la política con s3:*.

En M37 viste por qué esos errores son los que más incidentes causan en la nube. Esta guía los saca del incidente y los pone en el pull request: la infraestructura se escribe como código, el plan se calcula sin tocar ninguna cuenta y dos revisores automáticos lo leen antes de que alguien lo apruebe. Es la misma idea del gate de SEC01, aplicada a la nube.

No se crea nada en AWS. Todo corre en contenedores, en tu máquina y en GitHub Actions.

El plan en JSON tiene los valores de las variables: aquí no hay secretos en ellas, y la clave de la base no pasa por Terraform (lo verás en el paso 2).

Infraestructura como código

Analogía

Un plano de una casa contra una lista de instrucciones para el albañil. El plano dice cómo tiene que quedar; si ya hay una pared, nadie la vuelve a levantar. Terraform lee el plano (el HCL), mira la casa (el state) y te dice qué falta.

Cada recurso tiene una dirección, como aws_db_instance.tienda: el tipo y el nombre que le das en el HCL. Para Terraform esa dirección es la identidad del recurso. Si cambias el nombre, el plan dice borrar uno y crear otro, salvo que lo declares con un bloque moved (lo verás en la falla 6).

El state guarda todos los atributos de lo que creó, incluidas las claves que pasaron por Terraform. Por eso en esta guía ninguna clave pasa por Terraform, y por eso en producción el state vive en un backend cifrado con acceso restringido (Qué cambia en producción).

El plan sin cuenta

Analogía

Un simulador de vuelo: el piloto practica la ruta entera y el instructor revisa cada maniobra, pero el avión nunca despega. Si el piloto se equivoca, no se cae nada.

El provider de AWS, por defecto, le pregunta a AWS quién eres antes de hacer nada (la llamada sts:GetCallerIdentity). Con skip_credentials_validation y skip_requesting_account_id no lo hace Documentado, y como el state está vacío, el plan no tiene nada que leer de la cuenta: todo es crear. Funciona mientras el código no use data sources que consultan la cuenta (por ejemplo aws_ami o aws_caller_identity). El día que los use, el paso siguiente es un rol de solo lectura con OIDC, como explica 37.2; nunca llaves de administrador.

Políticas como código

Analogía

Un corrector ortográfico y la guía de estilo de tu editorial. El corrector ya sabe miles de reglas del idioma; la guía de estilo dice cosas que solo valen para tu casa, como "no usamos la región de Virginia".

Rego es el lenguaje de OPA, el motor de políticas que trae Conftest. Una regla deny contains msg if { … } se lee así: "el conjunto deny contiene msg si todas estas líneas son verdaderas". Cada línea es una condición; si una falla, la regla no agrega nada. Conftest 0.71 trae OPA 1.x, que usa la sintaxis de Rego v1 sin import rego.v1 Documentado.

HCL de por medio

var.region es una referencia a una variable, y "${var.region}a" (lo verás en el paso 2) es una interpolación dentro de una cadena, como un f-string de Python. Un bloque { … } con clave = valor es un objeto, parecido a un diccionario.

La decisión
Versiones exactas de Terraform y del provider, y el provider sin cuenta detrás de una variable.
Lo que descartas
Un rango como ~> 6.0: el plan de hoy y el de mañana podrían salir de dos providers distintos, con valores por defecto distintos.
Qué puede salir mal
Si alguien pone sin_cuenta = false por defecto, el pipeline empieza a fallar por falta de credenciales: que falle es lo correcto, no hay que "arreglarlo" con llaves.

Las fallas, a propósito

Cada falla va en una rama propia con su pull request, o en tu máquina con seguridad/infra.sh todo. Deshazla antes de la siguiente.

Falla 1: el bucket con política pública

Provócala. En infra/datos.tf, cambia block_public_policy = true por false.

Qué tiene que pasar. Checkov corta con CKV_AWS_54 sobre aws_s3_bucket_public_access_block.fotos. Si en lugar de eso borras el recurso entero, corta CKV2_AWS_6 sobre el bucket. Por qué importa. Con esa opción apagada, alguien puede ponerle al bucket una política con "Principal": "*" y las fotos (o lo que se suba después) quedan a la vista. Deshazla con git checkout infra/datos.tf.

Falla 2: SSH abierto a internet

Provócala. En el grupo api de infra/red.tf, agrega un ingress con from_port = 22, to_port = 22, protocol = "tcp", cidr_blocks = ["0.0.0.0/0"] y una description.

Qué tiene que pasar. Checkov corta con CKV_AWS_24 sobre aws_security_group.api. Por qué importa. Es lo primero que barren los escáneres de internet. La forma de entrar a una máquina sin abrir el 22 es Session Manager o un bastión, como en 37.3. Deshazla borrando el bloque.

Falla 3: la base con IP pública

Provócala. En infra/datos.tf, cambia publicly_accessible = false por true.

Qué tiene que pasar. Checkov corta con CKV_AWS_17 sobre aws_db_instance.tienda. Por qué importa. Con IP pública, el único control que queda es el security group. Un cambio en ese grupo y la base está en internet. Deshazla volviendo a false.

Falla 4: s3:* en la política de la API

Provócala. En infra/iam.tf, cambia la acción por Action = ["s3:*"].

Qué tiene que pasar. Checkov pasa: CKV_AWS_63 mira el asterisco solo, y CKV_AWS_62 el par asterisco en acción y recurso. Conftest corta con aws_iam_policy.api permite s3:*: nombra las acciones. Por qué importa. s3:* incluye s3:DeleteObject y s3:PutBucketPolicy: una inyección en la API podría borrar las fotos o hacer público el bucket. Es la razón de tener reglas propias. Deshazla volviendo a las dos acciones.

Falla 5: otra región

Provócala. Sin cambiar ningún archivo: seguridad/infra.sh plan -var region=us-east-1 y después seguridad/infra.sh conftest.

Qué tiene que pasar. El plan se calcula igual (no hay cuenta que diga que no) y Conftest corta con un solo mensaje: la región us-east-1 no está permitida. Las zonas cambian solas a us-east-1a y b por cómo se arman. Por qué importa. La región decide qué leyes aplican a los datos y dónde está tu monitoreo. Sin la regla, una persona con otro valor por defecto en su máquina crea una tienda paralela que nadie vigila. Deshazla volviendo a correr infra.sh plan sin la variable.

Limitaciones

  • Lo que no hace. No crea nada. Un plan que pasa no dice que el apply funcione: AWS puede rechazar una combinación (una versión de PostgreSQL que no existe en esa clase, un nombre de bucket ya tomado) que solo aparece al aplicar.
  • Dónde se rompe. El plan sin cuenta deja de servir el día que el código use data sources que leen la cuenta, o cuando haya un state con recursos: ahí el plan tiene que leer lo que existe, y hace falta un rol de solo lectura.
  • Riesgos que quedan. Las revisiones miran el código, no la cuenta. Un cambio hecho a mano en la consola no pasa por el pull request; eso se detecta comparando la cuenta con el state (terraform plan periódico) o con AWS Config.
  • Lo que Checkov no ve. Lee el HCL, así que una regla que depende de un valor calculado puede pasar o fallar distinto que en el plan. Checkov también puede leer el plan en JSON (--framework terraform_plan), que es el paso siguiente si encuentras diferencias.

Costo y tiempo, con la cuenta a mano

Con supuestos dichos como supuestos: si bajar las tres imágenes y el provider tarda 1 minuto, el plan 30 segundos, Checkov 1 minuto entre sus dos corridas y Conftest 10 segundos, cada pull request que toca infra/ usa unos 3 minutos de runner. Con 30 pull requests al mes son 90 minutos, gratis en un repositorio público y dentro de los minutos incluidos en uno privado. Lo que sí costaría es la nube descrita, que aquí no se crea: reemplaza estos supuestos por tus minutos y, si un día aplicas, saca el costo de la calculadora de AWS con la clase y el disco de datos.tf.

Qué cambia en producción

  • El state en un backend remoto (S3 con bloqueo, o Terraform Cloud), cifrado y con acceso solo para el rol que aplica.
  • Dos roles con OIDC de GitHub: uno de solo lectura para el plan de cada pull request y otro para el apply, que solo corre en main después de la aprobación, con un environment protegido.
  • El plan del pull request comentado en el mismo pull request, para que la persona que revisa lea qué cambia en la cuenta y no solo el diff del HCL.
  • Detección de deriva: un plan programado cada día que avisa si la cuenta se apartó del código.
  • Las reglas de Rego en un repositorio propio, compartido por todos los proyectos, con su versión.
