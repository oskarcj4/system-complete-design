Lo que no debe verse

Lo que tu servidor entrega sin que nadie lo pida: archivos ocultos, mensajes de error, versiones. Se cierra con una respuesta central, un registro fuera de htdocs y reglas de Apache que miran toda la ruta.

Al terminar podrás

  • Hacer que toda respuesta de la API salga por un solo lugar, con Content-Type: application/json, el código HTTP que le corresponde y sin el texto de ninguna excepción.
  • Mandar el detalle de cada error a un registro fuera de htdocs con un identificador que el cliente puede citar, y encontrarlo después.
  • Impedir que el backend arranque con la clave del ejemplo o sin las variables que necesita.
  • Cerrar desde Apache lo que no es de la web (.git/, notas, documentación, core/ y models/) y sacar el .env del alcance del servidor.

La excusa

Un atacante empieza mirando, no atacando. Pide /.git/config, /env.md, /README.md; provoca un error para ver si el mensaje trae una ruta o una consulta; mira la cabecera X-Powered-By para saber qué versión de PHP buscar. Nada de eso es un ataque todavía, y por eso pasa desapercibido. Esta guía cierra lo que tu servidor entrega sin que nadie lo pida.

En WEB00, el script lab/verificar.ps1 dejó una lista de rutas marcadas REVISAR. Ahora toca cerrarlas, y de paso arreglar la forma en que la API responde: hoy cada endpoint se acuerda de poner su Content-Type, los errores salen con HTTP 200 y Response::debugError sigue a un comentario de distancia de devolverle al cliente el mensaje de una excepción de PDO.

Los endpoints

Ningún endpoint cambia de función. Lo que cambia es el código HTTP con que responden los errores, y eso sí lo nota quien llama a la API:

Qué necesitas

El laboratorio de WEB00 andando, con su lab/verificar.ps1 y el archivo de cookies lab/jar.txt de una sesión de estudiante. No se instala nada nuevo: todo es PHP 8.3 y configuración de Apache.

La infraestructura

Dos cambios de configuración fuera del repositorio, que hace quien administra el servidor: que PHP no anuncie su versión y que Apache diga lo mínimo de sí mismo.

display_errors = Off
display_startup_errors = Off
log_errors = On
# C:\xampp\apache\conf\extra\httpd-default.conf

La decisión
expose_php = Off quita la cabecera X-Powered-By: PHP/8.3.x; ServerTokens Prod deja Server: Apache sin versión ni sistema; display_errors = Off en el php.ini además de en el código.
Lo que descartas
Creer que esconder la versión es seguridad: no lo es, y la guía no lo vende así. Lo que hace es que un escáner no te encuentre por una búsqueda de "PHP 8.3.x" con una CVE conocida. La defensa real es actualizar (XAMPP trae parches de PHP con cada versión).
Qué puede salir mal
Editar el php.ini equivocado: XAMPP puede tener más de uno. C:\xampp\php\php.exe --ini dice cuál carga la línea de comandos, y una página con phpinfo() cuál carga Apache; borra esa página en cuanto la mires.

Paso a paso

Paso 1. Una sola salida para todas las respuestas

core/response.php se reescribe entero. Conserva los nombres de los métodos y el orden de los parámetros que ya usan los endpoints y los modelos, así que nada más cambia de firma. Lo nuevo:

  1. Si quien llama no da un código HTTP, se deduce del code de la API con una tabla fija.
  2. Antes de escribir el cuerpo, se fijan siempre Content-Type, nosniff y Cache-Control: no-store.
  3. El JSON se codifica sin escapar los acentos y reemplazando los bytes UTF-8 inválidos en vez de fallar.
  4. debugError desaparece. En su lugar, serverError registra el detalle con un id y responde 500 con ese id.
<?php

declare(strict_types=1);

/**
 * Toda respuesta de la API sale por aquí: siempre JSON, siempre con el código HTTP
 * que corresponde y nunca con el texto de una excepción.
 */
class Response
{
    # code de la API -> código HTTP, cuando quien llama no indica uno
    private const HTTP_POR_CODIGO = [
        1  => 200,
        -1 => 400,
        -2 => 401,
        -3 => 405,
        -4 => 422,
    ];

    public static function json(int $code, string $message = "", mixed $data = [], ?int $httpCode = null): never
    {
        $httpCode ??= self::HTTP_POR_CODIGO[$code] ?? 400;
        if (!headers_sent()) {
            http_response_code($httpCode);
            header('Content-Type: application/json; charset=utf-8');
            header('X-Content-Type-Options: nosniff');
            header('Cache-Control: no-store');
        }
        echo json_encode(
            ["code" => $code, "message" => $message, "data" => $data],
            JSON_UNESCAPED_UNICODE | JSON_INVALID_UTF8_SUBSTITUTE
        );
        exit;
    }

    public static function success(mixed $data = [], string $message = "Operación exitosa"): never
    {
        self::json(1, $message, $data, 200);
    }

    public static function error(string $message = "Ocurrió un error", int $code = -1, ?int $httpCode = null): never
    {
        self::json($code, $message, [], $httpCode);
    }

    public static function invalidAccess(): never
    {
        self::json(-2, "No tienes permisos para acceder a este recurso", [], 403);
    }

    public static function invalidMethod(): never
    {
        self::json(-3, "Método no soportado", [], 405);
    }

    public static function invalidParams(): never
    {
        self::json(-4, "Parámetros inválidos", [], 422);
    }

    /** El detalle va al registro del servidor; el cliente recibe solo un id para citarlo. */
    public static function serverError(Throwable $e): never
    {
        $id = bin2hex(random_bytes(6));
        error_log(sprintf(
            '[api %s] %s: %s en %s:%d',
            $id, $e::class, $e->getMessage(), $e->getFile(), $e->getLine()
        ));
        self::json(-1, "Error interno. Referencia: $id", [], 500);
    }
}

PHP de por medio

never es el tipo de retorno de una función que no vuelve nunca (aquí, porque termina con exit). PHP 8.1 lo agregó, y sirve para que el analizador sepa que después de Response::error(...) no sigue nada. ??= asigna solo si la variable es null. Y llamar a un método estático desde un objeto, como hacen los modelos con $this->response->error(...), es válido en PHP: por eso esos modelos no cambian.

La decisión
Un solo lugar fija el tipo, el código HTTP y el formato; el código HTTP se deduce del code que la API ya usaba, para no tocar los 26 archivos que llaman a Response.
Lo que descartas
Agregar header('Content-Type…') a cada endpoint, que es lo que hay hoy: funciona hasta que alguien crea el endpoint 15 y se olvida. Tampoco conviene quitar el code del JSON y usar solo el HTTP: el frontend lo lee y la guía no lo rompe.
Qué puede salir mal
Que algún archivo llame a Response::json con un code que no es entero. El archivo nuevo usa declare(strict_types=1), pero esa directiva solo afecta a las llamadas que salen de él: un endpoint sin strict_types que pase "-1" se convierte a entero sin error. Si algo pasa un texto que no es número, PHP lanza TypeError y lo atrapa el manejador del paso 2.

Pruébalo ahora

Corre C:\xampp\php\php.exe -l api\core\response.php (tiene que decir No syntax errors detected) y después:

curl.exe -s -i -X PATCH http://localhost/SistemaControlPracticas/api/endpoints/login.php

La primera línea tiene que ser HTTP/1.1 405 Method Not Allowed y entre las cabeceras debe aparecer Content-Type: application/json; charset=utf-8.

Paso 2. Los errores, al registro

Tres piezas: un archivo que configura PHP para no mostrar nada y registrar todo, un manejador para las excepciones que nadie atrapa y un script que cambia los catch que hoy tragan la excepción y responden "Error".

<?php

declare(strict_types=1);

require_once __DIR__ . '/response.php';

# Hacia afuera, nada; hacia adentro, todo. El registro vive fuera de htdocs.
ini_set('display_errors', '0');
ini_set('display_startup_errors', '0');
ini_set('log_errors', '1');
ini_set('error_log', (string)Env::get('LOG_FILE', dirname(__DIR__, 4) . '/logs/practicas-api.log'));
error_reporting(E_ALL);

# Una excepción que ningún catch atrapó termina aquí y no en la pantalla de PHP.
set_exception_handler(function (Throwable $e): void {
    Response::serverError($e);
});

dirname(__DIR__, 4) sube cuatro carpetas desde api/core: api, SistemaControlPracticas, htdocs y C:/xampp. El registro queda en C:/xampp/logs/practicas-api.log, junto a los de Apache y lejos de cualquier URL. En un servidor con otra estructura, pon LOG_FILE en el .env.

Ahora el script que cambia los catch. Busca la forma que se repite en endpoints, modelos y connection.php, un Response::error(...) seguido del //Response::debugError(...) comentado, y la reemplaza por Response::serverError(...) con la misma variable:

param([string]$Api = "C:\xampp\htdocs\SistemaControlPracticas\api")

# (1) Un mensaje genérico ("Error" u "Ocurrio un error") seguido de //Response::debugError($e);
$generico = 'Response::error\("(?:Error|Ocurri[oó] un error)"(?:,\s*-?\d+)*\);\s*//\s*Response::debugError\((\$\w+)\);'
# (2) Cualquier otro comentario de debugError (detrás de un mensaje útil, que se conserva)
$suelto = '\r?\n[ \t]*//\s*Response::debugError\(\$\w+\);'

Get-ChildItem "$Api\endpoints", "$Api\models", "$Api\core" -Filter *.php | ForEach-Object {
  $texto = Get-Content $_.FullName -Raw
  $n = ([regex]::Matches($texto, $generico)).Count
  $m = ([regex]::Matches($texto, $suelto)).Count - $n
  if ($n + $m -gt 0) {
    $texto = [regex]::Replace($texto, $generico, 'Response::serverError($1);')
    $texto = [regex]::Replace($texto, $suelto, '')
    Set-Content -Path $_.FullName -Value $texto -NoNewline -Encoding utf8NoBOM
    "{0,-40} {1} a serverError, {2} comentario(s) quitado(s)" -f $_.Name, $n, $m
  }
}

Córrelo con pwsh .\lab\migrar-errores.ps1 sobre una rama limpia y revisa el resultado con git diff --stat y git diff api/models/carreras.php: cada cambio tiene que ser una línea Response::error("Error", -1, 500) que pasa a Response::serverError($e), y el comentario desaparece. Los catch (StorageException $e) de postulaciones.php y solicitudes_publicacion.php conservan su mensaje ("No se pudo guardar el archivo"), que sí le sirve a quien sube el CV: solo pierden el comentario. Al escribir esta guía, el repositorio tenía 92 de esos comentarios; las dos columnas del script, sumadas, deben dar el número que tengas tú (Select-String -Path api\*\*.php -Pattern "debugError" | Measure-Object). Los catch que no tenían el comentario (por ejemplo el de cambio_contrasena.php, que responde "Ocurrio un error") quedan igual: cámbialos a mano a Response::serverError($e);, y lista los que quedan con:

Select-String -Path api\endpoints\*.php, api\models\*.php, api\core\*.php -Pattern 'catch' -Context 0,2 |
  Where-Object { $_.Context.PostContext -notmatch 'serverError' }
La decisión
Separar lo que ve el cliente (un mensaje genérico y un id) de lo que ve quien opera (mensaje, clase, archivo y línea), y hacer la migración con un script que se revisa con git diff.
Lo que descartas
Dejar debugError "para desarrollo": es una línea comentada de distancia de estar en producción, y alguien la descomenta un viernes para entender un error. Tampoco se usa set_error_handler para convertir cada warning en excepción: es más estricto, pero cambiaría el comportamiento de código que hoy funciona con avisos silenciosos, y esta guía no reescribe tu lógica.
Qué puede salir mal
Que el registro no se pueda escribir (la carpeta no existe o Apache no tiene permiso): PHP no avisa al cliente, y simplemente no queda nada. Comprueba en la falla provocada 2 que la línea aparece. Y que el script de migración no encuentre nada porque el comentario tenga otra forma; el Select-String de arriba te lista lo que falta.

Paso 3. El arranque que se niega

env.php suma un método, exigir, que corta el arranque si una variable falta, está vacía o trae un valor de ejemplo. configuration.php lo llama antes de definir ninguna constante, y además busca primero el .env fuera de htdocs.

    /**
     * Corta el arranque si una variable falta, está vacía o trae un valor de ejemplo.
     * Se agrega a la clase Env, después del método get().
     */
    public static function exigir(array $claves, int $largoMinimoClave = 32): void
    {
        $deEjemplo = ['clave_secreta_cambiar', 'changeme', 'PEGA_AQUI_64_CARACTERES_HEX'];
        foreach ($claves as $clave) {
            $valor = (string)self::get($clave, '');
            if ($valor === '' || in_array($valor, $deEjemplo, true)) {
                self::fallar("$clave falta o tiene un valor de ejemplo");
            }
        }
        if (strlen((string)self::get('COOKIE_KEY', '')) < $largoMinimoClave) {
            self::fallar("COOKIE_KEY tiene menos de $largoMinimoClave caracteres");
        }
    }

    private static function fallar(string $motivo): never
    {
        error_log("[config] $motivo");
        http_response_code(500);
        header('Content-Type: application/json; charset=utf-8');
        echo '{"code":-1,"message":"Servidor mal configurado","data":[]}';
        exit;
    }
<?php
require_once(__DIR__ . "/env.php");

Env::load(is_file($envFuera) ? $envFuera : __DIR__ . '/.env');

require_once(__DIR__ . "/errores.php");

if (session_status() === PHP_SESSION_NONE) {
    # Nombre neutro: el predeterminado (PHPSESSID) delata que el backend es PHP
    session_name('sid');
    session_start();
}

Para sacar el .env de htdocs, crea la carpeta y muévelo; con eso, el archivo ya no tiene URL:

New-Item -ItemType Directory -Force C:\xampp\secretos | Out-Null
Move-Item C:\xampp\htdocs\SistemaControlPracticas\api\core\.env C:\xampp\secretos\practicas.env
La decisión
Fallar cerrado: un backend mal configurado no responde nada útil en vez de responder con una clave débil. Y el archivo de secretos fuera de la carpeta que Apache sirve.
Lo que descartas
Un valor por defecto para COOKIE_KEY en el código ("por si falta"): es la forma clásica de terminar con la misma clave en todas las instalaciones. Tampoco se exige PASSWORD_DB, porque el MariaDB de XAMPP viene con root sin clave y el laboratorio lo usa; en producción, súmala a la lista.
Qué puede salir mal
Que exigir corte también la línea de comandos y algún script tuyo deje de andar: es lo esperado si ese script usaba la clave del ejemplo. Y que el .env quede en los dos lugares: el código usa el de afuera, pero el de adentro sigue ahí para quien lo pida si el .htaccess falla. Bórralo.

Paso 4. Lo que Apache no tiene que entregar

El .htaccess raíz se reescribe con reglas que miran cualquier segmento de la ruta, no solo el final, y con un respaldo que funciona aunque mod_rewrite no esté cargado. Las reglas del frontend del final quedan como estaban.

Options -Indexes

<IfModule mod_rewrite.c>
  RewriteEngine On

  # (1) .well-known queda abierto (certificados ACME); todo otro segmento con punto, no
  RewriteRule ^\.well-known/ - [L]
  RewriteRule (^|/)\. - [F,L]

  # (2) Carpetas que no son de la web
  RewriteRule ^(database|docs|lab)(/|$) - [F,L,NC]
  RewriteRule ^frontend/node_modules(/|$) - [F,L,NC]
  RewriteRule ^api/(core|models)(/|$) - [F,L,NC]

  # (3) Archivos que no son de la web, estén donde estén
  RewriteRule \.(sql|env|log|lock|md|bak|old|swp|drawio)$ - [F,L,NC]
  RewriteRule (^|/)(package(-lock)?\.json|pnpm-lock\.yaml|vite\.config\.js)$ - [F,L,NC]

  # (4) Lo que ya estaba: estáticos y el frontend
  RewriteCond %{REQUEST_FILENAME} -f
  RewriteRule \.(css|js|png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf|webp)$ - [L,NC]
  RewriteCond %{REQUEST_FILENAME} !-f
  RewriteCond %{REQUEST_FILENAME} !-d
  RewriteRule ^$ frontend/ [L]
</IfModule>

# (5) Respaldo sin mod_rewrite: ningún archivo que empiece con punto
<FilesMatch "^\.">
  Require all denied
</FilesMatch>

(2)Carpetas del repositorio que no son la aplicación; core/ y models/ con la ruta real, api/core/database/seed.sql, /api/core/auth.php

La decisión
Reglas por segmento y por carpeta, más un respaldo con FilesMatch. La regla vieja para core y models no coincidía nunca, porque el .htaccess vive en la raíz del proyecto y la ruta que ve es api/core/…, no core/….
Lo que descartas
Mover .git fuera de htdocs con git --git-dir: funciona, pero complica cada comando de Git del equipo. La forma de producción es otra: desplegar solo api/, uploads/ y frontend/dist, sin el repositorio. Esta guía cierra el laboratorio y lo deja dicho en Limitaciones.
Qué puede salir mal
Que una regla bloquee algo que sí se usa: la (3) cierra .md en todo el sitio; si algún día sirves documentación en Markdown, ponla en otra carpeta con su propia regla. Y que RewriteRule (^|/)\. no cubra uploads/, que tiene su propio .htaccess con RewriteEngine Off: ahí manda Require all denied más la lista de extensiones que ya trae.

Paso 5. 401 y 403 no son lo mismo

Con la tabla del paso 1, Usuario no autenticado (code -2) ya sale como 401. Falta el otro caso: alguien con sesión válida pero sin el rol. Hoy requireAuth responde Response::error("Usuario no autorizado"), que la tabla convertiría en 400. Cambia esa línea en api/core/auth-middleware.php:

    if (!$esValido) {
        Response::error("Usuario no autorizado", -1, 403);
    }
La decisión
401 cuando falta la sesión ("identifícate"), 403 cuando sobra la sesión pero falta el permiso ("tú no"). Un cliente que recibe 401 puede mandar al login; con 403 no tiene sentido.
Lo que descartas
Responder 404 a quien no tiene el rol, para no revelar que el endpoint existe. Es válido para recursos de otros usuarios (lo hace WEB06 con BOLA), pero para un endpoint conocido como bitacora.php solo confunde al frontend.
Qué puede salir mal
Que el frontend muestre "Sesión expirada" ante un 403 porque trata igual cualquier error; revisa error.status en apiFetch si quieres distinguirlos.

Fallas provocadas

Falla 1. La clave del ejemplo. Pon COOKIE_KEY=clave_secreta_cambiar en C:\xampp\secretos\practicas.env y pide cualquier endpoint. Tiene que responder 500 con Servidor mal configurado, y el registro tiene que tener la línea [config] COOKIE_KEY falta o tiene un valor de ejemplo. Importa porque una clave conocida convierte la cookie firmada en una cookie que cualquiera fabrica: es preferible un servidor caído a uno que acepta un administrador inventado.

Falla 2. Una excepción con referencia. Cambia PASSWORD_DB a un valor incorrecto y repite el login. La respuesta tiene que ser 500 con Error interno. Referencia: seguido de doce caracteres hexadecimales, y el mensaje no debe decir nada de MariaDB. Busca la referencia en el registro:

Select-String -Path C:\xampp\logs\practicas-api.log -Pattern "REFERENCIA_QUE_TE_DIO"

La línea que aparece trae la clase (PDOException), el mensaje real de la base y el archivo y la línea. Eso es lo que antes podía llegar al cliente. Restaura la clave.

Falla 3. Sin mod_rewrite. Repite la falla 1 de WEB00 (renombrar el .htaccess) y corre verificar.ps1. Ahora el .env ya no está en htdocs, así que su ruta da 404 aunque el .htaccess falte. Las rutas de .git/ sí vuelven a salir: lo único que las cubre es el respaldo FilesMatch, que también vive en ese archivo, y por eso en producción el repositorio no se despliega. Devuelve el nombre.

Limitaciones
