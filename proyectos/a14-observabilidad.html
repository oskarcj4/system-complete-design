Observabilidad de un backend y su base

Un martes a las once, la lista de pedidos de la tienda empieza a tardar. Nadie cambió nada, o eso dicen. Construyes la API de la tienda y todo lo que hace falta para contestar en minutos tres preguntas: qué está lento, dónde se va el tiempo y por qué. Después rompes la tienda cuatro veces, a propósito, y sigues cada falla desde la alerta hasta la causa.

La excusa

La tienda vende 500 productos a 50 000 clientes y lleva un año guardando pedidos: dos millones de filas. Su API hace cuatro cosas: muestra un producto, lista los pedidos de un cliente, crea un pedido y arma un reporte de ventas por día. Un martes a las once, soporte avisa que «la app está lenta». ¿Toda? ¿Desde cuándo? ¿Para todos? Sin datos, la conversación es de adivinanzas: «será la base», «será Redis», «reinicia la API a ver».

Esta guía construye esa API y, alrededor, lo que convierte las adivinanzas en preguntas con respuesta. Cada request deja tres rastros: un número en un histograma, un trace con el tiempo de cada pieza y, si algo sale raro, una línea de log. Los tres llevan el mismo trace_id, y Grafana los enlaza. A eso se suman las métricas de la base, de PgBouncer y de Redis, que la API no ve, y dos objetivos escritos (un SLO de latencia y uno de disponibilidad) con alertas que avisan antes de que llame soporte.

Al final rompes la tienda cuatro veces y la arreglas: borras un índice, saturas el pool de conexiones con un reporte pesado, congelas Redis y agregas una etiqueta que no debías. Cada incidente deja una huella distinta en las señales, y aprender a leerlas es el objetivo de la guía.

Tres fronteras importan. La primera es tu máquina: nada de la telemetría sale de ella, y solo tres contenedores publican puertos (la API, Prometheus y Grafana), y solo en 127.0.0.1, así que nadie en tu red los ve. La segunda es la base: la API entra con un rol que puede leer tres tablas y crear pedidos, nada más, y cada consulta se corta a los 5 s; los exporters entran con roles que leen estadísticas pero no datos. La tercera es lo que viaja en la telemetría: los spans llevan el texto de las consultas, pero con parámetros ($1), no con valores; tú decides qué atributos con datos de clientes agregas. Los pasos 3 y 4 agregan el id del cliente dos veces, a propósito: en un span, donde sirve, y en una métrica, donde cuesta.

Trade-off

Cinco piezas de observabilidad separadas (Collector, Prometheus, Tempo, Loki y Grafana) en lugar de una imagen que las trae todas juntas, como grafana/otel-lgtm. La imagen única arranca en un minuto y alcanza para ver un trace; las piezas separadas te obligan a configurar cada enlace, y ese es el punto: cuando en producción el exemplar no lleve al trace, vas a saber qué archivo mirar. El precio es memoria: son doce contenedores. docker stats te dice cuánto usa cada uno en tu máquina.

Tres señales de una misma request

Observar un sistema es poder contestar preguntas sobre él que no anticipaste, sin cambiar su código. Para eso cada request deja tres tipos de rastro, las tres señales de M11:

  • Una métrica es un número que se agrega: cuántas requests hubo, cuántas fallaron, cuántas tardaron menos de 250 ms. Es barata (una request no crea nada nuevo, solo suma uno a un contador), pero no dice cuál request fue.
  • Un trace es el recorrido de una request, dividido en spans. Un span es un tramo con nombre, inicio y duración: «la consulta a pedidos tardó 300 ms». Los spans se anidan: el de HTTP contiene el del método, que contiene el de la consulta. Todos comparten un trace_id de 32 caracteres.
  • Un log es una línea de texto que escribe el código: «Redis no respondió al leer producto:31». Dice lo que el código sabe y el span no, y si lleva el trace_id, sabes a qué request pertenece.

Analogía

Un hospital. La métrica es el tablero de la sala de espera: 40 pacientes, 6 esperando más de una hora. El trace es la hoja de un paciente: llegó a las 10:02, triaje a las 10:05, rayos X de 10:20 a 11:40. El log es la nota de la enfermera: «la máquina de rayos X se trabó dos veces». El número de expediente, que aparece en las tres, es el trace_id.

El agente de OpenTelemetry

OpenTelemetry es un estándar abierto para producir y mandar las tres señales, con bibliotecas para muchos lenguajes. En Java tiene un agente: un jar que la JVM carga antes que tu aplicación, con -javaagent:opentelemetry-javaagent.jar. Cuando la JVM carga una clase de una biblioteca conocida (Spring MVC, el driver JDBC, HikariCP, Lettuce, Logback y cientos más), el agente le cambia el bytecode para que cree spans y métricas. Tu código no cambia ni se entera.

Lo que el agente no puede saber es lo que significa tu negocio: que esta consulta es de un cliente en particular, que el reporte es una operación propia, cuántos pedidos se crearon por canal. Eso lo agregas tú con la API de OpenTelemetry, que es solo un conjunto de interfaces: sin el agente, sus llamadas no hacen nada; con el agente, se conectan a su SDK. Lo ves en los pasos 3 y 4.

Java de por medio: qué es un javaagent

Un jar con una clase que tiene un método premain. La JVM lo llama antes del main de tu aplicación y le pasa un objeto Instrumentation, con el que el agente puede reescribir cada clase antes de que se use por primera vez. No es magia: es una API de la JVM desde Java 5, y la usan también los profilers y los APM comerciales.

OTLP y el Collector

OTLP es el protocolo de OpenTelemetry para mandar las señales: protobuf por HTTP (puerto 4318) o por gRPC (4317). El agente manda todo a una sola dirección, el Collector, un proceso aparte que recibe, procesa y reparte. Cada señal tiene su pipeline: receivers (por dónde entra), processors (qué se le hace: juntar en lotes, poner un tope de memoria) y exporters (a dónde sale).

¿Por qué no mandar directo de la API a Tempo, Prometheus y Loki? Porque la API conocería tres direcciones y tres formatos, y cada cambio de backend sería un deploy de la API. Con el Collector, la API conoce una sola, y el Collector absorbe los picos: si Tempo se cae un minuto, el que reintenta es él, no la API.

Histogramas y percentiles

Para saber qué tan lenta es una ruta no alcanza el promedio: diez requests de 10 ms y una de 2 s promedian 190 ms, y nadie esperó 190 ms. Se usan percentiles (M00): el p99 es la duración que el 99 % de las requests no supera. Pero guardar cada duración para ordenarlas es caro. Un histograma guarda solo cuántas requests cayeron hasta cada borde, llamado le («menor o igual»): 120 hasta 10 ms, 610 hasta 25 ms, y así. Las cuentas son acumuladas: cada cubeta incluye a las anteriores.

La cuenta del p99 con los números de la figura: de 1000 requests, el p99 es la request número 990. Hasta 100 ms van 975 y hasta 250 ms van 994, así que la 990 está en la cubeta de 100 a 250 ms, que tiene 994 − 975 = 19 requests. Es la número 990 − 975 = 15 de esas 19. Si están repartidas parejo, cae a 15 / 19 = 0.79 del ancho de la cubeta: 100 + 0.79 × 150 = 218 ms. Eso hace histogram_quantile en Prometheus. El resultado es una estimación: si las 19 requests tardaron todas 101 ms, el p99 real es 101 y el estimado sigue diciendo 218.

Por eso el umbral de un SLO tiene que ser un borde de cubeta. Las cubetas que el agente usa para la duración de HTTP incluyen 0.25 s, y «cuántas tardaron 250 ms o menos» se lee exacto de una sola cubeta: 994 de 1000, el 99.4 %. Con un umbral de 200 ms habría que interpolar, y la alerta dependería de la estimación.

RED y USE

Con tantas métricas, ¿cuáles miras primero? Dos recetas de M11. Para cada servicio, RED: Rate (requests por segundo), Errors (qué fracción falla) y Duration (los percentiles). Para cada recurso que se puede llenar, USE: Utilization (qué parte está ocupada), Saturation (cuánto trabajo espera) y Errors.

En esta guía, RED sale del histograma http.server.request.duration que crea el agente, separado por ruta, método y código de respuesta. USE sale de los exporters: el pool de PgBouncer, el de Hikari y Redis. Un tablero bien armado se lee de arriba abajo: primero RED, para saber qué ruta sufre; después USE, para saber qué recurso se llenó.

Dos filas antes de la base

La API no abre una conexión a PostgreSQL por request: usa un pool (M05). Aquí hay dos, uno detrás del otro. Hikari, dentro de la API, tiene 20 conexiones a PgBouncer. PgBouncer, en modo transaction, tiene 8 conexiones reales a PostgreSQL y se las presta a sus clientes una transacción a la vez. Si las 8 están ocupadas, la consulta espera en PgBouncer.

La ley de Little (glosario) dice cuánto aguanta cada fila: las conexiones ocupadas en promedio son las consultas por segundo por lo que tarda cada una. Una suposición para hacer la cuenta (tú medirás las tuyas): si el reporte de ventas tarda 0.4 s y 16 personas lo piden sin parar, quieren 16 conexiones a la vez, y hay 8. Las 8 se ocupan con reportes, que salen a 8 / 0.4 = 20 por segundo como mucho, y las otras 8 personas esperan. Una lista de pedidos que llega en ese momento queda en la fila detrás de ellos: espera del orden de un reporte o dos, entre 0.4 y 0.8 s, aunque su consulta tarde milisegundos.

La consecuencia es la lección más útil de la guía. pg_stat_statements mide desde que la consulta llega a PostgreSQL, así que dice «la lista de pedidos tarda 2 ms». El span de JDBC mide desde que la API manda la consulta, y con PgBouncer en modo transaction eso incluye la espera en la segunda fila: dice «800 ms». No se contradicen. La diferencia es la fila, y USE la muestra: cl_waiting mayor que cero.

Exemplars: del número al trace

Un p99 de 800 ms dice que algo anda mal, pero no cuál request mirar. Un exemplar (M11) es un trace_id que el SDK pega a un punto del histograma: «de las requests que cayeron en la cubeta de 500 a 750 ms, esta es una». Grafana lo dibuja como un rombo sobre la curva; un clic abre ese trace en Tempo. Y desde el trace, un botón abre en Loki los logs con el mismo trace_id.

Cardinalidad: las etiquetas se multiplican

Cada combinación de valores de etiquetas de una métrica es una serie distinta (M11), y cada serie cuesta memoria en el SDK, en el Collector y en Prometheus. Un contador de pedidos con la etiqueta canal (web, app, kiosko) tiene 3 series. Con cliente_id además, tiene una por cliente que compró y por canal: hasta 50 000 × 3 = 150 000.

El SDK de OpenTelemetry pone un tope: 2000 series por métrica. Pasado el tope, las mediciones nuevas van a una sola serie con el atributo otel.metric.overflow=true. La API no se queda sin memoria, pero esa métrica pierde el detalle justo cuando más lo necesitas. La cuenta del incidente que provocas en la comprobación: k6 crea 20 pedidos por segundo durante 5 minutos, 6000 pedidos, con clientes al azar entre 50 000. Los clientes distintos esperados son 50 000 × (1 − e−6000/50 000) = 50 000 × (1 − e−0.12) ≈ 5654, y el tope llega cuando hay 2000 distintos: tras unos 50 000 × ln(1 / 0.96) ≈ 2041 pedidos, poco más de un minuto y medio.

SLO, presupuesto y burn rate

Un SLO (M00) es un objetivo medible: «el 99 % de las listas de pedidos responde en 250 ms o menos, medido en 30 días». El 1 % restante es el presupuesto de errores: en 30 días, una de cada cien puede tardar más sin romper nada. Alertar cuando «hay requests lentas» no sirve, porque siempre hay alguna. Se alerta por burn rate (M11): cuántas veces más rápido que lo permitido se está gastando el presupuesto.

Las dos alertas de esta guía, con la cuenta. Un burn rate de 14.4 sostenido durante una hora gasta 14.4 / (30 × 24) = 2 % del presupuesto del mes; a ese ritmo dura 720 / 14.4 = 50 horas, y amerita despertar a alguien (page). Un burn rate de 6 durante seis horas gasta 6 × 6 / 720 = 5 % y, sostenido, dura 720 / 6 = 120 horas, 5 días: amerita un ticket. Cada alerta mira dos ventanas, una larga para no saltar con un pico y una corta para dejar de sonar en cuanto el problema se arregla: 1 h y 5 min para la rápida, 6 h y 30 min para la lenta.

¿Cuándo dispara la rápida si de golpe todas las listas tardan más de 250 ms? La fracción lenta de la última hora crece como t / 60 (t en minutos, si antes todo andaba bien), y tiene que pasar 14.4 × 1 % = 0.144: a los 0.144 × 60 ≈ 8.6 minutos. Más los 2 minutos del for y hasta 30 s de evaluación, unos 11 minutos. Si solo una fracción f de las requests se vuelve lenta, la de una hora llega a 0.144 a los 0.144 × 60 / f minutos, y con f menor que 0.144 la alerta rápida no dispara nunca: le toca a la lenta.

Un índice, y lo que pasa sin él

La lista de pedidos de un cliente pide sus 20 pedidos más recientes. Con un índice compuesto por (cliente_id, creado_en DESC) (M05), PostgreSQL baja por el árbol hasta el cliente y lee las entradas que ya están en el orden pedido. Sin el índice, lee la tabla entera.

Las cuentas a mano. Una fila de pedidos ocupa unos 76 bytes: 24 de cabecera, 4 del puntero de la página y unos 48 de datos (cinco columnas de 8 bytes, dos de 4 y el canal, con relleno). Dos millones de filas son unos 152 MB: 152 000 000 / 8192 ≈ 18 600 páginas de 8 KB. Cada cliente tiene, en promedio, 2 000 000 / 50 000 = 40 pedidos. Con el índice: 3 o 4 páginas de árbol, una o dos de hojas y hasta 20 de la tabla, unas 25. Sin él: las 18 600, en cada request. El tamaño real lo verás en el paso 1, y el plan, con EXPLAIN (M05), en la comprobación.

La decisión
Todo en un compose, con la API como un contenedor más, y solo tres puertos publicados en 127.0.0.1. Los exporters y los backends se hablan por la red interna.
Lo que descartas
Correr la API en tu IDE: el agente se puede cargar ahí también, pero la API tendría que llegar a PgBouncer, a Redis y al Collector por puertos publicados, y habría el doble de cosas que configurar. En la sección de pruebas la API corre fuera de Docker, sin agente.
Qué puede salir mal
Que el primer up parezca colgado: es la semilla, que tarda minutos. docker compose logs -f postgres te muestra el avance. Y que falte memoria: con doce contenedores, revisa docker stats.

Errores típicos

  • required variable POSTGRES_PASSWORD is missing a value: falta en .env: no copiaste .env.example a .env, o lo dejaste vacío.
  • Bind for 127.0.0.1:8014 failed: port is already allocated: otro proceso usa el puerto. Cambia el número de la izquierda (127.0.0.1:8015:8080) y usa ese en los comandos.
  • failed to solve: lstat …/target: no such file or directory al construir tienda: falta el JAR. Corre ./mvnw -DskipTests package antes de docker compose up --build.

@RestController
@RequestMapping("/v1")
public class Api {

    private final Catalogo catalogo;
    private final Pedidos pedidos;
    private final Reportes reportes;
    private final Metricas metricas;

    public Api(Catalogo catalogo, Pedidos pedidos, Reportes reportes, Metricas metricas) {
        this.catalogo = catalogo;
        this.pedidos = pedidos;
        this.reportes = reportes;
        this.metricas = metricas;
    }

    @GetMapping("/productos/{id}")
    public Catalogo.Producto producto(@PathVariable long id) {
        return catalogo.buscar(id)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "no existe el producto " + id));
    }

    @GetMapping("/clientes/{id}/pedidos")
    public List<Pedidos.Resumen> pedidosDe(@PathVariable long id, @RequestParam(defaultValue = "20") int limite) {
        if (limite < 1 || limite > 100) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "limite va de 1 a 100");
        }
        return pedidos.deCliente(id, limite);
    }
    @PostMapping("/pedidos")
    public ResponseEntity<Map<String, Long>> crear(@RequestBody Pedidos.Nuevo nuevo) {
        if (!Metricas.CANALES.contains(nuevo.canal())) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "canal desconocido");
        }
        if (nuevo.cantidad() < 1 || nuevo.cantidad() > 20) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "cantidad va de 1 a 20");
        }
        long id = pedidos.crear(nuevo);
        metricas.pedidoCreado(nuevo.canal(), nuevo.clienteId());
        return ResponseEntity.status(HttpStatus.CREATED).body(Map.of("id", id));
    }

    @GetMapping("/reportes/ventas")
    public List<Reportes.VentaDia> ventas(@RequestParam(defaultValue = "30") int dias) {
        if (dias < 1 || dias > 90) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "dias va de 1 a 90");
        }
        return reportes.ventas(dias);
    }

La decisión
El agente crea los spans de HTTP, JDBC y Redis; tú solo agregas lo que significa algo para el negocio: el cliente en el span, el reporte como span propio y, en el paso 4, el contador de pedidos.
Lo que descartas
Crear spans a mano en cada método con tracer.spanBuilder(…). Es más control, pero mucho código que hay que mantener, y es fácil olvidar el end() o el makeCurrent().
Qué puede salir mal
Que un atributo lleve datos personales: el id del cliente es un número opaco, pero un email o un nombre en un span quedan guardados en Tempo, con su propia retención, fuera de las reglas de la base.

La decisión
Un backend por señal (Prometheus, Tempo, Loki), con Grafana arriba y los enlaces configurados en archivos.
Lo que descartas
Un solo backend para las tres señales, como Elasticsearch o un SaaS de observabilidad. Es más simple de operar, pero cada señal tiene un patrón de acceso distinto (las métricas se agregan, los traces se buscan por id, los logs se filtran por texto), y los backends especializados son mucho más baratos por dato guardado.
Qué puede salir mal
Que un enlace no lleve a nada porque un nombre no coincide (la etiqueta del exemplar, el campo del log). Grafana no avisa: el botón simplemente no aparece.

9. Los exporters: lo que la API no ve

La API sabe cuánto tardó su consulta, pero no por qué: si esperó en PgBouncer, si PostgreSQL leyó la tabla entera, si Redis está vivo. Eso lo saben PgBouncer, PostgreSQL y Redis, y cada uno lo publica a su manera: SHOW POOLS, la vista pg_stat_statements, el comando INFO. Un exporter es un proceso chico que hace esas consultas cuando Prometheus le pide /metrics y traduce las respuestas a métricas. Ya están en compose.yaml y arrancaron en el paso 7; aquí compruebas que funcionan y aprendes qué publica cada uno.

La decisión
Un exporter por servicio, con un rol o un usuario que solo puede leer estadísticas.
Lo que descartas
Que la API publique las métricas de la base consultándolas ella misma. La API no tiene permiso para leer pg_stat_statements (y no debe tenerlo), y si la API se cae, perderías las métricas de la base justo cuando más las necesitas.
Qué puede salir mal
Que un exporter lento atrase los scrapes, o que su consulta pese en la base. pg_stat_statements con limit=20 es barata; un exporter con consultas propias sobre tablas grandes puede no serlo.

Errores típicos

  • "health":"down" en postgres: el exporter no pudo entrar. docker compose logs postgres-exporter dice por qué; si es password authentication failed, la contraseña de monitor no coincide con la de .env.
  • Ninguna métrica pg_stat_statements_*: falta el colector --collector.stat_statements, o la extensión no está en shared_preload_libraries.
  • pgbouncer_up 0: el usuario pgb_monitor no está en stats_users, o no está en la lista de DATABASE_URLS y PgBouncer no conoce su contraseña.

  • El SLO es de 30 días, pero Prometheus guarda 7: las alertas por burn rate funcionan (la ventana más larga es de 6 horas), pero cuánto presupuesto queda en el mes no se puede calcular aquí.

Dónde se rompe

  • El Collector es un solo proceso. Si se cae, el agente reintenta un rato con lo que tiene en memoria y después descarta: pierdes telemetría, no requests.
  • Prometheus, Tempo y Loki guardan en el disco de un contenedor. Si se llena el disco o se borra el volumen, se pierde la historia.
  • El p99 es una estimación dentro de una cubeta. Con las cubetas del agente, entre 250 y 500 ms no se distingue 260 de 490. Un SLO con un umbral que no es un borde necesita cubetas propias.
  • pg_stat_statements guarda 5000 consultas distintas por defecto (pg_stat_statements.max); una aplicación que arma SQL con valores en el texto en lugar de parámetros las llena y desplaza las que importan.
  • Las etiquetas de RED son tan buenas como http.route: si una ruta no tiene plantilla (un 404 de una URL inventada, por ejemplo), el agente no puede usar la URL como ruta, porque cada URL sería una serie.

Riesgos que quedan

  • La telemetría es una copia de tus datos con otras reglas. Los spans de JDBC llevan el texto de la consulta sin valores, pero un atributo que agregues, un mensaje de excepción o un log pueden llevar un email, un token o una dirección. Lo que entra a Loki y a Tempo queda ahí 72 horas, fuera de los permisos de la base.
  • El rol monitor puede leer el texto de todas las consultas de todos los usuarios en pg_stat_statements. Si alguien escribe valores en el SQL en lugar de usar parámetros, esos valores quedan visibles para quien vea el tablero.
  • Prometheus, Tempo y Loki no tienen autenticación. Aquí no se ven desde fuera de Docker (salvo Prometheus, en 127.0.0.1); en una red compartida, cualquiera que llegue a ellos lee todo.
  • El agente corre con todos los permisos de la JVM. El --checksum del Dockerfile asegura que es el jar publicado; actualizarlo es cambiar la versión y el hash juntos, a mano.

Costo y latencia, con la cuenta

Las cuentas son a mano y con supuestos dichos como supuestos; los tuyos los mides con las consultas de cada punto.

  • Series del histograma de HTTP. Cada combinación de ruta, método y código crea una serie por borde de cubeta, más +Inf, _sum y _count. Con las 14 cubetas por defecto del agente, son 17 series por combinación. Con 4 rutas y unos 2 códigos cada una, unas 8 combinaciones: unas 136 series. Lo comprobarás con count({__name__=~"http_server_request_duration_seconds.*"}). Los exporters publican muchas más: prometheus_tsdb_head_series te dice el total. Cuánta memoria cuesta cada serie lo calcula M11.
  • Volumen de traces. Supuesto: 3 spans por request y 1 KB por span sin comprimir. A 20 requests por segundo: 20 × 3 = 60 spans por segundo, 60 × 86 400 = 5 184 000 por día, unos 5 GB por día antes de comprimir. A 2000 requests por segundo, 100 veces más. Por eso en producción se muestrea. El tamaño real lo ves en el volumen: docker system df -v.
  • Lo que agrega el agente. Más tiempo de arranque y algo de CPU y memoria por cada span. No hay un número general: compáralo tú. Quita -javaagent del ENTRYPOINT, reconstruye, corre la misma carga 10 minutos y compara el p50 y el p99 del resumen de k6 con los de tu línea de base.
  • La memoria de doce contenedores. docker stats --no-stream. Anota cuánto usan Prometheus, Loki, Tempo y el Collector juntos, contra la API.

Qué cambia en producción

  • Muestreo en la cola. El Collector espera a que termine el trace y se queda con todos los que tienen error o pasan de un umbral, y con una fracción del resto (tail sampling). Requiere que todos los spans de un trace lleguen al mismo Collector.
  • Dos niveles de Collector. Uno junto a cada servicio (agente) y un grupo central (gateway) que muestrea, limpia atributos con datos personales y reparte.
  • Almacenamiento en objetos. Tempo y Loki guardan en S3 o GCS, y Prometheus manda a un almacén de largo plazo (Mimir, Thanos o uno administrado) para cubrir los 30 días del SLO.
  • Alertas que llegan. Alertmanager con rutas por severidad, silencios y un runbook_url en cada alerta (M11).
  • Seguridad entre piezas. TLS entre el agente, el Collector y los backends, autenticación en Grafana con el proveedor de identidad de la empresa, y multi-tenant en Loki y Tempo.
  • Cardinalidad con dueño. Un límite por métrica en el SDK y en el backend, y una alerta cuando una métrica crece de golpe.

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A02, una API que no se rompe

    El catálogo de un millón de libros tiene la misma pregunta que la lista de pedidos: ¿la consulta usa el índice? Con pg_stat_statements y el agente en A02, puedes comparar la paginación por OFFSET contra la de cursor con EXPLAIN y con el span de cada página (M02).

  • Con A03, la caché del día de ofertas

    El acierto de caché de este tablero es la métrica que A03 calculaba a mano. Con el agente, cada GET a Redis es un span: en un stampede (glosario) verías decenas de spans de la misma consulta a la base en el mismo instante.

  • Con A04, primario y réplicas

    postgres-exporter también publica el atraso de las réplicas. Con un SLO de «leer lo que escribiste» y una alerta sobre ese atraso, el problema de A04 deja de ser una sorpresa (M05).

  • Con A09, colas y pub/sub

    El agente propaga el contexto del trace en las cabeceras de los mensajes: el trace de un pedido sigue del productor al consumidor que manda el correo. El lag del consumer group es la métrica de USE de la cola (M11).

  • Con A12, sesiones, cookies y CSRF

    Un panel de administración es justo donde un log o un atributo pueden filtrar una cookie de sesión o un token CSRF. Revisa qué atributos agrega el agente a los spans de HTTP en A12 y qué escriben tus logs, antes de mandarlos a Loki (M10).
