La excusa

En desarrollo, el frontend corre en http://localhost:5173 y llama a /SistemaControlPracticas/api/..., una ruta relativa. El proxy de Vite la manda a Apache. Para el navegador, la página y la API son el mismo origen, y la política del mismo origen no tiene nada que frenar: las 14 cabeceras Access-Control-* de CORS de los endpoints no las lee nadie.

Por eso nadie notó lo que pasa cuando el frontend llama a Apache directo (otro puerto, otro host, el frontend compilado en un CDN):

  • Ninguna escritura funciona, salvo el login. Toda escritura lleva X-CSRF-Token, una cabecera propia, y eso dispara un preflight. El preflight es un OPTIONS sin cookie. Solo login.php lo responde; los otros 13 endpoints lo mandan a requireAuth, que responde 401, y el navegador cancela la request real.
  • El origen está escrito 14 veces. Sumar uno (producción, una vista previa) es editar 14 archivos, y cambio_contrasena.php ya tiene una copia rota: Access-Control-Alow-Methods, con una sola l.
  • Falta Vary: Origin. Con un único origen fijo no importa. El día que la respuesta dependa del Origin, un caché intermedio puede servirle a un origen la respuesta calculada para otro.

Y el riesgo de verdad: cuando esto se rompa, el arreglo que aparece primero en cualquier buscador es devolver el Origin que llegue, o un *. Esta guía hace el arreglo correcto antes de que alguien haga el otro. Es el hallazgo F de la re-auditoría.

El frontend, con o sin proxy

Para probar CORS de verdad hace falta un frontend que llame a Apache directo. Hoy BASE_API es una ruta relativa y no se puede cambiar sin editar el código. Una línea la vuelve configurable, y sin la variable todo queda como estaba:

Remove-Item Env:VITE_API_BASE
La decisión
Una variable de Vite con la ruta relativa por defecto: el modo de siempre no cambia, y el modo sin proxy se prende para una prueba y se apaga.
Lo que descartas
Sacar el proxy de vite.config.js: obligaría a todo el equipo a tener CORS bien configurado para trabajar, y M75 recomienda justamente lo contrario para un sistema como este, el mismo origen. Esta guía deja CORS bien hecho para el día que haga falta, sin imponerlo.
Qué puede salir mal
Olvidar la variable puesta en la consola y creer que se está probando con el proxy. Get-ChildItem Env:VITE_API_BASE dice si sigue ahí. Vite lee la variable al arrancar: si la cambias, reinicia npm run dev.

Paso a paso

Paso 1. cors.php

Dos funciones: una que calcula las cabeceras sin enviarlas, para poder probarla sin servidor, y otra que las envía y termina el preflight.

  1. Siempre: Vary: Origin, porque la respuesta cambia según quién pregunta.
  2. Si el Origin no está en la lista exacta, nada más: sin Access-Control-Allow-Origin, el navegador no deja leer.
  3. Si está: ese mismo origen (nunca *) y Allow-Credentials.
  4. Si es un preflight: los métodos del endpoint, las dos cabeceras que manda el frontend y diez minutos de caché. Responde 204 y termina, antes de la sesión.
<?php

declare(strict_types=1);

require_once __DIR__ . '/origen.php';

/**
 * Las cabeceras CORS de una respuesta, sin enviarlas (así se prueban sin servidor).
 * $lista existe para la prueba; en el servidor sale del .env.
 */
function cabecerasCors(?string $origen, string $metodo, array $metodos, ?array $lista = null): array
{
    $h = ['Vary' => 'Origin'];
    if ($origen === null || !esOrigenPermitido($origen, $lista)) {
        return $h;
    }
    $h['Access-Control-Allow-Origin'] = $origen;   # ya comparado con la lista: no es texto ajeno
    $h['Access-Control-Allow-Credentials'] = 'true';

    if ($metodo === 'OPTIONS') {
        $h['Access-Control-Allow-Methods'] = implode(', ', $metodos);
        $h['Access-Control-Allow-Headers'] = 'Content-Type, X-CSRF-Token';
        $h['Access-Control-Max-Age'] = '600';
    } else {
        $h['Access-Control-Expose-Headers'] = 'Retry-After';   # el 429 del login (WEB02)
    }
    return $h;
}

/** Primera línea de cada endpoint. El preflight termina aquí: no trae cookie y no llega a requireAuth. */
function aplicarCors(array $metodos): void
{
    $metodo = strtoupper((string)($_SERVER['REQUEST_METHOD'] ?? 'GET'));
    $origen = isset($_SERVER['HTTP_ORIGIN']) ? (string)$_SERVER['HTTP_ORIGIN'] : null;

    foreach (cabecerasCors($origen, $metodo, $metodos) as $nombre => $valor) {
        header("$nombre: $valor", $nombre !== 'Vary');   # Vary se suma a otro Vary, no lo pisa
    }
    if ($metodo === 'OPTIONS') {
        http_response_code(204);
        exit;
    }
}

Si no hiciste WEB03, crea api/core/origen.php con solo las dos primeras funciones:

<?php

declare(strict_types=1);

require_once __DIR__ . '/response.php';

function origenesPermitidos(): array
{
    static $lista = null;
    if ($lista === null) {
        $lista = array_values(array_filter(array_map('trim',
            explode(',', (string)Env::get('ORIGENES_PERMITIDOS', '')))));
    }
    return $lista;
}

function esOrigenPermitido(string $origen, ?array $lista = null): bool
{
    return $origen !== 'null' && in_array($origen, $lista ?? origenesPermitidos(), true);
}

PHP de por medio

El segundo argumento de header() dice si la cabecera reemplaza a otra con el mismo nombre (true, el valor por defecto) o se suma (false). Vary se suma porque otra parte del código podría haber puesto Vary: Accept-Encoding. El ?string del parámetro acepta un texto o null: un Origin ausente (null) no es lo mismo que un Origin: null literal, que mandan los iframes con sandbox y los archivos locales.

La decisión
La lista exacta del .env, el origen devuelto solo después de compararlo, y el preflight resuelto en la primera línea del endpoint, como en la política de M75.
Lo que descartas
Access-Control-Allow-Origin: *: el navegador no deja leer con * una respuesta pedida con credenciales, así que no funcionaría, y si alguien quita las credenciales para que funcione, deja de mandarse la cookie. Tampoco una expresión regular sobre el origen: /localhost:5173/ acepta http://localhost:5173.atacante.test. Y la lista en una constante, como en M75: sirve, pero cambiar de entorno sería cambiar código.
Qué puede salir mal
Devolver el Origin sin comparar: es la falla 1, y además mete en una cabecera un texto que escribe el cliente. Y poner aplicarCors después de requireAuth: el preflight no trae cookie, recibe 401 y el navegador cancela la request real (falla 2).

Paso 2. Los 14 endpoints

Un script quita de cada endpoint las líneas header("Access-Control-...") (todas, también la que tiene la errata) y pone en su lugar la llamada, justo antes de la línea de Content-Type. Sin -Aplicar solo cuenta qué haría; con -Aplicar escribe. Córrelo desde la raíz del proyecto.

# Reemplaza las cabeceras CORS copiadas en cada endpoint por aplicarCors([...]).
# Uso: .\lab\migrar-cors.ps1            (solo muestra)
#      .\lab\migrar-cors.ps1 -Aplicar   (escribe los archivos)
param([switch]$Aplicar)

$todos = "'GET', 'POST', 'PUT', 'DELETE'"
$metodos = [ordered]@{
  'asignaciones_roles.php'           = "'GET', 'POST', 'DELETE'"
  'bitacora.php'                     = "'GET'"
  'cambio_contrasena.php'            = "'PUT'"
  'carreras.php'                     = $todos
  'estadisticas.php'                 = "'GET'"
  'historial_estado_postulacion.php' = $todos
  'instituciones.php'                = $todos
  'login.php'                        = "'GET', 'POST', 'DELETE'"
  'notificaciones.php'               = $todos
  'oportunidades.php'                = $todos
  'postulaciones.php'                = $todos
  'roles.php'                        = $todos
  'solicitudes_publicacion.php'      = $todos
  'usuarios.php'                     = $todos
}
$cors = [regex]'(?m)^header\("Access-Control-[^\r\n]*\r?\n'
$tipo = [regex]'(?m)^header\("Content-Type: application/json"\);'
$utf8 = New-Object System.Text.UTF8Encoding($false)

foreach ($archivo in $metodos.Keys) {
  $ruta  = Join-Path 'api\endpoints' $archivo
  $texto = [IO.File]::ReadAllText((Resolve-Path $ruta))
  $n = $cors.Matches($texto).Count
  if ($n -eq 0) { "{0,-34} sin cabeceras CORS: ¿ya migrado?" -f $archivo; continue }
  if (-not $tipo.IsMatch($texto)) { "{0,-34} REVISAR: no tiene la línea de Content-Type" -f $archivo; continue }

  $llamada = 'require_once __DIR__ . "/../core/cors.php";' + "`r`n" + "aplicarCors([$($metodos[$archivo])]);" + "`r`n"

  if ($Aplicar) { [IO.File]::WriteAllText((Resolve-Path $ruta), $nuevo, $utf8) }
}
if (-not $Aplicar) { "`nNada se escribió. Revisa la lista y vuelve a correr con -Aplicar." }

Pruébalo ahora

Corre primero .\lab\migrar-cors.ps1, sin -Aplicar. Tienen que salir 14 líneas: login.php quita 4 (también Allow-Headers), las demás quitan 3. Si alguna dice REVISAR, ese archivo no tiene la forma esperada y va a mano. Con la lista bien, córrelo con -Aplicar y revisa el resultado con git diff --stat: 14 archivos cambiados. Después, C:\xampp\php\php.exe -l sobre cada uno tiene que decir No syntax errors detected.

La decisión
Un script que escribe solo con -Aplicar y cuenta antes, sobre una tabla de métodos leída de los case de cada archivo, no de la lista copiada.
Lo que descartas
Poner aplicarCors dentro de requireAuth: el preflight tiene que terminar antes, y además login.php no siempre llama a requireAuth. Tampoco poner la política en el .htaccess con Header set: Apache no sabe qué métodos atiende cada endpoint, y la lista de orígenes viviría en dos lugares.
Qué puede salir mal
Que el script deje archivos con BOM o cambie los finales de línea: escribe UTF-8 sin BOM, y la llamada nueva usa CRLF como el resto del repositorio; git diff muestra si algo más cambió. Si un archivo quedó mal, git checkout -- api/endpoints/<archivo> lo vuelve atrás.

Paso 3. El preflight viejo de login.php

login.php era el único que respondía el preflight, con un bloque propio. Ahora lo hace aplicarCors, así que el bloque sobra. Bórralo a mano:

La decisión
Un solo lugar que responde el preflight, el mismo para los 14 endpoints.
Lo que descartas

El botón 3 es un cierre de sesión: si llega a pasar, lo único que hace es sacarte del frontend. No hay datos en juego. Abre la página en http://atacante.test/web04.html y en http://localhost:8081/web04.html, antes y después de los pasos 1 a 3, y anota en la tabla.

Errores típicos

  • El botón 1 dice Failed to fetch y nada más. Es lo esperado cuando CORS no deja leer: el navegador no le da al JavaScript el motivo, a propósito. El motivo exacto lo escribe en Console.
  • El botón 2 muestra un OPTIONS en Network pero no un POST. También es lo esperado: si el preflight no autoriza, la request real nunca sale.
  • Desde localhost:8081 el botón 1 lee la sesión sin haber tocado nada. Algo devuelve el Origin: revisa que la migración no haya dejado una línea vieja y que 8081 no esté en ORIGENES_PERMITIDOS.
La decisión
Leer, escribir con preflight y reusar el token, en ese orden, que son las tres cosas que CORS decide.
Lo que descartas
Pedir algo con datos sensibles reales: la sesión del estudiante de seed.sql alcanza para ver si se puede leer. Tampoco se prueban formas de saltar el navegador: cada botón es una llamada normal de fetch.
Qué puede salir mal
Probar con la sesión cerrada en la otra pestaña: el botón 1 devuelve un 401 y parece que la política funciona, cuando en realidad no había nada que leer.

Cómo comprobar que funciona

La prueba sin servidor

cabecerasCors no envía nada, así que se prueba con una lista fija y sin .env. Cada caso es un origen que alguna vez se coló en una política real.

<?php

declare(strict_types=1);

require __DIR__ . '/../api/core/cors.php';

$fallos = 0;
function caso(string $nombre, bool $esperado, bool $obtenido): void
{
    global $fallos;
    $ok = $esperado === $obtenido;
    if (!$ok) {
        $fallos++;
    }
    printf("%s %s\n", $ok ? 'ok    ' : 'FALLA ', $nombre);
}

$lista = ['http://localhost:5173', 'http://localhost'];
$lee = fn(?string $o): bool => array_key_exists('Access-Control-Allow-Origin', cabecerasCors($o, 'GET', ['GET'], $lista));

caso('el frontend lee',                      true,  $lee('http://localhost:5173'));
caso('Apache sin puerto lee',                true,  $lee('http://localhost'));
caso('otro sitio no',                        false, $lee('http://atacante.test'));
caso('el vecino del mismo sitio no',         false, $lee('http://localhost:8081'));
caso('Origin: null no',                      false, $lee('null'));
caso('el permitido como prefijo no',         false, $lee('http://localhost:5173.atacante.test'));
caso('con barra al final no',                false, $lee('http://localhost:5173/'));
caso('https no es http',                     false, $lee('https://localhost:5173'));
caso('sin Origin no hay CORS',               false, $lee(null));

$rechazo = cabecerasCors('http://atacante.test', 'GET', ['GET'], $lista);
caso('Vary también en un rechazo',           true,  ($rechazo['Vary'] ?? '') === 'Origin');

La matriz con curl

curl no aplica CORS, pero muestra las cabeceras que el servidor manda, y eso es todo lo que CORS es del lado del servidor. Los preflights van sin cookie, como los manda el navegador.

# Sesión de estudiante (lab\login.json es el de WEB00)
& curl.exe -s -o NUL -c $Jar -H "Content-Type: application/json" --data-binary "@lab\login.json" "$Base/login.php"

function Cabecera([string[]]$respuesta, [string]$nombre) {
  $linea = $respuesta | Where-Object { $_ -match "^${nombre}:" } | Select-Object -First 1
  if ($linea) { ($linea -replace "^${nombre}:\s*", '').Trim() } else { '(ninguna)' }
}
function Fila($nombre, $cabecera, $esperado, [string[]]$extra, [switch]$Preflight) {

}

Fallas provocadas

Falla 1. El arreglo de internet. En cabecerasCors, cambia la condición por if ($origen === null) {: devuelve cualquier Origin que llegue. Corre tests\cors_test.php (seis casos tienen que fallar) y repite la página del paso 4. El diseño espera lo de la figura WEB04.2: desde atacante.test, el botón 1 lee un 401, porque la cookie Strict no viajó; desde localhost:8081, lee tu nombre y tu csrfToken. Después, el botón 3 manda ese token: con WEB03 aplicada, requireOrigenConfiable lo corta con 403 (Origin no permitido); sin WEB03, cierra tu sesión del frontend. Vuelve la condición a su lugar.

Falla 2. El preflight detrás de la sesión. En un endpoint, por ejemplo notificaciones.php, mueve aplicarCors(...) debajo de requireAuth(). Con el frontend sin proxy, marcar una notificación como leída falla, y Console dice que el preflight no tuvo un estado HTTP correcto (el texto exacto depende del navegador). Es el estado de hoy de 13 endpoints. Vuelve la línea arriba.

Falla 3. El asterisco. En cabecerasCors, pon $h['Access-Control-Allow-Origin'] = '*';. Desde el frontend sin proxy, todo lo que va con credentials: 'include' (o sea, todo) deja de poder leerse: el navegador rechaza * junto con credenciales, y Console lo dice. El caso nunca un asterisco de la prueba falla. Vuelve la línea.

Limitaciones

  • CORS no frena requests. Decide quién lee la respuesta, en el navegador. Un formulario de otro sitio sigue llegando a PHP; lo que frena eso es WEB03.
  • El proxy sigue siendo lo más simple. Con el frontend y la API en el mismo origen, nada de esta guía se usa. Esta política queda lista para el día que haga falta.
  • Un origen permitido es de confianza total. Si el frontend de localhost:5173 tiene un XSS, ese script lee y escribe con tu sesión: está en la lista. Eso es WEB05.
  • El preflight cuesta una ida y vuelta. Max-Age: 600 lo reusa diez minutos por URL; Chrome pone un tope de dos horas y Firefox de un día Documentado. Sobre localhost no se nota; con 80 ms de latencia hasta el servidor, la primera escritura a cada URL tarda unos 80 ms más (una ida y vuelta, el supuesto es la latencia).
  • Nada se ejecutó al escribir esta guía. Las columnas del navegador son tuyas; las filas de la matriz salen de leer el código.

Cómo conectar

Esta guía funciona sola. Si quieres juntarla con otras:

  • Con WEB03, CSRF

    cors.php y requireOrigenConfiable leen la misma lista de origen.php. En la falla 1, la capa de WEB03 es la que impide que el token leído sirva para algo.

  • Con WEB02, la sesión

    Expose-Headers: Retry-After deja que un frontend de otro origen lea cuánto esperar después del 429 del login.

  • Con WEB01, lo que no debe verse

    Con los códigos HTTP reales, el preflight roto de hoy se ve como un 401 en Network y no como un 200 que el navegador rechaza sin que se entienda por qué.

  • Con M75, CORS a fondo

    La política es la de 75.9, con la lista en el .env; las credenciales y el *, en 75.5, y Vary, en su sección.
