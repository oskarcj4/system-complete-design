La excusa

Una API de notas: crear, leer, actualizar, borrar y listar las últimas. Es tan chica que no distrae, y por eso sirve para fijar lo que todos los proyectos siguientes repiten sin volver a explicarlo: la base de datos con su pooler, las migraciones, las pruebas, la integración continua y la forma de medir.

No vas a escribir el código. Está hecho en el repositorio oficial: lo clonas, y la guía recorre cada archivo, copiado tal cual, para explicar qué hace y por qué. Los comandos sí los corres tú: son los que levantan la base, prueban y provocan las fallas.

La guía supone que conoces Spring (controladores, servicios, inyección de dependencias), REST, SQL y Docker. No supone que sabes escribir pruebas ni configurar CI: esas partes (pasos 9, 10 y 11) se explican desde cero, línea por línea.

Puerto 5433

Si tienes un PostgreSQL instalado en tu sistema, ya ocupa el 5432. Con el contenedor en el 5432, Flyway se conecta al equivocado y falla con "la autentificación password falló para el usuario app". Publicarlo en el 5433 evita la confusión.

container_name

Nombres fijos (postgres_notas_v1, pgbouncer_notas_v1) para reconocerlos en docker ps. Los comandos de la guía usan el nombre del servicio (postgres, pgbouncer) con docker compose exec, que funciona igual.

El volumen

En la imagen 17, los datos viven en /var/lib/postgresql/data. Desde la 18 cambió a /var/lib/postgresql: si subes la imagen, cambia también el volumen o el contenedor no arranca. Documentado

El healthcheck

pg_isready cada 15 s. PgBouncer espera a que postgres esté healthy (depends_on con condition: service_healthy), así que el primer arranque tarda hasta 15 s.

AUTH_TYPE y AUTH_USER

PostgreSQL guarda las claves con SCRAM, y PgBouncer tiene que hablar el mismo método. AUTH_USER es el usuario con el que PgBouncer consulta las claves en la base.

POOL_MODE: transaction

PgBouncer le presta una conexión del servidor a un cliente solo mientras dura una transacción. Con 20 conexiones reales atiende a cientos de clientes, pero lo que vive en la sesión deja de ser tuyo: lo vas a provocar en Cómo comprobar que funciona.

DEFAULT_POOL_SIZE y MAX_CLIENT_CONN

20 conexiones reales con PostgreSQL por cada par de usuario y base (cada una es un proceso del servidor con su memoria; el límite protege a la base) y hasta 500 clientes conectados a PgBouncer.

ADMIN_USERS: app

Deja entrar a app a la consola de PgBouncer para correr SHOW POOLS.

Paso 3. La tabla, con Flyway directo a PostgreSQL

Flyway corre las migraciones al arrancar la aplicación: busca los archivos V<n>__<nombre>.sql en db/migration, aplica los que faltan en orden y anota cada uno en la tabla flyway_schema_history. Esta es la única:

CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE OR REPLACE FUNCTION uuid_generate_v7()
RETURNS uuid AS $$
DECLARE 
    unix_time_ms bytea;
    uuid_bytes bytea;
BEGIN
    -- 48 bits de epoch time en milisegundos
    unix_time_ms = substring(int8send(floor(extract(epoch from clock_timestamp()) * 1000)::bigint) from 3 for 6);
    
    -- 10 bytes aleatorios (requiere pgcrypto)
    uuid_bytes = unix_time_ms || gen_random_bytes(10);
    
    -- Ajustar versión (0111 -> 7) en el byte 7
    uuid_bytes = set_byte(uuid_bytes, 6, (get_byte(uuid_bytes, 6) & 15) | 112);
    -- Ajustar variante RFC 4122 (10xx) en el byte 9
    uuid_bytes = set_byte(uuid_bytes, 8, (get_byte(uuid_bytes, 8) & 63) | 128);

    RETURN encode(uuid_bytes, 'hex')::uuid;
END;
$$ LANGUAGE plpgsql VOLATILE;

CREATE TABLE IF NOT EXISTS notes (
    id uuid PRIMARY KEY DEFAULT uuid_generate_v7(),
    title text NOT NULL CHECK(length(title) BETWEEN 1 AND 150),
    body text NOT NULL DEFAULT '',
    created_at timestamptz NOT NULL DEFAULT now()
);

Es el arreglo clásico de la falla 3; ahí lo vas a quitar para ver qué pasa sin él.

flyway.url

Las migraciones van directo a PostgreSQL (5433), sin PgBouncer. El bloque mvc que quedó dentro de flyway no lo lee nadie: la propiedad que cuenta es spring.mvc.problemdetails.enabled, más abajo.

jpa.hibernate.ddl-auto: validate

Hibernate no crea ni cambia tablas: al arrancar, compara la entidad Note con la tabla y, si no coinciden, la aplicación no arranca. Flyway corre antes que Hibernate, así que la tabla ya existe desde el primer arranque. El esquema es de Flyway; Hibernate solo lo revisa.

mvc.problemdetails.enabled

Los errores de validación y los ResponseStatusException salen como Problem Details sin escribir un manejador.

server.web.error

Incluye el error y los errores de validación en las respuestas de error. Ayuda a aprender; en producción no se expone tanto detalle.

La decisión
Dos URLs: la aplicación usa PgBouncer (6432) y Flyway va directo a PostgreSQL (5433).
Lo que descartas
Migrar a través de PgBouncer en modo transacción. Flyway toma un advisory lock de sesión para que dos instancias no migren a la vez, y una migración suele hacer SET lock_timeout y después un ALTER TABLE. Detrás de PgBouncer, el lock no excluye y el SET cae en la conexión de otro cliente: son las fallas 1 y 2, que vas a provocar.
Qué puede salir mal
Olvidar que hay dos URLs. En producción, la de Flyway apunta al primario, no a una réplica ni al pooler. Y si la red solo deja pasar el puerto del pooler, la migración se corre aparte, como un paso del despliegue.

Paso 4. La entidad y el DTO

package com.a00.laboratorio.comun.notasv1.entities;

import com.fasterxml.uuid.Generators;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.PrePersist;
import jakarta.persistence.Table;
import java.time.OffsetDateTime;
import java.util.UUID;

@Entity
@Table(name = "notes")
public class Note {

    @Id
    @Column(name = "id", columnDefinition = "uuid", updatable = false, nullable = false)
    private UUID id;

    @Column(nullable = false, length = 150)
    private String title;

    @Column(nullable = false)
    private String body;

    @Column(name = "created_at", nullable = false, updatable = false)
    private OffsetDateTime createdAt;

    public Note() {
    }

    public Note(String title, String body) {
        this.title = title;
        this.body = body;
    }

    @PrePersist
    protected void onPrePersist() {
        if (this.id == null) {
            this.id = Generators.timeBasedEpochGenerator().generate(); // UUIDv7
        }
        if (this.createdAt == null) {
            this.createdAt = OffsetDateTime.now();
        }
    }

    public UUID getId() {
        return id;
    }

    public void setId(UUID id) {
        this.id = id;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public String getBody() {
        return body;
    }

    public void setBody(String body) {
        this.body = body;
    }

    public OffsetDateTime getCreatedAt() {
        return createdAt;
    }

    public void setCreatedAt(OffsetDateTime createdAt) {
        this.createdAt = createdAt;
    }
}

@PrePersist corre justo antes del INSERT: pone el id con Generators.timeBasedEpochGenerator(), que genera UUIDv7 en Java, y la fecha. Como el id ya existe antes de insertar, Hibernate no necesita leerlo de vuelta de la base.

La decisión
Separar lo que entra (NoteRequest, con las reglas de validación) de lo que se guarda (Note, con id y fecha). El cliente no puede mandar un id ni una fecha.
Lo que descartas
Recibir la entidad Note como body. Cualquier campo de la entidad pasaría a ser escribible desde afuera, incluido el id.
Qué puede salir mal
Que las reglas no coincidan: @Size(max = 150) en el DTO, length = 150 en la entidad y CHECK (length(title) BETWEEN 1 AND 150) en la tabla dicen lo mismo. Si cambias una, cambia las tres, o el error sale de la base como un 500 en lugar de un 400.

Paso 8. El tamaño del pool

Hay dos pools en fila: Hikari, en la aplicación, con 10 conexiones hacia PgBouncer, y PgBouncer, con hasta 20 hacia PostgreSQL. La configuración está en el application.yaml del paso 3.

La decisión
Hikari con 10 conexiones y connection-timeout de 10 000 ms. Si el pool está lleno 10 s, la request falla con un 500 y el problema se ve.
Lo que descartas
Un pool de 100 "por si acaso" y el timeout por defecto de 30 s. Más conexiones no hacen más rápida a la base: compiten por los mismos núcleos y discos. Y 30 s de espera convierten una base lenta en hilos colgados en toda la aplicación.
Qué puede salir mal
Escalar a 5 réplicas de la aplicación con 10 conexiones cada una: son 50 clientes para 20 conexiones reales. En modo transacción está bien, porque una conexión real solo se presta mientras dura una transacción; en modo sesión, 30 clientes esperarían.

El connection-timeout de Hikari es un número en milisegundos. Si escribes 10s, la aplicación no arranca: "Failed to convert from type [java.lang.String] to type [long] for value [10s]".

Antes de las fallas: qué es una sesión

Cada conexión con PostgreSQL es un proceso del servidor, con un número (el pid), y todo lo que haces en esa conexión vive en su sesión: los parámetros que cambias con SET, los locks de sesión, los prepared statements con nombre, las tablas temporales. La sesión dura lo que dura la conexión.

El código que usa la base supone que su sesión es suya: si hizo un SET, lo ve; si tomó un lock, nadie más lo tiene. PgBouncer en modo transacción rompe ese supuesto, porque la misma conexión real pasa de un cliente a otro entre transacciones, sin limpiarla:

Las tres fallas que siguen son la misma idea con tres cosas distintas que viven en la sesión. Las tres pasan en sistemas reales y son difíciles de diagnosticar: el síntoma aparece en un cliente que no hizo nada malo, y solo a veces, según en qué conexión real cayó su transacción.

Falla 1. Un SET que se filtra a otro cliente

Por qué importa

Los parámetros de sesión deciden cómo se comporta cada consulta: statement_timeout (cuánto puede durar), search_path (en qué esquema busca las tablas), TimeZone (cómo se muestran las fechas) y los parámetros propios, como el tenant que lee la row-level security. Si uno se filtra, otro cliente consulta con reglas que no son las suyas. Con statement_timeout, la aplicación empieza a fallar con canceling statement due to statement timeout sin que nadie haya tocado su código. Con el tenant de RLS es peor: una request lee los datos de otro cliente. Por eso M05 pide SET LOCAL, no SET.

Hazlo

Con el compose y la aplicación corriendo (./mvnw spring-boot:run), mira qué conexión usa la aplicación; después conéctate a PgBouncer con psql, cambia un parámetro de sesión y vuelve a mirar:

  -c "SET statement_timeout = '50ms'" -c "SELECT pg_backend_pid()"

# {"backendPid":179,"statementTimeout":"50ms"}

Qué significa cada salida

  1. Primer curlbackendPid es el proceso del servidor que atendió la consulta de la aplicación, y statementTimeout vale "0": sin límite, el valor por defecto.
  2. psqlOtro cliente, que no es la aplicación, entra por PgBouncer, hace SET y se va. El SELECT pg_backend_pid() dice en qué proceso quedó su SET. Al desconectarse psql, PgBouncer no cierra ese proceso: lo devuelve al pool, tal como quedó.
  3. Segundo curlLa aplicación recibe ese mismo proceso y ve "50ms", un valor que ella nunca puso. Desde ahora, cualquier consulta suya que caiga en esa conexión y tarde más de 50 ms se cancela.

Si el segundo curl muestra otro backendPid y "0", la consulta cayó en otra conexión real: repítelo unas veces. Las que caigan en el proceso que imprimió psql van a mostrar "50ms"; las demás, no. Ese "a veces sí, a veces no" es lo que hace difícil esta falla en producción.

Cómo se evita

En modo transacción, si una consulta necesita un parámetro, usa SET LOCAL dentro de su transacción: dura hasta el commit y no se filtra. Un valor que todos necesitan va en la configuración del rol o de la base (ALTER ROLE app SET …), no en un SET suelto. En modo sesión, PgBouncer corre DISCARD ALL al soltar cada conexión y este problema no existe, pero pierdes el reparto de conexiones.

Falla 2. Un advisory lock que no excluye

Por qué importa

Un advisory lock es un lock sobre un número que eliges tú: PostgreSQL no sabe qué protege, solo garantiza que dos sesiones no lo tengan a la vez. Se usa para que una tarea corra en una sola instancia aunque haya varias: un job nocturno que cobra suscripciones con tres réplicas de la aplicación, la elección de un líder, o Flyway, que lo toma para que dos instancias no migren a la vez (por eso migra directo, paso 3). Si el lock no excluye, la tarea corre dos veces: cobros dobles, correos repetidos, migraciones pisándose. Y hay una segunda mitad: el lock queda tomado en una conexión real después de que su dueño se fue, y quien lo pida directo queda bloqueado sin saber por qué.

Hay dos versiones: pg_advisory_lock es de sesión (dura hasta pg_advisory_unlock o hasta que se cierra la conexión) y pg_advisory_xact_lock es de transacción (se suelta solo en el commit o el rollback).

Hazlo

P='docker compose exec -T postgres psql -At postgres://app:app@pgbouncer:5432/app'

P=… guarda el comando en una variable de bash para no repetirlo; $P lo usa. -At le pide a psql la salida sin adornos: los valores separados por |, sin encabezados. pg_try_advisory_lock no espera: devuelve t si obtuvo el lock y f si otro lo tiene.

Qué significa cada salida

  1. Cliente A: |179pg_advisory_lock no devuelve nada (por eso la columna vacía antes de |) y deja el lock 42 tomado en el proceso 179. psql termina y se desconecta de PgBouncer, pero la conexión real 179 sigue viva en el pool, con el lock.
  2. Cliente B: t|179Otro cliente pide el mismo lock, recibe el mismo proceso 179 y lo obtiene: t. Un lock de sesión es reentrante para su sesión, y para PostgreSQL A y B son la misma. Si A y B fueran dos instancias de tu job, las dos correrían.
  3. Directo: f|308Sin PgBouncer, en una conexión propia (el proceso 308), la respuesta es la correcta: f, el lock está tomado. Tomado por un cliente que ya no existe.

Detrás de PgBouncer en modo transacción, usa la versión de transacción, pg_try_advisory_xact_lock, dentro de la transacción de la tarea: se suelta en el commit y no se filtra. Si la tarea dura más que una transacción, conéctala directo a PostgreSQL, como Flyway.
